# Part 022 — Stakeholder Management for Engineers

## 1. Source notes and scope boundary

This part uses public Scrum guidance and general enterprise engineering practice.

Public references to verify independently:

- The Scrum Guide describes Sprint Review as an event where the Scrum Team presents results to key stakeholders and collaborates on what to do next.
- Scrum does not define a detailed stakeholder-management process. Teams must adapt stakeholder collaboration to their product, organization, and delivery model.
- CSG internal stakeholder structure, product leadership, customer-facing teams, support model, architecture governance, security review, and platform responsibilities must be verified internally.

This part does **not** assume a specific stakeholder map at CSG.

The goal is to build a reusable stakeholder-management operating model for senior engineers.

---

## 2. Core thesis

Stakeholder management is not politics.

For senior engineers, stakeholder management is the discipline of making sure the right people know the right risks at the right time so the product can move safely.

A backend change in Quote & Order can affect stakeholders far beyond the Scrum Team:

- Product Owner,
- Product Manager,
- QA/Test Engineer,
- Scrum Master,
- Engineering Manager,
- Architect,
- Security,
- Platform/SRE/DevOps,
- Support,
- Customer Success,
- Professional Services,
- Customer integration team,
- Billing team,
- Fulfillment/OSS team,
- Data/reporting team,
- Release manager,
- On-prem deployment owner,
- downstream consumer teams.

A senior engineer must know when to involve each stakeholder.

Not every change needs a committee.

But the wrong change made without the right stakeholder can become a production incident, customer escalation, or release delay.

---

## 3. Stakeholder management vs status reporting

Status reporting says:

> We are 70% done.

Stakeholder management says:

> The API behavior is implemented, but the downstream fulfillment team has not confirmed callback compatibility. The risk is duplicate cancellation if we release without idempotency agreement. We need either a narrower Sprint scope or a stakeholder decision by Wednesday.

Status reports often hide risk.

Stakeholder management exposes risk while there is still time to act.

## 6. RACI-like thinking without bureaucracy

A lightweight decision map can prevent confusion.

Use categories:

- **Responsible** — does the work.
- **Accountable** — owns the outcome/decision.
- **Consulted** — provides input before decision.
- **Informed** — needs awareness after/before change.

### 6.1 Example: Kafka event schema change

| Stakeholder | Role |
|---|---|
| Scrum Team Developers | Responsible |
| Event/API owner or architecture owner | Accountable for schema governance if defined |
| Downstream consumer teams | Consulted |
| QA/test automation | Consulted |
| Platform/Kafka owner | Consulted if topic/runtime impact |
| Support | Informed if customer-facing behavior changes |
| Product Owner | Accountable for product priority/value |

The actual decision rights must be verified internally.

The point is to avoid accidental unilateral decisions.

## 7. When to involve stakeholders

### 7.1 Too early vs too late

Too early:

- every idea becomes a meeting,
- stakeholders are asked before problem is understood,
- engineers outsource thinking,
- process slows down.

Too late:

- stakeholder discovers issue at release,
- architecture veto arrives after implementation,
- QA lacks test data,
- support lacks runbook,
- downstream consumer breaks,
- customer escalation surprises team.

The senior engineer's skill is timing.

### 7.2 Involve early when impact is hard to reverse

Involve stakeholders early for:

- public API change,
- Kafka event contract change,
- database migration/backfill,
- security/tenant boundary,
- pricing/approval semantics,
- order lifecycle state change,
- customer-specific behavior,
- on-prem upgrade impact,
- release process change,
- production data repair.

### 7.3 Involve later when change is local and reversible

You may not need broad stakeholder involvement for:

- internal refactor with characterization tests,
- logging improvement,
- small bugfix with no contract change,
- documentation correction,
- non-risky UI copy improvement,
- local test fixture cleanup.

Still use judgment.

A “small” code change can be product-critical if it touches pricing, authorization, or state transition.

## 8. Communication levels

Different stakeholders need different depth.

### 8.1 Product-level communication

Focus:

- customer outcome,
- scope,
- trade-off,
- release impact,
- support/customer messaging.

Example:

> We can support cancellation before fulfillment starts this Sprint. Cancellation after fulfillment acceptance needs downstream confirmation and idempotency handling. Shipping both now increases risk of inconsistent customer status.

### 8.2 Engineering-level communication

Focus:

- design,
- data model,
- event/API contract,
- migration,
- tests,
- observability,
- rollout.

Example:

> The cancellation command will write transition history and outbox event in the same transaction. We need a uniqueness guard for cancellation request ID and a consumer test for duplicate callback.

### 8.3 Executive/customer-facing communication

Focus:

- impact,
- mitigation,
- timeline,
- risk status,
- customer action needed.

Example:

> This release adds phase-one cancellation support for orders that have not entered fulfillment. Orders already accepted by fulfillment will continue to use existing support workflow until downstream cancellation is supported.

Do not send implementation-level uncertainty to customer-facing stakeholders without translation.

## 9. How to escalate well

Escalation is not complaining.

Escalation is moving a decision to the level where it can be resolved.

### 9.1 Weak escalation

> We are blocked by the fulfillment team.

### 9.2 Strong escalation

> We need fulfillment callback semantics by Tuesday to meet the Sprint Goal. Without it, we can still ship pre-fulfillment cancellation but must defer post-acceptance cancellation. Decision needed: reduce scope or accept spillover risk. Owner needed from fulfillment to confirm duplicate callback behavior.

### 9.3 Escalation template

```md
## Issue
What is blocked?

## Impact
What Sprint Goal, release, customer, or risk is affected?

## Decision needed
What choice must be made?

## Options
A: ...
B: ...
C: ...

## Recommendation
Which option do we recommend and why?

## Deadline
When is the decision needed?

## Owner
Who can decide or unblock?
```

This makes escalation actionable.

## 10. Stakeholder communication during Sprint events

### 10.1 Refinement

Stakeholder goal:

- clarify value,
- expose unknowns,
- identify dependencies,
- improve acceptance criteria.

Useful stakeholders:

- PO,
- QA,
- domain SME,
- architect/platform/security when needed,
- downstream team representative for integration-heavy work.

Senior engineer contribution:

- ask risk questions,
- propose slicing,
- identify spike need,
- capture dependency.

### 10.2 Sprint Planning

Stakeholder goal:

- create achievable Sprint Goal and Sprint Backlog.

Senior engineer contribution:

- make dependency and risk explicit,
- challenge overcommitment,
- protect DoD,
- identify capacity impact from support/on-call.

### 10.3 Daily Scrum

Stakeholder goal:

- not primarily stakeholder reporting; this is Developers' synchronization.

Senior engineer contribution:

- raise blockers clearly,
- identify stakeholder decision needed,
- trigger follow-up outside Daily.

### 10.4 Sprint Review

Stakeholder goal:

- inspect outcome and adapt Product Backlog.

Senior engineer contribution:

- show evidence, not just demo,
- explain known limitations,
- collect stakeholder feedback,
- translate feedback into backlog impact.

### 10.5 Retrospective

Stakeholder goal:

- improve team process.

Senior engineer contribution:

- identify systemic stakeholder-friction pattern,
- propose improvement,
- follow through.

## 11. Sprint Review as stakeholder alignment

Sprint Review is one of the most important stakeholder events.

Do not use it only for UI demos.

For enterprise backend work, show:

- API behavior,
- event emitted,
- audit history,
- dashboard panel,
- error handling,
- feature flag state,
- support workflow,
- migration status,
- known limitations,
- next adaptation.

### 11.1 Example Sprint Review narrative

> This Sprint Goal was to enable phase-one order cancellation before fulfillment starts. We implemented the API command, state transition guard, audit event, and cancellation-requested Kafka event. We intentionally did not implement post-fulfillment cancellation because downstream callback semantics are not confirmed. Here is the happy path, the rejected path, and the audit trail. The proposed next backlog item is downstream cancellation handling after fulfillment team confirms idempotency behavior.

This gives stakeholders useful product adaptation information.

## 12. Managing stakeholder disagreement

Stakeholders may disagree.

Examples:

- PO wants fast release.
- QA wants broader regression.
- Security wants review before launch.
- Platform worries about DB migration.
- Support wants runbook first.
- Architecture worries about contract drift.
- Customer team wants customer-specific workaround.

Senior engineer role:

- clarify decision criteria,
- separate facts from preferences,
- identify reversible vs irreversible choices,
- propose options,
- recommend path,
- document decision.

### 12.1 Disagreement decision frame

Ask:

- What is the customer/business impact?
- What is the technical risk?
- Is the risk reversible?
- What is the cost of delay?
- What evidence do we have?
- What evidence is missing?
- Can we reduce scope?
- Can we use feature flag/canary?
- Who has decision authority?
- What follow-up is required?

This moves disagreement from opinion to trade-off.

## 14. Stakeholder updates by format

### 14.1 Short update

Use for routine progress.

```md
Status: On track.
Risk: Fulfillment callback contract still pending.
Decision needed: confirm duplicate callback behavior by Wednesday.
Next: implement pre-fulfillment cancellation slice; defer post-acceptance cancellation if not confirmed.
```

### 14.2 Risk update

Use when risk changes.

```md
We discovered the existing order state model cannot represent partial cancellation safely. The original Sprint scope assumed full cancellation only. Recommendation: ship rejection for post-fulfillment cancellation this Sprint, create spike for partial cancellation semantics, and update Product Backlog.
```

### 14.3 Release readiness update

Use before release.

```md
Ready for release behind feature flag for tenant group A. API tests, audit tests, and cancellation-before-fulfillment E2E passed. Not included: downstream cancellation after fulfillment acceptance. Support runbook updated. Dashboard panel added for cancellation failures. Rollback is feature-flag disable; DB migration is additive and backward-compatible.
```

### 14.4 Incident stakeholder update

Use during incident.

```md
Impact: orders for tenant X may remain stuck in cancellation pending state.
Current containment: cancellation worker paused for tenant X.
Customer impact: no new duplicate cancellations observed after 10:20 UTC.
Next: validate affected order list, repair through approved admin command, then resume worker.
ETA: next update in 30 minutes or sooner if risk changes.
```

Always tailor to stakeholder need.

## 15. Stakeholder risk register

For complex features, maintain a lightweight register.

```md
| Risk | Stakeholder | Impact | Decision needed | Due | Status |
|---|---|---|---|---|---|
| Fulfillment duplicate callback semantics unclear | Fulfillment team | duplicate cancellation state | confirm idempotency contract | Tue | open |
| DB migration may lock hot order table | Platform/DBA | release outage risk | approve expand-contract plan | Wed | in review |
| Customer-specific rule conflicts with base approval policy | PO/Product | product semantics | decide config vs product behavior | Thu | open |
| Support lacks cancellation runbook | Support | incident recovery delay | review runbook | Fri | draft |
```

This creates transparency without requiring constant meetings.

## 16. Managing stakeholders without becoming a bottleneck

Senior engineers can become accidental bottlenecks if every decision routes through them.

Avoid this by creating reusable structures:

- decision templates,
- PR checklists,
- stakeholder maps,
- runbooks,
- ownership tables,
- escalation templates,
- risk registers,
- architecture decision records.

A good senior engineer does not personally coordinate every future issue.

They improve the system so coordination becomes easier.

## 17. Common anti-patterns

### 17.1 Over-broadcasting

Sending every detail to every stakeholder creates noise.

Better:

- send targeted updates,
- separate FYI from decision-needed,
- keep context concise.

### 17.2 Under-communicating risk

Hiding uncertainty until the end creates surprise.

Better:

- surface risk early,
- state confidence level,
- propose options.

### 17.3 Technical language without translation

Bad:

> The saga has a race with compensating command.

Better:

> A retry can cause the order to be cancelled after it has already moved into fulfillment. We need an idempotency guard before enabling this path.

### 17.4 Escalating without recommendation

Bad:

> What should we do?

Better:

> Option A is safer but smaller. Option B is faster but needs support readiness. I recommend A for this Sprint.

### 17.5 Treating stakeholders as blockers

Stakeholders often protect real constraints.

Security, QA, platform, and support are not obstacles. They represent product survival surfaces.

- Which decisions can the Scrum Team make alone?
- Which decisions require PO approval?
- Which decisions require architecture/security/platform approval?
- Which decisions require customer-facing stakeholder input?
- How are risk exceptions approved?
- Where are decisions documented?

### 18.3 Communication channels

- Where are sprint updates posted?
- Where are blockers escalated?
- Where are architecture decisions discussed?
- Where are incidents coordinated?
- Where are release notes managed?
- Where are support handoffs written?

### 18.4 Stakeholder pain points

- Which stakeholders are usually involved too late?
- Which meetings are noisy?
- Which decisions are unclear?
- Which dependencies repeatedly surprise the team?
- Which stakeholders need better technical context?
- Which engineers need better product context?

## 20. What good looks like

After this part, you should be able to:

- identify stakeholders for a technical change,
- communicate risk in stakeholder language,
- escalate with options and recommendation,
- use Sprint Review as stakeholder alignment,
- avoid late surprises in API/event/migration/security/release work,
- balance enough communication with avoiding noise,
- help Scrum Team maintain transparency across enterprise complexity.

## 21. Final mental model

Stakeholder management is not about pleasing everyone.

It is about maintaining product and engineering transparency across the people who can affect or be affected by the work.

For senior engineers in enterprise Quote & Order systems, this is a core technical skill because architecture, production, customer integration, and product value are inseparable.
