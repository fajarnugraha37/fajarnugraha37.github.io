# Part 023 — Sprint Review as Evidence Demo

## 1. Source notes and scope boundary

This part is grounded in the Scrum Guide and Scrum.org's explanation of Sprint Review as a working session where the Scrum Team and stakeholders inspect what was accomplished, discuss what changed in the environment, and collaborate on what to do next.

This part adapts that idea for enterprise software engineering, especially Quote & Order / CPQ / order management systems where a meaningful Increment may include backend behavior, API contract changes, Kafka events, database migration safety, production observability, runbooks, and operational readiness.

This part does **not** assume CSG has a specific Sprint Review format, demo ritual, release cadence, stakeholder set, or product governance model.

Use the internal verification checklist to map these ideas to your actual team.

---

## 2. Core thesis

Sprint Review is not a status meeting.

Sprint Review is not a slide show.

Sprint Review is not only a UI demo.

Sprint Review is a product and engineering evidence inspection event.

A strong Sprint Review answers:

> What did we learn, what working Increment exists, what evidence proves it, what changed in our product/customer/technical environment, and what should we adapt next?

For a Quote & Order team, this matters because many valuable increments are invisible to a stakeholder if the team only demos screens.

Examples of valuable invisible increments:

- quote acceptance now rejects stale prices correctly;
- order conversion is idempotent;
- Kafka event schema is backward-compatible;
- PostgreSQL migration is now expand-contract safe;
- new observability dashboard detects stuck order decomposition;
- support runbook now explains recovery for duplicate fulfillment callback;
- tenant isolation test coverage prevents cross-tenant quote retrieval;
- API error model is now stable for customer integrations;
- fulfillment adapter now handles unknown outcome safely.

These are not always visually impressive.

But they are product value.

The senior engineer's role is to make that value inspectable.

---

## 3. Sprint Review purpose in senior engineer language

Sprint Review has four senior-engineering purposes:

1. **Inspect the Increment** — what is now usable and what evidence proves it?
2. **Inspect product direction** — is this still the right next step given stakeholder feedback and environment changes?
3. **Expose risk and learning** — what did the Sprint reveal about domain, architecture, integration, data, or operations?
4. **Adapt the Product Backlog** — what should change in ordering, slicing, acceptance criteria, or technical work?

The output of Sprint Review should influence future backlog work.

If Sprint Review does not change understanding, ordering, or confidence, it is probably underpowered.

---

## 4. Demo vs evidence demo

A traditional demo says:

> Here is what we built.

An evidence demo says:

> Here is the business behavior, here is the proof that it works, here are the edge cases handled, here are the risks reduced, here is what remains uncertain, and here is what we recommend doing next.

| Demo type | What it shows | Weakness |
|---|---|---|
| UI demo | visible screen flow | misses backend correctness and production readiness |
| API demo | request/response behavior | may miss async effects and observability |
| Technical demo | code/design change | may not connect to product value |
| Evidence demo | product behavior plus proof | requires preparation and storytelling |

For enterprise backend teams, evidence demo is usually the strongest form.

## 5. Evidence categories

A Sprint Review for Quote & Order should include multiple evidence categories depending on the work.

### 5.1 Business behavior evidence

Examples:

- quote can be created for eligible customer;
- discount above threshold requires approval;
- unauthorized user cannot approve quote;
- accepted quote converts to exactly one order;
- order cancellation behaves correctly in allowed states;
- amendment validates installed base;
- fallout operator can resume a failed fulfillment task.

Evidence:

- UI/API walkthrough;
- acceptance criteria mapping;
- example business scenario;
- state transition proof;
- before/after behavior comparison.

### 5.2 Contract evidence

Examples:

- OpenAPI diff shows additive non-breaking change;
- generated client still compiles;
- customer-facing error code remains stable;
- Kafka schema compatibility check passes;
- old event fixture can be consumed by new code.

Evidence:

- OpenAPI diff screenshot or artifact;
- contract test result;
- example payload;
- consumer verification result;
- event fixture replay result.

### 5.3 Data evidence

Examples:

- migration runs from previous schema;
- new nullable column backfill is chunked;
- query plan improves quote search;
- tenant predicate exists on search/export query;
- old rows remain readable.

Evidence:

- migration dry-run result;
- EXPLAIN output summary;
- row-count validation;
- before/after query latency;
- data invariant test.

### 5.4 Operational evidence

Examples:

- dashboard panel shows quote acceptance failures;
- alert links to runbook;
- logs include quote ID/order ID/correlation ID;
- trace connects API call to Kafka event;
- outbox lag is visible;
- stuck order query is documented.

Evidence:

- dashboard screenshot;
- runbook link;
- sample structured log;
- trace screenshot;
- alert test or manual watch plan.

### 5.5 Security and audit evidence

Examples:

- cross-tenant quote read denied;
- approver cannot approve own quote if maker-checker applies;
- audit event captures actor/reason/before/after;
- service token cannot perform user-only action;
- sensitive data not leaked in logs/events.

Evidence:

- negative test result;
- audit record example;
- authorization matrix snippet;
- log redaction example;
- security review note.

## 6. What to demo for non-UI backend work

A common mistake is skipping Sprint Review for backend work because "there is nothing to demo".

There is always something to inspect.

### 6.1 API work

Demo:

- request payload;
- response payload;
- error response;
- idempotency behavior;
- OpenAPI diff;
- authorization behavior;
- audit/event side effects.

Example demo flow:

```text
1. Create quote with discount above threshold.
2. Show response indicates approval required.
3. Attempt approval as unauthorized actor and show denial.
4. Approve as authorized approver.
5. Accept quote.
6. Show resulting order ID.
7. Show audit event and emitted Kafka event.
```

### 6.2 Kafka/event work

Demo:

- event payload before/after;
- schema compatibility result;
- consumer processing result;
- duplicate event handling;
- DLQ behavior;
- consumer lag dashboard.

Example evidence:

```json
{
  "eventType": "ProductOrderStateChanged",
  "aggregateId": "PO-123",
  "aggregateVersion": 7,
  "tenantId": "tenant-a",
  "correlationId": "corr-789",
  "payload": {
    "previousState": "IN_PROGRESS",
    "currentState": "COMPLETED"
  }
}
```

Do not only show that an event was produced.

Show that the event is useful, compatible, and traceable.

### 6.3 Database migration work

Demo:

- migration sequence;
- expand-contract strategy;
- dry-run output;
- old/new app compatibility;
- query plan impact;
- validation query;
- rollback/roll-forward plan.

Good Sprint Review statement:

> The migration is additive. The old app ignores the new nullable column. The new app writes it for new quotes. Existing quotes are backfilled in chunks. Validation shows no approved quote without approval basis hash after backfill in the test fixture. The contract migration will happen in a later story after all supported environments have run the backfill.

### 6.4 Observability work

Demo:

- dashboard panel;
- metric definition;
- alert threshold;
- runbook link;
- example incident question the dashboard can answer;
- trace/log correlation.

Bad demo:

> We added some metrics.

Better demo:

> Previously, support could not tell whether quote-to-order conversion failed before order creation or after fulfillment submission. This dashboard separates quote acceptance failures, conversion failures, outbox lag, and fulfillment adapter failures by tenant and correlation ID. Here is a sample failed test transaction and how the dashboard leads to diagnosis.

## 7. Sprint Review structure for enterprise backend teams

Use this structure when the Increment is not purely visual.

### 7.1 Opening: Sprint Goal and context

Start with:

- Sprint Goal;
- why it mattered;
- what changed in product/customer/technical environment;
- which PBIs are Done;
- which PBIs are not Done and why.

Example:

> Sprint Goal: make quote acceptance safer for enterprise discount quotes by preserving approval evidence and preventing stale price acceptance. Done: stale price guard, approval audit extension, API negative test, dashboard panel. Not Done: customer-specific approval threshold import because external config format changed mid-sprint.

### 7.2 Evidence walkthrough

For each Done item:

1. state the business behavior;
2. show the evidence;
3. show the edge case;
4. show production-readiness evidence;
5. state remaining risk.

### 7.3 Stakeholder feedback

Ask targeted questions:

- Is this behavior correct for the customer scenario?
- Is the error message actionable?
- Is this enough for support?
- Are there customer-specific variants?
- Does this change priority for remaining backlog?
- Are we missing a compliance/audit concern?

### 7.4 Backlog adaptation

End with:

- new backlog items discovered;
- changed ordering;
- scope adjustments;
- technical debt created or reduced;
- risks requiring refinement;
- candidate Sprint Goal implications.

## 8. Evidence demo template

Use this template for each demonstrated item.

```md
## Demo Item: <PBI/title>

### Business outcome
- What user/customer/system behavior changed?

### Sprint Goal connection
- How did this support the Sprint Goal?

### Evidence
- UI/API/example payload:
- Test result:
- Contract evidence:
- Data/migration evidence:
- Observability evidence:
- Security/audit evidence:

### Edge cases covered
- Case 1:
- Case 2:
- Case 3:

### Remaining risk
- Known limitation:
- Follow-up backlog item:
- Stakeholder decision needed:

### Feedback requested
- Question 1:
- Question 2:
```

This turns Sprint Review into a working session rather than a presentation.

## 9. Quote & Order Sprint Review examples

### 9.1 Quote approval enhancement

Sprint Review evidence:

- show quote with discount requiring approval;
- show unauthorized approval denied;
- show authorized approval succeeds;
- show quote modification invalidates approval;
- show audit event includes actor, threshold, reason;
- show acceptance fails if approval expired;
- show API error code is stable;
- show test coverage summary.

Stakeholder questions:

- Should approval invalidation happen on every price-affecting change?
- Are there customer-specific approval thresholds?
- Does support need to see approval reason?
- Is the error message acceptable for sales users?

Backlog adaptation:

- add story for approval threshold import;
- add runbook for approval stuck state;
- add product decision for maker-checker edge case.

### 9.2 Order fallout recovery

Sprint Review evidence:

- show order item failure from fulfillment simulator;
- show order enters fallout;
- show operator retry action;
- show duplicate callback is idempotent;
- show order completion after recovery;
- show dashboard for fallout backlog;
- show audit event for manual retry.

Stakeholder questions:

- Which fallout reasons should support see?
- Which retries should be automatic vs manual?
- Is the customer-facing status wording correct?
- Does operations need alerting on backlog age?

Backlog adaptation:

- create story for fallout reason taxonomy;
- create technical item for retry dashboard;
- create product item for customer-facing status copy.

### 9.3 Kafka event compatibility improvement

Sprint Review evidence:

- show old event fixture consumed by new code;
- show new optional field ignored by old consumer;
- show schema compatibility result;
- show replay test result;
- show correlation ID in trace;
- show no DLQ growth in test run.

Stakeholder questions:

- Which consumers need this field?
- Is the field customer-facing or internal?
- Is it safe for on-prem integrations?
- Should this be included in release notes?

Backlog adaptation:

- add consumer documentation;
- add API/event changelog item;
- add follow-up to remove deprecated field after support window.

## 10. Stakeholder-specific framing

Different stakeholders need different evidence.

| Stakeholder | What they care about | Evidence style |
|---|---|---|
| Product Owner | value, behavior, priority | scenario walkthrough, backlog adaptation |
| QA | testability, edge cases | test matrix, fixture, failure paths |
| Support | diagnosis, customer explanation | runbook, dashboard, error codes |
| Platform/SRE | operability, rollout | metrics, logs, alerts, rollback |
| Security | auth, tenant, audit | negative tests, audit evidence |
| Architecture | compatibility, evolution | ADR/design trade-offs |
| Customer-facing teams | impact and communication | release notes, behavior examples |
| Developers | implementation confidence | test evidence, technical risk |

A senior engineer should shape the demo so each stakeholder can inspect what matters to them.

## 11. Sprint Review anti-patterns

### 11.1 Status-report review

Symptoms:

- each developer says what they did;
- no working evidence;
- no stakeholder feedback;
- no backlog adaptation.

Fix:

- organize by Sprint Goal and Increment evidence, not by person.

### 11.2 Slide-only review

Symptoms:

- screenshots replace working behavior;
- risks are hidden;
- stakeholders cannot inspect anything real.

Fix:

- include live or recorded evidence, test artifacts, dashboards, API examples.

### 11.3 UI-only review

Symptoms:

- backend/API/event/data work is invisible;
- production readiness is not inspected;
- important technical increments look like no progress.

Fix:

- demo evidence categories beyond UI.

### 11.4 Surprise-the-stakeholder review

Symptoms:

- stakeholders first hear about scope/risk at review;
- PO is surprised by what was built;
- unresolved decisions appear too late.

Fix:

- use refinement, daily sync, and mid-sprint adaptation to surface major changes earlier.

### 11.5 No adaptation

Symptoms:

- review ends without backlog update;
- feedback is not captured;
- same confusion repeats next sprint.

Fix:

- end review with explicit adaptation decisions.

---

## 12. Senior engineer responsibilities during Sprint Review

A senior engineer should help the team:

- connect technical work to product value;
- make invisible backend work inspectable;
- surface remaining technical risk honestly;
- translate stakeholder questions into backlog items;
- avoid defensive reactions to feedback;
- protect quality evidence from being skipped;
- identify where Sprint Goal was achieved or missed;
- distinguish Done work from partially completed work;
- propose next-step adaptation.

The senior engineer should not dominate the event.

The goal is shared inspection, not technical performance.

## 13. Internal verification checklist

Verify in your CSG/team context:

- How is Sprint Review currently run?
- Who attends?
- Does the Product Owner lead, facilitate, or co-facilitate?
- Are stakeholders active or passive?
- Are backend increments demonstrated clearly?
- Are API/Kafka/DB/security/observability changes shown?
- Are Not Done items discussed transparently?
- Are stakeholder feedback items captured?
- Does Product Backlog ordering change after review?
- Are Sprint Review outcomes linked to next refinement?
- Are customer-facing changes tied to release notes?
- Are production-readiness gaps captured?
- Are support/QA/security/platform stakeholders invited when relevant?
- Are demos recorded or documented?
- Are review outcomes visible later?

## 14. Practical exercise

Pick one completed backend PBI from your team.

Rewrite its Sprint Review demo using this format:

1. Business outcome.
2. Sprint Goal connection.
3. API/behavior evidence.
4. Test evidence.
5. Data/event/observability evidence.
6. Remaining risk.
7. Stakeholder question.
8. Backlog adaptation.

If you cannot produce evidence beyond "the PR was merged", the item may not have been truly inspectable.

---

## 15. Key takeaways

- Sprint Review is a collaborative inspection and adaptation event, not a status presentation.
- Backend and platform work must be made visible through evidence.
- Evidence includes behavior, tests, contracts, data, observability, security, audit, and readiness.
- Senior engineers help translate technical increments into stakeholder-inspectable value.
- A strong Sprint Review changes backlog understanding and future direction.

The best Sprint Review does not merely show what was built.

It improves the team's understanding of what should be built next.
