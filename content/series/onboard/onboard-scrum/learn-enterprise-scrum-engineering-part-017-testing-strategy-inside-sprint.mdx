# Part 017 — Testing Strategy Inside the Sprint

## 1. Source notes and scope boundary

This part uses public Scrum and engineering practice references, especially:

- Scrum Guide: Increment must be usable and meet the Definition of Done.
- Scrum.org material on Definition of Done and Sprint execution.
- Common Java backend testing practice: unit tests, integration tests, contract tests, migration tests, end-to-end tests, security tests, and performance smoke checks.
- Previous CSG Quote & Order engineering series parts on unit testing, integration testing, contract testing, migration testing, E2E testing, security testing, and operational readiness.

This part does **not** assume the actual internal CSG test stack, CI stages, QA ownership model, test data platform, environment topology, or release gate policy.

Verify internally:

- test frameworks used,
- CI pipeline stages,
- ownership of automated tests,
- QA collaboration model,
- flaky test policy,
- release branch policy,
- manual regression expectations,
- production readiness gates.

## 2. Core thesis

Testing in Scrum should not be a phase after development.

Testing is part of building a Done Increment.

For senior engineers, the important question is not:

> Did QA test the ticket?

The important question is:

> What evidence do we need inside the Sprint to trust that this Increment is correct, compatible, secure, observable, and releasable?

In enterprise Quote & Order systems, testing must prove more than endpoint success. It must protect:

- quote lifecycle correctness,
- pricing and approval evidence,
- product catalog versioning,
- quote-to-order conversion,
- order decomposition,
- Kafka event compatibility,
- PostgreSQL transaction and migration safety,
- tenant isolation,
- audit defensibility,
- operational observability,
- release readiness.

If testing happens only after coding is finished, the team discovers risk too late.

Testing should shape story design, acceptance criteria, Sprint Planning, PR review, and Definition of Done.

## 3. Testing is not one activity

Testing is a portfolio of evidence.

| Test type | Main question | Typical owner | Sprint timing |
|---|---|---|---|
| Unit test | Is local business logic correct? | Developer | During implementation |
| Integration test | Does code work with real infrastructure boundary? | Developer/QA | During implementation |
| Contract test | Is producer/consumer compatibility preserved? | Developer/QA/consumer owner | Before merge |
| Migration test | Can schema/data change deploy safely? | Developer/DB/platform | Before merge/release |
| E2E test | Does an important journey compose correctly? | Developer/QA | During or before release |
| Security test | Are auth, tenant, audit, and abuse boundaries protected? | Developer/security/QA | During implementation |
| Performance smoke | Did hot path degrade obviously? | Developer/platform | Before release for high-risk changes |
| Exploratory test | What did automation miss? | QA/dev/product | During or after implementation |

A mature Scrum Team does not ask “unit or E2E?”

It asks:

> Which evidence layer best catches this specific risk earliest and cheapest?

## 4. Why testing must start in refinement

If testing starts after implementation, the team has already made hidden decisions.

During refinement, a senior engineer should ask:

- What is the key business behavior?
- What state transitions are introduced or changed?
- What data is created or migrated?
- What API/event contract changes?
- Which downstream systems are affected?
- What failure paths must be covered?
- What security/tenant/audit requirements exist?
- What should be automated vs manually explored?
- What production signals must exist?

Testing strategy should be visible before Sprint Planning.

A refined story should often include a test plan section.

Example:

```md
## Test strategy
- Unit: approval threshold calculation and invalidation rules.
- Integration: quote acceptance transaction persists accepted version and outbox event.
- Contract: quote acceptance API response remains compatible.
- Kafka: QuoteAccepted event contains accepted quote version and correlation ID.
- Security: user without approval authority cannot approve.
- E2E: enterprise discount quote can be approved and converted to order.
- Observability: acceptance failure metric and structured log with quote ID.
```

This does not mean every story needs every test type.

It means risk should choose tests deliberately.

## 5. Testing strategy by work type

## 5.1 Pure domain logic change

Examples:

- quote expiry calculation,
- discount threshold rule,
- approval invalidation rule,
- order state transition rule,
- cancellation eligibility rule.

Recommended evidence:

- unit tests for all rule branches,
- parameterized tests for edge cases,
- negative tests for illegal state,
- deterministic time/money tests,
- mutation-thinking review,
- small integration test if rule depends on persisted state.

Do not rely on E2E for all rule combinations.

Unit tests should carry the rule matrix.

## 5.2 API behavior change

Examples:

- new quote endpoint,
- new order search filter,
- changed error code,
- added field to TMF-like response,
- new idempotency behavior.

Recommended evidence:

- controller/API integration tests,
- OpenAPI diff,
- contract tests,
- generated client compatibility if relevant,
- negative auth/tenant tests,
- error model tests,
- E2E only for critical journey.

## 5.3 Kafka/event change

Examples:

- new event type,
- added event field,
- changed partition key,
- changed event timing,
- new consumer behavior.

Recommended evidence:

- event schema compatibility test,
- producer test,
- consumer test,
- duplicate event test,
- replay test,
- DLQ/retry test where applicable,
- contract with known consumers,
- operational metric/lag visibility.

## 5.4 PostgreSQL persistence change

Examples:

- new table,
- new index,
- new mapper query,
- changed transaction boundary,
- new uniqueness constraint,
- migration/backfill.

Recommended evidence:

- mapper integration test against real PostgreSQL,
- transaction/concurrency test if race-sensitive,
- migration test from previous schema,
- query plan check for hot path,
- tenant predicate test,
- rollback/roll-forward discussion for migration.

## 5.5 Security-sensitive change

Examples:

- new privileged action,
- new support/admin endpoint,
- tenant model change,
- audit model change,
- service-to-service callback.

Recommended evidence:

- positive authorization test,
- negative authorization tests,
- cross-tenant tests,
- mass-assignment test,
- audit assertion,
- security review where required,
- sensitive data redaction check.

## 5.6 Operational behavior change

Examples:

- new retry policy,
- new timeout,
- new circuit breaker,
- new scheduler,
- new outbox relay behavior,
- new deployment/config behavior.

Recommended evidence:

- integration test for failure path,
- bounded retry/backoff test,
- observability check,
- runbook update,
- dashboard/alert update,
- failure-mode review.

## 6. Testing in Sprint Planning

Sprint Planning should include test capacity.

A story is not sized only by implementation code.

It includes:

- test design,
- fixture creation,
- automation,
- debugging CI failures,
- contract updates,
- migration validation,
- manual exploratory test if required,
- documentation/runbook update,
- review and rework.

If a team plans only coding work, it will either:

- spill testing into the next Sprint,
- reduce quality silently,
- overload QA,
- or claim Done before the Increment is actually usable.

### 6.1 Planning questions

For each selected PBI, ask:

- What tests are already available?
- What tests must be added?
- Who owns automation?
- Who owns exploratory testing?
- Is a test environment needed?
- Is test data available?
- Is external system simulation needed?
- Is there a migration or data setup cost?
- Is this PR review-heavy?
- Is there a release readiness artifact?

### 6.2 Capacity smell

If the Sprint has many backend changes but no explicit testing work, the Sprint is under-planned.

If the team says “QA will test it later,” the Sprint may not produce a Done Increment.

## 7. Testing and the Definition of Done

Definition of Done should define minimum quality for the product Increment.

For enterprise backend work, DoD often includes:

- code reviewed,
- automated tests passing,
- relevant unit/integration/contract tests added,
- security checks satisfied,
- migration tested,
- observability added,
- documentation/runbook updated where relevant,
- no critical known regression,
- release notes or operational notes updated where needed.

But DoD should not be a mindless checklist.

It should be interpreted by work type.

Example:

| Work type | DoD testing emphasis |
|---|---|
| Pure domain rule | unit/parameterized rule tests |
| API change | API integration + contract tests |
| Kafka event | schema compatibility + producer/consumer tests |
| DB migration | migration dry run + backward compatibility |
| Security action | negative auth + audit tests |
| Operational change | failure path + observability test |

A senior engineer should help the team apply DoD with judgment.

## 8. Shift-left without shifting burden

“Shift-left testing” is often misunderstood.

It does not mean dumping QA responsibility onto developers.

It means moving risk discovery earlier.

Good shift-left:

- QA joins refinement to clarify edge cases.
- Developers automate critical business rules.
- Contract issues are found before merge.
- Migration risk is tested before release.
- Exploratory testing targets unknowns, not basic regression.
- Testability is designed into the solution.

Bad shift-left:

- Developers throw code over the wall with weak tests.
- QA is expected to catch everything manually.
- Automation is postponed because “Sprint is full”.
- Defects are accepted as normal carryover.

A healthy Scrum Team treats testing as shared product quality work.

## 9. Collaboration between Developers and QA

In Scrum, quality is not owned by QA alone.

QA brings specialized testing skill, scenario thinking, exploratory discipline, and quality advocacy.

Developers bring implementation context, automation capability, and system internals.

The best pattern is partnership.

### 9.1 Useful collaboration moments

During refinement:

- QA identifies edge cases and test data needs.
- Developers identify automation boundaries and technical risk.

During implementation:

- Developers add unit/integration/contract tests.
- QA reviews acceptance criteria and exploratory charters.

Before PR merge:

- Developer proves automation and local evidence.
- QA reviews test coverage for business risk where needed.

Before Sprint Review/release:

- QA validates business journey and regression risk.
- Developers ensure observability/runbook/data migration evidence.

### 9.2 Anti-patterns

Avoid:

- QA as final safety net,
- developers writing only happy-path tests,
- QA testing unclear stories,
- manual regression for every small change,
- automated tests nobody trusts,
- “QA failed the ticket” language.

A better language:

> The Increment is not yet Done because the risk evidence is incomplete.

## 10. Test data strategy inside Sprint

Testing Quote & Order systems requires realistic, deterministic test data.

Important test data dimensions:

- tenant,
- customer/account,
- agreement,
- product offering,
- catalog version,
- price list,
- quote state,
- approval state,
- order state,
- installed base,
- fulfillment simulator behavior,
- user role/permission.

If test data is not planned, testing becomes slow and flaky.

### 10.1 Good test data properties

Good test data is:

- deterministic,
- named by business purpose,
- isolated by tenant/run,
- versioned with catalog/config,
- easy to reset or recreate,
- safe for parallel tests,
- documented enough for QA/dev use.

Bad test data is:

- manually created in QA environment,
- shared by many tests,
- dependent on “latest catalog”,
- changed by another team,
- impossible to reproduce locally,
- missing role/tenant context.

### 10.2 Example fixture naming

```yaml
fixture: enterprise-discount-approval-v1
tenant: tenant-e2e-commercial
customer: customer-enterprise-acme
agreement: agreement-acme-2026
catalogVersion: cat-2026-07-v3
offering: enterprise-fiber-bundle
salesUser: sales-rep-basic
approverUser: margin-approver-level-2
expectedApprovalRequired: true
```

Fixtures should communicate intent.

## 11. Flaky tests as Sprint risk

A flaky test is not just annoying.

It damages Scrum transparency.

If CI is red randomly, the team cannot inspect Increment quality reliably.

Flaky tests create:

- delayed PR merges,
- ignored test failures,
- hidden regressions,
- false confidence,
- reduced trust in automation,
- Sprint spillover.

### 11.1 Flaky test triage categories

| Category | Example | Fix direction |
|---|---|---|
| Async wait issue | arbitrary sleep | wait for business signal |
| Shared data | two tests use same quote | isolate fixture |
| Environment drift | QA service version mismatch | environment ownership |
| Time dependency | current date affects quote expiry | deterministic clock |
| Order dependency | test passes only after another | independent setup |
| External system instability | real downstream unavailable | simulator/contract boundary |
| Race condition | concurrency bug in product | fix product, not test |

Senior engineers should treat recurring flaky tests as engineering debt.

## 12. Testing and PR size

Large PRs are harder to test.

A huge PR often has:

- too many behavior changes,
- unclear risk surface,
- weak review quality,
- delayed feedback,
- broad regression risk,
- incomplete test evidence.

Story slicing and PR slicing are connected.

A well-sliced story should usually produce a reviewable PR.

### 12.1 PR test evidence section

Encourage PR descriptions to include:

```md
## Test evidence
- Unit:
- Integration:
- Contract:
- Migration:
- Security:
- E2E/manual:
- Observability:
- Not tested / intentionally deferred:
```

The “not tested” section is important.

It makes risk explicit.

## 13. Manual testing and exploratory testing

Automated testing is essential, but manual/exploratory testing still has value.

Use exploratory testing for:

- new UX/workflow,
- ambiguous domain behavior,
- customer-specific configuration,
- unexpected edge cases,
- integration workflows,
- failure-path exploration,
- support/operator tooling.

Exploratory testing should not be random clicking.

Use charters.

Example:

```md
## Exploratory charter: quote approval invalidation
Goal: Find cases where an approved quote can be changed without requiring reapproval.
Scope:
- price change
- item add/remove
- discount change
- catalog version change
- customer/account change
Evidence:
- screenshots/logs
- quote IDs
- API responses
- audit events
```

Manual testing should generate learning.

If a manual scenario is repeatedly valuable, automate it at the right level.

---

## 14. Production readiness tests

Some tests are not about functionality.

They are about operability.

For high-risk work, include checks such as:

- metric emitted,
- log contains correlation ID,
- trace contains quote/order ID where allowed,
- audit event written,
- alert/runbook updated,
- rollback path tested,
- migration can be resumed,
- feature flag can disable behavior,
- admin/support view works.

A story can be functionally correct but operationally unready.

That is not Done for enterprise systems.

## 15. Testing anti-patterns in Scrum

### 15.1 Testing after Sprint

If testing happens after Sprint, Sprint Review inspects incomplete work.

### 15.2 QA as gatekeeper of unclear work

QA cannot rescue ambiguous requirements.

### 15.3 Only happy-path automation

Happy path proves little for Quote & Order complexity.

### 15.4 E2E everything

Too many E2E tests slow feedback and increase flakiness.

### 15.5 Unit-test-only confidence

Unit tests cannot prove DB transaction, Kafka schema, or API contract behavior.

### 15.6 Ignoring migration testing

DB changes can break production even when application tests pass.

### 15.7 Treating observability as outside testing

If you cannot detect failure, release confidence is incomplete.

## 16. Senior engineer checklist during Sprint

At Sprint start:

- Are high-risk stories testable?
- Is test data available?
- Is QA involved where needed?
- Are contract/migration/security tests planned?
- Is DoD realistic for selected work?

During Sprint:

- Are tests being added with code?
- Are PRs showing test evidence?
- Are flaky tests blocking flow?
- Are discovered risks triggering scope adjustment?
- Are manual scenarios being converted to automation where appropriate?

Before Sprint Review:

- Is the Increment really Done?
- Are known risks visible?
- Are demos backed by evidence?
- Are operational artifacts ready?
- Are incomplete test gaps explicitly tracked?

## 18. Practical exercise

Pick one current or recent story.

Create a testing strategy table:

| Risk | Test type | Evidence | Owner | Sprint timing |
|---|---|---|---|---|
| Business rule wrong | Unit | parameterized rule tests | dev | during implementation |
| DB transaction race | Integration | concurrent command test | dev | before PR merge |
| API compatibility break | Contract | OpenAPI diff + consumer test | dev/QA | before merge |
| Tenant leakage | Security | cross-tenant negative test | dev/security | before merge |
| Operational invisibility | Observability | dashboard/log metric check | dev | before Done |

Then ask:

- Which evidence is missing today?
- Which evidence is too late?
- Which test belongs at a lower level?
- Which manual test should become automated?

---

## 19. Summary

Testing inside Scrum means quality evidence is created during the Sprint, not after the Sprint.

For enterprise Quote & Order work, the testing strategy must be risk-driven.

A senior engineer should ensure that every important PBI answers:

1. What can go wrong?
2. Which test layer catches it earliest?
3. What evidence proves it?
4. Who owns that evidence?
5. Is it part of Done?

The goal is not to maximize test count.

The goal is to maximize confidence in a usable, releasable Increment.
