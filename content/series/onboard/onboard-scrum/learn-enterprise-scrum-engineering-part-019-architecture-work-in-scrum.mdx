# Part 019 — Architecture Work in Scrum

## 1. Source notes and scope boundary

This part uses public Scrum and architecture references, especially:

- The Scrum Guide: Scrum is founded on empiricism and lean thinking; Scrum events provide formal opportunities for inspection and adaptation; the Increment is committed to the Definition of Done.
- Scrum.org material on emergent architecture and the need for professional Scrum Teams to let design and architecture evolve through empirical learning.
- Martin Fowler's Architecture Decision Record explanation: an ADR is a short document that captures a single architecture-relevant decision, its context, and consequences.
- The previous Quote & Order engineering series: design docs, ADRs, architecture review, operational readiness, migration safety, Kafka/event compatibility, PostgreSQL, and production failure modelling.

This part does **not** assume CSG uses a specific architecture board, ADR format, design doc tool, architecture runway framework, or approval process.

Use the internal verification checklist to validate how architecture work is actually handled in your team.

---

## 2. Core thesis

Architecture work belongs inside Scrum.

Not before Scrum.

Not after Scrum.

Not hidden in someone's head.

Not disguised as a vague technical task.

Not postponed until production forces the issue.

For enterprise Quote & Order systems, architecture is not an ivory-tower activity. It is the set of decisions that determine whether the team can safely evolve:

- quote lifecycle,
- pricing snapshot,
- approval authority,
- catalog versioning,
- order state machine,
- decomposition,
- Kafka event contract,
- PostgreSQL schema,
- tenant isolation,
- audit evidence,
- Kubernetes deployment,
- on-prem/cloud rollout,
- observability,
- data repair.

A Scrum Team that ignores architecture does not become agile.

It becomes fragile.

A Scrum Team that freezes architecture upfront does not become safe.

It becomes slow and speculative.

The senior engineer's task is to keep architecture work **incremental, explicit, evidence-based, and connected to product value**.

## 3. The false choice: big design upfront vs no design

Many teams fall into a false binary.

### 3.1 Big design upfront

Characteristics:

- months of architecture before real delivery,
- speculative future-proofing,
- diagrams disconnected from code,
- decisions made before uncertainty is reduced,
- architecture treated as approval gate,
- Scrum reduced to implementation tracking.

Risk:

- slow feedback,
- wrong assumptions,
- low ownership by developers,
- stale decisions,
- expensive rework.

### 3.2 No design

Characteristics:

- architecture emerges accidentally,
- every story makes local choices,
- hidden coupling grows,
- integration contracts drift,
- migrations become unsafe,
- operational readiness is late,
- production incidents become architecture review.

Risk:

- fragile codebase,
- inconsistent patterns,
- high cognitive load,
- scaling difficulty,
- unpredictable delivery.

### 3.3 Professional Scrum architecture

The better path:

- enough upfront thinking to avoid obvious traps,
- small decisions documented at the right time,
- architecture hypotheses validated through increments,
- design refined as learning emerges,
- architecture work visible in the Product Backlog,
- Definition of Done protects quality,
- ADRs record durable decisions,
- production feedback informs future architecture.

This is architecture as empirical control.

## 4. Architecture work types

Not all architecture work is the same.

Classify it before planning it.

| Work type | Example | Scrum treatment |
|---|---|---|
| Architecture discovery | Explore whether order replay can be made idempotent | Spike with hypothesis and decision output |
| Architecture decision | Choose event partition key strategy | ADR/design review |
| Architecture enablement | Add outbox table and relay foundation | Product Backlog Item or enabler story |
| Architecture refactoring | Centralize quote state transition logic | Incremental refactoring stories |
| Architecture guardrail | Add OpenAPI compatibility check | CI/DoD improvement item |
| Architecture migration | Expand-contract DB change | Multi-sprint planned backlog slice |
| Architecture validation | Load test new pricing cache | Test/measurement story |
| Architecture cleanup | Remove old dual-write path | Contract/cleanup story after migration window |

A vague ticket like `Improve architecture` is not useful.

A useful ticket says:

> Add a transactional outbox for order creation events so `ProductOrderCreated` is emitted only after the order transaction commits and can be retried safely. Include migration, relay test, duplicate-publish protection, dashboard metric, and ADR.

## 5. When architecture work is required

Architecture work is required when a backlog item changes a hard-to-reverse decision.

### 5.1 Triggers in Quote & Order

Architecture review or design work is likely needed when the change affects:

- quote lifecycle state machine,
- pricing snapshot immutability,
- approval invalidation,
- quote-to-order conversion,
- order decomposition,
- fulfillment fallout/retry,
- public/customer-facing API,
- TMF API mapping,
- Kafka topic/schema/partition key,
- database ownership or migration strategy,
- tenant isolation,
- audit evidence,
- identity/authorization boundary,
- cloud/on-prem deployment model,
- customer-specific configuration model,
- data repair/reconciliation flow.

### 5.2 Signals during refinement

Architecture work is needed when you hear:

- "We can just add a flag for this customer."
- "This event is only internal."
- "We can fix the data later."
- "The database migration is simple."
- "The old clients probably do not use that field."
- "The order status just needs one more enum."
- "We can call downstream directly from inside the transaction."
- "We can do this cleanup after release."
- "We do not need a runbook; it should not fail."

These are not automatically wrong.

They are signals that assumptions must be made explicit.

## 6. Architecture work in the Product Backlog

Architecture work should be visible in the Product Backlog when it consumes meaningful team capacity or affects delivery risk.

Bad backlog item:

```text
Tech design
```

Better backlog item:

```text
Design order cancellation event compatibility strategy
```

Great backlog item:

```text
As the Order service team, we need an ADR for order cancellation event compatibility so that old fulfillment and billing consumers can safely process cancellation-related events during rolling rollout and customer upgrade windows.

Acceptance criteria:
- current cancellation event producers/consumers identified;
- old/new event examples documented;
- compatibility options compared;
- replay and duplicate-handling impact documented;
- recommended option reviewed by API/event owners;
- follow-up implementation PBIs created.
```

Architecture work is product work when it protects future product delivery.

## 7. Architecture runway without waterfall

Architecture runway means the team has enough technical foundation to deliver upcoming product work safely.

It does not mean months of pre-building speculative infrastructure.

### 7.1 Good runway

Good runway is:

- connected to near-term Product Goal,
- validated through increments,
- small enough to inspect,
- tied to known risk,
- documented through ADR/design notes,
- maintained by the Developers who use it.

Example:

> Before adding three new order fallout flows, add a single lifecycle transition service and state history table so future fallout transitions are consistent and auditable.

### 7.2 Bad runway

Bad runway is:

- generic platform work without product pull,
- speculative framework creation,
- hidden architecture branch,
- no acceptance criteria,
- no production evidence,
- no cleanup plan.

Example:

> Build a generic workflow framework for all future order processes before delivering any fallout scenario.

Maybe someday useful.

Probably too speculative now.

## 8. Architecture slicing patterns

Architecture work can be sliced.

### 8.1 Slice by decision

Instead of one giant design:

- ADR 1: event partition key strategy,
- ADR 2: event envelope metadata,
- ADR 3: replay policy,
- ADR 4: DLQ handling,
- ADR 5: schema compatibility policy.

### 8.2 Slice by risk

Start with the riskiest uncertainty.

Example for pricing cache:

1. Measure current pricing latency.
2. Prototype cache invalidation strategy.
3. Add cache for one read-only catalog lookup.
4. Add dashboard and correctness comparison.
5. Expand to pricing path behind feature flag.

### 8.3 Slice by boundary

For Quote & Order:

- API contract first,
- domain invariant second,
- database model third,
- event contract fourth,
- observability fifth,
- rollout sixth.

### 8.4 Slice by reversible step

Each slice should be safe to roll forward or abandon.

Example:

1. Add nullable column.
2. Write new data while still reading old.
3. Backfill.
4. Switch reads.
5. Validate.
6. Remove old path later.

### 8.5 Slice by customer exposure

- internal dark launch,
- tenant-scoped feature flag,
- low-risk customer cohort,
- broader rollout,
- default enablement,
- cleanup.

## 9. Architecture decision records in Scrum

An ADR is useful when a decision is durable enough that future engineers will ask, "Why did we do this?"

### 9.1 When to write an ADR

Write an ADR when choosing:

- event schema versioning strategy,
- outbox/inbox implementation,
- API versioning policy,
- tenant isolation pattern,
- quote price snapshot policy,
- order state transition model,
- database migration strategy,
- customer-specific extension strategy,
- deployment topology,
- fallback/rollback strategy.

Do not write ADRs for tiny local decisions that are obvious in code.

### 9.2 ADR template

```md
# ADR-XXX: <Decision title>

## Status
Proposed / Accepted / Superseded / Deprecated

## Context
What problem are we solving?
What constraints matter?
What uncertainty exists?

## Decision
What are we deciding?

## Consequences
Positive:
- ...

Negative:
- ...

Neutral/trade-off:
- ...

## Alternatives considered
1. Option A
2. Option B
3. Option C

## Verification
How will we know this decision works?

## Supersession policy
What would cause this ADR to be revisited?
```

### 9.3 ADR as Sprint output

A Sprint can produce an ADR as part of valuable work if the ADR reduces material uncertainty and enables future delivery.

But an ADR alone is not always an Increment.

The team should be clear whether the ADR is:

- a discovery output,
- a decision artifact,
- part of a larger implementation Increment,
- a prerequisite for future work.

## 10. Design docs in Scrum

A design doc is larger than an ADR.

Use it when a change spans multiple concerns.

### 10.1 Design doc triggers

Use a design doc for:

- new order orchestration flow,
- significant pricing engine change,
- new customer integration model,
- migration across large tables,
- major API/event compatibility change,
- tenant isolation model change,
- production data repair framework,
- cloud/on-prem deployment architecture.

### 10.2 Design doc minimum sections

```md
# Design: <title>

## Problem
## Goals
## Non-goals
## Current behavior
## Proposed behavior
## Domain invariants
## API impact
## Event impact
## Database/migration impact
## Security/tenant/audit impact
## Observability
## Failure modes
## Rollout plan
## Rollback/repair plan
## Testing strategy
## Alternatives
## Open questions
## Decision log
```

A design doc should make implementation easier, not become a document graveyard.

## 11. Architecture work and Scrum events

Architecture work should appear in every Scrum event in the right form.

### 11.1 Refinement

Use refinement to discover architecture risk.

Ask:

- Does this story change a lifecycle invariant?
- Does it affect public contract?
- Does it need migration?
- Does it need event compatibility?
- Does it affect tenant/security/audit?
- Is there production observability?
- Is the work sliceable?
- Is a spike needed?

### 11.2 Sprint Planning

Use Sprint Planning to decide architecture capacity.

Ask:

- Is architecture work required to achieve Sprint Goal?
- Is architecture work reducing near-term risk?
- Is it sized and testable?
- Are reviewers available?
- Are dependencies known?
- Does it affect Definition of Done?

### 11.3 Daily Scrum

Use Daily Scrum to surface architecture blockers.

Examples:

- "We discovered the old event consumer cannot tolerate this enum."
- "The migration requires non-transactional index creation."
- "The design doc has one unresolved decision about rollback."
- "The PR is blocked on architecture owner review."

### 11.4 Sprint Review

Use Sprint Review to inspect architecture evidence.

Show:

- working slice,
- before/after metrics,
- contract diff,
- migration dry run,
- dashboard,
- ADR decision,
- failure scenario result.

Do not show only diagrams if the Sprint intended to produce a usable technical increment.

### 11.5 Retrospective

Use Retro to improve architecture practice.

Ask:

- Did architecture risk appear too late?
- Did design review block flow?
- Did we over-design?
- Did we under-design?
- Were ADRs useful?
- Did our Definition of Done catch architecture concerns?
- What architecture checklist should be updated?

## 12. Architecture work acceptance criteria

Architecture PBIs need acceptance criteria too.

### 12.1 Example: ADR story

```text
PBI: Decide event partition key for ProductOrder lifecycle events.

Acceptance criteria:
- current producers/consumers identified;
- candidate keys compared: orderId, customerId, tenantId+orderId;
- ordering guarantees documented;
- consumer replay impact documented;
- partition skew risk considered;
- recommendation accepted by event owners;
- implementation PBIs created;
- ADR stored in agreed location.
```

### 12.2 Example: architecture enablement story

```text
PBI: Add order lifecycle transition service.

Acceptance criteria:
- all new order state transitions go through transition service;
- transition service validates legal transition matrix;
- state history row is written in same transaction;
- outbox event is created for externally visible transition;
- duplicate command behavior tested;
- tenant scope preserved;
- audit/correlation metadata preserved;
- existing direct update paths identified for future migration.
```

### 12.3 Example: architecture validation story

```text
PBI: Validate pricing cache invalidation strategy.

Acceptance criteria:
- current pricing latency baseline captured;
- cache invalidation scenarios identified;
- one catalog update scenario tested;
- stale price risk documented;
- feature flag strategy proposed;
- dashboard metric proposed;
- go/no-go recommendation documented.
```

## 13. Senior engineer architecture review checklist

Use this checklist during refinement, design review, or PR review.

### 13.1 Domain

- What business invariant changes?
- Which lifecycle state is affected?
- Is the model using domain language correctly?
- Are historical objects still interpretable?
- Are customer-specific variants explicit?

### 13.2 API and contract

- Does the API change remain backward compatible?
- Are error semantics stable?
- Is OpenAPI/TMF mapping updated?
- Are generated clients affected?
- Are old consumers still safe?

### 13.3 Eventing

- Is the event emitted after commit?
- Is the schema compatible?
- Is partition key correct?
- Is replay safe?
- Is duplicate handling defined?
- Are correlation and causation IDs preserved?

### 13.4 Data

- What owns the source of truth?
- Is migration expand-contract?
- Are old and new app versions compatible?
- Are indexes/query plans considered?
- Is data repair possible if it fails?

### 13.5 Security/audit

- Does tenant isolation hold?
- Are authorization checks state-aware?
- Is audit evidence preserved?
- Are sensitive fields redacted?
- Is support/admin path safe?

### 13.6 Operations

- How will we detect failure?
- What dashboard/alert/runbook exists?
- Can this be disabled?
- Can this be rolled back or rolled forward?
- What happens during partial deployment?

### 13.7 Scrum flow

- Is this work visible in the backlog?
- Is it sliced safely?
- Are acceptance criteria clear?
- Is it tied to Sprint/Product Goal?
- Are dependencies and reviewers available?

## 14. Common anti-patterns

### 14.1 Architecture hidden inside feature ticket

The story says "add status field" but actually changes order lifecycle semantics.

Fix:

- split architecture decision from implementation,
- document lifecycle impact,
- update tests and DoD.

### 14.2 Sprint 0 forever

The team spends a long time designing without producing usable increments.

Fix:

- create thin vertical slices,
- validate assumptions quickly,
- document decisions incrementally.

### 14.3 Architecture by PR surprise

Major decision appears in a PR after implementation is done.

Fix:

- detect design triggers in refinement,
- use lightweight ADR before large implementation,
- identify reviewers early.

### 14.4 Generic platform before product pull

The team builds generic framework without immediate product need.

Fix:

- tie architecture work to concrete near-term use case,
- avoid speculative abstraction,
- keep escape hatches.

### 14.5 ADR graveyard

ADRs are written but never read, linked, or superseded.

Fix:

- keep ADRs short,
- link ADRs from PRs/design docs,
- supersede rather than edit history,
- review ADR relevance during architecture changes.

### 14.6 Architecture owner bottleneck

One person must approve every decision.

Fix:

- define decision thresholds,
- empower Developers,
- create review checklist,
- reserve formal review for high-risk decisions.

## 15. Internal verification checklist

Verify these in your actual CSG/team context.

### 15.1 Architecture governance

- When is a design doc required?
- When is an ADR required?
- Who approves architecture decisions?
- Is there an architecture review forum?
- Which decisions can the Scrum Team make independently?
- Which decisions require cross-team review?
- Where are design docs and ADRs stored?
- How are ADRs superseded?

### 15.2 Scrum integration

- Are architecture PBIs visible in the Product Backlog?
- Are spikes timeboxed?
- Is architecture work estimated?
- Does Sprint Planning reserve capacity for architecture risk?
- Are architecture decisions demonstrated in Sprint Review?
- Are architecture process improvements discussed in Retrospective?

### 15.3 Quote & Order specifics

- Which lifecycle changes require design review?
- Which API/event changes require compatibility review?
- Which migrations require DBA/platform review?
- Which tenant/security changes require security review?
- Which customer-specific changes require product/support review?
- Which deployment/on-prem changes require release review?

### 15.4 Artifact quality

- Do design docs include failure modes?
- Do ADRs include consequences?
- Are alternatives compared fairly?
- Are rollout/rollback/data repair considered?
- Are observability and testing included?
- Are open questions tracked?

## 16. Practical exercise: architecture work from a feature

Take a feature:

> Allow quote acceptance after manual approval for a special enterprise discount exception.

Identify architecture concerns:

- approval authority,
- approval invalidation,
- pricing snapshot,
- quote version,
- audit evidence,
- quote-to-order conversion,
- API error model,
- tenant/customer-specific rule,
- event emitted after acceptance,
- migration if approval basis stored differently,
- observability for failed acceptance.

Now split into PBIs:

1. Spike approval invalidation policy.
2. ADR approval evidence model.
3. Add domain tests for approval exception.
4. Implement acceptance guard.
5. Add audit event.
6. Add API contract test.
7. Add dashboard/log field.
8. Add E2E journey for special discount acceptance.

This is architecture inside Scrum.

Not upfront ceremony.

Not hidden work.

Incremental risk reduction.

---

## 17. Summary

Architecture work in Scrum should be:

- visible,
- incremental,
- tied to product risk,
- validated by evidence,
- documented just enough,
- integrated with Scrum events,
- protected by Definition of Done,
- improved through retrospection.

The senior engineer's responsibility is not to choose between agility and architecture.

The responsibility is to make architecture agile enough to learn, and disciplined enough to survive enterprise production.
