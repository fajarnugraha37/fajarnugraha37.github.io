# Part 015 — Flow, WIP, and Scrum with Kanban

## 1. Source notes and scope boundary

This part uses public Scrum and Kanban references, especially:

- The Scrum Guide for the role of the Sprint, Sprint Goal, Sprint Backlog, Increment, and Definition of Done.
- Scrum.org's Kanban Guide for Scrum Teams, which positions Kanban as a strategy for optimizing flow that can complement Scrum.
- Scrum.org flow-metrics material around Work in Progress, Cycle Time, Throughput, and Work Item Age.
- The previous parts in this series on Sprint Planning, estimation, Daily Scrum, and mid-sprint trade-offs.

This part does **not** assume the team uses a particular board tool, Jira workflow, Azure DevOps workflow, Kanban policy, Scrumban variant, WIP limit convention, or engineering metrics dashboard.

Use the `Internal verification checklist` sections to validate how your CSG team currently manages work, WIP, blockers, reviews, deployments, production interrupts, and carryover.

---

## 2. Core thesis

Scrum gives a team an empirical delivery loop.

Kanban-style flow thinking helps the team see whether work is actually moving.

For senior engineers, the key insight is:

> A Sprint can look busy while value is barely flowing.

Symptoms:

- many tickets in progress;
- many tickets almost done;
- many PRs waiting for review;
- many QA-ready items waiting for environment;
- many items blocked on dependency;
- many items carried over;
- many people context-switching;
- Sprint Review has low-quality demo/evidence;
- team says “we were busy” but the Increment is weak.

Flow thinking makes the invisible visible.

Instead of asking only:

> How many story points did we commit to?

Ask:

> How smoothly does work move from selected to done, where does it wait, and what prevents us from producing a usable Increment?

---

## 3. Scrum and Kanban are not enemies

A common misunderstanding is that a team must choose either Scrum or Kanban.

A better framing:

- Scrum defines accountabilities, events, artifacts, commitments, and an empirical cadence.
- Kanban practices help visualize and improve the flow of work through a system.

Scrum answers:

- What is the Sprint Goal?
- What Increment are we producing?
- How do we inspect and adapt?
- What does Done mean?
- Who is accountable for product value, facilitation, and delivery?

Kanban-style flow thinking answers:

- Where is work waiting?
- How much work is active?
- How old is active work?
- How often do we finish work?
- How long does work take to finish?
- Which policies create bottlenecks?

For an enterprise backend team, combining both is powerful.

Scrum provides purpose and cadence.

Flow metrics provide operational visibility.

## 4. Why flow matters in enterprise Quote & Order work

Quote & Order engineering work often crosses many boundaries:

- product backlog refinement;
- product/domain clarification;
- architecture review;
- Java implementation;
- MyBatis/PostgreSQL change;
- Kafka event/schema change;
- API contract update;
- test data setup;
- QA verification;
- security review;
- platform/deployment work;
- on-prem compatibility;
- support/runbook update;
- release readiness.

A story can be “in progress” for a long time because it is blocked by one of these hidden queues.

Examples:

- API work complete, but OpenAPI review is pending.
- Backend code complete, but DB migration review is pending.
- Order workflow implemented, but fulfillment simulator is unstable.
- Kafka producer implemented, but consumer contract is unclear.
- Quote pricing change coded, but product owner cannot confirm edge-case behavior.
- Story done locally, but CI environment has flaky Testcontainers failure.
- PR open for five days because all senior reviewers are overloaded.
- Feature flag implemented, but release enablement policy is unclear.

Flow management helps the team detect these problems early.

## 5. The flow unit: choose what you measure

Before using flow metrics, define the work item type.

Possible work item types:

- Product Backlog Item;
- user story;
- bug;
- spike;
- production incident;
- PR;
- design doc;
- DB migration;
- release ticket;
- customer escalation;
- support repair;
- QA task.

Do not mix everything blindly.

A production incident has different flow behavior than a feature story.

A PR has different flow behavior than an epic.

A data repair ticket has different flow behavior than a UI copy change.

### 5.1 Recommended starting point

For Scrum team execution, measure flow at three levels:

| Level | Work item | Why it matters |
|---|---|---|
| Team delivery flow | Sprint Backlog item | Shows whether Sprint-selected work becomes Done |
| Engineering flow | PR | Shows review/merge bottlenecks |
| Production flow | deployable change/release item | Shows whether Done work reaches usable/releasable state |

A team can have strong PR flow but weak release flow.

A team can have strong story flow but weak production readiness.

Senior engineers should care about all three.

## 6. Visualizing work

A board is not just a reporting tool.

It is a model of the team's delivery system.

A useful board makes work states and waiting states visible.

Weak board:

```text
To Do | In Progress | Done
```

Better board for enterprise backend work:

```text
Ready for Sprint
In Development
Code Review
Integration/Test
PO/QA Verification
Ready for Release
Done
Blocked
```

Even better: add explicit policies for each column.

Example:

| Column | Entry policy | Exit policy |
|---|---|---|
| In Development | Story selected and engineer assigned/pulled | Code complete, local tests run, PR opened |
| Code Review | PR open with description/tests | Required reviewers approved, comments resolved |
| Integration/Test | Merged or ready for environment validation | Integration/contract tests pass |
| PO/QA Verification | Behavior ready to inspect | Acceptance criteria verified |
| Ready for Release | Increment Done but not enabled/released | Release criteria satisfied |
| Done | Meets Definition of Done | No pending quality/release obligations |

Explicit policies prevent board theater.

## 7. Work in Progress (WIP)

WIP is the amount of work currently started but not finished.

High WIP creates:

- context switching;
- review overload;
- merge conflicts;
- stale assumptions;
- delayed feedback;
- hidden blockers;
- low predictability;
- more carryover;
- lower quality.

### 7.1 WIP in Scrum

Scrum already has natural WIP constraints:

- Sprint length;
- Sprint Goal;
- Sprint Backlog;
- team capacity;
- Definition of Done.

But Scrum does not automatically prevent a team from starting too much.

A team can select ten items and start all ten.

The Sprint still exists, but flow suffers.

### 7.2 WIP limits

A WIP limit is an explicit agreement that limits how many items can be active in a state.

Examples:

- maximum 3 stories in development;
- maximum 2 PRs waiting for review per reviewer group;
- maximum 1 high-risk migration in progress;
- maximum 2 blocked items before Daily Scrum escalates;
- maximum 1 production incident before Sprint Goal renegotiation.

The purpose is not to punish people.

The purpose is to force conversation.

When a column exceeds WIP limit, the team asks:

- Should we finish before starting more?
- Who can swarm?
- Is the work item too large?
- Is there a dependency bottleneck?
- Is review ownership unclear?
- Is environment/QA/platform blocking flow?

---

## 8. WIP anti-patterns

### 8.1 Everyone starts one item alone

Five developers start five stories.

By mid-sprint:

- all stories are 50% done;
- no story is Done;
- reviews pile up late;
- integration problems appear late;
- Sprint Review is weak.

Better:

- swarm on first high-risk item;
- finish one vertical slice;
- learn early;
- reduce uncertainty;
- then pull next work.

### 8.2 PR queue as invisible WIP

A team limits story WIP but ignores PR WIP.

The board says “In Progress: 2”.

But there are 8 open PRs waiting.

That is still WIP.

PR review delay is delivery delay.

### 8.3 Blocked items stay hidden

A ticket sits in progress for six days because the engineer is waiting for an external answer.

If the board does not show blocked state, the team cannot adapt.

### 8.4 WIP limit as management control

WIP limits should help the team manage flow.

They should not become a management weapon.

The right question is not:

> Who violated WIP?

The right question is:

> What does this WIP violation reveal about our system?

## 9. The four practical flow metrics

Start with four metrics:

1. Work in Progress.
2. Cycle Time.
3. Throughput.
4. Work Item Age.

These are simple, powerful, and usable in Scrum events.

### 9.1 Work in Progress

Question:

> How much work is currently started but not done?

Use in Daily Scrum:

- What is active?
- What is blocked?
- What can we finish today?
- Are we starting too much?

Use in Sprint Planning:

- How many items can we reasonably have active?
- Which items need swarming?
- Which items should not start until dependency clears?

### 9.2 Cycle Time

Question:

> How long does it take a work item to finish after it starts?

Useful for:

- forecasting;
- detecting bottlenecks;
- comparing work types;
- spotting outliers;
- improving review/test/deploy policies.

Do not weaponize cycle time per person.

Measure system behavior.

### 9.3 Throughput

Question:

> How many work items are completed per time period?

Useful for:

- probabilistic forecasting;
- understanding actual delivery rate;
- comparing sprint commitments to historical reality;
- detecting flow degradation.

Throughput is not velocity.

It counts finished items, not estimated points.

### 9.4 Work Item Age

Question:

> How old is currently active work?

This is often the most actionable Daily Scrum metric.

A story with 8 days of age in a 10-day Sprint deserves attention.

Ask:

- Is it blocked?
- Is it too large?
- Did scope expand?
- Is the acceptance criteria unclear?
- Is review or QA waiting?
- Should the team swarm?
- Should Sprint Goal be renegotiated?

---

## 10. Flow metrics are signals, not grades

Flow metrics should not be used to rank individuals.

That creates gaming.

Bad uses:

- compare developer cycle time;
- reward number of tickets closed;
- pressure team to split artificially;
- hide hard work because it hurts metrics;
- avoid production incidents because they reduce throughput.

Good uses:

- identify bottlenecks;
- improve board policy;
- reduce WIP;
- improve review flow;
- make blockers visible;
- improve forecast realism;
- reduce carryover;
- improve Sprint Goal confidence.

The senior engineer's role is to protect metrics as learning tools.

## 11. Applying flow to Scrum events

## 11.1 Sprint Planning

Use flow data to improve planning.

Ask:

- How many items did we finish in recent sprints?
- Which work types carried over?
- Which items had long cycle time?
- Which blockers repeated?
- How much production interrupt work happened?
- How many open PRs existed at Sprint start?
- Which dependencies are not ready?
- Which story is most likely to age badly?

Planning output:

- smaller Sprint Backlog;
- clearer Sprint Goal;
- explicit WIP policy;
- risk-first ordering;
- planned swarming for high-risk item;
- interrupt buffer if needed.

## 11.2 Daily Scrum

Use flow to focus the Daily Scrum.

Good Daily Scrum prompts:

- Which item is closest to Done?
- Which item is oldest?
- Which item is blocked?
- Which PR needs review today?
- Which item threatens the Sprint Goal?
- Which new work should we avoid starting?
- Where should we swarm?

Avoid pure status:

- yesterday I did X;
- today I will do Y;
- no blockers.

That format can be fine if it reveals flow, but often it hides system risk.

## 11.3 Sprint Review

Use flow data to explain delivery reality.

Show:

- what became Done;
- what did not become Done;
- what changed because of feedback;
- what flow bottleneck affected the Increment;
- what production-readiness evidence exists;
- what risk remains.

Sprint Review should inspect product progress, not merely output count.

## 11.4 Retrospective

Use flow data to select systemic improvement.

Examples:

- PR review wait time too long;
- blocked work not escalated until late;
- stories too large;
- QA environment unstable;
- DB migration review bottleneck;
- incidents repeatedly disrupt sprint;
- integration test flakiness increases cycle time.

Turn these into experiments.

Example retro action:

> For the next two sprints, we will limit open PRs to 4 and use Daily Scrum to assign reviewer ownership for every PR older than 24 hours.

## 12. Flow for PR review

PR review is one of the most common hidden queues.

Track:

- PR age;
- review wait time;
- number of open PRs;
- number of PRs per reviewer;
- time from first review to merge;
- rework cycles;
- blocked PRs;
- PR size.

### 12.1 PR WIP policy example

```md
## PR Flow Policy

- Prefer PRs that can be reviewed in under 30 minutes.
- Every PR must include intent, risk, test evidence, and rollback/compatibility notes if relevant.
- PRs older than 24 hours are discussed in Daily Scrum.
- PRs touching DB migration, security, API contract, or Kafka event require named owner review.
- Review comments use severity: blocking, strong suggestion, question, nit, future.
- Engineers should review before pulling new work when PR queue exceeds WIP limit.
```

This turns review from ad hoc goodwill into team flow responsibility.

## 13. Flow for QA and verification

In many teams, development flow looks healthy until work reaches verification.

Common queues:

- QA environment unavailable;
- test data missing;
- acceptance criteria ambiguous;
- external simulator unstable;
- product owner unavailable;
- integration dependency broken;
- E2E suite flaky.

Senior engineers should help make verification constraints visible during refinement and Sprint Planning.

For Quote & Order work, ask:

- Which test data is needed?
- Which catalog version is required?
- Which customer/account fixture is required?
- Which downstream simulator behavior is required?
- Which Kafka event should be observed?
- Which audit event should be checked?
- Which migration state should be tested?
- Which tenant/security case should be verified?

---

## 14. Flow for production incidents

Production incidents are work.

If they are invisible, Sprint metrics become fantasy.

Track incident work separately:

- incident triage;
- mitigation;
- data repair;
- root cause analysis;
- prevention work;
- customer support follow-up;
- postmortem actions.

Do not hide incident work inside feature tickets.

If production interrupts consume 30% of team capacity, Sprint Planning should reflect that.

If the same incident type repeats, Retrospective should address the system, not blame the interruption.

---

## 15. Flow and service ownership

Flow problems often reveal ownership problems.

Examples:

- DB migration PRs wait because no DB owner is available.
- Kafka schema changes wait because event ownership is unclear.
- Security review waits because role/permission ownership is unclear.
- Customer-specific behavior waits because no one owns the tenant configuration model.
- Runbook updates wait because operations ownership is unclear.

A senior engineer should interpret queues as architecture signals.

A queue is not always a people problem.

It may be a boundary problem.

## 16. Flow diagnostics for Quote & Order teams

Use this table during Retrospective or flow review.

| Symptom | Possible cause | Senior engineer response |
|---|---|---|
| Many items in development | Starting too much | Swarm, reduce active work, split stories |
| Many PRs waiting | Review ownership unclear | Define reviewer rotation / PR WIP policy |
| Many items blocked | Dependencies discovered too late | Improve refinement and DoR |
| Many QA failures late | AC/test data unclear | Add verification planning earlier |
| Many carryovers | Stories too large or hidden work | Improve slicing and risk discovery |
| Many bugs after Done | DoD too weak | Strengthen DoD and tests |
| Long cycle time for DB work | Migration review bottleneck | Create DB review checklist/pattern |
| Long cycle time for event work | Consumer compatibility unclear | Add event contract/refinement policy |
| Sprint Goal missed despite high effort | WIP/context switching | Limit active work and focus on goal |
| Production interrupts dominate | Operational debt | Make prevention work visible in backlog |

## 17. Scrum with Kanban board design for enterprise backend

A practical board might use these columns:

```text
Refined
Ready for Sprint
In Development
PR Open
Review Changes Needed
Merged / Integration
QA / Product Verification
Ready for Release
Done
Blocked
```

But column count is not the main issue.

The important questions:

- Does the board show waiting states?
- Does it show blocked work?
- Does it show review queues?
- Does it distinguish Done from ready-for-release?
- Does it expose production interrupt work?
- Does it help the team adapt daily?

### 17.1 Explicit policies example

```md
## Ready for Sprint
- Acceptance criteria clear enough for implementation.
- Major dependencies identified.
- Test data approach known.
- No unresolved architecture/security question that blocks start.

## In Development
- Engineer actively working.
- If no progress for 1 day, raise in Daily Scrum.

## PR Open
- PR description includes intent, risk, tests, and affected surfaces.
- Named reviewer assigned.
- PR older than 24 hours is escalated in Daily Scrum.

## QA / Product Verification
- AC can be verified in available environment.
- Required test data exists.
- Failures create either bug, story update, or AC clarification.

## Done
- Meets Definition of Done.
- No hidden verification, documentation, migration, or release-readiness work remains.
```

## 18. Flow and Sprint Goal

Flow should serve the Sprint Goal.

Do not optimize flow by finishing low-value work while the Sprint Goal fails.

Bad behavior:

- finish many small unrelated tickets;
- ignore the high-risk Sprint Goal item;
- claim high throughput;
- deliver weak Increment.

Good behavior:

- identify the work item most tied to Sprint Goal;
- reduce WIP around it;
- swarm on blockers;
- avoid starting unrelated items until core goal is safe;
- inspect Sprint Goal confidence daily.

Flow metrics help, but Sprint Goal gives direction.

---

## 19. Flow and estimation

Flow metrics can improve forecasting.

Instead of relying only on story points, the team can ask:

- How many similar items do we usually finish per Sprint?
- What is the cycle-time distribution for this type of work?
- How often do migration stories carry over?
- How often do stories with external dependencies exceed one Sprint?
- What is the probability this item finishes this Sprint if started today?

Do not replace conversation with formula.

Use flow data to make planning more honest.

## 20. Flow and technical debt

Technical debt shows up in flow.

Examples:

- slow test suite delays every PR;
- flaky tests force reruns;
- unclear ownership creates review wait;
- weak local dev setup delays onboarding;
- brittle integration environment blocks verification;
- monolithic PRs become review bottleneck;
- unsafe migration pattern creates release delays;
- poor observability slows incident resolution.

When proposing technical debt work, tie it to flow evidence.

Weak argument:

> We need to refactor because the code is ugly.

Stronger argument:

> Over the last four sprints, order lifecycle stories had the longest cycle time. Three of five carryovers were caused by duplicate status mutation paths and missing test fixtures. Centralizing transitions behind a tested lifecycle service should reduce review/rework and lower production risk.

## 21. Practical flow review ritual

Run this every 2-4 weeks.

### 21.1 Inputs

- board history;
- carryover items;
- blocked items;
- PR age;
- review wait time;
- cycle-time outliers;
- production interrupts;
- escaped defects;
- deployment delays.

### 21.2 Questions

1. Which items aged the most?
2. Which states accumulated the most waiting?
3. Which dependencies blocked us?
4. Which work type was hardest to finish?
5. Which policy was missing or unclear?
6. Which quality gap caused rework?
7. Which improvement experiment should we try next Sprint?

### 21.3 Output

One or two experiments, not ten.

Examples:

- WIP limit open PRs to 4.
- Assign reviewer at PR creation.
- Split stories with DB migration into expand/backfill/contract items.
- Add test-data readiness check during refinement.
- Escalate blocked items after 24 hours.
- Add a QA environment smoke check before Sprint starts.

## 22. Internal verification checklist

Validate these in your actual CSG/team context.

### 22.1 Board and workflow

- What board tool is used?
- What columns exist?
- Do columns reflect real work states?
- Does the board show blocked work?
- Does the board show PR review state?
- Does the board distinguish Done from ready-for-release?
- Are production incidents tracked in the same board or separate board?

### 22.2 WIP policy

- Are there WIP limits?
- Are they explicit or informal?
- Do engineers start too many items?
- Does the team swarm?
- What happens when WIP is exceeded?
- Are WIP limits used for learning or pressure?

### 22.3 Flow metrics

- Is cycle time measured?
- Is throughput measured?
- Is work item age visible?
- Is blocked time visible?
- Is PR review wait time visible?
- Are metrics used in retrospectives?
- Are metrics used responsibly, not for individual performance ranking?

### 22.4 Bottlenecks

- Where do stories wait most often?
- Where do PRs wait most often?
- Which review ownership is unclear?
- Which environments are unstable?
- Which dependencies often block the team?
- Which work types most often carry over?

### 22.5 Improvement loop

- Does Retrospective generate flow experiments?
- Are experiments reviewed later?
- Are policies updated based on evidence?
- Are recurring blockers converted into backlog items?

## 23. PR review checklist for flow-sensitive changes

When reviewing process/board/flow changes, ask:

- Does this make real waiting visible?
- Does this help the team finish Sprint Goal work?
- Does this reduce hidden WIP?
- Does this improve review/verification flow?
- Does this create useful data or bureaucracy?
- Does this protect quality or encourage gaming?
- Does this clarify policies?
- Does this help production readiness?
- Does this help cross-team dependencies surface earlier?

## 24. Practical exercise

For the last three sprints, collect:

- number of items selected;
- number of items Done;
- number of carryovers;
- oldest item per Sprint;
- number of open PRs at peak;
- average PR review wait time if available;
- blocked items;
- production interrupts;
- items that were Done but not releasable.

Then answer:

1. What is the main bottleneck?
2. What is the strongest evidence?
3. What policy should be changed for one Sprint?
4. How will you know whether the experiment helped?

Do not try to fix everything.

Pick one flow constraint and improve it deliberately.

---

## 25. Summary

Scrum gives the team a cadence and empirical framework.

Kanban-style flow thinking helps the team see how work actually moves.

For a senior engineer, flow is not project-management trivia.

It is a way to detect:

- hidden WIP;
- review bottlenecks;
- unclear ownership;
- poor story slicing;
- weak acceptance criteria;
- environment friction;
- production interrupt load;
- technical debt;
- Definition of Done gaps.

The key principle:

> Do not optimize for being busy. Optimize for producing a Done, usable, production-ready Increment with less waiting, less rework, and less hidden risk.
