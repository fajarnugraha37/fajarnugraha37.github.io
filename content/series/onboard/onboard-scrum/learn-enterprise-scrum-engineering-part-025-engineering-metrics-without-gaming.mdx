# Part 025 — Engineering Metrics Without Gaming

## 1. Source notes and scope boundary

This part uses public references and general engineering practice:

- Scrum.org Evidence-Based Management describes four Key Value Areas: Current Value, Unrealized Value, Time to Market, and Ability to Innovate.
- Scrum with Kanban material commonly uses flow-oriented measures such as Work in Progress, Cycle Time, Work Item Age, and Throughput.
- DORA research popularized software delivery performance metrics such as lead time for changes, deployment frequency, change failure rate, and failed deployment recovery time.
- Scrum Guide emphasizes empiricism, transparency, inspection, adaptation, Sprint Goal, Increment, and Definition of Done.

This part does not assume CSG uses a specific tool, dashboard, metric framework, performance review process, Jira workflow, DORA implementation, or Evidence-Based Management implementation.

Use internal verification checklists to adapt these ideas to actual team practice.

---

## 2. Core thesis

Metrics are not truth.

Metrics are instruments.

A thermometer does not understand illness. A speedometer does not understand destination. A sprint chart does not understand domain risk. A deployment frequency number does not understand whether customers received value.

Engineering metrics are useful when they help the team ask better questions:

- Where is work stuck?
- What risk do we discover too late?
- Which defects escape our Definition of Done?
- Which backlog items are too large or ambiguous?
- Which PRs wait too long?
- Which tests slow feedback?
- Which production signals show product pain?
- Which system areas are becoming harder to change?
- Which improvements actually reduce future risk?

Metrics become harmful when they become targets detached from context.

A senior engineer's job is not to maximize metrics.

A senior engineer's job is to interpret metrics as evidence, connect them to real system behavior, and prevent gaming.

---

## 3. Why metrics get gamed

Metrics get gamed because people adapt to incentives.

If velocity is used to judge team performance, teams inflate estimates.

If number of tickets closed is rewarded, teams split work into tiny low-value tickets.

If deployment frequency is worshipped, teams deploy harmless config changes frequently while avoiding hard changes.

If cycle time is pressured without quality context, teams skip review and testing.

If escaped defects are punished, teams under-report defects.

If story points are compared across teams, planning becomes negotiation theater.

If incidents are used to blame teams, incident classification becomes political.

The cure is not "no metrics".

The cure is good metric hygiene:

1. Use metrics for learning, not punishment.
2. Combine quantitative signals with qualitative context.
3. Measure systems, not individuals.
4. Prefer trends over single numbers.
5. Use multiple balancing metrics.
6. Inspect outliers with curiosity.
7. Connect metrics to business and production outcomes.
8. Retire metrics that create harmful behavior.

## 4. Metrics taxonomy for Scrum engineering

Use at least five categories.

| Category | Primary question | Example metrics |
|---|---|---|
| Product value | Are we moving toward meaningful outcomes? | adoption, conversion, customer pain reduction, support volume |
| Flow | How smoothly does work move? | WIP, cycle time, throughput, work item age, blocked time |
| Quality | Are we building safely? | escaped defects, flaky tests, test failure patterns, regression count |
| Delivery | Can we release changes safely? | lead time, deployment frequency, change failure rate, recovery time |
| Operability | Can we detect and recover production issues? | SLOs, alert quality, MTTR, incident recurrence, runbook coverage |

A team that tracks only velocity has a shallow picture.

A Quote & Order team should care about value, flow, quality, delivery, and operability at the same time.

## 5. Product value metrics

Product value metrics answer:

> Is the product becoming more valuable to customers and users?

For a Quote & Order team, possible value signals include:

- quote creation success rate;
- quote-to-order conversion rate;
- quote pricing latency;
- quote approval cycle time;
- order capture success rate;
- order fallout rate;
- time from quote acceptance to product order creation;
- time from product order creation to fulfillment completion;
- number of manual support interventions;
- customer integration error rate;
- billing handoff rejection rate;
- number of stuck orders;
- customer-reported defects by workflow;
- reduction in manual work for sales/support/operations.

These are not always owned purely by engineering.

But engineering should understand them.

### 5.1 Product metric anti-pattern

Bad metric:

> We delivered 45 story points.

Better metric:

> We reduced order fallout caused by duplicate fulfillment callbacks from 3.2% to 0.4% for affected workflows, and the new dashboard detects remaining failures within 5 minutes.

The second describes product/operational impact.

## 6. Flow metrics

Flow metrics show how work moves through the team.

### 6.1 Work in Progress

WIP is work started but not finished.

High WIP causes:

- context switching;
- longer cycle time;
- stale branches;
- review bottlenecks;
- hidden blockers;
- many almost-done tickets;
- lower Sprint Goal focus.

For enterprise backend work, WIP often hides in:

- PRs waiting review;
- tickets waiting QA;
- stories blocked by environment;
- design discussions waiting decision;
- migration PRs waiting DBA/platform review;
- features merged but not released;
- work done but missing observability/runbook.

Senior engineer action:

- reduce WIP before starting new work;
- swarm blocked PRs;
- split over-large stories;
- make hidden queues visible;
- protect Sprint Goal from uncontrolled starts.

### 6.2 Cycle time

Cycle time measures how long work takes from start to finish.

But define boundaries clearly.

Possible start points:

- moved to `In Progress`;
- branch created;
- first commit;
- PR opened;
- Sprint started.

Possible finish points:

- PR merged;
- QA passed;
- deployed to staging;
- deployed to production;
- customer enabled;
- meets Definition of Done.

For enterprise Scrum, "done" should align with Definition of Done, not simply merge.

### 6.3 Work item age

Work item age asks:

> How long has this active item been in progress?

This is often more useful than average cycle time because it highlights current risk.

A story active for seven days in a two-week sprint deserves attention.

Possible reasons:

- unclear acceptance criteria;
- dependency hidden;
- PR too large;
- test environment broken;
- integration ambiguity;
- waiting for architecture decision;
- engineer overloaded;
- work was started too early.

### 6.4 Throughput

Throughput counts finished work items per time window.

Use carefully.

Throughput helps forecasting when item sizes are reasonably stable.

It becomes misleading when teams split work differently to improve the number.

Do not compare throughput across teams without context.

## 7. Delivery metrics

Delivery metrics show whether the team can change production safely.

Common useful signals:

- lead time for changes;
- deployment frequency;
- change failure rate;
- recovery time from failed deployment;
- rollback frequency;
- release queue time;
- environment promotion time;
- migration failure rate;
- deployment blocked by test failure;
- deployment blocked by manual approval wait.

### 7.1 Lead time for changes

Ask:

> How long from code committed to safely running in production/customer environment?

For cloud SaaS, this may be short.

For on-prem/customer-managed deployments, the path may be much longer.

Separate:

- development lead time;
- PR review time;
- CI time;
- staging wait;
- release approval wait;
- production deployment wait;
- customer enablement wait;
- on-prem packaging wait.

A single lead time number hides too much.

### 7.2 Deployment frequency

More frequent deployment is not automatically better if deployments are unsafe.

Deployment frequency should be paired with:

- change failure rate;
- rollback rate;
- production incident rate;
- test reliability;
- release confidence;
- customer value delivered.

### 7.3 Change failure rate

Change failure rate asks:

> How often does a change cause production degradation requiring remediation?

For Quote & Order, remediation may include:

- rollback;
- hotfix;
- feature flag disable;
- data repair;
- replay/reconciliation;
- support intervention;
- customer communication.

Include data correction and manual remediation, not only code rollback.

### 7.4 Recovery time

Recovery time should measure from detection to restored safe state.

Be explicit:

- detection time;
- mitigation time;
- full recovery time;
- data repair completion time;
- customer communication closure.

For enterprise workflows, mitigation may happen quickly but full data correction may take longer.

## 8. Quality metrics

Quality metrics should reveal where Definition of Done is weak.

Possible signals:

- escaped defects;
- defects by lifecycle stage;
- defect recurrence;
- automated test failure rate;
- flaky test rate;
- mutation/coverage signals where useful;
- contract test failures;
- migration dry-run failures;
- security test failures;
- production data repair count;
- incidents caused by missing observability;
- incidents caused by missing acceptance criteria.

### 8.1 Escaped defects

Classify escaped defects by cause:

| Cause | Example | Improvement |
|---|---|---|
| Missing unit test | approval threshold edge case | add invariant test |
| Missing integration test | MyBatis mapper missed tenant predicate | mapper integration test |
| Missing contract test | API enum broke client | OpenAPI/consumer contract gate |
| Missing migration test | old rows failed new NOT NULL | production-like migration test |
| Missing E2E path | order fallout resume broken | high-value journey test |
| Missing observability | stuck order detected by customer | dashboard/alert/runbook |
| Ambiguous AC | expected behavior unclear | better refinement template |

The metric matters less than the prevention.

### 8.2 Flaky tests

Flaky tests are not just annoying.

They destroy trust in CI.

Track:

- top flaky tests;
- failure rate;
- time lost rerunning;
- module/component;
- root cause;
- owner;
- age.

Possible root causes:

- time-based assumptions;
- shared state;
- environment instability;
- async waiting with sleep;
- order-dependent tests;
- real external dependency;
- test data collision;
- resource starvation.

Make flaky tests visible in retrospectives.

## 9. Operability metrics

Operability metrics answer:

> Can the team understand and recover production behavior?

For Quote & Order, useful signals include:

- quote creation error rate;
- quote pricing latency;
- quote acceptance failures;
- order creation failure rate;
- order fallout rate;
- order stuck-state count;
- outbox backlog age;
- Kafka consumer lag age;
- DLQ growth;
- PostgreSQL lock wait time;
- slow query count;
- pod restart count;
- JVM memory/GC pressure;
- auth/authorization denial spikes;
- audit write failure;
- support tickets by workflow.

### 9.1 Alert quality

Track alert quality:

- actionable alerts;
- noisy alerts;
- duplicate alerts;
- alerts with runbook;
- alerts that detected real incidents;
- incidents not detected by alerts;
- time from symptom to alert;
- time from alert to triage.

Bad alert metric:

> Number of alerts.

Better:

> Percentage of incidents detected by actionable alerts before customer report.

## 10. Scrum metrics

Scrum metrics should support empiricism.

Use carefully.

### 10.1 Sprint Goal confidence

Track whether the Sprint Goal is likely to be met.

Daily signal:

- green: on track;
- yellow: risk discovered;
- red: goal unlikely without trade-off.

This is more useful than asking each person for status.

### 10.2 Sprint Goal achievement

At Sprint Review or Retrospective, ask:

- Was Sprint Goal achieved?
- If not, why?
- Was scope too broad?
- Was refinement weak?
- Did production interrupt load exceed expectation?
- Did dependencies slip?
- Did quality gates discover late risk?
- Was the goal poorly written?

### 10.3 Carryover

Carryover is not automatically bad.

Some work carries over because the team learned something important.

Classify carryover:

- scope too large;
- hidden dependency;
- unclear AC;
- review bottleneck;
- test instability;
- environment issue;
- production incident;
- PO priority change;
- unplanned technical discovery;
- overcommitment.

Do not shame carryover.

Learn from it.

### 10.4 Velocity

Velocity is useful for a team forecasting its own near-future capacity when used carefully.

Velocity is harmful when used to compare people or teams.

Rules:

- do not compare velocity across teams;
- do not use velocity as individual productivity metric;
- do not force velocity to rise;
- inspect large changes in velocity;
- pair velocity with quality/flow/outcome signals;
- remember that point inflation is easy.

## 12. Metric interpretation examples

### 12.1 Cycle time increased

Weak interpretation:

> Engineers are slower.

Better investigation:

- Are stories larger?
- Are PRs larger?
- Is review queue backed up?
- Did QA wait increase?
- Did CI become slower?
- Did production interrupts increase?
- Did dependencies outside team increase?
- Did Definition of Done become stronger?
- Is work more architecture-heavy this Sprint?

### 12.2 Velocity increased sharply

Possible explanations:

- team got better;
- work was easier;
- story points inflated;
- work split smaller;
- quality skipped;
- technical debt postponed;
- several old items completed at once.

Do not celebrate blindly.

Inspect.

### 12.3 Deployment frequency is high, but incidents increased

Possible causes:

- releases too small but under-tested;
- feature flags uncontrolled;
- migration gates weak;
- test suite unreliable;
- observability insufficient;
- change review rushed.

Pair speed with safety.

### 12.4 Escaped defects decreased, but support tickets increased

Possible causes:

- defects are classified differently;
- customers report usability/config issues not counted as bugs;
- product behavior changed but technically works;
- support friction increased;
- observability finds internal defects while customers still struggle.

Metrics need context.

## 13. Metrics for senior engineer self-management

Use personal metrics privately as reflection, not as performance theater.

Ask monthly:

- Which PR review found real risk?
- Which review comment taught a reusable principle?
- Which design decision became clearer because of my input?
- Which production signal did I improve?
- Which recurring friction did I reduce?
- Which teammate did I enable?
- Which debt item did I turn into actionable backlog?
- Which assumption did I verify?

Do not measure yourself by lines of code.

Measure yourself by leverage and risk reduction.

---

## 14. Metrics anti-patterns

### 14.1 Velocity as productivity

Velocity is a planning signal.

It is not productivity.

### 14.2 Individual story points

This destroys team behavior.

Scrum Team delivers together.

### 14.3 Ticket count worship

Closing many small tickets does not mean delivering valuable Increment.

### 14.4 Ignoring aging work

Average cycle time can look fine while one critical item is stuck.

### 14.5 No balancing metrics

Improving speed while quality collapses is not improvement.

### 14.6 Hiding quality work

If tests, observability, runbooks, and migration safety are invisible, they will be squeezed.

### 14.7 Metrics without action

A dashboard nobody uses is decorative.

### 14.8 Metrics as blame

Blame causes distortion.

Learning creates improvement.

## 17. Practical exercises

### Exercise 1 — Metric inventory

List all metrics your team currently uses.

Classify each as:

- product value;
- flow;
- quality;
- delivery;
- operability;
- vanity;
- unclear.

For each metric, ask:

- what decision does this support?
- what behavior could it accidentally encourage?
- what balancing metric is needed?

### Exercise 2 — Build a balanced team dashboard

Design a dashboard with no more than 12 metrics.

Include at least:

- one product/journey metric;
- one flow metric;
- one quality metric;
- one delivery metric;
- one operability metric.

### Exercise 3 — Analyze carryover

Take last 5 carryover items.

Classify root cause.

Create one improvement action.

### Exercise 4 — Review PR latency

Measure last 20 PRs:

- time from open to first review;
- time from first review to merge;
- number of review rounds;
- PR size;
- escaped defects if any.

Identify one review system improvement.

---

## 18. Summary

Engineering metrics should support empirical improvement.

They should not become a scoreboard for fear, blame, or vanity.

For senior engineers in Quote & Order systems, useful metrics connect:

- product value,
- flow,
- quality,
- delivery,
- operability,
- team learning.

The goal is not to make every number green.

The goal is to understand the system well enough to improve it safely.
