# Part 012 — Estimation Under Uncertainty

## 1. Source notes and scope boundary

This part uses public Scrum guidance and modern agile engineering practice.

Public references to verify independently:

- Scrum does not mandate story points, velocity, planning poker, t-shirt sizing, or any particular estimation method.
- Scrum.org materials commonly frame estimation as a tool for conversation, forecasting, and planning, not as a measure of individual productivity.
- Scrum.org Evidence-Based Management emphasizes using evidence, experimentation, feedback, and metrics to make better-informed decisions and reduce risk.

This part does **not** assume CSG uses story points, ideal days, no-estimates, planning poker, throughput forecasting, Monte Carlo simulation, or any specific estimation policy.

Use the `Internal verification checklist` sections to validate actual team practice.

---

## 2. Core thesis

Estimation is not prediction.

Estimation is structured uncertainty communication.

A useful estimate says:

> Based on what we currently know, this work appears roughly this large, has these unknowns, carries these risks, and should be planned with these assumptions.

A harmful estimate says:

> This is exactly 5 points, and therefore it will be done by Thursday.

In enterprise Quote & Order work, uncertainty is normal because work may involve:

- ambiguous domain rules;
- customer-specific behavior;
- TMF/API compatibility;
- downstream integration;
- Kafka event replay;
- PostgreSQL migration;
- legacy code paths;
- test environment instability;
- production incident load;
- security/audit review;
- on-prem deployment constraints.

Senior engineers help the team estimate honestly, not optimistically.

---

## 3. What estimation is for

Estimation can support:

- Sprint Planning;
- capacity conversation;
- backlog ordering;
- dependency negotiation;
- delivery forecasting;
- scope slicing;
- risk discovery;
- deciding whether a spike is needed;
- deciding whether a story is too large;
- stakeholder expectation setting.

Estimation should **not** be used for:

- comparing individual productivity;
- judging engineer performance;
- forcing false commitments;
- hiding uncertainty;
- measuring business value;
- replacing Product Owner ordering judgment;
- avoiding refinement;
- pretending complex work is deterministic.

## 4. Estimate size, uncertainty, and risk separately

Many teams overload one number.

A story point often mixes:

- effort;
- complexity;
- uncertainty;
- dependency;
- risk;
- testing cost;
- coordination cost.

That can be useful for rough sizing, but it can also hide important differences.

Compare:

| Work | Size | Uncertainty | Risk |
|---|---:|---:|---:|
| Add validation message | Small | Low | Low |
| Add optional API field | Small | Low | Medium if public contract |
| Change quote approval rule | Medium | Medium | High |
| Add DB index to hot order table | Small SQL | Medium | High operational risk |
| Integrate new fulfillment callback | Medium | High | High |
| Refactor order state transition | Large | Medium | High |

A senior engineer should say:

> This may be small in code size, but high in production risk.

That distinction prevents dangerous under-planning.

## 5. Relative sizing

Relative sizing asks:

> Compared to known work, is this smaller, similar, or larger?

It is usually more reliable than absolute time prediction.

### 5.1 Use reference stories

Maintain reference examples.

| Size | Reference story |
|---|---|
| XS | Add one non-contract log field with test update |
| S | Add validation for one draft quote field |
| M | Add new API filter with mapper/index/test changes |
| L | Add new quote approval edge case across API/domain/audit |
| XL | Change order decomposition behavior with Kafka event and migration |

Reference stories should be local to the team.

A 5-point story in one team is not equivalent to a 5-point story in another team.

### 5.2 Avoid false precision

A debate between 5 and 8 may be useful if it exposes hidden risk.

A long debate between 5 and 6 is usually waste.

The real question:

> Is the work small enough, clear enough, and safe enough for the Sprint?

## 6. Confidence levels

Every estimate should have a confidence level.

Example:

```text
Estimate: Medium
Confidence: Low
Reason: downstream fulfillment sandbox behavior unknown; callback schema not verified.
Next action: spike before committing implementation story.
```

### 6.1 Confidence scale

| Confidence | Meaning | Planning implication |
|---|---|---|
| High | Similar work done recently; dependencies known | Can plan normally |
| Medium | Some unknowns but bounded | Plan with buffer or early de-risking |
| Low | Key assumptions unverified | Spike/split before full commitment |
| Unknown | Not enough information | Do not commit as delivery story |

A low-confidence estimate is not a failure.

It is useful information.

## 7. Estimation signals for Quote & Order work

### 7.1 Domain uncertainty

Signals:

- unclear lifecycle state;
- unclear approval rule;
- unclear price validity rule;
- unclear customer/account hierarchy;
- unclear installed base semantics;
- multiple customer-specific variants;
- conflict between product wording and code behavior.

Response:

- domain clarification;
- example mapping;
- acceptance criteria improvement;
- spike or design note.

### 7.2 Technical uncertainty

Signals:

- unfamiliar legacy module;
- hidden side effects;
- duplicated logic;
- unclear transaction boundary;
- missing tests;
- uncertain mapper behavior;
- unknown performance profile.

Response:

- characterization test;
- code archaeology;
- small refactor seam;
- integration test;
- pair with owner.

### 7.3 Integration uncertainty

Signals:

- downstream API unclear;
- sandbox unstable;
- callback behavior unknown;
- retry/idempotency not documented;
- unknown outcome case not modeled.

Response:

- simulator;
- contract test;
- spike;
- integration owner alignment;
- failure-mode mapping.

### 7.4 Data/migration uncertainty

Signals:

- large table;
- hot query;
- non-null column;
- backfill required;
- old data shape unknown;
- on-prem upgrade path unknown.

Response:

- migration spike;
- production-like fixture;
- expand-contract plan;
- DBA/platform review;
- split migration from behavior activation.

### 7.5 Operational uncertainty

Signals:

- no dashboard;
- no runbook;
- no alert;
- no rollback path;
- unknown support workflow;
- production incident history in area.

Response:

- include operability in estimate;
- add runbook/dashboard task;
- reduce scope;
- plan feature flag.

## 8. Estimation by work type

### 8.1 Pure domain logic

Estimate drivers:

- number of rules;
- state combinations;
- edge cases;
- existing test coverage;
- audit requirement;
- approval/security interaction.

Example:

> Add rule: quote cannot be accepted after price expiry.

Hidden work:

- define expiry semantics;
- test accepted/draft/pending states;
- API error behavior;
- audit event;
- UI/API consumer expectation;
- existing quote compatibility.

### 8.2 API work

Estimate drivers:

- contract visibility;
- client compatibility;
- error model;
- pagination/filtering;
- auth/tenant scope;
- generated client impact.

Small code changes can be high coordination work.

### 8.3 Kafka/event work

Estimate drivers:

- producer logic;
- schema compatibility;
- consumers;
- replay safety;
- ordering;
- DLQ/retry behavior;
- test infrastructure.

### 8.4 Database work

Estimate drivers:

- schema change complexity;
- migration safety;
- data volume;
- backfill;
- query plan;
- lock risk;
- rollback/roll-forward;
- on-prem upgrade.

### 8.5 Refactoring

Estimate drivers:

- characterization tests;
- behavior preservation;
- number of callers;
- release slicing;
- backward compatibility;
- cleanup criteria.

Refactoring without test coverage has high uncertainty.

### 8.6 Production bug

Estimate drivers:

- reproducibility;
- blast radius;
- known root cause vs symptom;
- data repair need;
- customer communication;
- regression tests;
- release path.

A bug estimate should separate:

- diagnosis time;
- fix time;
- verification time;
- production correction time.

## 9. The senior engineer's estimation questions

Ask these in refinement or planning.

### 9.1 Clarity

- What behavior are we changing?
- What is explicitly out of scope?
- Which examples prove the rule?
- Which edge cases are known?
- Which assumptions are unverified?

### 9.2 Scope

- Which services are touched?
- Which tables are touched?
- Which APIs/events are touched?
- Which tests must change?
- Which docs/runbooks must change?

### 9.3 Risk

- What is the worst plausible failure?
- Could this create duplicate orders?
- Could this change accepted price evidence?
- Could this leak tenant data?
- Could this break old clients?
- Could this lock production DB?

### 9.4 Dependency

- Do we need another team?
- Do we need environment access?
- Do we need sample data?
- Do we need security/architecture review?
- Do we need customer-specific configuration?

### 9.5 Evidence

- What test proves this is done?
- What production signal proves it works?
- What demo/evidence will Sprint Review show?
- What validation is needed after deployment?

## 10. When to split instead of estimate

If estimate debate is long, the item may be too large or unclear.

Split when:

- the team cannot agree on what is included;
- estimate range is huge;
- key dependency is unknown;
- story mixes discovery and delivery;
- story touches too many services;
- migration and behavior activation are combined;
- testing strategy is unclear;
- rollout risk is high.

### 10.1 Split patterns

| Problem | Split |
|---|---|
| Unknown downstream API | spike first, integration story later |
| Large migration | expand schema, backfill, activate behavior, contract cleanup |
| Big feature | vertical slice by journey/state/actor |
| Many edge cases | happy path + high-risk negative cases first |
| Refactor | characterization tests, seam, migrate one path, cleanup |
| Kafka change | schema add, producer change, consumer change, replay validation |

Splitting is often better than arguing whether something is 8 or 13.

## 11. Estimation and spikes

A spike should reduce uncertainty, not produce hidden delivery.

Good spike estimate:

```text
Spike: Verify whether order cancellation callback can be made idempotent with current downstream correlation ID.
Timebox: 2 days.
Output:
- sequence diagram;
- downstream behavior evidence;
- recommendation;
- delivery story split;
- revised estimate confidence.
```

Bad spike:

```text
Investigate order cancellation.
```

A spike is successful if it changes what the team knows.

## 12. Story points as conversation tool

If your team uses story points, treat them as relative sizing for planning.

Healthy uses:

- comparing with reference work;
- exposing disagreement;
- checking Sprint Backlog feasibility;
- forecasting at team level;
- noticing oversized work.

Unhealthy uses:

- measuring individual productivity;
- comparing teams;
- turning points into deadlines;
- forcing exact precision;
- rewarding inflated estimates;
- punishing honest uncertainty.

### 12.1 Planning poker disagreement

If one engineer says 3 and another says 13, do not average.

Ask why.

Possible discoveries:

- one knows about migration risk;
- one assumes downstream API exists;
- one assumes tests are already present;
- one knows a similar change broke production;
- one includes observability/DoD and the other does not.

The disagreement is valuable.

---

## 13. No-estimates and flow-based planning

Some teams reduce reliance on story points and use flow metrics.

Useful signals:

- throughput;
- cycle time;
- lead time;
- blocked time;
- WIP;
- item age;
- review latency;
- defect escape rate.

Flow-based planning can work well when items are sliced small and similarly sized.

It works poorly if backlog items vary wildly in size or hide large uncertainty.

A pragmatic senior engineer does not fight religious wars over estimation method.

They ask:

> Does our method help us make better planning decisions and expose risk early?

---

## 14. Forecasting vs Sprint commitment

Forecasting asks:

> When might this larger outcome be done?

Sprint commitment asks:

> What can we reasonably pursue this Sprint?

Do not confuse them.

A release forecast may use:

- historical throughput;
- known dependencies;
- risk buffers;
- milestone constraints;
- scope range;
- confidence intervals.

A Sprint plan should use:

- current capacity;
- Sprint Goal;
- item readiness;
- selected scope;
- Definition of Done;
- current production load.

## 15. Estimating production bug work

Production bugs are often underestimated because the visible fix seems small.

Use this breakdown:

```text
Total bug work = diagnosis + reproduction + fix + regression test + data correction + release + verification + prevention
```

Example:

Bug: duplicate order created after quote acceptance retry.

Work components:

- reproduce duplicate path;
- identify idempotency gap;
- inspect existing duplicate orders;
- add unique/idempotency guard;
- add concurrency/integration test;
- data repair for affected orders;
- release/rollback plan;
- monitoring for recurrence;
- postmortem action.

The code fix may be one line.

The safe correction is not.

## 16. Estimation confidence template

Use this in backlog comments.

```md
## Estimate
Relative size: S / M / L / XL
Confidence: High / Medium / Low

## Why
- Known similar work:
- Unknowns:
- Dependencies:
- Risk:

## Included in estimate
- Implementation:
- Tests:
- Migration:
- Contract update:
- Observability/runbook:
- Review/security/architecture:

## Not included
- Explicit exclusions:

## Next action to improve confidence
- Spike/refinement/design/test fixture/etc.
```

This is more useful than a number alone.

## 17. Examples

### 17.1 Example: optional quote API field

Request:

> Add `approvalRequiredReason` to quote response.

Naive estimate:

> Small. One field.

Senior estimate:

```text
Size: Small/Medium
Confidence: Medium
Risk: API compatibility and source-of-truth ambiguity.
Included: DTO mapping, OpenAPI update, unit/integration test, old client compatibility check, null behavior, authorization check if reason contains sensitive approval policy.
Unknown: whether reason is persisted or derived.
Next action: verify approval reason source and sensitivity.
```

### 17.2 Example: order cancellation before fulfillment

Naive estimate:

> Medium. Add cancel endpoint.

Senior estimate:

```text
Size: Large
Confidence: Medium/Low
Risk: lifecycle, fulfillment adapter, idempotency, audit, downstream cancellation semantics.
Split:
1. Clarify cancellation state model.
2. Implement cancellation for pre-submission order.
3. Add downstream cancellation path.
4. Add fallout/retry behavior.
5. Add support/runbook visibility.
```

### 17.3 Example: add index to speed quote search

Naive estimate:

> Small. SQL index.

Senior estimate:

```text
Size: Small implementation, Medium operational risk
Confidence: Medium
Risk: hot table, lock behavior, index build time, query plan uncertainty.
Included: EXPLAIN before/after, migration test, concurrent index strategy if needed, deployment note.
Unknown: production row count and current query distribution.
```

## 18. Estimation anti-patterns

### 18.1 Precision theater

Pretending estimates are exact.

Correction:

- use ranges/confidence;
- revisit after discovery;
- split large unknowns.

### 18.2 Velocity as productivity score

Using velocity to pressure teams or individuals.

Correction:

- use velocity/throughput for planning, not performance judgement;
- inspect quality and outcomes.

### 18.3 Estimates without DoD

Estimating implementation only, excluding testing, docs, migration, observability.

Correction:

- explicitly include DoD work;
- make hidden work visible.

### 18.4 Hero estimates

One engineer says they can do a risky item quickly because they know the area.

Correction:

- ask about review, tests, supportability, documentation, bus factor.

### 18.5 Re-estimating as blame

After work grows, asking why the estimate was wrong instead of what new information emerged.

Correction:

- treat estimate error as learning;
- improve refinement and reference stories.

## 19. Internal verification checklist

Verify these inside your team:

- Does the team estimate?
- Which method: story points, t-shirt, ideal days, no-estimates, throughput?
- Are estimates used for planning only or performance reporting?
- What reference stories exist?
- Does the team track confidence/uncertainty?
- Are spikes estimated differently?
- How is production support work estimated?
- How is carryover handled?
- How are bugs estimated?
- Are DB migration/testing/observability included in estimates?
- Does the team inspect estimation error in retrospectives?
- Are velocity/throughput metrics used responsibly?

## 20. Practical exercise

Pick five upcoming Product Backlog Items.

For each, write:

1. Relative size.
2. Confidence level.
3. Domain uncertainty.
4. Technical uncertainty.
5. Integration/data/security/operational risk.
6. What is included in the estimate.
7. What is excluded.
8. Next action to improve confidence.

Then ask:

- Which item should be split?
- Which item needs a spike?
- Which item has small implementation but high production risk?
- Which item should not enter Sprint Planning yet?

This exercise turns estimation into risk discovery.

---

## 21. Key takeaways

- Estimation is uncertainty communication, not prediction.
- Size, uncertainty, and risk should be discussed separately.
- Story points are useful only when they create shared understanding and better planning.
- Senior engineers must expose hidden work: tests, migration, observability, security, release, support, and data repair.
- Low-confidence estimates should trigger refinement, spike, or splitting.
- Estimation method matters less than whether the team learns and plans honestly.
