# Part 020 — Technical Debt in Sprint Planning

## 1. Source notes and scope boundary

This part uses public technical debt and Scrum references, especially:

- Martin Fowler's explanation of technical debt as a metaphor for internal quality deficiencies that make future changes harder, with the extra effort acting like interest.
- Martin Fowler's Technical Debt Quadrant: reckless/prudent and deliberate/inadvertent categories.
- The Scrum Guide: Product Backlog is emergent and ordered; the Increment must meet the Definition of Done.
- Previous parts in this series on Product Backlog as risk map, Sprint Planning, flow/WIP, Definition of Done, and architecture work.

This part does **not** assume CSG uses a specific technical debt label, debt register, architecture runway framework, engineering allocation model, or refactoring budget.

Use the internal verification checklist to adapt the practice to your team.

---

## 2. Core thesis

Technical debt is not a moral failure.

Technical debt is not simply "bad code".

Technical debt is a future cost created by current system structure, knowledge gaps, shortcuts, or changed context.

In a Scrum team, technical debt becomes dangerous when it is invisible during Sprint Planning.

If technical debt is invisible, the team repeatedly commits to feature work using a false model of capacity and risk.

Eventually the team pays through:

- slower delivery,
- bigger estimates,
- more defects,
- harder testing,
- unsafe releases,
- production incidents,
- painful onboarding,
- fragile integrations,
- risky migrations,
- repeated support escalations.

For enterprise Quote & Order systems, debt is not theoretical. It can affect pricing correctness, quote acceptance, order lifecycle, tenant isolation, Kafka replay, PostgreSQL migrations, audit evidence, and customer upgrades.

Sprint Planning must therefore treat technical debt as product risk, not developer preference.

## 3. What counts as technical debt?

Technical debt is any internal weakness that increases the cost or risk of future change.

### 3.1 Code debt

Examples:

- duplicated quote validation logic,
- direct status mutation in multiple services,
- unclear mapper methods,
- giant service classes,
- implicit state machine,
- poor naming around domain concepts,
- exception handling that hides failure cause.

### 3.2 Test debt

Examples:

- no unit tests for pricing edge cases,
- no integration tests for MyBatis queries,
- no contract tests for public API changes,
- flaky E2E suite,
- missing migration tests,
- no duplicate event tests.

### 3.3 Architecture debt

Examples:

- dual writes without outbox,
- inconsistent event envelopes,
- no clear source of truth,
- customer-specific branching without policy,
- no API versioning strategy,
- no tenant isolation pattern.

### 3.4 Data debt

Examples:

- historical quotes missing catalog version snapshot,
- nullable fields that should have been backfilled,
- inconsistent order parent/item states,
- old enum values with unclear meaning,
- unvalidated constraints,
- manual repair history not recorded.

### 3.5 Operational debt

Examples:

- no dashboard for quote-to-order conversion failure,
- noisy alerts,
- no runbook for stuck orders,
- no migration runtime visibility,
- unclear rollback path,
- data repair scripts not standardized.

### 3.6 Security/compliance debt

Examples:

- tenant predicate duplicated manually in SQL,
- missing negative authorization tests,
- audit events missing actor/reason,
- sensitive fields in logs,
- service tokens with too much authority.

Debt is broader than refactoring.

## 4. Debt taxonomy for Sprint Planning

Classify debt before negotiating it.

### 4.1 By intent

| Type | Meaning | Example |
|---|---|---|
| Deliberate prudent debt | Team knowingly accepts short-term compromise for good reason | Defer cleanup path until migration validation completes |
| Deliberate reckless debt | Team knowingly cuts safety without sufficient reason | Skip tenant isolation test to hit date |
| Inadvertent prudent debt | Team learns a better design later | Pricing model looked sufficient until customer agreement variants emerged |
| Inadvertent reckless debt | Team did not know or ignored basics | No transaction boundary around order creation and event publish |

The goal is not to avoid all debt.

The goal is to avoid unmanaged debt.

### 4.2 By interest rate

Debt has interest.

High-interest debt hurts every Sprint.

Low-interest debt may be acceptable for a while.

| Interest | Signal |
|---|---|
| High | Every change in area is slow/risky |
| Medium | Regular bugs or review confusion |
| Low | Annoying but rarely affects delivery |
| Dormant | No current effect but may become risky with roadmap change |

### 4.3 By risk class

| Risk class | Example |
|---|---|
| Correctness risk | duplicate pricing logic creates wrong quote total |
| Delivery risk | unclear service boundary slows every feature |
| Production risk | no alert for stuck order fallout |
| Security risk | tenant predicate missing in export path |
| Compliance risk | approval audit evidence incomplete |
| Integration risk | event schema undocumented |
| Upgrade risk | DB migration path not tested for on-prem |

Sprint Planning should prioritize debt by impact, not annoyance.

## 5. Why technical debt gets ignored in Scrum

### 5.1 It is not expressed as Product Backlog value

Bad debt item:

```text
Clean up quote service
```

This competes poorly against customer-visible features.

Better:

```text
Centralize quote acceptance guard so accepted quotes cannot be converted after price expiry through alternate code path.
```

Now the value is visible.

### 5.2 It has no owner

If everyone complains about debt but no one owns the next step, the debt remains background noise.

### 5.3 It is too large

"Refactor order service" is not plannable.

Split it.

### 5.4 It is not linked to incidents

A debt item with production evidence is easier to prioritize.

Example:

> Three incidents in two months involved orders stuck without a clear state transition history. Add lifecycle history and transition guard.

### 5.5 It is framed as developer preference

Avoid:

> I want cleaner code.

Prefer:

> This duplication means the approval invalidation rule must be updated in three places. We already missed one path. The repayment reduces correctness risk and future change cost.

## 6. Turning debt into backlog items

A technical debt PBI should include:

- problem,
- affected capability,
- current evidence,
- risk/interest,
- proposed repayment,
- scope boundary,
- acceptance criteria,
- testing strategy,
- rollout/rollback if relevant.

### 6.1 Template

```md
# Technical Debt PBI: <title>

## Problem
What internal weakness exists?

## Evidence
What proves this is real?
- incidents:
- slow PRs:
- bugs:
- code search:
- metrics:
- customer/support signal:

## Impact
How does this affect product delivery, correctness, production, security, or support?

## Proposed repayment
What is the smallest safe improvement?

## Non-goals
What are we not fixing now?

## Acceptance criteria
- ...

## Testing/verification
- ...

## Follow-up
What future cleanup may remain?
```

### 6.2 Example: weak vs strong

Weak:

```text
Refactor Kafka events
```

Strong:

```text
Standardize ProductOrder event envelope for three order lifecycle events.

Evidence:
- `ProductOrderCreated` has correlation ID but `ProductOrderCancelled` does not.
- Support cannot trace cancellation event to original command.
- Replay tooling requires aggregate ID and event ID consistently.

Acceptance criteria:
- event envelope includes eventId, tenantId, aggregateId, eventType, eventVersion, occurredAt, correlationId, causationId;
- old consumers tolerate additive metadata;
- schema compatibility test passes;
- producer integration test asserts metadata;
- dashboard/log query can trace event by correlation ID.
```

## 7. Debt refinement

Technical debt needs refinement like feature work.

During refinement, ask:

- What is the actual weakness?
- What evidence do we have?
- What happens if we do nothing?
- Is this blocking near-term Product Goal?
- Is this high-interest debt?
- Can it be repaid incrementally?
- Does repayment require architecture decision?
- Does repayment require migration?
- Does repayment change public behavior?
- Can we verify improvement?

Do not allow debt PBIs to remain vague.

If the team cannot define verification, the item may need a spike first.

---

## 8. Debt prioritization in Sprint Planning

Technical debt competes with feature work.

Make the trade-off explicit.

### 8.1 Prioritization signals

Prioritize debt when it:

- blocks current Sprint Goal,
- blocks near-term Product Goal,
- causes repeated bugs,
- slows many PBIs,
- creates production incidents,
- affects security/tenant isolation,
- makes release unsafe,
- prevents migration/refactoring,
- increases support load,
- makes on-prem upgrade risky.

Defer debt when:

- impact is local and low,
- no near-term feature touches the area,
- repayment is speculative,
- team lacks enough understanding,
- there is a safer smaller step first.

### 8.2 Debt capacity models

Different teams use different models.

| Model | Useful when | Risk |
|---|---|---|
| Fixed percentage | steady debt load | can become entitlement or too rigid |
| Risk-triggered | debt linked to product work | invisible slow degradation may continue |
| Incident-derived | production learning drives debt | proactive debt may be missed |
| Boy Scout rule | small cleanup during normal work | larger systemic debt remains |
| Dedicated debt sprint | accumulated debt is severe | can become hardening mini-waterfall |

There is no universal best model.

The important thing is transparency and follow-through.

## 9. Debt and Sprint Goal

Debt work should support the Sprint Goal when possible.

Weak Sprint Goal:

> Complete tickets 123, 124, 125.

Better Sprint Goal:

> Make quote acceptance safer for enterprise discount exceptions.

Under this goal, debt work may be valid:

- centralize quote acceptance guard,
- add missing approval invalidation test,
- add audit assertion,
- clean up duplicate acceptance code path.

Debt becomes part of achieving the goal, not a separate favor to engineers.

## 10. Quote & Order debt examples

### 10.1 Quote lifecycle debt

Debt:

- quote state transitions are scattered.

Impact:

- illegal transitions can bypass audit/outbox.

Repayment:

- introduce transition service for one command,
- add transition matrix tests,
- migrate paths incrementally.

### 10.2 Pricing debt

Debt:

- pricing total calculated in multiple places.

Impact:

- quote total, approval threshold, and display can diverge.

Repayment:

- centralize calculation or snapshot verification,
- add golden price tests,
- compare old/new calculation in shadow mode.

### 10.3 Order management debt

Debt:

- parent order state not derived consistently from item states.

Impact:

- order can show completed while item remains failed.

Repayment:

- define aggregation invariant,
- add tests,
- implement single aggregation function,
- repair historical inconsistencies if needed.

### 10.4 Kafka debt

Debt:

- event metadata inconsistent across producers.

Impact:

- tracing, replay, support, and idempotency become harder.

Repayment:

- standardize envelope for one topic family,
- add producer tests,
- add consumer compatibility tests.

### 10.5 PostgreSQL debt

Debt:

- query uses dynamic filters without adequate index.

Impact:

- quote search latency grows with data volume.

Repayment:

- capture EXPLAIN plan,
- add targeted index or query rewrite,
- add performance guard for common query.

### 10.6 Security debt

Debt:

- tenant predicate repeated manually.

Impact:

- new mapper query can leak cross-tenant data.

Repayment:

- add tenant-scoped repository helpers,
- add cross-tenant integration tests,
- review cache/search/export paths.

### 10.7 Operational debt

Debt:

- no dashboard for outbox backlog by service/topic.

Impact:

- event publication failure discovered late.

Repayment:

- add metric,
- dashboard panel,
- alert/runbook,
- test relay failure path.

## 11. Debt repayment slicing patterns

### 11.1 Characterization first

Before refactoring legacy code, add tests that describe current behavior.

### 11.2 One path at a time

Do not refactor every command.

Start with one high-risk path.

### 11.3 Parallel safe abstraction

Introduce new abstraction and migrate gradually.

Example:

- create `OrderTransitionService`,
- route cancellation through it,
- route fulfillment completion later,
- block direct updates after migration.

### 11.4 Expand-contract cleanup

For data/schema debt:

1. add new safe structure,
2. write both if needed,
3. backfill,
4. switch reads,
5. validate,
6. remove old structure later.

### 11.5 Observability first

For risky areas, add measurement before changing behavior.

Example:

- measure order stuck-state count before changing fallout logic.

### 11.6 Guardrail first

Add CI/test guardrail to stop new debt while gradually paying old debt.

Example:

- forbid new direct mapper status update through code review/static rule.

---

## 12. Measuring debt repayment

Debt repayment should have observable improvement.

Potential signals:

- fewer defects in area,
- shorter cycle time for related stories,
- smaller PRs,
- fewer review comments about same issue,
- faster onboarding to area,
- improved test reliability,
- reduced incident recurrence,
- reduced alert noise,
- safer migrations,
- improved query latency,
- clearer runbook usage.

Avoid measuring debt only by "lines refactored".

The goal is reduced future cost and risk.

---

## 13. Debt in Retrospective

Retrospective is a good place to identify systemic debt.

Ask:

- What slowed us this Sprint?
- Which area required repeated clarification?
- Which tests failed repeatedly?
- Which PRs were hard to review?
- Which production issue interrupted Sprint Goal?
- Which bug reveals missing guardrail?
- Which manual work should become automation?
- Which dependency caused delay?

Convert one or two findings into actionable PBIs.

Do not let retro debt become a complaint archive.

---

## 14. Debt anti-patterns

### 14.1 Debt as vague complaint

"The code is messy" is not actionable.

Name the weakness and impact.

### 14.2 Debt as secret developer backlog

If debt consumes capacity, it must be visible.

### 14.3 Debt as feature hostage

Do not say every feature requires total cleanup first.

Find the smallest safe repayment.

### 14.4 Debt as endless refactor

Refactoring must have a stopping condition.

### 14.5 Debt only after incident

Incident-derived debt is important, but proactive debt management prevents incidents.

### 14.6 Debt never deleted

Old compatibility code, feature flags, and migration paths must eventually be removed.

### 14.7 Debt without Product Owner conversation

The PO does not need to understand every implementation detail, but they do need to understand product risk, delivery impact, and trade-off.

---

## 15. Communicating technical debt to Product Owner

Translate engineering debt into product language.

| Engineering statement | Product-relevant framing |
|---|---|
| Mapper query is hard to maintain | New search filters are slower and riskier to deliver |
| No integration test | We may break customer workflow without noticing before release |
| Event schema inconsistent | Downstream teams/support cannot reliably trace order lifecycle |
| Missing migration test | Customer upgrade may fail or require manual support |
| Duplicate pricing logic | Quote total and approval threshold can diverge |
| No runbook | Incident recovery depends on developer memory |

A good senior engineer helps the PO make informed trade-offs.

Pick one service or capability.

Create a debt inventory with columns:

- debt item,
- type,
- evidence,
- affected Product Goal,
- interest rate,
- risk class,
- smallest repayment,
- owner,
- candidate Sprint.

Example:

| Debt | Type | Evidence | Interest | Repayment |
|---|---|---|---|---|
| Quote acceptance guard duplicated | correctness | bug QO-123 | high | centralize one path + tests |
| Outbox backlog not visible | operational | incident INC-45 | high | metric + dashboard + runbook |
| Old migration path not cleaned | data | code search | medium | validate no old versions + remove |

Bring the top three to refinement.

## 19. Practical exercise: debt-to-PBI rewrite

Rewrite this weak debt item:

```text
Clean up order service.
```

A strong rewrite:

```text
Centralize order cancellation transition through OrderLifecycleService.

Problem:
Three paths currently update cancellation-related status directly. One path does not write state history or outbox event.

Impact:
Support cannot reconstruct cancellation timeline and downstream consumers may miss cancellation.

Acceptance criteria:
- cancellation command uses OrderLifecycleService;
- illegal cancellation states are rejected;
- state history is written in same transaction;
- cancellation event outbox row is created;
- duplicate cancellation command is idempotent;
- direct mapper update path is marked deprecated for follow-up cleanup.
```

This is now plannable.

## 20. Summary

Technical debt must be managed inside Scrum because Scrum is where product trade-offs are inspected and adapted.

For senior engineers, the key responsibilities are:

- make debt visible,
- classify debt by impact and interest,
- connect debt to Product/Sprint Goals,
- slice repayment safely,
- write acceptance criteria,
- verify improvement,
- prevent new debt through Definition of Done,
- use retrospectives and incidents as learning inputs.

The goal is not a debt-free codebase.

The goal is a codebase whose debt is understood, bounded, and intentionally repaid before it blocks product learning or damages production.
