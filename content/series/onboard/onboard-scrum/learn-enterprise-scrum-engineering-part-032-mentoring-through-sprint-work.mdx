# Part 032 — Mentoring Through Sprint Work

## 1. Source notes and scope boundary

This part uses public references and general engineering practice, especially:

- Google Engineering Practices on code review quality and code health.
- Google re:Work material on team effectiveness and psychological safety.
- The Scrum Guide and Scrum.org material on Scrum values, self-management, Developers, and Sprint events.
- Prior parts of this series on PR review, Daily Scrum, stakeholder collaboration, retrospectives, and force multiplication.

This part does **not** assume CSG has a formal mentoring program, pairing policy, career ladder, coaching framework, or dedicated mentorship time allocation.

Use the `Internal verification checklist` sections to adapt the guidance to your actual team norms.

---

## 2. Core thesis

The best mentoring for engineers often happens inside real work, not outside it.

A senior engineer in Scrum has daily opportunities to mentor through:

- backlog refinement;
- story slicing;
- Sprint Planning;
- Daily Scrum;
- pairing;
- code review;
- test design;
- debugging;
- incident response;
- Sprint Review;
- Retrospective;
- design discussions;
- production readiness checks.

Mentoring through sprint work is powerful because it teaches judgment in context.

The goal is not to make another engineer copy your style.

The goal is to help them understand:

- what matters;
- why it matters;
- how to reason about trade-offs;
- how to detect risk early;
- how to make safe changes;
- how to learn from production;
- how to become independently reliable.

Mentoring is not interruption if it improves the team's future execution.

But mentoring becomes waste if it is vague, performative, condescending, or disconnected from actual delivery.

## 3. Mentoring is judgment transfer

A junior/mid engineer may ask:

> What code should I write?

A senior mentor gradually teaches them to ask:

> What invariant am I protecting, what failure mode am I preventing, and what evidence will prove the change is safe?

This is the core of mentoring in enterprise systems.

### 3.1 From instruction to reasoning

| Situation | Low-leverage response | High-leverage mentoring response |
|---|---|---|
| Engineer asks how to implement order status change | "Update this field here." | "Let's identify the legal transition, audit requirement, outbox event, and idempotency expectation first." |
| Engineer writes mapper query without tenant filter | "Add tenant ID." | "This query is a cross-tenant access risk. Let's build a habit: every source-of-truth query should state tenant scope unless explicitly shared data." |
| Engineer adds event field | "Looks fine." | "Who consumes this event, are old consumers tolerant, and is this semantic or structural compatibility?" |
| Engineer wants large refactor | "Too big." | "Let's create characterization tests and split by behavior seam so we can merge safely." |
| Engineer misses audit | "You forgot audit." | "Any privileged commercial action needs defensible evidence. Let's define the audit invariant." |

Mentoring should leave behind a reusable mental model.

## 4. Mentoring modes

Different situations need different mentoring modes.

| Mode | Best for | Risk |
|---|---|---|
| Direct teaching | New concept or urgent gap | Can become lecture |
| Pair programming | Complex code path or debugging | Can become passive watching |
| Socratic questioning | Building reasoning | Can frustrate if overused |
| Review coaching | PR-specific improvement | Can feel critical if tone is poor |
| Design walkthrough | Architecture and trade-offs | Can become abstract |
| Incident debrief | Real failure learning | Needs psychological safety |
| Template/checklist | Repeated patterns | Can become bureaucracy |
| Shadowing | Observing production/review behavior | Needs follow-up reflection |

A good mentor chooses the mode intentionally.

Example:

> I will be direct here because this is a release blocker. After we fix it, let's do a short debrief so the pattern is clear for next time.

## 5. Mentoring through refinement

Refinement is one of the best mentoring moments because it happens before code is written.

### 5.1 What to teach in refinement

Teach engineers to identify:

- unclear business behavior;
- missing actor/role;
- missing state precondition;
- hidden downstream dependency;
- missing test strategy;
- missing production readiness work;
- migration and rollout risk;
- insufficient acceptance criteria;
- need for spike/discovery.

### 5.2 Refinement mentoring questions

For each story, ask newer engineers:

- What is the smallest user-visible or system-visible behavior here?
- Which domain object changes state?
- What must remain true before and after the change?
- Which existing tests would fail if this breaks?
- Which new test should we add?
- What dependency could block us?
- What is unknown enough to spike?
- How would support know this works in production?

### 5.3 Example: mentoring during quote approval story

Story:

> As a sales user, I want to request approval for a quote with high discount.

Mentoring path:

1. Identify actor: sales user.
2. Identify object: quote.
3. Identify precondition: quote priced, not expired, not accepted.
4. Identify business rule: discount above threshold.
5. Identify authority: approver with sufficient limit.
6. Identify state transition: draft/priced → pending approval.
7. Identify audit evidence: who requested, why, threshold, price snapshot.
8. Identify negative cases: expired quote, missing price, unauthorized user.
9. Identify event/API impact.
10. Identify tests and observability.

This teaches domain reasoning, not just ticket interpretation.

## 6. Mentoring through Sprint Planning

Sprint Planning is a chance to teach delivery judgment.

### 6.1 What to teach

- capacity is not just hours;
- unknowns need spikes or buffer;
- review and test time count;
- incidents and support work consume capacity;
- Sprint Goal matters more than ticket count;
- dependencies must be visible;
- cut lines should be explicit;
- high-risk work needs sequencing.

### 6.2 Sprint Planning mentoring prompts

Ask:

- Which item is riskiest?
- Which item must start first because of dependency?
- Which item can be cut without breaking Sprint Goal?
- Which item requires architecture review?
- Which item requires QA/security/platform involvement?
- Which item needs production readiness work?
- Which item has unclear estimate because of unknowns?

### 6.3 Teaching estimation honesty

When someone gives an estimate, ask:

- What are you assuming?
- What could make this double?
- What evidence would reduce uncertainty?
- Is this implementation time only, or includes test/review/readiness?
- Should this be split or spiked?

Do not punish honest uncertainty.

If engineers learn that uncertainty is punished, they will hide it.

## 7. Mentoring through Daily Scrum

Daily Scrum can teach self-management.

### 7.1 Mentor behaviors

Good mentoring:

- ask who owns unblocking;
- surface stuck PRs;
- ask whether Sprint Goal is still safe;
- help split oversized work;
- redirect detailed debugging outside the Daily;
- encourage early help-seeking.

Bad mentoring:

- turn Daily into a status interrogation;
- solve every issue in the meeting;
- shame slow progress;
- dominate discussion;
- bypass the Scrum Master;
- create dependency on senior decisions.

### 7.2 Daily mentoring examples

If a teammate says:

> I am still working on the order decomposition story.

A useful senior prompt:

> What is the next observable milestone? Is the blocker domain rule, test data, or downstream simulator?

If a teammate says:

> My PR is waiting for review.

A useful senior prompt:

> Who is the right reviewer for the risk surface? Is this blocked on domain review, DB review, or just reviewer availability?

If a teammate says:

> I found the migration is harder than expected.

A useful senior prompt:

> Do we need to split expand/backfill/contract and adjust the Sprint Backlog before it endangers the Sprint Goal?

## 8. Mentoring through pairing

Pairing is useful when context is dense.

### 8.1 Good pairing targets

Pair on:

- first change in unfamiliar service;
- tricky MyBatis mapper and transaction boundary;
- Kafka consumer replay/idempotency logic;
- quote/order state transition;
- migration/backfill design;
- production debugging;
- test fixture creation;
- design doc first draft.

### 8.2 Pairing modes

| Mode | Description | Use when |
|---|---|---|
| Driver/navigator | One types, one guides | Implementation with learning |
| Ping-pong TDD | Alternate writing tests and code | Test design skill building |
| Debugging pair | Both inspect evidence | Production/complex defect |
| Design pair | Build diagram/ADR together | Ambiguous architecture |
| Review pair | Walk through PR together | Review judgment transfer |

### 8.3 Pairing anti-patterns

Avoid:

- senior takes keyboard and does everything;
- junior watches silently;
- pairing without goal;
- pairing too long without breaks;
- using pairing to micromanage;
- skipping reflection after pairing.

End a pairing session with:

- what we changed;
- what we learned;
- what risk remains;
- what the other engineer can now do alone;
- what artifact/test/doc should capture the learning.

## 9. Mentoring through PR review

PR review is the most common mentoring channel in engineering teams.

But it can either build confidence or create fear.

### 9.1 Review tone principles

Use comments that are:

- specific;
- risk-based;
- respectful;
- actionable;
- severity-labeled;
- educational when helpful;
- not overloaded with unrelated lessons.

Weak comment:

> Bad naming.

Better:

> `isValid` hides the domain condition. Could we name this `isQuoteAcceptableAfterApproval` so the lifecycle rule is visible? This will help future readers avoid treating it as generic validation.

Weak comment:

> This is wrong.

Better:

> Blocking: this updates order state without writing transition history or outbox event. That can make support unable to reconstruct fulfillment fallout. Can we route this through the lifecycle transition service?

### 9.2 Teaching through review without overwhelming

Not every lesson belongs in a blocking comment.

Use severity:

- `blocking` for correctness/security/production risk;
- `suggestion` for important maintainability improvement;
- `nit` for small style issue;
- `note` for optional learning;
- `future` for follow-up not needed in this PR.

This helps mentees distinguish must-fix from learning context.

### 9.3 PR review mentoring checklist

When reviewing as mentor, ask:

- What is the most important risk in this PR?
- Did I explain why it matters?
- Did I offer a path forward?
- Did I avoid preference-only comments?
- Did I praise something specific that was good?
- Did I leave optional learning as optional?
- Did I avoid expanding scope unnecessarily?
- Did this review help the author become more independent?

## 10. Mentoring through tests

Tests are executable mentoring.

A good test shows future engineers how the system is supposed to behave.

### 10.1 Teach test intent

Do not teach only syntax.

Teach:

- what risk the test protects;
- why this fixture exists;
- what invariant should never break;
- why a negative test matters;
- what belongs at unit vs integration vs contract level;
- why E2E should be rare and high-value.

### 10.2 Example: teaching quote acceptance test

Instead of only writing:

```java
@Test
void acceptQuote() {
  // ...
}
```

Teach the invariant:

```java
@Test
void cannotAcceptApprovedQuoteAfterPriceExpiry() {
  // Protects commercial invariant:
  // approval is valid only for the approved price snapshot and validity window.
}
```

The name itself mentors the next reader.

### 10.3 Test review prompts for mentees

Ask:

- What bug would this test catch?
- Could the implementation be broken while this test still passes?
- Is this testing business behavior or implementation detail?
- Is there a negative test?
- Is this test deterministic?
- Does it use realistic tenant/user/state fixture?
- Should this be lower-level than E2E?

## 11. Mentoring through incidents

Incidents are painful but powerful learning moments.

### 11.1 During incident

Mentoring during incident must not slow mitigation.

Use concise narration:

- "We are checking outbox lag because the order state changed but downstream did not receive event."
- "We are pausing the consumer before repair because duplicate processing could worsen impact."
- "We are collecting affected order IDs before deciding repair scope."

This helps observers build diagnostic models.

### 11.2 After incident

Do a learning debrief:

- What was the first signal?
- What was the actual invariant failure?
- What detection was missing?
- What test was missing?
- What runbook was missing?
- What was hard to understand?
- What should we automate or document?

### 11.3 Avoid blame mentoring

Never teach through humiliation.

Bad:

> You should have known this.

Good:

> This failure mode is easy to miss because the DB write and Kafka publish are separate concerns. Let's document the dual-write risk and add an outbox test.

Psychological safety matters because engineers must surface mistakes and uncertainty early for Scrum to work well.

## 12. Mentoring through design discussion

Design discussions are high-leverage mentoring opportunities.

### 12.1 Teach a design frame

Use this structure:

1. problem;
2. context;
3. domain invariant;
4. constraints;
5. options;
6. trade-offs;
7. failure modes;
8. rollout;
9. observability;
10. decision.

### 12.2 Example: mentoring event design

Question:

> Should we publish `OrderCompleted` immediately after all items complete?

Mentoring frame:

- What does `completed` mean?
- Are all required downstream handoffs complete?
- Does billing depend on this event?
- Does product inventory need update first?
- What if a duplicate completion callback arrives?
- What is the aggregate version?
- What is the partition key?
- Is replay safe?
- Is this lifecycle event or projection event?

This teaches event semantics, not just Kafka mechanics.

## 13. Mentoring through Sprint Review

Sprint Review can teach engineers to demonstrate evidence.

### 13.1 Mentor engineers to demo beyond UI

For backend work, encourage showing:

- API request/response;
- event emitted;
- database migration proof;
- dashboard metric;
- audit record;
- runbook update;
- error behavior;
- feature flag behavior;
- production readiness evidence.

### 13.2 Demo coaching questions

Ask before Sprint Review:

- What business behavior changed?
- What stakeholder should care?
- What evidence proves the behavior?
- What is still not enabled or not production-ready?
- What feedback do we need?
- What risk remains?

This helps engineers communicate impact, not just implementation.

## 14. Mentoring through Retrospective

Retrospectives teach systemic thinking.

### 14.1 Help mentees move from complaint to system

Complaint:

> Reviews were slow.

Systemic analysis:

- Were PRs too large?
- Were reviewers unclear?
- Was domain ownership unclear?
- Did reviews start too late?
- Did Sprint Planning ignore review capacity?
- Was WIP too high?

Action:

- limit PR size;
- pre-identify domain reviewers;
- reserve review capacity;
- add design discussion before code for risky items.

### 14.2 Retrospective mentoring prompts

Ask:

- What surprised us?
- What should we have known earlier?
- What repeated from previous Sprint?
- What is the smallest process change?
- What evidence will show improvement?
- Who owns the action?
- When will we inspect it?

## 15. Mentoring different experience levels

### 15.1 New engineer

Needs:

- domain vocabulary;
- codebase map;
- safe first PR;
- test patterns;
- review expectations;
- who-to-ask map.

Mentor through:

- onboarding map;
- pairing;
- glossary;
- small PR;
- explicit feedback.

### 15.2 Mid-level engineer

Needs:

- ownership of feature slices;
- better trade-off reasoning;
- production awareness;
- review judgment;
- clearer communication.

Mentor through:

- design questions;
- PR review coaching;
- incident debrief;
- test strategy ownership.

### 15.3 Senior peer

Needs:

- alignment;
- shared standards;
- architecture debate;
- cross-team coordination;
- decision records.

Mentor through:

- peer review;
- ADR collaboration;
- architecture review;
- honest disagreement.

### 15.4 Specialist outside your area

Examples:

- QA;
- SRE/platform;
- security;
- product owner;
- support.

Mentor by explaining technical context while learning their constraints.

Do not treat cross-functional partners as less technical simply because their expertise is different.

## 16. Mentoring without micromanagement

Micromanagement tells people what to do at every step.

Mentoring improves their ability to choose steps.

### 16.1 Use the autonomy ladder

| Level | Mentor behavior |
|---|---|
| Observe | "Watch me debug this incident; I will narrate decisions." |
| Pair | "Let's implement this transition together." |
| Guided | "You draft the approach; I will review before code." |
| Independent with review | "You implement; I will review PR/design." |
| Independent ownership | "You own this area; pull me in for high-risk changes." |
| Mentor others | "You teach this pattern to the next engineer." |

Move people up the ladder intentionally.

### 16.2 Delegation with safety

When delegating:

- define expected outcome;
- name risk areas;
- agree check-in point;
- clarify decision boundary;
- point to examples;
- avoid taking back the work too quickly.

Example:

> You own adding the negative tests for quote approval invalidation. Please cover price change, quote item change, expired validity, and unauthorized approver. Let's review the test cases before implementation.

## 17. Psychological safety and high standards

Psychological safety does not mean low standards.

It means people can surface uncertainty, mistakes, and dissent without fear of humiliation.

High-performing Scrum teams need both:

- high safety;
- high standards.

### 17.1 Low safety, high standards

Symptoms:

- people hide uncertainty;
- estimates become political;
- incidents become blame games;
- juniors stop asking questions;
- PR reviews feel hostile.

### 17.2 High safety, low standards

Symptoms:

- weak work passes;
- defects normalize;
- retros become venting;
- Definition of Done erodes;
- production readiness is optional.

### 17.3 High safety, high standards

Symptoms:

- risks surface early;
- PR reviews are direct but respectful;
- defects become learning;
- team improves DoD;
- people ask for help sooner;
- senior engineers are trusted, not feared.

Mentoring should aim for high safety and high standards.

## 18. Mentoring artifacts

Create artifacts that reduce repeated explanation.

Useful artifacts:

- first PR guide;
- local setup troubleshooting guide;
- quote lifecycle diagram;
- order lifecycle diagram;
- Kafka event debugging guide;
- PostgreSQL migration checklist;
- MyBatis mapper test example;
- PR review checklist;
- incident diagnosis runbook;
- Sprint Review evidence template;
- refinement question bank;
- glossary of domain terms.

Artifacts should be short enough to use.

A giant document nobody reads is not mentoring.

## 20. Practical exercise: mentoring plan for one Sprint

Pick one engineer and one growth goal.

Example:

- Engineer: mid-level backend engineer.
- Growth goal: improve Kafka consumer idempotency reasoning.
- Sprint work: event consumer change for order state update.

Plan:

1. Refinement: ask them to identify duplicate/replay cases.
2. Planning: ensure test work is included.
3. Pairing: review existing consumer pattern.
4. PR review: focus comments on idempotency and event semantics.
5. Sprint Review: have them demo duplicate event behavior.
6. Retro: ask what pattern should become reusable.

This is mentoring embedded in work.

## 21. Practical exercise: convert one review into teaching

Take a recent PR comment you wrote.

Rewrite it using this structure:

1. severity;
2. observed issue;
3. risk;
4. principle;
5. suggested fix;
6. optional learning link or note.

Example:

> Blocking: this mapper query searches orders by ID without tenant scope. Risk: a direct ID access path could leak cross-tenant data if IDs collide or are guessable. Principle: all source-of-truth order queries must be scoped by trusted tenant context unless explicitly shared reference data. Suggested fix: change mapper signature to include tenant ID and add cross-tenant negative integration test.

This teaches the pattern behind the fix.

## 23. Mentoring anti-patterns

### 23.1 Answering everything immediately

This creates dependency.

Better:

- answer urgent blockers;
- then explain reasoning;
- point to artifact;
- ask them to solve the next similar case.

### 23.2 Teaching without context

Abstract lectures are less useful than concrete work.

Better:

- teach through the current PR/story/incident.

### 23.3 Overloading PRs with education

Too much commentary can overwhelm.

Better:

- separate blocking issues from optional notes;
- use follow-up discussion for broad topics.

### 23.4 Making people afraid to be wrong

Fear kills transparency.

Better:

- treat mistakes as system learning;
- keep standards high but comments respectful.

### 23.5 Keeping all hard work yourself

This prevents others from growing.

Better:

- delegate bounded hard work with safety rails.

### 23.6 Mentoring only juniors

Mid-level and senior peers also need mentoring and challenge.

Better:

- create peer learning through design review, incident debrief, and architecture debate.

## 24. What good looks like

After applying this part, you should be able to:

- mentor inside Scrum events without derailing them;
- use refinement to teach domain and risk thinking;
- use Sprint Planning to teach capacity and uncertainty judgment;
- use PR review to transfer principles, not preferences;
- use pairing to build independence;
- use incidents to teach diagnosis and prevention;
- use retrospectives to teach systemic improvement;
- maintain high standards with psychological safety;
- create artifacts that reduce repeated explanation;
- move engineers up the autonomy ladder.

The best mentoring outcome is not that someone needs you more.

The best mentoring outcome is that someone can safely own more without you.
