# Part 007 — Story Slicing for Quote & Order Systems

## 1. Source notes and scope boundary

This part uses public Scrum guidance and general agile engineering practice:

- The Scrum Guide defines the Product Backlog as an emergent, ordered list of what is needed to improve the product and states that the moment a Product Backlog item meets the Definition of Done, an Increment is born.
- Scrum.org discusses vertical slicing as a way to align Product Backlog Items with Sprint Goals and deliver usable value within a Sprint.
- Scrum.org Product Backlog refinement material emphasizes focused discussions that create shared understanding of Product Backlog Items.
- Agile Alliance material on user stories emphasizes expressing acceptance criteria in a form usable as automated acceptance tests.

This part does **not** assume CSG has a specific Jira workflow, story template, point system, Definition of Ready, Definition of Done, release cadence, or slicing convention.

Use the internal verification checklist to adapt this material to the actual CSG Quote & Order team.

---

## 2. Core thesis

Story slicing is not about making tickets smaller.

Story slicing is about making learning, value, risk, and integration feedback available earlier.

For enterprise Quote & Order systems, bad slicing creates hidden mini-waterfall:

1. sprint 1: database tables,
2. sprint 2: backend logic,
3. sprint 3: Kafka events,
4. sprint 4: UI/API,
5. sprint 5: integration tests,
6. sprint 6: observability,
7. sprint 7: production hardening.

This can look organized, but it delays the most important feedback:

- Does the quote journey actually work?
- Does pricing produce explainable output?
- Does approval evidence remain defensible?
- Does order conversion preserve commercial snapshot?
- Does the Kafka event contract work for consumers?
- Does the DB migration survive rolling deployment?
- Can support diagnose a failure?

A strong slice should be small enough to complete in a Sprint and meaningful enough to produce usable evidence.

The senior engineer's role is to help the team slice work so that each item reduces a real uncertainty without destroying architecture integrity.

## 3. Horizontal slicing vs vertical slicing

### 3.1 Horizontal slicing

Horizontal slicing splits by technical layer.

Example:

| Slice | Work |
|---|---|
| Slice 1 | Create PostgreSQL tables |
| Slice 2 | Implement Java domain service |
| Slice 3 | Expose REST endpoint |
| Slice 4 | Publish Kafka event |
| Slice 5 | Add UI |
| Slice 6 | Add tests |
| Slice 7 | Add dashboard |

The problem is that no early slice proves business value.

A database table alone is not a customer-usable increment.

A Java service without API/event/testing/observability may be technically real but not product-real.

### 3.2 Vertical slicing

Vertical slicing cuts through enough layers to deliver a narrow end-to-end behavior.

Example:

| Slice | Behavior |
|---|---|
| Slice 1 | Create simple draft quote for one offering type with audit and basic validation |
| Slice 2 | Add pricing snapshot for recurring charge only |
| Slice 3 | Add discount threshold requiring approval |
| Slice 4 | Add quote acceptance with idempotency |
| Slice 5 | Add quote-to-order conversion for one order item type |
| Slice 6 | Add failure/retry path for duplicate acceptance |

Each slice is small, but each teaches something about the integrated system.

### 3.3 The rule

A good vertical slice should include the minimum necessary amount of:

- domain behavior,
- API/command boundary,
- persistence,
- validation,
- tests,
- observability,
- compatibility consideration,
- operational readiness.

It does not need every final capability.

It needs enough to be real.

## 4. Why slicing is hard in Quote & Order

Quote & Order systems are harder to slice than simple CRUD products because each story may touch:

- product catalog,
- product offering versioning,
- customer/account context,
- eligibility rules,
- pricing rules,
- discounts,
- approval policy,
- quote state machine,
- quote versioning,
- order lifecycle,
- order item hierarchy,
- fulfillment integration,
- product inventory,
- billing handoff,
- Kafka events,
- PostgreSQL migrations,
- tenant isolation,
- audit evidence,
- support runbooks.

The temptation is to build a broad foundation first.

Sometimes foundation work is necessary.

But if foundation work runs for many Sprints without an observable slice, risk grows silently.

The senior engineer must ask:

> What is the smallest useful behavior that exercises the riskiest assumptions?

## 5. Slicing principles

## 5.1 Slice by business behavior, not implementation layer

Weak slice:

> Implement quote database schema.

Better slice:

> Sales user can create a draft quote for one simple product offering, and the quote is persisted with tenant, customer, catalog version, and audit record.

The second slice still includes database work, but the value is expressed as behavior.

## 5.2 Slice by risk

If the riskiest unknown is pricing, slice around pricing.

If the riskiest unknown is fulfillment callback, slice around callback.

If the riskiest unknown is migration safety, slice around migration and compatibility.

Do not always slice by the easiest happy path.

## 5.3 Slice by decision point

A good slice often exists to answer a decision.

Examples:

- Can we use the existing approval engine for enterprise discount exceptions?
- Can the new event payload remain backward compatible with old consumers?
- Can the new order decomposition model represent amendment orders?
- Can the migration run without blocking writes?

If the slice answers a decision, it is valuable even if small.

## 5.4 Slice by lifecycle state

Quote/order systems are state-heavy.

Slice along lifecycle transitions:

- draft quote creation,
- quote priced,
- quote submitted for approval,
- quote approved,
- quote accepted,
- order created,
- order decomposed,
- fulfillment started,
- fallout raised,
- order completed,
- order cancelled.

Each transition can be a slice if it produces useful feedback.

## 5.5 Slice by actor and authority

Some slices should isolate authority differences:

- sales user creates quote,
- approver approves quote,
- order manager resumes fallout,
- support user views audit,
- service identity handles fulfillment callback.

This avoids discovering authorization gaps too late.

## 5.6 Slice by integration boundary

For enterprise systems, integration is often the risk.

Slice around one integration at a time:

- catalog lookup,
- pricing engine,
- approval service,
- order service,
- fulfillment adapter,
- billing handoff,
- Kafka consumer,
- product inventory lookup.

The slice should include enough simulation or contract testing to prove the boundary.

## 6. Slicing dimensions for Quote & Order

Use this matrix during refinement.

| Dimension | Slice options |
|---|---|
| Product type | simple offering, bundle, configurable product, amendment product |
| Customer type | consumer, SMB, enterprise, special agreement customer |
| Pricing | list price, agreement price, discount, tax/fee, margin exception |
| Approval | no approval, single approval, multi-level approval, rejection, expiry |
| Lifecycle | draft, priced, pending approval, approved, accepted, ordered, cancelled |
| Order type | new sale, modify, disconnect, move, renewal, cancellation |
| Fulfillment | synchronous mock, async callback, partial success, fallout |
| Integration | REST API, Kafka event, external adapter, batch/reconciliation |
| Deployment | feature flag off, tenant enabled, canary, on-prem upgrade |
| Risk | data migration, contract change, tenant isolation, performance, audit |

A good slice chooses a narrow path through this matrix.

A bad slice tries to cover every dimension at once.

## 7. Example: slicing a quote approval feature

Large epic:

> Support approval workflow for enterprise discount quotes.

This is too broad.

Potential vertical slices:

### Slice 1 — Detect approval requirement

Behavior:

> When a sales user creates a quote with discount above configured threshold, the quote is marked as requiring approval and cannot be accepted.

Includes:

- one customer fixture,
- one product offering fixture,
- one threshold rule,
- quote state update,
- API response field,
- unit/integration tests,
- audit event for approval requirement if required.

Excludes:

- approval UI,
- multi-level approvals,
- email notification,
- delegation,
- advanced price overrides.

### Slice 2 — Approver can approve

Behavior:

> A user with approval authority can approve the quote, and acceptance becomes allowed.

Includes:

- authorization check,
- approval evidence,
- state transition,
- audit event,
- negative test for unauthorized user.

### Slice 3 — Approval invalidates on price-changing edit

Behavior:

> If a quote changes after approval in a way that changes commercial terms, approval is invalidated.

Includes:

- quote versioning,
- commercial snapshot comparison,
- invalidation audit,
- acceptance denial test.

### Slice 4 — Quote acceptance after approval is idempotent

Behavior:

> Retrying quote acceptance after timeout does not create duplicate product orders.

Includes:

- idempotency key,
- quote-to-order uniqueness,
- duplicate request test,
- order event assertion.

### Slice 5 — Approval journey appears in support/audit view

Behavior:

> Support can reconstruct who approved the quote, under which authority, and what commercial values were approved.

Includes:

- audit query/view,
- redaction rules,
- support role authorization,
- E2E or API test.

Each slice is meaningful.

Each slice reduces risk.

None requires building the entire approval universe at once.

## 8. Example: slicing order decomposition

Large epic:

> Implement order decomposition for product orders.

Potential slices:

### Slice 1 — Decompose one simple new-sale order

Behavior:

> A product order with one supported offering is decomposed into one fulfillment task.

Includes:

- order accepted state,
- deterministic decomposition rule,
- persistence of task,
- audit/event if required,
- unit/integration tests.

### Slice 2 — Idempotent decomposition retry

Behavior:

> Retrying decomposition for the same order does not create duplicate tasks.

Includes:

- unique constraint or idempotency guard,
- duplicate command test,
- Kafka replay test if triggered by event.

### Slice 3 — Bundle decomposition

Behavior:

> A bundle order item decomposes into multiple ordered tasks with dependency metadata.

Includes:

- simple dependency graph,
- task ordering rule,
- tests for deterministic output.

### Slice 4 — Partial fulfillment failure raises fallout

Behavior:

> If one fulfillment task fails, the order enters fallout with operator-visible reason.

Includes:

- simulator callback,
- state transition,
- fallout audit,
- dashboard/runbook note.

### Slice 5 — Resume fallout

Behavior:

> Operator can retry failed task safely without duplicating completed tasks.

Includes:

- authorization,
- retry guard,
- audit,
- E2E test for duplicate callback.

## 9. Example: slicing Kafka event work

Large story:

> Publish order events to downstream consumers.

Potential slices:

### Slice 1 — Publish `ProductOrderCreated` for one order creation path

Includes:

- outbox record,
- event envelope,
- tenant ID,
- aggregate ID,
- correlation ID,
- consumer contract test or schema test,
- operational metric for publish failure.

### Slice 2 — Consumer handles duplicate event

Includes:

- inbox/deduplication,
- duplicate event test,
- idempotency assertion.

### Slice 3 — Event replay safety

Includes:

- replay old event fixture,
- no duplicate side effect,
- correlation/causation verification.

### Slice 4 — Add backward-compatible field

Includes:

- schema compatibility check,
- old consumer fixture,
- contract test.

### Slice 5 — DLQ and runbook

Includes:

- malformed event test,
- DLQ behavior,
- dashboard/runbook.

This slicing is better than implementing all events first and discovering consumer failures later.

## 10. Example: slicing database migration work

Large story:

> Add approval basis hash to quote approval evidence.

Bad slicing:

1. add non-null column,
2. update app,
3. fix later.

Safer slicing:

### Slice 1 — Expand schema safely

Behavior:

> Nullable `approval_basis_hash` exists and old app remains compatible.

Includes:

- migration test,
- old/new compatibility check,
- no behavior switch.

### Slice 2 — Write hash for new approvals

Behavior:

> New approval records store hash while old records remain readable.

Includes:

- app write path,
- fallback read path,
- audit test.

### Slice 3 — Backfill old approvals

Behavior:

> Historical approval records are backfilled in chunks with dry-run and validation.

Includes:

- backfill script/job,
- idempotency,
- metrics,
- validation query.

### Slice 4 — Enforce read requirement

Behavior:

> Application relies on hash only after validation passes.

Includes:

- feature flag or config gate,
- compatibility check.

### Slice 5 — Contract old path

Behavior:

> Old fallback is removed only after all supported environments are migrated.

Includes:

- cleanup PR,
- compatibility window closure.

This is Scrum slicing plus production migration discipline.

## 11. Slicing patterns

## 11.1 Happy-path thin slice

Use when the team lacks end-to-end wiring.

Example:

> Create draft quote for one product offering and retrieve it by ID.

Good for:

- first increment,
- new service wiring,
- test infrastructure,
- API/persistence path.

Risk:

- too many happy-path slices can ignore real production complexity.

## 11.2 Risk-first slice

Use when one uncertainty dominates.

Example:

> Prove order decomposition can represent amendment orders with one installed-base fixture.

Good for:

- complex domain,
- architecture decision,
- integration uncertainty.

Risk:

- may not look like immediate user value unless framed well.

## 11.3 Contract slice

Use when external consumers are affected.

Example:

> Add optional field to Quote API and verify old generated client remains compatible.

Good for:

- public APIs,
- TMF alignment,
- partner/customer integrations.

## 11.4 Data-safety slice

Use when migration or data repair risk dominates.

Example:

> Add nullable column and verify old app/new schema compatibility before using it.

Good for:

- PostgreSQL migrations,
- on-prem upgrades,
- expand-contract changes.

## 11.5 Observability slice

Use when new workflow is hard to operate.

Example:

> Add order fallout metric and dashboard panel before enabling retry automation.

Good for:

- async workflows,
- production support,
- ORR readiness.

## 11.6 Feature-flagged slice

Use when behavior must be deployed separately from activation.

Example:

> Deploy new pricing rule behind tenant-scoped flag, disabled by default.

Good for:

- customer-specific rollout,
- risky behavior,
- gradual enablement.

Risk:

- flags create long-term complexity if cleanup is not planned.

## 12. Anti-patterns

### 12.1 Layer-only tickets

Symptoms:

- DB ticket,
- API ticket,
- UI ticket,
- Kafka ticket,
- test ticket,
- observability ticket.

Problem:

- no early integrated feedback.

Fix:

- create vertical slices that include enough layers to prove behavior.

### 12.2 Skeleton with no learning

A skeleton can be useful.

But a skeleton that only creates folders/classes without testing a real behavior is weak.

Better:

- skeleton plus one real command,
- skeleton plus one real persistence path,
- skeleton plus one real API test.

### 12.3 Big-bang domain completeness

Trying to implement every product type, every customer type, every approval path, and every order type before releasing anything increases risk.

Prefer representative slices.

### 12.4 Test-later slicing

If tests are a later story, the slice is not done.

A slice without proof is inventory.

### 12.5 Observability-later slicing

If a new async workflow has no metric/log/runbook until the end, production risk is deferred.

### 12.6 Migration-later slicing

If data migration is deferred until all code is done, the team may discover late that the release path is impossible.

### 12.7 Customer-specific all-in-one slice

Customer-specific behavior often touches many areas.

Slice by capability and risk, not by customer commitment as one giant item.

## 13. Slicing checklist for refinement

Use this during backlog refinement.

### 13.1 Value

- What user/customer/operator behavior becomes possible?
- Is this slice meaningful alone?
- Which Sprint Goal does it support?
- What decision or uncertainty does it reduce?

### 13.2 Scope

- Which actor?
- Which product offering/customer type?
- Which lifecycle state?
- Which happy path?
- Which failure path?
- What is explicitly excluded?

### 13.3 Technical boundary

- Which API/command?
- Which database tables?
- Which Kafka event/topic?
- Which external integration?
- Which config/feature flag?
- Which migration?

### 13.4 Safety

- Does it preserve tenant isolation?
- Does it preserve authorization?
- Does it preserve audit?
- Does it preserve idempotency?
- Does it preserve API/event compatibility?
- Does it survive rolling deployment?

### 13.5 Evidence

- What unit tests?
- What integration tests?
- What contract tests?
- What migration tests?
- What E2E journey?
- What dashboard/log/metric?
- What demo evidence?

### 13.6 Release

- Can this be deployed independently?
- Does it require feature flag?
- Is it release-ready or only merged?
- Is support/runbook impact clear?
- Is cleanup needed later?

## 14. Story slicing templates

### 14.1 Behavior-first template

```md
As a <actor>,
I want <narrow behavior>,
so that <business value or risk reduction>.

Scope:
- Included:
- Excluded:

Acceptance evidence:
- Behavior:
- Data:
- API/event:
- Security:
- Observability:
- Tests:
```

Example:

```md
As a sales user,
I want to submit a priced enterprise quote for approval,
so that discount exceptions are reviewed before quote acceptance.

Scope:
- Included: one enterprise customer fixture, one discount threshold, quote state transition to PENDING_APPROVAL.
- Excluded: multi-level approval, email notification, approval delegation.

Acceptance evidence:
- Quote above threshold cannot be accepted before approval.
- Quote below threshold does not require approval.
- Unauthorized user cannot approve.
- Approval-required audit event exists.
- Unit and integration tests cover threshold and state transition.
```

### 14.2 Risk-reduction template

```md
We need to learn whether <technical/domain assumption> is true
before committing to <larger implementation>,
so this slice will prove <decision criteria>.

Decision criteria:
- Pass:
- Fail:
- Evidence:
- Follow-up:
```

Example:

```md
We need to learn whether the existing order decomposition model can represent amendment orders
before committing to the full amendment roadmap,
so this slice will decompose one installed-base amendment into deterministic order item actions.

Decision criteria:
- Pass: add/modify/delete actions can be represented without custom one-off branching.
- Fail: model requires new action taxonomy or task dependency model.
- Evidence: test fixture, decomposition output, design note.
```

### 14.3 Migration slice template

```md
This slice changes data shape by <change>.

Expand step:
- Migration:
- Backward compatibility:

Use step:
- Code path:
- Tests:

Backfill step:
- Strategy:
- Metrics:
- Validation:

Contract step:
- Cleanup:
- Compatibility window:
```

## 15. Senior engineer questions during slicing

Ask these before accepting a slice into Sprint Planning.

1. What is the smallest meaningful behavior?
2. What is the riskiest unknown?
3. Is the slice vertical enough to produce feedback?
4. Is it small enough for one Sprint?
5. What is the explicit non-goal?
6. Does it create production-incomplete inventory?
7. Does it require a migration?
8. Does it require contract compatibility review?
9. Does it need a feature flag?
10. How will we demo it as evidence?
11. What tests are part of the slice?
12. What operational signal proves it works?
13. What would make this slice unsafe to merge?
14. What cleanup will be required later?

## 16. Internal verification checklist

Verify these inside the actual team context.

### 16.1 Scrum/process

- How does the team define Product Backlog Items?
- Are PBIs usually stories, tasks, bugs, spikes, enablers, or mixed?
- Does the team explicitly prefer vertical slices?
- Are technical enabler items allowed?
- How are spikes handled?
- How are carryover items analysed?
- Are stories expected to be releasable?

### 16.2 Product/domain

- Which quote/order journeys are most important?
- Which product/customer types are representative?
- Which customer-specific cases distort slicing?
- Which lifecycle states are high-risk?
- Which integrations are hardest to simulate?

### 16.3 Architecture

- Which services are involved in common slices?
- Is there a feature flag system?
- Is there contract testing?
- Are Kafka events backward-compatible by policy?
- Are migrations expand-contract by default?

### 16.4 Delivery

- Can the team deploy a partial slice safely?
- What does Done mean for a backend slice?
- Are tests included in the same story?
- Is observability included in the same story?
- Are support/runbook updates included when needed?

## 17. Practical exercise

Take one real Product Backlog Item from the team.

Rewrite it into three possible slicing plans:

1. **Happy-path vertical slice**.
2. **Risk-first slice**.
3. **Migration/contract-safe slice**.

For each slice, document:

- actor,
- behavior,
- included scope,
- excluded scope,
- tests,
- API/event/data impact,
- operational evidence,
- release/flag strategy.

Then ask:

> Which slice gives the team the most useful feedback in the next Sprint?

---

## 18. Summary

Story slicing is one of the most powerful senior-engineering skills in Scrum.

For Quote & Order systems, slicing must account for:

- business value,
- lifecycle state,
- pricing/approval correctness,
- order conversion,
- Kafka event safety,
- PostgreSQL migration safety,
- tenant isolation,
- audit evidence,
- observability,
- release strategy.

The goal is not small tickets.

The goal is small, meaningful, safe increments that expose important feedback early.

A strong senior engineer helps the team avoid both extremes:

- giant stories that hide risk,
- tiny technical tasks that produce no usable increment.

The best slice is the smallest one that teaches the most and can be made truly Done.
