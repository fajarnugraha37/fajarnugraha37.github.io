# Part 026 — Production Readiness Inside Scrum

## 1. Source notes and scope boundary

This part uses public references and general production engineering practice:

- Scrum Guide defines the Increment as usable and thoroughly verified, with Definition of Done as the commitment for Increment.
- AWS Well-Architected Operational Excellence material describes evaluating operational readiness through consistent processes, runbooks, playbooks, and readiness checks.
- Site reliability and DevOps practices commonly treat observability, rollback, incident response, and operational learning as part of production system design.

This part does not assume CSG uses a specific ORR process, deployment platform, release train, SRE model, on-call structure, or production readiness checklist.

Use the internal verification checklist to adapt this to your actual Scrum Team.

---

## 2. Core thesis

A Scrum Increment is not truly valuable if it cannot be operated.

For enterprise backend systems, "done" must include production readiness.

Not always full release to all customers.

But enough readiness that the team knows:

- what changed;
- what can fail;
- how to detect failure;
- how to rollback or mitigate;
- how to support customers;
- how to repair data if necessary;
- how to prove the behavior works;
- how to continue safely next Sprint.

Production readiness must happen inside Scrum, not after Scrum.

If every Sprint ends with "development done, hardening later", the Scrum process is hiding unfinished work.

---

## 3. Done versus release-ready versus customer-enabled

These are different states.

| State | Meaning | Example |
|---|---|---|
| Code complete | Implementation written | Branch has code, tests maybe incomplete |
| PR merged | Code merged to main | Still may not be deployed or observable |
| Sprint Done | Meets Definition of Done | Increment usable under team DoD |
| Release-ready | Safe to deploy/activate | Operational checks complete |
| Production deployed | Running in production | Feature may still be disabled |
| Customer-enabled | Customer can use it | Feature flag/config/customer rollout complete |

A mature Scrum Team names these states clearly.

The Definition of Done should prevent "code complete" from masquerading as "done".

## 4. Production readiness as part of Definition of Done

For enterprise Quote & Order work, DoD should include readiness dimensions by work type.

### 4.1 Common readiness dimensions

- tests passed;
- contract compatibility verified;
- migration safety checked;
- observability added;
- logs contain correlation identifiers;
- metrics/dashboard updated;
- alert/runbook updated where needed;
- feature flag/config documented;
- security/tenant/audit checks complete;
- rollback/disable path known;
- support impact documented;
- release notes prepared where needed.

Not every story needs every item.

But every story needs explicit reasoning about which readiness items apply.

---

## 5. Why production readiness gets pushed out

Production readiness is often delayed because it is invisible during planning.

Common causes:

- backlog item describes only user-visible behavior;
- acceptance criteria omit observability;
- testing is treated as QA phase;
- runbooks are considered documentation after work;
- migration risk is discovered at release time;
- support handoff happens after customer issue;
- feature flags are added without cleanup plan;
- Sprint Review demos UI but not operational evidence;
- velocity pressure rewards starting new work over finishing fully.

The fix is to make readiness visible in refinement, planning, execution, and review.

## 6. Production readiness by work type

## 6.1 REST API change

Readiness checklist:

- OpenAPI updated;
- backward compatibility reviewed;
- error model reviewed;
- authentication/authorization covered;
- tenant behavior covered;
- contract tests updated;
- API logs contain request/correlation ID;
- metrics for success/error/latency exist where needed;
- rate limit or abuse concern considered;
- support troubleshooting path documented.

Example readiness AC:

```gherkin
Given an old client sends a create quote request without the new optional field
When the API processes the request
Then the request still succeeds with previous default behavior
And the response remains backward-compatible
And the operation is visible in quote API metrics
```

## 6.2 Kafka event change

Readiness checklist:

- event schema updated;
- compatibility verified;
- topic/partition key unchanged or reviewed;
- producer test updated;
- consumer test updated;
- replay safety considered;
- duplicate handling tested;
- DLQ behavior known;
- consumer lag dashboard checked;
- event includes tenant/correlation/causation metadata;
- support can trace event by aggregate ID.

Example readiness AC:

```gherkin
Given a ProductOrderCreated event from the previous schema version
When the new consumer processes the event
Then it remains backward-compatible
And no duplicate fulfillment task is created on replay
And consumer lag/error signals remain observable
```

## 6.3 PostgreSQL migration

Readiness checklist:

- migration tested on empty DB;
- migration tested on previous-release fixture;
- large-table lock risk reviewed;
- expand-contract used where needed;
- backfill chunking/resume designed;
- old/new app compatibility considered;
- rollback/roll-forward plan documented;
- query plan impact checked;
- on-prem upgrade impact considered.

Example readiness AC:

```gherkin
Given a database containing quotes created by the previous release
When the migration runs
Then existing quotes remain readable by the new service
And the migration can be rerun safely or fails with explicit guard
And the expected validation query passes
```

## 6.4 Security-sensitive change

Readiness checklist:

- auth path tested;
- negative authorization tests added;
- tenant isolation tested;
- audit event verified;
- sensitive logs redacted;
- support/admin access considered;
- security review completed if required;
- threat model updated where needed.

Example readiness AC:

```gherkin
Given a user from tenant B
When they request a quote belonging to tenant A by direct ID
Then access is denied according to policy
And no quote data is leaked in response, logs, or metrics
```

## 6.5 Production workflow change

Examples:

- order decomposition;
- fulfillment callback;
- pricing recalculation;
- quote acceptance;
- fallout resume;
- billing handoff.

Readiness checklist:

- success path tested;
- failure path tested;
- retry/idempotency tested;
- stuck-state detection exists;
- dashboard/runbook updated;
- data repair/reconciliation path considered;
- downstream simulator or contract test exists;
- support can identify affected business object.

## 7. Readiness inside Scrum events

### 7.1 Refinement

Ask early:

- What does production-ready mean for this PBI?
- Does it affect API, Kafka, DB, security, audit, observability, or support?
- What failure modes should acceptance criteria cover?
- Does this need a spike?
- Does this need design/ADR?
- Does this need migration or rollout plan?
- Who needs to review this?

Refinement should discover readiness work before Sprint Planning.

### 7.2 Sprint Planning

Ask:

- Is readiness work included in estimates?
- Does capacity include testing/review/operability?
- Is the Sprint Goal achievable with readiness included?
- Are external dependencies visible?
- Are release/feature flag constraints known?
- Is production interrupt load considered?

Do not plan only coding effort.

### 7.3 Daily Scrum

Ask:

- Is any story at risk of missing DoD?
- Are tests failing?
- Is review blocked?
- Is observability/runbook work forgotten?
- Is a migration/release risk emerging?
- Do we need to adapt Sprint Backlog?

Daily Scrum should expose readiness risk before the final day.

### 7.4 Sprint Review

Demonstrate evidence:

- behavior works;
- tests pass;
- API/event contract is compatible;
- dashboard shows signals;
- runbook exists if relevant;
- rollback/flag behavior is known;
- stakeholders understand release constraints.

A Sprint Review demo can include logs, metrics, traces, API examples, event payloads, and migration validation results.

### 7.5 Retrospective

Inspect readiness problems:

- What was discovered too late?
- Which DoD item was hardest?
- Which story looked done but was not release-ready?
- Which production defect escaped?
- Which test/runbook/dashboard would have prevented it?
- What should change in refinement or DoD?

## 8. Production readiness evidence packet

For high-risk work, create a small evidence packet.

Template:

```md
# Production Readiness Evidence: <PBI/Feature>

## Change summary
- What changed?
- Which domain capability is affected?

## Risk surfaces
- API:
- Kafka:
- DB:
- Security/tenant/audit:
- Observability:
- Support/customer:

## Evidence
- Unit tests:
- Integration tests:
- Contract tests:
- Migration validation:
- E2E/manual journey:
- Security tests:

## Operations
- Dashboard:
- Alert/runbook:
- Rollback/disable:
- Data repair/reconciliation:

## Decision
- Done for Sprint?
- Release-ready?
- Customer-enabled now or later?
```

This does not need to be heavy.

The goal is clarity.

## 9. Observability readiness

Observability should be designed with the feature.

Not after an incident.

### 9.1 Logging readiness

Check:

- logs include correlation ID;
- logs include tenant ID where safe;
- logs include quote/order ID where safe;
- errors have actionable messages;
- logs avoid PII and sensitive commercial data;
- important state transitions are logged or audited;
- duplicate/retry decisions are visible.

### 9.2 Metrics readiness

Check:

- success count;
- failure count;
- latency;
- queue/backlog age;
- retry count;
- DLQ count;
- business state count;
- stuck-state count;
- downstream failure count.

### 9.3 Tracing readiness

Check:

- trace flows through API/service/DB/Kafka/downstream;
- correlation ID and causation ID are connected;
- async boundaries are traceable;
- support can reconstruct a journey.

### 9.4 Dashboard readiness

Check:

- dashboard exists or existing dashboard updated;
- baseline known;
- new feature signal visible;
- high-risk failure mode visible;
- dashboard linked in runbook if needed.

## 10. Runbook readiness

Not every story needs a runbook.

But every new operational workflow should answer:

- How do we know it is failing?
- What does failure look like to customer/support?
- What dashboard/log/query should be checked?
- What is safe to retry?
- What must not be retried?
- Can it be disabled?
- Can it be rolled back?
- Does it require data repair?
- Who owns escalation?

### 10.1 Minimal runbook template

```md
# Runbook: <failure mode>

## Symptoms

## Impact

## Immediate mitigation

## Diagnosis steps

## Safe retry/repair steps

## Escalation

## Recovery verification

## Follow-up backlog
```

A runbook should be useful under stress.

Long prose is less useful than precise steps and warnings.

## 11. Feature flags and production readiness

Feature flags are useful but dangerous.

Readiness checklist:

- flag default known;
- flag owner known;
- flag scope known: global, tenant, customer, environment;
- behavior tested on and off;
- mixed-state behavior tested if rollout partial;
- data written under flag compatible with old path;
- observability includes flag state;
- rollback means flag disable or code rollback?
- cleanup/removal plan exists.

Feature flags should not become permanent hidden product variants.

---

## 12. Release notes and support readiness

Some work requires support/customer-facing readiness.

Check:

- release note drafted;
- known behavior change explained;
- migration/upgrade instruction provided;
- support troubleshooting notes updated;
- customer-specific config impact known;
- API/event deprecation documented;
- operational limitation noted.

For Quote & Order, support needs practical business identifiers:

- quote ID;
- order ID;
- customer/account;
- tenant;
- catalog version;
- correlation ID;
- time window;
- user/action.

## 13. Production readiness anti-patterns

### 13.1 Done but not deployable

Code works locally but lacks migration, config, or deployment readiness.

### 13.2 Deployable but not observable

Change is live but no one can detect failure.

### 13.3 Observable but not recoverable

Alerts fire but no mitigation/runbook exists.

### 13.4 Recoverable but not auditable

Manual repair works but no evidence exists.

### 13.5 Feature-flagged forever

Complexity remains because old/new paths never converge.

### 13.6 Testing outside Sprint

Sprint ends with unverified work, creating fake progress.

### 13.7 Release readiness owned by someone else

Developers assume QA/SRE/release team will make it production-ready later.

Scrum Team owns the Increment.

## 14. Internal verification checklist

Verify these inside your team:

- What is the official Definition of Done?
- Does DoD include observability?
- Does DoD include security/tenant/audit?
- Does DoD include API/event compatibility?
- Does DoD include migration safety?
- What does release-ready mean internally?
- What does customer-enabled mean internally?
- Is there an ORR process?
- Who approves production release?
- Are runbooks required?
- Are dashboards reviewed during Sprint Review?
- How are feature flags managed?
- How are release notes created?
- How are support teams informed?
- How are production incidents converted to backlog work?
- How are data repair procedures approved?
- How do cloud and on-prem readiness differ?

## 15. Practical exercises

### Exercise 1 — Readiness gap analysis

Pick one completed story from a recent Sprint.

Ask:

- Was it code complete?
- Was it Sprint Done?
- Was it release-ready?
- Was it customer-enabled?
- What evidence existed?
- What evidence was missing?

### Exercise 2 — Add readiness AC

Take a story with only business acceptance criteria.

Add engineering readiness criteria for:

- testing;
- API/event compatibility;
- migration;
- security;
- observability;
- rollback;
- support.

### Exercise 3 — Build a mini runbook

Choose one failure mode:

- quote acceptance fails;
- order stuck in fallout;
- Kafka consumer lag grows;
- migration partially fails;
- pricing calculation latency spikes.

Write a 1-page runbook.

### Exercise 4 — Sprint Review evidence demo

For your next completed backend story, demo:

- business behavior;
- API response/event payload;
- test evidence;
- dashboard/log signal;
- failure path;
- rollout/flag state.

---

## 16. Summary

Production readiness belongs inside Scrum.

A usable Increment is not merely code that compiles.

For enterprise Quote & Order systems, readiness means the team has considered:

- domain behavior;
- tests;
- compatibility;
- migration;
- security;
- audit;
- observability;
- runbooks;
- rollout;
- rollback;
- support;
- data correction.

The senior engineer contribution is to make readiness visible early, keep it inside the Sprint, and ensure "Done" means safe enough to operate.
