# Part 008 — Acceptance Criteria for Production-Grade Work

## 1. Source notes and scope boundary

This part uses public Scrum and agile practice references:

- The Scrum Guide defines the Definition of Done as a formal description of the state of the Increment when it meets the quality measures required for the product.
- The Scrum Guide states that once a Product Backlog item meets the Definition of Done, an Increment is born.
- Scrum.org material explains that Product Backlog refinement creates shared understanding of Product Backlog Items through focused discussion.
- Scrum Alliance describes acceptance criteria as conditions that must be satisfied for a product, user story, or increment of work to be accepted; acceptance criteria are not part of the Scrum Guide, but many teams use them as a practical refinement tool.
- Agile Alliance material emphasizes that acceptance criteria can be expressed in ways directly usable as automated acceptance tests.

This part does **not** assume CSG has a specific acceptance criteria template, Gherkin standard, Jira field, QA process, release gate, Definition of Done, or automated test policy.

Use the internal verification checklist to align this material with actual team practice.

---

## 2. Core thesis

Acceptance criteria are not a place to restate the story.

Acceptance criteria are a shared agreement about what evidence will prove the work behaves correctly.

For enterprise Quote & Order systems, weak acceptance criteria create expensive ambiguity.

Weak acceptance criteria:

> User can approve a quote.

Production-grade acceptance criteria:

> A user with approval authority for the tenant/account can approve a pending quote whose price snapshot has not changed since approval evaluation; the approval records actor, authority, threshold basis, reason, timestamp, quote version, and correlation ID; unauthorized users are denied; approved quote can be accepted exactly once idempotently; approval is invalidated by price-changing edits; all behavior is covered by unit/integration/API tests and visible in audit.

The second version is longer because the product is riskier.

In enterprise systems, ambiguity is not free.

It becomes defects, rework, support escalations, production incidents, and customer trust loss.

---

## 3. Acceptance Criteria vs Definition of Done

Acceptance criteria and Definition of Done are related but different.

| Concept | Scope | Example |
|---|---|---|
| Acceptance Criteria | Specific Product Backlog Item | Quote above discount threshold requires approval |
| Definition of Done | Product/team-wide quality bar | Code reviewed, tested, secure, observable, documented, releasable |

Acceptance criteria describe what this item must do.

Definition of Done describes what every done increment must satisfy.

A story can meet its acceptance criteria but still not be Done if it lacks required tests, review, security checks, observability, documentation, or release readiness.

A strong team uses both.

---

## 4. Why normal AC often fails for backend enterprise work

Many teams write acceptance criteria mostly for UI behavior.

Example:

- button is visible,
- user can submit form,
- success message appears.

That is not enough for Quote & Order backend work.

A backend story may need criteria for:

- state transition,
- transaction boundary,
- API response,
- Kafka event,
- database migration,
- old client compatibility,
- tenant isolation,
- authorization,
- audit event,
- idempotency,
- retry behavior,
- performance baseline,
- observability,
- supportability,
- rollback.

If acceptance criteria only describe the happy path, engineers will implement the happy path and discover production reality later.

## 5. Production-grade AC model

Use this model:

```md
Acceptance Criteria = Behavior + Boundary + Evidence + Safety + Operability
```

### 5.1 Behavior

What business behavior must occur?

Example:

- quote above threshold requires approval.
- order cancellation creates cancellation request for active fulfillment task.
- duplicate quote acceptance does not create duplicate order.

### 5.2 Boundary

Where is behavior observed?

Example:

- REST API,
- UI,
- Kafka event,
- database state,
- audit view,
- downstream simulator,
- dashboard.

### 5.3 Evidence

How will we prove it?

Example:

- unit test,
- integration test,
- contract test,
- E2E test,
- migration dry run,
- dashboard screenshot,
- manual demo.

### 5.4 Safety

Which failure conditions are covered?

Example:

- unauthorized user denied,
- duplicate request idempotent,
- old clients compatible,
- tenant boundary enforced,
- migration backward compatible.

### 5.5 Operability

Can production/support understand the behavior?

Example:

- structured log includes quote ID,
- metric records failure rate,
- audit event exists,
- runbook updated,
- alert/watch criteria defined.

## 6. AC quality ladder

### Level 1 — vague

```md
- User can create quote.
```

Problem:

- actor unclear,
- product/customer unclear,
- state unclear,
- validation unclear,
- evidence unclear.

### Level 2 — behavior-specific

```md
- Sales user can create a draft quote for an active product offering.
```

Better, but still incomplete.

### Level 3 — testable

```md
- Given an authenticated sales user in tenant A and an active product offering,
  when the user creates a quote with valid required characteristics,
  then the API returns 201 and the quote is stored in DRAFT state with tenant ID, customer ID, offering ID, and catalog version.
```

Better.

### Level 4 — production-grade

```md
- Quote creation stores tenant ID, customer ID, catalog version, and quote version.
- Invalid required characteristics return a machine-readable validation error.
- User from another tenant cannot create quote for tenant A customer.
- Quote creation is idempotent for the same idempotency key if the endpoint supports idempotency.
- Audit event `QuoteCreated` is recorded with actor and correlation ID.
- Structured logs include correlation ID and quote ID after creation.
- Unit and integration tests cover valid, invalid, unauthorized, and duplicate paths.
```

This is the level expected for high-risk enterprise backend work.

## 7. AC categories for Quote & Order work

## 7.1 Business behavior AC

Examples:

- Quote can be created only for active offering.
- Quote cannot be accepted after expiry.
- Quote above discount threshold requires approval.
- Approval is invalidated when commercial terms change.
- Accepted quote creates exactly one product order.
- Order cannot be completed while required item is still active.
- Cancellation behavior depends on fulfillment progress.

## 7.2 State machine AC

Examples:

- DRAFT quote can transition to PRICED.
- PENDING_APPROVAL quote cannot be accepted.
- APPROVED quote can be accepted only if not expired.
- ACCEPTED quote cannot be edited.
- IN_PROGRESS order can transition to FALLOUT when fulfillment task fails.
- COMPLETED order cannot be resumed.

State-machine AC should include invalid transitions.

## 7.3 Data AC

Examples:

- Quote stores immutable price snapshot at acceptance.
- Order references accepted quote version.
- Tenant ID is stored on every new aggregate row.
- New nullable column is safe for old app version.
- Backfill is idempotent and resumable.
- Query returns only rows for authorized tenant/account.

## 7.4 API contract AC

Examples:

- API response includes `quoteId`, `state`, `version`, and `correlationId`.
- Error response is machine-readable and does not expose internal stack trace.
- Existing fields remain backward compatible.
- New enum values are documented and tested against known clients.
- Pagination/filter behavior is unchanged unless explicitly versioned.

## 7.5 Event contract AC

Examples:

- `QuoteAccepted` event includes tenant ID, quote ID, quote version, event ID, correlation ID, causation ID.
- Event is emitted only after transaction commit through outbox.
- Duplicate command does not create duplicate business event.
- Old consumer fixture can deserialize new event.
- Replay of event is idempotent.

## 7.6 Security AC

Examples:

- User without approval authority cannot approve quote.
- User cannot access quote from another tenant.
- Service token cannot perform human-only action.
- Request body cannot set privileged fields such as `approvedBy`, `tenantId`, or `state`.
- Sensitive fields are not logged or emitted in events.

## 7.7 Audit AC

Examples:

- Approval records actor, authority, reason, quote version, and timestamp.
- Price override records before/after value and reason.
- Denied privileged action is logged/audited according to policy.
- Repair/correction action is auditable.

## 7.8 Observability AC

Examples:

- New command logs correlation ID and aggregate ID.
- New async workflow has metric for success/failure/lag.
- Dashboard panel exists for new fallout state.
- Alert/runbook is updated if new failure mode is introduced.

## 7.9 Performance AC

Examples:

- Quote search query uses expected index under representative data.
- Pricing response stays within agreed threshold for representative fixture.
- Kafka consumer processes expected throughput without consumer lag growth.
- Migration runtime is measured on production-like data volume.

## 7.10 Release/readiness AC

Examples:

- Feature is disabled by default behind tenant-scoped flag.
- Rollback path is documented.
- Old app can run against expanded schema.
- Release notes mention API behavior change.
- Support runbook updated for new fallout reason.

## 8. Given/When/Then patterns

Gherkin-style AC can be useful when behavior is stateful.

### 8.1 Quote approval example

```gherkin
Scenario: Quote above discount threshold requires approval
  Given a sales user in tenant A
  And an enterprise customer with discount threshold 10 percent
  And an active product offering
  When the user creates a quote with 15 percent discount
  Then the quote state is PENDING_APPROVAL
  And the quote cannot be accepted
  And an approval-required audit event is recorded
```

### 8.2 Negative authorization example

```gherkin
Scenario: Unauthorized user cannot approve quote
  Given a quote in PENDING_APPROVAL state
  And a user without approval authority
  When the user attempts to approve the quote
  Then the request is denied
  And the quote state remains PENDING_APPROVAL
  And no approval evidence is created
```

### 8.3 Idempotency example

```gherkin
Scenario: Duplicate quote acceptance does not create duplicate order
  Given an approved quote with a valid price snapshot
  When quote acceptance is submitted twice with the same idempotency key
  Then exactly one product order exists for the quote version
  And both responses reference the same order ID
  And only one logical ProductOrderCreated event is emitted
```

### 8.4 Migration example

```gherkin
Scenario: Old application remains compatible with expanded schema
  Given the database has been migrated with a new nullable column
  And the old application version is running
  When an existing quote is read and updated through the old application path
  Then the operation succeeds
  And no required data is lost
```

Gherkin is optional.

The important part is clear behavior, condition, and expected evidence.

## 10. Example: weak to strong AC transformation

Original story:

> As a sales user, I want to accept a quote so that I can create an order.

Weak AC:

```md
- User can accept quote.
- Order is created.
```

Problems:

- quote state unclear,
- price validity unclear,
- approval unclear,
- duplicate behavior unclear,
- order uniqueness unclear,
- event/audit unclear,
- tenant/security unclear.

Production-grade AC:

```md
### Business behavior
- Only APPROVED or approval-not-required quotes can be accepted.
- Expired quotes cannot be accepted.
- Accepted quote creates one product order for the accepted quote version.

### State and lifecycle
- Quote transitions from APPROVED to ACCEPTED.
- ACCEPTED quote cannot be edited or repriced through normal edit endpoint.
- Repeated accept command with same idempotency key returns same order ID.

### Data
- Order stores reference to quote ID and quote version.
- Quote acceptance timestamp and actor are persisted.
- A uniqueness guard prevents two orders for same accepted quote version.

### Events
- `QuoteAccepted` and/or `ProductOrderCreated` event is emitted according to internal event model.
- Event includes tenant ID, aggregate ID, event ID, correlation ID, causation ID.

### Security
- User must have permission to accept quote for tenant/account.
- User from another tenant cannot accept quote.

### Audit
- Audit record captures actor, quote ID, quote version, previous state, new state, and correlation ID.

### Tests
- Unit tests for valid and invalid state transitions.
- Integration test for uniqueness/idempotency.
- API test for unauthorized user.
- Event/outbox test for emitted event.
```

This version gives engineering and QA enough clarity to build evidence.

## 11. Example: AC for Kafka event story

Story:

> Publish product order state change events.

Production-grade AC:

```md
### Business behavior
- When a product order changes state through the approved lifecycle service, a state-change event is recorded for publication.

### Event contract
- Event includes event ID, tenant ID, product order ID, previous state, new state, aggregate version, occurredAt, correlation ID, causation ID.
- Event schema change is backward compatible with existing consumers.
- Event is not emitted for failed transaction rollback.

### Idempotency and replay
- Duplicate command does not create duplicate logical state-change event.
- Replaying the event does not duplicate downstream side effects for idempotent consumers.

### Data and transaction
- Event is persisted through outbox in same transaction as order state change.
- Outbox relay failure leaves event retryable.

### Observability
- Outbox backlog metric reflects unpublished events.
- Publish failure is logged with event ID and order ID.

### Tests
- Unit test for event creation from transition.
- Integration test for transaction rollback.
- Contract/schema compatibility test.
- Duplicate command test.
```

## 12. Example: AC for PostgreSQL migration story

Story:

> Add catalog version snapshot to quote item.

Production-grade AC:

```md
### Migration
- Add nullable `catalog_version` or equivalent field without breaking old application version.
- Migration succeeds on empty DB and representative old DB fixture.
- Migration does not require long blocking lock on hot table.

### Application behavior
- New quote items store catalog version on creation.
- Existing quote items without catalog version remain readable through fallback logic.

### Backfill
- Historical quote items can be backfilled in chunks.
- Backfill is idempotent and resumable.
- Validation query identifies rows still missing catalog version after backfill.

### Compatibility
- Old app version can read/write quote items after expand migration.
- New app can read old rows before backfill completes.

### Observability
- Backfill progress metric or execution report is available.

### Tests
- Migration test on old fixture.
- Integration test for fallback read.
- Backfill idempotency test.
```

## 13. Example: AC for security-sensitive story

Story:

> Allow support user to resume stuck fulfillment task.

Production-grade AC:

```md
### Business behavior
- Support user can resume a task only when order is in FALLOUT or equivalent recoverable state.
- Completed/cancelled tasks cannot be resumed.

### Authorization
- Only support role with required permission can resume task.
- User from another tenant cannot resume task.
- Service token cannot perform support-user resume action unless explicitly allowed.

### Audit
- Resume action records actor, tenant, order ID, task ID, previous state, new state, reason, timestamp, correlation ID.

### Idempotency
- Repeating resume command does not create duplicate downstream fulfillment request.

### Observability
- Resume attempts and failures are measurable.
- Runbook documents when resume is safe.

### Tests
- Positive support-user test.
- Negative unauthorized-role test.
- Negative cross-tenant test.
- Duplicate resume test.
- Audit assertion.
```

## 14. Common AC anti-patterns

### 14.1 AC restates the story

```md
- User can do the thing.
```

This adds no clarity.

### 14.2 Only happy path

Missing failure paths create production defects.

At minimum, include:

- invalid input,
- unauthorized actor,
- wrong state,
- duplicate request,
- cross-tenant access if applicable.

### 14.3 UI-only criteria for backend risk

A UI success message does not prove:

- transaction committed,
- event emitted,
- audit created,
- downstream integration works,
- migration safe.

### 14.4 Technical implementation disguised as AC

```md
- Use class `QuoteApprovalHandler`.
```

Implementation detail may be useful in task notes, but AC should focus on observable outcome unless architecture constraint is the value.

### 14.5 AC without testability

If nobody can test it, it is not good acceptance criteria.

### 14.6 AC without non-goals

For complex domains, non-goals prevent accidental scope explosion.

Example:

```md
Non-goals:
- Multi-level approval.
- Email notification.
- Delegated approval.
- Historical quote migration.
```

### 14.7 AC that ignores DoD

A story can pass product AC but fail DoD if it lacks tests, review, security, or observability.

## 15. AC review checklist

Use during refinement or Sprint Planning.

### 15.1 Clarity

- Is actor clear?
- Is business object clear?
- Is lifecycle state clear?
- Is tenant/customer/account scope clear?
- Are included and excluded cases clear?

### 15.2 Behavior

- Is the happy path clear?
- Are important failure paths clear?
- Are duplicate/retry conditions clear?
- Are state transitions clear?
- Is expected error behavior clear?

### 15.3 Data and integration

- Are database changes described?
- Is migration/backfill impact described?
- Are API contract changes described?
- Are Kafka/event changes described?
- Are external integrations described?

### 15.4 Security and audit

- Are authorization rules clear?
- Is tenant isolation covered?
- Are sensitive data rules clear?
- Is audit evidence required?

### 15.5 Operability

- Are logs/metrics/traces required?
- Is supportability considered?
- Is runbook/release note needed?
- Is rollback/feature flag needed?

### 15.6 Testing

- Which tests prove the criteria?
- Are negative tests included?
- Are contract/migration tests needed?
- Is E2E necessary or would lower-level tests be better?

## 17. Practical exercise

Take this weak story:

> As a sales user, I want to apply a discount to a quote.

Write production-grade acceptance criteria covering:

1. allowed discount,
2. discount above threshold,
3. unauthorized override,
4. approval required,
5. approval invalidation after price change,
6. audit evidence,
7. tenant boundary,
8. API response,
9. tests,
10. observability.

Then mark each criterion as:

- product behavior,
- engineering safety,
- test evidence,
- Definition of Done item,
- non-goal.

This exercise teaches the difference between product acceptance and production readiness.

## 18. Summary

Production-grade acceptance criteria make hidden risk visible before Sprint execution.

For Quote & Order systems, AC should often cover:

- business behavior,
- lifecycle state,
- pricing/approval correctness,
- API/event contract,
- data migration,
- tenant/security,
- audit,
- observability,
- testing,
- release readiness.

The senior engineer's job is not to make every story bloated.

The job is to ensure high-risk stories contain enough explicit evidence to avoid ambiguity-driven defects.

Good AC answers:

> What must be true for this work to be accepted as correct, safe, and usable?

Definition of Done answers:

> What must be true for this work to be part of a releasable Increment?

Both matter.
