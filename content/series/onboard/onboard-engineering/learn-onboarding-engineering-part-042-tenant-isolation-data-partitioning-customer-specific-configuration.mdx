# Part 042 — Tenant Isolation, Data Partitioning, and Customer-Specific Configuration

> Core idea: multi-tenancy is not just adding `tenant_id` to tables.  
> It is a system-wide invariant that must hold across identity, API, domain logic, database access, events, caches, logs, configuration, deployment, support tools, and operations.

In Quote & Order systems, tenant isolation failure can become catastrophic.

A single cross-tenant bug can expose:

- customer account data,
- quotes and negotiated prices,
- enterprise agreement terms,
- discount and margin information,
- order status,
- installed base/product inventory,
- fulfillment information,
- audit records,
- customer-specific catalog/pricing configuration.

For a CPQ/order management product, tenant data is not just application data.
It may include commercially sensitive negotiation artifacts.

This part explains how to reason about tenant isolation as an architecture invariant, not an afterthought.

## 2. What Is a Tenant?

A tenant is a boundary of ownership and isolation.

But the word is overloaded.

Possible meanings:

| Meaning | Example |
|---|---|
| Commercial customer | A telecom operator using the product. |
| Deployment unit | A dedicated environment for one customer. |
| Logical organization | A business unit inside a customer. |
| Security realm | Identity provider realm or issuer. |
| Data partition | Row/schema/database boundary. |
| Configuration scope | Customer-specific catalog/pricing/workflow rules. |
| Operational scope | On-call/support responsibility and data access boundary. |

Before touching tenant-sensitive code, clarify which meaning applies.

Dangerous assumption:

```text
tenant_id == customer_id
```

This may be false.

In enterprise/telco contexts, a customer may have:

- multiple operating companies,
- multiple brands,
- multiple countries,
- partner/channel tenants,
- sandbox/prod tenants,
- separate legal entities,
- shared catalog but separate customer data,
- shared customer hierarchy but separate pricing policy.

Internal verification question:

```text
What invariant does tenant_id actually enforce in this codebase?
```

## 3. Tenant Isolation as a System Invariant

A system invariant:

```text
Data, actions, configuration, and operational visibility for tenant A must not be accessible to tenant B except through explicitly designed and audited cross-tenant administrative paths.
```

This invariant must hold across:

- authentication,
- authorization,
- API routing,
- domain command handling,
- repository queries,
- database constraints,
- Kafka events,
- caches,
- search indexes,
- object storage,
- logs,
- metrics,
- traces,
- admin tools,
- data exports,
- backups,
- test data,
- support scripts,
- migration/backfill jobs.

The hardest bugs often appear outside the main API path.

Examples:

- batch export misses tenant filter,
- reconciliation query scans all tenants,
- admin repair tool takes quote ID only,
- Kafka consumer processes event without tenant validation,
- cache key omits tenant ID,
- log aggregation exposes customer name or quote data,
- feature flag default applies to wrong customer,
- migration backfill updates all tenants,
- test fixture uses production-like customer IDs across tenants.

## 4. Deployment Models and Isolation Trade-offs

### 4.1 Shared Application, Shared Database

```text
All tenants share services and database tables.
Rows carry tenant_id.
```

Pros:

- operationally efficient,
- easier global upgrades,
- resource sharing,
- simpler platform operations,
- easier fleet-wide observability.

Cons:

- highest cross-tenant leakage risk,
- noisy neighbor risk,
- query/index design must account for tenant,
- complex customer-specific customization,
- harder data residency isolation,
- harder backup/restore per tenant.

### 4.2 Shared Application, Separate Schemas

```text
Same service deployment, separate schema per tenant.
```

Pros:

- stronger data separation than row-level,
- easier tenant-specific backup/export,
- some query mistakes fail by schema boundary,
- per-tenant migration possible.

Cons:

- migration complexity,
- many schemas operational overhead,
- connection/session routing complexity,
- harder cross-tenant analytics,
- schema drift risk.

### 4.3 Shared Application, Separate Databases

```text
Same service, separate database per tenant.
```

Pros:

- stronger isolation,
- easier customer-specific backup/restore,
- blast radius reduction,
- better data residency/customer compliance story.

Cons:

- operational overhead,
- connection management complexity,
- harder fleet migration,
- capacity fragmentation,
- higher cost.

### 4.4 Dedicated Deployment Per Customer

```text
Separate application stack and database per customer.
```

Pros:

- strong isolation,
- customer-specific configuration easier,
- blast radius contained,
- on-prem/dedicated cloud friendly,
- customer compliance alignment.

Cons:

- upgrade matrix complexity,
- version drift,
- support overhead,
- duplicated infrastructure,
- slower feature rollout,
- harder platform-wide standardization.

### 4.5 On-Prem / Customer-Managed Deployment

```text
Product runs in customer environment.
```

Pros:

- customer control,
- compliance/data residency,
- integration with local systems,
- possible air-gapped support.

Cons:

- limited observability,
- upgrade friction,
- environment variability,
- customer-managed dependencies,
- slower incident diagnosis,
- customization drift.

Senior engineer lens:

```text
There is no universally best model.
Isolation strength, operational cost, upgrade complexity, customization flexibility, and customer compliance requirements trade against each other.
```

## 5. Tenant Context Propagation

Tenant context must be explicit and trusted.

Possible tenant sources:

| Source | Risk |
|---|---|
| JWT claim | Must validate issuer/audience and claim mapping. |
| Hostname/subdomain | Must be bound to trusted routing config. |
| Request path | Easy to spoof unless cross-checked. |
| Header | Dangerous if accepted from external clients without gateway enforcement. |
| API key/client credential | Must map to tenant server-side. |
| Database lookup | Needs safe bootstrap identifier. |
| Session/context | Risk of thread-local leakage if mishandled. |

Bad pattern:

```java
String tenantId = request.getHeader("X-Tenant-Id");
```

Better pattern:

```java
TenantContext tenant = tenantResolver.resolveFromTrustedIdentity(request);
tenantVerifier.verifyRequestBinding(tenant, request);
```

Then pass tenant context explicitly:

```java
public record TenantContext(
    String tenantId,
    String tenantRealm,
    String deploymentId,
    String source,
    String correlationId
) {}
```

Avoid hidden globals where possible.
If thread-local is used, ensure it is cleared reliably in finally blocks and not leaked across async tasks.

## 6. Tenant in API Design

There are several external API shapes.

### Tenant in Hostname

```text
https://tenant-a.example.com/api/quotes
```

Pros:

- clean resource URLs,
- gateway can route by host,
- common in SaaS.

Cons:

- certificate/DNS complexity,
- not always suitable for on-prem,
- tenant context can be hidden from application tests.

### Tenant in Path

```text
/api/tenants/{tenantId}/quotes
```

Pros:

- explicit,
- easy testing,
- useful for admin APIs.

Cons:

- user can submit different tenant ID,
- must cross-check against token/scope,
- can make URLs noisy.

### Tenant from Token Only

```text
/api/quotes
```

Pros:

- less spoofing surface,
- clean API,
- tenant is identity-bound.

Cons:

- hard for cross-tenant admin tools,
- multi-tenant service accounts need careful design,
- errors less explicit.

Practical rule:

```text
Whatever API shape is used, tenant must be resolved server-side from trusted identity/configuration and resource ownership must be checked.
```

## 7. Database Isolation Patterns

### 7.1 Row-Level Tenant Column

Typical table:

```sql
create table quote (
    tenant_id varchar(100) not null,
    id uuid not null,
    state varchar(50) not null,
    account_id varchar(100) not null,
    version int not null,
    created_at timestamptz not null,
    primary key (tenant_id, id)
);
```

Composite primary key forces tenant-aware joins.

This is better than:

```sql
primary key (id)
```

with tenant merely as ordinary column.

Tenant-aware foreign key:

```sql
create table quote_item (
    tenant_id varchar(100) not null,
    id uuid not null,
    quote_id uuid not null,
    product_offering_id varchar(100) not null,
    primary key (tenant_id, id),
    foreign key (tenant_id, quote_id) references quote (tenant_id, id)
);
```

This prevents accidental cross-tenant relationship.

### 7.2 PostgreSQL Row-Level Security

PostgreSQL supports row security policies.
RLS can be an additional defense layer.

Potential benefit:

```text
Even if application query misses tenant predicate, database policy may deny rows.
```

Potential risk:

- operational complexity,
- session variable correctness,
- superuser/bypass behavior,
- migration/backfill interactions,
- harder debugging,
- performance considerations.

RLS is not a replacement for application-level tenant modelling.
It is defense in depth.

### 7.3 Schema/Database Per Tenant

Separate schema/database reduces accidental row leakage but increases operational complexity.

Key questions:

- How are migrations applied to all tenants?
- How is schema drift detected?
- How are connection pools routed?
- How are backup/restore operations done?
- How are cross-tenant admin operations governed?
- How are customer-specific versions handled?

## 8. Repository and MyBatis Tenant Discipline

Every tenant-scoped repository method should require tenant context.

Bad:

```java
Optional<QuoteRecord> findById(UUID quoteId);
```

Better:

```java
Optional<QuoteRecord> findByTenantIdAndId(String tenantId, UUID quoteId);
```

Bad MyBatis mapper:

```xml
<select id="findQuote" resultMap="QuoteMap">
  SELECT * FROM quote WHERE id = #{quoteId}
</select>
```

Better:

```xml
<select id="findQuote" resultMap="QuoteMap">
  SELECT *
  FROM quote
  WHERE tenant_id = #{tenantId}
    AND id = #{quoteId}
</select>
```

For state-changing commands:

```xml
<update id="updateQuoteState">
  UPDATE quote
  SET state = #{newState},
      version = version + 1,
      updated_at = now()
  WHERE tenant_id = #{tenantId}
    AND id = #{quoteId}
    AND version = #{expectedVersion}
</update>
```

Rule:

```text
Tenant ID should not be optional in tenant-scoped data access methods.
```

Static review tactic:

Search for:

```text
findById(
WHERE id =
UPDATE quote SET
DELETE FROM
SELECT * FROM
```

Then verify tenant predicate.

## 9. Cache Isolation

Cache keys must include tenant.

Bad:

```text
catalog:offering:OFFER-123
quote:QUOTE-123
price-rule:RULE-7
```

Better:

```text
tenant:{tenantId}:catalog:offering:{offeringId}:version:{version}
tenant:{tenantId}:quote:{quoteId}
tenant:{tenantId}:price-rule:{ruleId}:version:{version}
```

Cache failure modes:

- tenant A sees tenant B's catalog offering,
- customer-specific price rule reused across tenants,
- feature flag cached without tenant dimension,
- permission cache shared across tenants,
- quote calculation uses stale agreement config,
- cache warmup loads all tenants without isolation.

Mitigations:

- tenant prefix in every key,
- typed cache key builders,
- cache tests for cross-tenant collision,
- TTL aligned with policy risk,
- explicit invalidation on config/catalog publish,
- deny or fallback safely on cache corruption.

Code shape:

```java
public record CacheKey(String value) {
    public static CacheKey tenantCatalogOffering(String tenantId, String offeringId, int version) {
        return new CacheKey("tenant:" + tenantId + ":catalog:offering:" + offeringId + ":version:" + version);
    }
}
```

Avoid ad-hoc string concatenation scattered across services.

## 10. Kafka and Event Tenant Isolation

Events must carry tenant context.

Typical event envelope:

```json
{
  "eventId": "...",
  "eventType": "QuoteApproved",
  "tenantId": "tenant-a",
  "aggregateType": "Quote",
  "aggregateId": "quote-123",
  "aggregateVersion": 8,
  "correlationId": "...",
  "causationId": "...",
  "occurredAt": "2026-07-08T10:00:00Z",
  "payload": {}
}
```

Partitioning options:

| Partition key | Pros | Cons |
|---|---|---|
| Tenant ID | Tenant-local ordering, easier tenant isolation. | Hot tenant can create partition skew. |
| Aggregate ID | Quote/order ordering. | Tenant events spread; tenant-local replay harder. |
| Tenant + aggregate hash | Good balance. | Requires clear convention. |

Shared topics vs tenant topics:

### Shared topic

```text
quote-events
```

Pros:

- simpler topic management,
- easier global consumers,
- less operational overhead.

Cons:

- consumers must enforce tenant filtering,
- risk of cross-tenant processing,
- retention/replay per tenant harder.

### Tenant-specific topics

```text
tenant-a.quote-events
```

Pros:

- stronger isolation,
- tenant-specific retention/replay possible,
- blast radius reduction.

Cons:

- topic explosion,
- operational complexity,
- harder fleet-wide consumers.

Internal verification checklist:

- Are topics shared or tenant-specific?
- Is tenant ID mandatory in event envelope?
- Is partition key tenant-aware?
- Are consumers allowed to process all tenants?
- Is replay tenant-scoped?
- Are DLQs tenant-safe?

## 11. Search, Reporting, and Export Isolation

Search/report/export paths are frequent leakage points.

Examples:

- global quote search omits tenant predicate,
- export job accepts account ID but not tenant ID,
- reporting read model aggregates multiple tenants,
- support dashboard shows customer names across tenants,
- CSV export includes hidden columns,
- BI connector has broader access than application.

Rules:

```text
Search must be tenant-scoped by default.
Export must be tenant-scoped and audited.
Reporting must classify whether it is tenant-local, fleet-level, or support-only.
```

Export checklist:

- tenant ID derived from trusted context,
- resource scope verified,
- PII/commercial sensitivity classified,
- export reason/audit required,
- generated file stored with tenant boundary,
- download authorization checked,
- retention/cleanup defined.

## 12. Logs, Metrics, and Traces

Observability must not become a leakage channel.

Logs may accidentally contain:

- customer names,
- account IDs,
- quote line items,
- negotiated prices,
- discount values,
- agreement terms,
- JWT claims,
- PII,
- full request/response bodies.

Guidelines:

- log tenant ID as routing/debug dimension if allowed,
- avoid full payload logs,
- mask sensitive fields,
- hash or tokenize identifiers where needed,
- control access to logs by support role,
- define retention per deployment/customer requirement,
- avoid high-cardinality tenant metrics if telemetry backend cannot handle it.

Metrics:

```text
quote_created_total{tenant="..."}
```

May be useful internally, but can be high-cardinality and sensitive.
Consider aggregation or controlled dashboards.

Trace baggage:

- include correlation ID,
- include tenant ID if policy allows,
- avoid customer/account names,
- avoid JWT or sensitive attributes.

## 13. Customer-Specific Configuration

Customer-specific configuration is unavoidable in enterprise products.

Examples:

- approval thresholds,
- discount limits,
- product eligibility rules,
- catalog visibility,
- pricing formula variants,
- order decomposition rules,
- downstream endpoint credentials,
- feature flags,
- workflow steps,
- notification templates,
- SLA/timeouts,
- adapter transformation mappings.

The risk is uncontrolled customization.

Bad model:

```text
if (tenantId.equals("customer-x")) {
    special behavior
}
```

This creates configuration debt.

Better model:

```text
Versioned, validated, audited configuration selected by tenant and effective date.
```

Configuration should have:

- schema,
- validation,
- owner,
- version,
- effective date,
- environment scope,
- audit history,
- rollout plan,
- rollback plan,
- test coverage,
- observability.

## 14. Configuration as Data vs Code

### Configuration as Data

Example:

```yaml
approvalPolicy:
  version: 17
  effectiveFrom: "2026-07-01T00:00:00Z"
  thresholds:
    - role: SALES_MANAGER
      maxDiscountPct: 15
      maxContractValue: 100000
    - role: FINANCE_APPROVER
      maxDiscountPct: 40
      maxContractValue: 1000000
  makerCheckerRequired: true
```

Pros:

- customer-specific without code deployment,
- auditable,
- testable with fixtures,
- can be versioned/effective-dated.

Cons:

- configuration language can become programming language,
- validation complexity,
- runtime failure if invalid config deployed,
- harder debugging if config not visible in traces.

### Configuration as Code

Pros:

- strongly typed,
- normal CI review,
- easier refactoring,
- good for complex behavior.

Cons:

- deployment required,
- customer-specific branches/conditionals risk,
- slower business changes,
- codebase clutter.

Practical rule:

```text
Use data configuration for stable variation points.
Use code for complex algorithmic behavior.
Do not use configuration to hide unbounded custom code.
```

## 15. Feature Flags and Tenant Flags

Feature flags are powerful and dangerous.

Use cases:

- gradual rollout,
- customer pilot,
- kill switch,
- migration toggle,
- behavior switch for compatibility,
- emergency mitigation.

Risks:

- flag explosion,
- forgotten flags,
- inconsistent behavior across services,
- flags used as permanent customer forks,
- flag evaluated differently in UI/API/worker,
- missing flag in event consumer,
- impossible test matrix.

Flag metadata should include:

- owner,
- purpose,
- type: release/experiment/ops/permission/migration,
- tenant scope,
- default value,
- rollout plan,
- expiry/removal date,
- audit history,
- test cases.

For enterprise systems, permanent customer behavior should usually graduate from feature flag to explicit configuration or product capability.

## 16. Config Versioning and Effective Dating

Quote/order workflows are long-lived.
A quote may be created under one configuration and accepted under another.
An order may be decomposed under one rule version and fulfilled after another version is published.

Therefore, configuration versioning matters.

Questions:

- Should a quote use config version from creation time?
- Should pricing re-evaluate using latest config?
- Should approval policy be snapshot at submission time?
- Should order decomposition use quote-time catalog or order-time catalog?
- What changes invalidate prior approval?
- Can support reconstruct what config was used?

Pattern:

```text
For commercial decisions, snapshot or reference exact config version.
For operational routing, use policy-defined current version unless workflow snapshot is required.
```

Example fields:

```sql
alter table quote add column pricing_policy_version varchar(100);
alter table quote add column approval_policy_version varchar(100);
alter table product_order add column decomposition_policy_version varchar(100);
```

But do not add version fields blindly.
First define reconstruction requirements.

## 17. Secrets Per Tenant

Enterprise integrations often require tenant/customer-specific secrets:

- CRM credentials,
- billing API credentials,
- fulfillment gateway certificates,
- OAuth client secrets,
- mTLS keys,
- webhook signing secrets,
- SFTP keys,
- database credentials for dedicated deployments.

Secrets must not be stored as ordinary config.

Controls:

- secret manager or Kubernetes Secret with encryption policy appropriate to deployment,
- access limited by service identity,
- rotation procedure,
- audit access,
- no secret in logs/traces/errors,
- no secret in Git unless encrypted/sealed according to approved process,
- per-tenant secret naming convention,
- incident process for leaked secret.

Internal verification checklist:

- Where are secrets stored?
- How are secrets rotated?
- Are tenant secrets shared across environments?
- Are secrets exposed to all pods or only needed services?
- Are webhook signatures verified per tenant?
- Are credentials included in support bundles/logs?

## 18. Kubernetes and Runtime Isolation

If tenants share Kubernetes cluster/namespace, isolation must be intentional.

Kubernetes namespaces provide a scope for names and policies, but they are not a complete security boundary by themselves.

Runtime concerns:

- namespace per environment/customer,
- network policies,
- service account permissions,
- secret scoping,
- config map scoping,
- ingress routing,
- pod security settings,
- resource quotas,
- noisy neighbor control,
- observability access,
- backup/restore boundary.

Dedicated deployment may use:

```text
customer namespace + customer database + customer secrets + customer ingress
```

Shared deployment may use:

```text
shared namespace + tenant-aware app + shared database + tenant-aware config
```

Each model must be documented.

Internal verification checklist:

- Are tenants separated by namespace?
- Are network policies enabled?
- Are secrets tenant-scoped?
- Are service accounts least-privileged?
- Are resource quotas defined?
- Can support tools access all tenants?
- Is ingress tenant routing trusted?

## 19. Data Residency and Environment Boundary

Enterprise customers may require:

- region-specific data storage,
- no cross-border transfer,
- customer-managed encryption keys,
- dedicated environments,
- on-prem deployment,
- air-gapped deployment,
- restricted support access,
- audit export,

- logging platform,

- observability vendor,


## 20. Migration and Backfill Safety

Migration/backfill scripts are high-risk for tenant isolation.

Bad script:

```sql
update quote set approval_policy_version = 'v2' where approval_policy_version is null;
```

Maybe correct globally.
Maybe disastrous if tenants have different policies.

Safer approach:

```sql
update quote q
set approval_policy_version = p.default_policy_version
from tenant_policy_defaults p
where q.tenant_id = p.tenant_id
  and q.approval_policy_version is null;
```

Backfill job must include:

- tenant batching,
- dry run count per tenant,
- audit log,
- progress checkpoint,
- tenant-specific error reporting,
- rollback/repair plan,
- performance guardrails,
- customer upgrade constraints.

Migration PR review must ask:

```text
Does this script update all tenants intentionally?
If yes, is that documented and approved?
If not, where is the tenant predicate?
```

## 21. Admin and Support Tooling

Support teams often need cross-tenant visibility.
That is legitimate but dangerous.

Admin tools should have:

- separate authentication/authorization,
- explicit tenant selection,
- reason/ticket reference,
- least privilege,
- read vs write separation,
- break-glass workflow,
- session recording/logging if required,
- strong audit trail,
- masking of sensitive fields,
- protection against accidental all-tenant operations.

Dangerous admin UI:

```text
Search quote by ID globally and open first match.
```

Better:

```text
Require tenant/customer context first.
Then search within tenant.
Cross-tenant search requires elevated permission and reason.
```

For repair actions, default to dry run.

## 22. Testing Tenant Isolation

Tenant isolation requires explicit negative tests.

Unit tests:

- tenant context resolver,
- cache key builder,
- policy evaluation,
- config selection,
- feature flag selection.

Integration tests:

- tenant A cannot read tenant B quote,
- tenant A cannot update tenant B order,
- tenant A event does not update tenant B projection,
- cache values do not collide,
- search/export tenant filter enforced,
- migration/backfill respects tenant policy,
- admin action requires elevated permission and reason.

Property-style test idea:

```text
For any tenant A and tenant B where A != B,
commands issued under tenant A must not mutate resources owned by tenant B.
```

Test data should use two tenants in every integration test suite.

Bad test setup:

```text
Only one tenant exists in test DB.
```

This cannot catch missing tenant predicates.

Better baseline fixture:

```text
tenant-a:
  quote-a-1
  account-a-1
  catalog offering X with price 100

tenant-b:
  quote-b-1
  account-b-1
  catalog offering X with price 200
```

Same IDs across tenants can expose incorrect unique-key/cache assumptions.

Logs should capture:

- tenant ID,
- actor,
- action,
- resource type,
- resource ID,
- decision/result,
- correlation ID,
- config version,
- policy version.

For privacy/security, define which tenant/customer identifiers are safe to expose in shared observability tools.

Alert candidates:

- API request missing tenant context,
- repository call without tenant context if detectable,
- spike in cross-tenant denied attempts,
- admin cross-tenant export,
- config fallback used for tenant-specific policy,
- all-tenant migration job started outside maintenance window.

## 24. Failure Modes

### Missing Tenant Predicate

```text
A repository method queries by quote ID only.
```

Detection:

- cross-tenant integration test,
- SQL review,
- query audit,
- static analysis.

Mitigation:

- tenant-required repository APIs,
- composite primary keys,
- RLS defense-in-depth,
- negative tests.

### Cache Key Collision

```text
catalog offering ID shared across tenants but cache key omits tenant.
```

Detection:

- cross-tenant cache tests,
- telemetry showing unexpected config version,
- customer complaint.

Mitigation:

- typed tenant-aware cache keys,
- cache namespace isolation,
- safe invalidation.

### Config Drift

```text
Tenant production config differs from expected Git/config registry state.
```

Detection:

- drift detection job,
- config checksum dashboard,
- deployment audit.

Mitigation:

- GitOps/config registry,
- versioned config,
- rollout approval,
- environment promotion discipline.

### Support Tool Overreach

```text
Support user exports all tenant quotes accidentally.
```

Detection:

- export audit,
- anomaly detection,
- access review.

Mitigation:

- tenant-first UI,
- elevated permission,
- reason/ticket required,
- row limits,
- approval for bulk export.

### Event Misrouting

```text
Tenant B consumer processes tenant A event.
```

Detection:

- event tenant validation,
- projection consistency check,
- reconciliation.

Mitigation:

- tenant-aware event envelope,
- consumer allowlist,
- partition/topic strategy,
- idempotent validation.

## 27. Senior Engineer Mental Model

A senior engineer reviewing tenant-sensitive changes asks:

```text
What is the tenant boundary here?
Where does tenant context come from?
Can it be spoofed?
Is tenant enforced in API, domain, DB, cache, event, and admin tooling?
What happens in batch/replay/migration paths?
Can tenant-specific configuration drift?
Can we reconstruct which config was used for a quote/order?
Could support tooling accidentally cross tenant boundary?
Do tests include at least two tenants?
Does this design work for SaaS, dedicated, and on-prem deployments?
```

Tenant isolation is not a security feature you add later.
It is an invariant that shapes the system.

If you cannot describe how tenant context flows through a request, event, job, cache, and repair operation, you do not yet understand the system enough to safely change it.
