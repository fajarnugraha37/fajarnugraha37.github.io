# Part 037 — MyBatis Data Access Layer for Enterprise Java Systems

> Core idea: MyBatis gives you explicit SQL power.  
> That power is valuable in enterprise systems only when the data access boundary is disciplined, testable, transaction-aware, tenant-safe, and reviewed as part of the domain design.

In Quote & Order systems, data access is not a boring infrastructure detail.

It decides whether the system can safely:

- load a quote aggregate without silent data loss,
- persist state transitions without race conditions,
- enforce tenant isolation on every query,
- handle approval/version checks atomically,
- write outbox events in the same transaction as state changes,
- avoid N+1 query explosions in quote/order screens,
- support large customer datasets,
- keep SQL reviewable by senior engineers,
- make production debugging possible.

MyBatis is especially useful when the application needs control over SQL. That is common in enterprise CPQ/order systems because the queries are often domain-specific, performance-sensitive, and difficult to express cleanly through generic ORM abstractions.

But MyBatis does not protect the system from bad SQL, poor transaction boundaries, missing tenant predicates, over-broad dynamic SQL, hidden N+1 patterns, or mapper methods that bypass aggregate invariants.

This part is about how to use MyBatis as a serious engineering tool.

## 2. Mental Model: MyBatis Is a SQL Boundary, Not a Domain Boundary

A common mistake is to treat a MyBatis mapper as the repository, the domain service, and the query service all at once.

That creates code like this:

```text
Controller -> Mapper -> SQL -> DB
```

This is dangerous because the application can bypass:

- command validation,
- lifecycle state guards,
- authorization checks,
- tenant scoping,
- optimistic locking,
- audit/outbox writes,
- business-level error mapping,
- domain event creation.

A better mental model is:

```text
API/controller
  -> application service / command handler
    -> domain policy / aggregate logic
      -> repository port
        -> MyBatis mapper
          -> SQL
            -> PostgreSQL
```

For read-only query screens, the flow can be intentionally different:

```text
API/controller
  -> query service
    -> read mapper
      -> SQL projection
        -> PostgreSQL
```

The key distinction:

- **Command path** protects business invariants.
- **Query path** optimizes read shape.

Do not force every read through a heavy aggregate. Do not let writes bypass the aggregate.

## 3. Why MyBatis Fits Enterprise Quote & Order Workloads

MyBatis is a good fit when SQL needs to be explicit.

Quote & Order workloads often include:

- quote search with many optional filters,
- order list pagination by customer/account/status/date,
- approval queue queries,
- state transition updates with optimistic locking,
- worker queries using `FOR UPDATE SKIP LOCKED`,
- complex joins for operational dashboards,
- batch backfill jobs,
- outbox/inbox processing,
- reporting-adjacent operational projections,
- customer-specific integration lookup,
- hierarchy loading for quote items or order items.

In these situations, explicit SQL is not a weakness. It is often the only practical way to reason about:

- indexes,
- query plans,
- lock behavior,
- result set size,
- projection shape,
- transaction duration,
- tenant predicates,
- database-specific features.

The trade-off is clear:

| Choice | Benefit | Cost |
|---|---|---|
| MyBatis explicit SQL | High control and performance transparency | More SQL discipline required |
| Full ORM | Less SQL boilerplate for simple CRUD | Hidden SQL and accidental loading risk |
| JDBC template | Maximum directness | More manual mapping and boilerplate |
| jOOQ-style DSL | Type-safe SQL construction | Tooling/model generation complexity |

For a domain-heavy system, MyBatis works best when SQL is treated as part of the design, not as incidental plumbing.

## 4. The Data Access Boundary You Want

A production-grade module should usually separate these concerns:

```text
quote/
  application/
    AcceptQuoteCommandHandler.java
    SearchQuotesQueryHandler.java
  domain/
    Quote.java
    QuoteState.java
    QuotePolicy.java
  persistence/
    QuoteRepository.java
    MyBatisQuoteRepository.java
    QuoteMapper.java
    QuoteMapper.xml
    QuoteRecord.java
    QuoteItemRecord.java
    QuoteSearchRow.java
```

### 4.1 Mapper interface

The mapper interface is close to SQL.

```java
@Mapper
public interface QuoteMapper {
    QuoteRecord findQuoteForUpdate(
        @Param("tenantId") String tenantId,
        @Param("quoteId") UUID quoteId
    );

    List<QuoteItemRecord> findQuoteItems(
        @Param("tenantId") String tenantId,
        @Param("quoteId") UUID quoteId
    );

    int updateQuoteState(
        @Param("tenantId") String tenantId,
        @Param("quoteId") UUID quoteId,
        @Param("expectedVersion") long expectedVersion,
        @Param("newState") String newState,
        @Param("newVersion") long newVersion,
        @Param("updatedBy") String updatedBy
    );
}
```

The mapper should not decide what state transition is legal. It should execute persistence operations requested by the repository/application layer.

### 4.2 Repository implementation

The repository coordinates mapping from records to domain objects.

```java
public final class MyBatisQuoteRepository implements QuoteRepository {
    private final QuoteMapper quoteMapper;

    public Quote loadForUpdate(TenantId tenantId, QuoteId quoteId) {
        QuoteRecord quote = quoteMapper.findQuoteForUpdate(tenantId.value(), quoteId.value());
        if (quote == null) {
            throw new QuoteNotFoundException(quoteId);
        }

        List<QuoteItemRecord> items = quoteMapper.findQuoteItems(tenantId.value(), quoteId.value());
        return QuoteHydrator.fromRecords(quote, items);
    }

    public void saveStateTransition(Quote quote, Actor actor) {
        int updated = quoteMapper.updateQuoteState(
            quote.tenantId().value(),
            quote.id().value(),
            quote.previousVersion(),
            quote.state().name(),
            quote.version(),
            actor.id()
        );

        if (updated != 1) {
            throw new ConcurrentQuoteModificationException(quote.id());
        }
    }
}
```

The repository can enforce persistence expectations, but it should not become a god object containing all business logic.

### 4.3 Query service projection

Read models can be optimized separately.

```java
public interface QuoteSearchMapper {
    List<QuoteSearchRow> searchQuotes(QuoteSearchFilter filter);
}
```

This avoids loading large quote aggregates just to render a list page.

## 5. Command Mapper vs Query Mapper

Do not mix write-oriented aggregate persistence and read-oriented screen projections in one mapper just because they hit the same table.

Use this split:

```text
Command mapper:
- load aggregate for update
- insert quote
- update state with expected version
- insert audit entry
- insert outbox event

Query mapper:
- search quote list
- load approval queue
- load order dashboard
- load operational projection
```

Why this matters:

- command methods need strict tenant and version checks,
- query methods need performance-focused projections,
- command SQL should be boring and safe,
- query SQL can be more complex but should never mutate,
- test strategy differs.

A good naming convention makes intent visible:

```text
QuoteCommandMapper.updateQuoteStateIfVersionMatches(...)
QuoteQueryMapper.searchQuoteSummaries(...)
OrderWorkerMapper.claimPendingOutboxBatch(...)
ApprovalQueueMapper.findPendingApprovals(...)
```

Bad names hide risk:

```text
QuoteMapper.update(...)
QuoteMapper.getData(...)
QuoteMapper.process(...)
QuoteMapper.save(...)
```

## 6. Result Mapping: Be Explicit About Shape

MyBatis supports `resultType` for simple mappings and `resultMap` for more complex mappings. The official documentation describes result maps as one of MyBatis' most powerful features, especially for difficult mapping cases.

Use simple result types for flat projection rows:

```xml
<select id="searchQuoteSummaries" resultType="com.example.quote.QuoteSummaryRow">
  SELECT
    q.id,
    q.quote_number AS quoteNumber,
    q.state,
    q.customer_name AS customerName,
    q.updated_at AS updatedAt
  FROM quote q
  WHERE q.tenant_id = #{tenantId}
  ORDER BY q.updated_at DESC, q.id DESC
  LIMIT #{limit}
</select>
```

Use result maps when the mapping is not trivial:

```xml
<resultMap id="QuoteRecordMap" type="com.example.quote.persistence.QuoteRecord">
  <id property="id" column="id" />
  <result property="tenantId" column="tenant_id" />
  <result property="state" column="state" />
  <result property="version" column="version" />
  <result property="catalogVersion" column="catalog_version" />
  <result property="priceSnapshotId" column="price_snapshot_id" />
</resultMap>
```

For quote/order item hierarchies, be careful with large join-based nested result maps. They can produce row multiplication:

```text
quote x quote_item x quote_item_price x quote_item_characteristic
```

A single quote with 100 items, 5 prices per item, and 20 characteristics can produce 10,000 joined rows before mapping.

Sometimes the better approach is multiple simple queries inside one transaction:

```text
1. load quote header
2. load quote items
3. load item prices
4. load item characteristics
5. assemble in memory
```

This is not automatically an N+1 problem if each query is set-based and bounded.

Bad:

```text
for each quote item:
  query prices
  query characteristics
```

Better:

```text
query all prices where quote_id = ?
query all characteristics where quote_id = ?
```

## 7. Parameter Binding: `#{}` Is the Default; `${}` Is a Loaded Gun

Use `#{}` for values.

```xml
WHERE q.tenant_id = #{tenantId}
  AND q.id = #{quoteId}
```

This binds parameters through prepared statements.

Avoid `${}` for user input.

```xml
ORDER BY ${sortColumn}
```

This is unsafe unless `sortColumn` comes from a strict whitelist controlled by application code.

A safe pattern:

```java
public enum QuoteSortField {
    UPDATED_AT("q.updated_at"),
    CREATED_AT("q.created_at"),
    QUOTE_NUMBER("q.quote_number");

    private final String sqlExpression;
}
```

Then mapper receives only the validated SQL fragment from the enum, never raw request input.

```xml
ORDER BY ${sortExpression} ${sortDirection}, q.id DESC
```

This still deserves careful review because `${}` performs text substitution. Use it rarely and document why it is safe.

## 8. Tenant Isolation Must Be Visible in SQL

In multi-tenant enterprise systems, tenant scoping is not optional.

Every data access method must answer:

```text
Which tenant/customer boundary does this query enforce?
```

Good:

```xml
SELECT *
FROM quote
WHERE tenant_id = #{tenantId}
  AND id = #{quoteId}
```

Bad:

```xml
SELECT *
FROM quote
WHERE id = #{quoteId}
```

The bad query may pass all unit tests if IDs are globally unique in test data. It is still a security defect if the tenant boundary is part of the authorization model.

For write operations, tenant checks are equally important:

```xml
UPDATE quote
SET state = #{newState},
    version = #{newVersion},
    updated_by = #{updatedBy},
    updated_at = now()
WHERE tenant_id = #{tenantId}
  AND id = #{quoteId}
  AND version = #{expectedVersion}
```

A missing tenant predicate in `UPDATE` or `DELETE` is worse than a missing predicate in a read because it can corrupt another customer's data.

### Internal verification checklist

Check whether tenant isolation is enforced through:

- explicit `tenant_id` predicates,
- row-level security,
- schema/database per tenant,
- service-layer context injection,
- query interceptors,
- custom MyBatis plugin,
- repository convention,
- database constraints.

Do not assume. Verify.

## 9. Optimistic Locking With MyBatis

Quote and order state transitions should usually be protected by expected version updates.

```xml
<update id="acceptQuote">
  UPDATE quote
  SET state = 'ACCEPTED',
      version = version + 1,
      accepted_at = now(),
      accepted_by = #{actorId}
  WHERE tenant_id = #{tenantId}
    AND id = #{quoteId}
    AND state = 'APPROVED'
    AND version = #{expectedVersion}
</update>
```

The application must check the affected row count.

```java
int updated = quoteMapper.acceptQuote(command);
if (updated != 1) {
    throw new ConcurrentOrIllegalTransitionException(command.quoteId());
}
```

Do not ignore update counts.

This is one of the simplest ways to prevent:

- stale quote acceptance,
- double submit,
- approval bypass,
- lost update,
- two workers claiming the same task,
- order transition from an invalid prior state.

The SQL should include both technical and business guards:

```text
technical guard: version = expectedVersion
business guard: state = allowedPreviousState
security guard: tenant_id = tenantId
```

## 10. Pessimistic Locking and Worker Claims

Some workflows need row claiming.

Example: claim outbox records.

```xml
<select id="claimOutboxBatch" resultMap="OutboxRecordMap">
  SELECT id, aggregate_type, aggregate_id, event_type, payload
  FROM outbox_event
  WHERE status = 'PENDING'
    AND tenant_id = #{tenantId}
  ORDER BY created_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT #{batchSize}
</select>
```

The service should run this inside a transaction, mark rows as `PROCESSING`, commit, then publish or process according to the chosen relay pattern.

Be precise:

- `FOR UPDATE` locks selected rows.
- `SKIP LOCKED` helps concurrent workers avoid waiting on already-claimed rows.
- The transaction must be short.
- Long processing should not hold row locks while calling external systems.

Bad pattern:

```text
begin transaction
claim row
call external API for 30 seconds
update row
commit
```

Better pattern:

```text
transaction 1: claim row quickly
outside transaction: call external API or publish
transaction 2: mark result
```

The exact pattern depends on whether the side effect is idempotent and whether unknown outcome is acceptable.

## 11. Dynamic SQL: Useful, But Easy to Abuse

Search screens often need dynamic filters.

```xml
<select id="searchQuotes" resultType="QuoteSearchRow">
  SELECT q.id, q.quote_number, q.state, q.customer_name, q.updated_at
  FROM quote q
  WHERE q.tenant_id = #{tenantId}
  <if test="state != null">
    AND q.state = #{state}
  </if>
  <if test="customerNamePrefix != null">
    AND q.customer_name ILIKE CONCAT(#{customerNamePrefix}, '%')
  </if>
  <if test="updatedAfter != null">
    AND q.updated_at &gt;= #{updatedAfter}
  </if>
  ORDER BY q.updated_at DESC, q.id DESC
  LIMIT #{limit}
</select>
```

Dynamic SQL is acceptable when:

- every optional predicate is indexed or intentionally unindexed,
- every path includes tenant scoping,
- `ORDER BY` is whitelisted,
- maximum limit is enforced,
- result size is bounded,
- the generated SQL is tested for important combinations,
- query plans are reviewed for hot paths.

Dynamic SQL becomes dangerous when:

- it produces many unreviewed query shapes,
- it hides table scans behind optional filters,
- it uses string substitution for user input,
- it mixes business decisions into SQL fragments,
- it becomes unreadable XML logic.

If a mapper XML starts looking like a programming language, move decision logic into Java and pass a simpler filter object.

## 12. Type Handlers and Value Objects

A production domain should avoid primitive obsession.

You may have value objects like:

```java
record TenantId(String value) {}
record QuoteId(UUID value) {}
record Money(BigDecimal amount, String currency) {}
enum QuoteState { DRAFT, PENDING_APPROVAL, APPROVED, ACCEPTED, ORDERED, EXPIRED }
```

MyBatis can map custom types through type handlers.

Use type handlers when they clarify:

- domain-specific IDs,
- enums with stable database values,
- money/currency representation,
- JSONB payload wrappers,
- encrypted fields,
- value objects that must not leak as raw strings.

Be careful with enum mapping.

Bad:

```text
store ordinal 3
```

Better:

```text
store stable code 'PENDING_APPROVAL'
```

If state names are part of persisted business history, renaming enum constants is a migration. Treat it as such.

## 13. Mapping Domain State vs Persistence State

Do not assume the database record is the domain object.

Persistence record:

```java
public record QuoteRecord(
    UUID id,
    String tenantId,
    String state,
    long version,
    String catalogVersion,
    UUID priceSnapshotId,
    Instant createdAt,
    Instant updatedAt
) {}
```

Domain object:

```java
public final class Quote {
    private final QuoteId id;
    private final TenantId tenantId;
    private QuoteState state;
    private Version version;
    private CatalogSnapshotRef catalogSnapshot;
    private PriceSnapshotRef priceSnapshot;
    private final List<QuoteItem> items;

    public void accept(Actor actor, Clock clock) {
        ensureState(QuoteState.APPROVED);
        ensurePriceStillValid(clock);
        this.state = QuoteState.ACCEPTED;
        this.version = this.version.next();
        recordDomainEvent(new QuoteAccepted(id, actor.id(), clock.instant()));
    }
}
```

The mapper should not hydrate a half-valid domain object directly if invariants require reconstruction logic.

Use a hydrator/factory where needed:

```java
Quote quote = QuoteHydrator.fromRecords(header, items, prices, characteristics);
```

This makes invariant reconstruction explicit.

## 14. Outbox Writes Belong in the Same Transaction

For command paths, state change and event creation must be atomic.

```java
@Transactional
public void acceptQuote(AcceptQuoteCommand command) {
    Quote quote = quoteRepository.loadForUpdate(command.tenantId(), command.quoteId());
    quote.accept(command.actor(), clock);

    quoteRepository.saveStateTransition(quote, command.actor());
    outboxRepository.appendAll(quote.pullDomainEvents());
}
```

The MyBatis mapper for outbox can be boring:

```xml
<insert id="insertOutboxEvent">
  INSERT INTO outbox_event (
    id,
    tenant_id,
    aggregate_type,
    aggregate_id,
    aggregate_version,
    event_type,
    payload,
    status,
    created_at
  ) VALUES (
    #{id},
    #{tenantId},
    #{aggregateType},
    #{aggregateId},
    #{aggregateVersion},
    #{eventType},
    CAST(#{payloadJson} AS jsonb),
    'PENDING',
    now()
  )
</insert>
```

Critical invariant:

```text
If the quote state changed, the corresponding event must be durable.
If the transaction rolled back, neither state nor event exists.
```

Do not publish Kafka events directly before the database commit.

## 15. Query Method Design: Name the Business Access Pattern

Bad method names:

```java
List<QuoteRow> find(Map<String, Object> params);
List<OrderRow> query(Filter filter);
QuoteRecord get(UUID id);
```

Better method names:

```java
List<QuoteSearchRow> searchQuotesForSalesWorkspace(QuoteSearchFilter filter);
List<ApprovalQueueRow> findApprovalQueueForApprover(ApprovalQueueFilter filter);
List<OrderWorkItemRow> findFulfillmentWorkItemsReadyToClaim(WorkerFilter filter);
QuoteRecord findQuoteHeaderForStateTransition(TenantId tenantId, QuoteId quoteId);
```

Names should expose:

- consumer/use case,
- consistency expectation,
- locking expectation,
- result shape,
- risk level.

For example, these two methods should not share a vague name:

```java
QuoteRecord findQuoteForRead(...);
QuoteRecord findQuoteForUpdate(...);
```

One is a normal read. The other may acquire locks and belongs in a transaction.

## 16. Pagination: Offset Is Not Always Safe

Offset pagination is easy:

```sql
ORDER BY updated_at DESC
LIMIT 50 OFFSET 10000
```

But large offsets can become expensive because the database still needs to walk past skipped rows.

For high-volume quote/order list pages, consider keyset pagination:

```xml
<select id="searchQuotesAfterCursor" resultType="QuoteSearchRow">
  SELECT q.id, q.quote_number, q.state, q.updated_at
  FROM quote q
  WHERE q.tenant_id = #{tenantId}
    <if test="cursorUpdatedAt != null and cursorId != null">
      AND (q.updated_at, q.id) &lt; (#{cursorUpdatedAt}, #{cursorId})
    </if>
  ORDER BY q.updated_at DESC, q.id DESC
  LIMIT #{limit}
</select>
```

This requires a matching index:

```sql
CREATE INDEX quote_tenant_updated_id_idx
ON quote (tenant_id, updated_at DESC, id DESC);
```

Review pagination with the same seriousness as business logic because slow list endpoints often become production incidents.

## 17. Batch Operations

Batch operations show up in:

- quote item inserts,
- order item inserts,
- outbox event inserts,
- backfill jobs,
- migration support tools,
- reconciliation results.

Batching reduces round trips but increases transaction size.

A safe approach:

```text
1. Define max batch size.
2. Keep transaction duration bounded.
3. Avoid unbounded memory accumulation.
4. Check affected row count.
5. Emit metrics per batch.
6. Make batch operation resumable.
```

Do not batch blindly if each row represents a different business command with different failure semantics.

For example, batch inserting quote items during quote creation is usually fine. Batch accepting quotes is dangerous unless each acceptance is independently guarded and auditable.

## 18. Caching: Be Very Conservative

MyBatis supports local session cache and second-level cache settings. In enterprise quote/order systems, cache correctness is often harder than query performance.

Be cautious with cached data when:

- quote state changes frequently,
- pricing depends on time/effective date,
- catalog publish events invalidate behavior,
- tenant/customer-specific configuration exists,
- approval authority changes,
- order lifecycle changes are event-driven.

A stale cache can cause:

- stale price acceptance,
- invalid approval display,
- old catalog rule usage,
- duplicate processing,
- wrong tenant data exposure if cache key is incomplete.

Prefer explicit application-level caching with:

- tenant-aware keys,
- versioned catalog keys,
- invalidation semantics,
- metrics,
- safe TTL,
- clear owner.

Do not enable mapper-level second-level caching by habit.

## 19. Error Handling and SQL Exceptions

Raw SQL exceptions should not leak into API responses.

Map them into meaningful application errors:

| Persistence issue | Application meaning |
|---|---|
| unique constraint violation on idempotency key | duplicate command or replay |
| zero rows updated on optimistic update | concurrent modification or illegal transition |
| foreign key violation | invalid reference or stale data |
| serialization failure | retryable transaction conflict |
| lock timeout | contention or overloaded workflow |
| not-null violation | application bug or incomplete migration |

A good application service distinguishes:

```text
retryable conflict
business rejection
security denial
not found
unexpected infrastructure failure
```

Do not turn everything into HTTP 500.

## 20. Observability for Data Access

Data access observability should answer:

- Which query is slow?
- Which endpoint/command triggered it?
- Which tenant/customer is affected?
- Is this read path or write path?
- Is there lock wait?
- Is there connection pool starvation?
- Did a state update affect zero rows?
- Did a batch process partial data?
- Did an outbox insert happen with the state change?

Minimum useful metrics:

```text
mybatis.query.duration{mapper,statement,outcome}
mybatis.query.rows{mapper,statement}
db.transaction.duration{use_case,outcome}
db.optimistic_update.conflict{aggregate,state_transition}
db.lock_timeout{mapper,statement}
db.connection_pool.active
db.connection_pool.pending
```

Log fields should include:

```text
tenant_id
correlation_id
causation_id
aggregate_id
aggregate_type
command_id
mapper_statement
state_before
state_after
expected_version
actual_outcome
```

Never log sensitive payloads blindly.

## 21. Testing MyBatis Mappers

Mocking mapper interfaces is not enough. It only tests that Java calls a method.

For serious SQL, use integration tests with PostgreSQL-compatible behavior.

Test categories:

### 21.1 Mapper mapping tests

Verify columns map correctly:

```text
insert known row -> select -> assert fields
```

Catch:

- alias mismatch,
- null handling,
- enum mapping,
- timestamp precision issues,
- JSONB parsing issues.

### 21.2 State transition tests

Verify row count behavior:

```text
valid state + expected version -> update count 1
wrong state -> update count 0
wrong version -> update count 0
wrong tenant -> update count 0
```

### 21.3 Tenant isolation tests

Create same IDs or similar IDs across tenants where possible.

```text
query tenant A cannot read tenant B
update tenant A cannot mutate tenant B
```

### 21.4 Query plan tests for hot paths

For critical queries, capture `EXPLAIN` during review or performance test.

Do not overfit unit tests to exact planner output in small datasets, but do require query plan evidence for hot paths.

### 21.5 Dynamic SQL combination tests

For search filters, test important filter combinations:

- no optional filters,
- each filter independently,
- common combinations,
- worst-case broad query,
- invalid sort,
- max limit enforcement.

### 21.6 Concurrency tests

Use real database transactions to test:

- optimistic update conflict,
- row claiming,
- lock timeout behavior,
- duplicate idempotency key insert,
- outbox atomicity.

## 22. Failure Modes and Detection

| Failure mode | How it happens | Detection | Prevention |
|---|---|---|---|
| Missing tenant predicate | Query uses only ID | Cross-tenant test, SQL review | Mapper checklist, repository convention |
| SQL injection via `${}` | Raw sort/filter text substitution | Security test, code review | Whitelist only, prefer `#{}` |
| Ignored update count | Optimistic update returns 0 but service proceeds | Invariant test, production anomaly | Always assert affected rows |
| N+1 queries | Loop calls mapper per item | Trace/query count test | Set-based loading |
| Row multiplication | Huge join for nested graph | Slow query, memory spike | Multi-query assembly |
| Stale cache | Mapper cache or application cache wrong key | Inconsistent reads | Disable by default, version keys |
| Enum drift | Java enum rename without DB migration | Mapping failure, bad state | Stable DB codes |
| Lock held too long | External call inside transaction | Lock wait metrics | Short transaction boundary |
| Query plan regression | Changed SQL/index/data distribution | Slow query dashboard | Plan review, load test |
| Backfill overload | Batch mapper updates too much | DB CPU/IO spike | Chunking, throttling, resume |

## 23. Senior Engineer PR Review Checklist

When reviewing MyBatis changes, ask:

### Boundary

- Is this mapper used by command path, query path, worker path, or migration path?
- Is business logic kept outside mapper XML?
- Is aggregate invariant protected in application/domain layer?

### SQL safety

- Does every query include tenant scoping if required?
- Are all user-controlled values bound with `#{}`?
- Is every `${}` usage strictly whitelisted and documented?
- Is result size bounded?

### Correctness

- Does write SQL include expected version or allowed state where needed?
- Is affected row count checked?
- Are unique constraints used for idempotency where appropriate?
- Are null/default values compatible with migrations?

### Performance

- Is there a matching index for common predicates and ordering?
- Is pagination safe for large datasets?
- Is query shape stable and reviewable?
- Is there risk of row multiplication or N+1 queries?

### Transactions

- Is mapper called inside the correct transaction boundary?
- Is lock duration bounded?
- Are external calls outside DB transactions?
- Are outbox writes atomic with state changes?

### Testing

- Are mapper integration tests present?
- Are tenant isolation tests present?
- Are dynamic SQL combinations tested?
- Are concurrency/update-count cases tested?

### Observability

- Can this query be identified in logs/metrics?
- Are lock timeout/conflict outcomes visible?
- Does failure map to a meaningful application error?

## 26. Key Takeaways

- MyBatis is powerful because SQL is explicit.
- Explicit SQL is only safe when the boundary is disciplined.
- Mappers should not become domain services.
- Command and query paths deserve different mapper designs.
- Tenant scoping must be visible and tested.
- `#{}` should be the default; `${}` needs strict whitelist discipline.
- Affected row count is a correctness signal.
- Optimistic locking belongs in SQL and in application error handling.
- Outbox writes must be atomic with state changes.
- Mapper tests should use a real PostgreSQL-like database behavior.
- Senior review of SQL is architecture review, not just implementation review.
