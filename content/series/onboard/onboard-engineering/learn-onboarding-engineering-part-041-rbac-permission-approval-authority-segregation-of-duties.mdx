# Part 041 — RBAC, Permission Model, Approval Authority, and Segregation of Duties

> Core idea: authorization is not a boolean check around an endpoint.  
> In Quote & Order systems, authorization is business governance encoded as executable policy.

Authentication tells the system who the caller is.

Authorization answers a harder question:

```text
Can this actor perform this action on this resource,
inside this tenant/account/customer context,
at this lifecycle state,
with this commercial risk,
under this approval policy,
and should this decision be auditable later?
```

In an enterprise CPQ/order management product, authorization bugs are rarely small.
They can cause:

- cross-tenant quote exposure,
- unauthorized discount approval,
- quote acceptance without customer authority,
- order submission by wrong sales channel,
- cancellation by unauthorized operations user,
- approval bypass through API/UI inconsistency,
- support/admin override without evidence,
- commercial leakage because role membership was treated as approval authority,
- audit records that cannot prove who approved what and why.

The trap is to reduce authorization to code like this:

```java
if (currentUser.hasRole("SALES_MANAGER")) {
    approveQuote(quoteId);
}
```

That may be acceptable for a toy application.
For enterprise Quote & Order, it is incomplete.

A better authorization decision needs at least:

```text
subject:        user/service/admin actor
resource:       quote/order/customer/account/agreement
operation:      approve-discount / accept-quote / submit-order / cancel-order
context:        tenant, channel, account hierarchy, state, amount, margin, discount, region
policy:         role, authority limit, maker-checker, tenant scope, SoD constraint
obligation:     audit fields, reason code, approval evidence, maybe step-up auth
result:         permit / deny / require approval / require escalation
```

This part builds the mental model and implementation discipline for that.

## 1. Source Boundary and Fact Discipline

This part uses public security and access-control references for RBAC/ABAC and application authorization testing. It does not assume CSG's internal authorization model, identity provider, role naming, permission table, policy engine, approval engine, or tenant model.

Useful public references:

- NIST RBAC project: https://csrc.nist.gov/projects/role-based-access-control
- NIST SP 800-162 Attribute Based Access Control: https://csrc.nist.gov/pubs/sp/800/162/upd2/final
- OWASP Application Security Verification Standard: https://owasp.org/www-project-application-security-verification-standard/
- OWASP Authorization Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- OAuth 2.0 and JWT references from Part 040.

Important source-boundary rule:

> RBAC, ABAC, ReBAC, policy engines, and approval workflows are industry concepts.  
> The actual CSG implementation must be verified in codebase and internal docs.

Internal verification checklist:

- Where are roles defined?
- Where are permissions defined?
- Are permissions endpoint-based, action-based, resource-based, or workflow-based?
- Is tenant scope enforced in authorization, data access, or both?
- Are quote/order lifecycle transitions guarded by policy?
- Is approval authority separate from ordinary role membership?
- Are approval thresholds configurable per customer/tenant/agreement?
- Is maker-checker / segregation-of-duties implemented?
- Is support/admin override possible?
- Are override actions audited differently?
- Are authorization decisions logged or traceable?
- Are negative authorization tests present?

## 2. Authorization as Business Control, Not UI Entitlement

A common weak model:

```text
Role controls menu visibility.
Backend trusts the UI.
```

This fails immediately in enterprise APIs.

Any caller can bypass UI controls and call the API directly if they have a token, compromised client, integration credential, or misconfigured gateway.

Backend authorization must be authoritative.

UI permissions are for ergonomics:

- hide disabled actions,
- reduce user confusion,
- guide workflow,
- avoid unnecessary API calls.

Backend permissions are for security and business correctness:

- deny unauthorized action,
- enforce tenant/account boundary,
- enforce approval rules,
- protect commercial terms,
- preserve audit defensibility.

Rule:

```text
Every state-changing command must authorize in the backend using current server-side state.
```

For example, `ApproveQuote` must not rely on client-provided quote amount, discount, margin, account, or approval threshold.

The server must load authoritative data and evaluate policy against it.

## 3. RBAC Mental Model

Role-Based Access Control maps users to roles and roles to permissions.

Basic model:

```text
User -> Role -> Permission -> Operation
```

Example:

```text
alice -> Sales Manager -> quote.approve.discount
```

RBAC is useful because it simplifies administration.
Instead of assigning every permission to every user, enterprise admins assign roles.

But RBAC alone is usually insufficient for Quote & Order.

Why?

Because quote/order authorization depends on contextual business facts:

- tenant,
- account hierarchy,
- sales region,
- quote state,
- discount percentage,
- absolute contract value,
- margin impact,
- product family,
- agreement terms,
- whether the actor created the quote,
- whether another person already approved it,
- whether the customer requires custom delegation,
- whether the order is already in fulfillment.

RBAC says:

```text
Alice is a Sales Manager.
```

It does not automatically say:

```text
Alice can approve this 37% discount on this strategic account in this tenant,
when she created the quote herself, after the quote was repriced using stale catalog version.
```

For enterprise CPQ, RBAC is the base layer, not the complete model.

## 4. Permission Model: Prefer Business Actions Over Endpoints

Endpoint-based authorization is tempting:

```text
POST /quotes/{id}/approve -> requires ROLE_MANAGER
```

This is weak because business actions can be invoked through different interfaces:

- REST API,
- UI backend endpoint,
- batch job,
- workflow engine,
- admin tool,
- Kafka command consumer,
- internal service call,
- customer-specific adapter.

Better model:

```text
business permission: quote.approve_discount
operation: ApproveQuoteDiscount
resource: Quote
```

Then all entry points call the same application command:

```java
public ApprovalResult approveQuote(ApproveQuoteCommand command, ActorContext actor) {
    Quote quote = quoteRepository.getForUpdate(command.quoteId());

    authorizationService.requirePermission(
        actor,
        Permission.QUOTE_APPROVE_DISCOUNT,
        AuthorizationResource.quote(quote),
        AuthorizationContext.from(quote)
    );

    quote.approve(command.reason(), actor);
    quoteRepository.save(quote);
    auditWriter.writeQuoteApproved(quote, actor, command.reason());

    return ApprovalResult.approved(quote.id());
}
```

The endpoint should not be the policy owner.
The endpoint should be a transport adapter.

## 5. Authorization Decision Anatomy

A production-grade authorization decision contains five dimensions.

| Dimension | Example |
|---|---|
| Subject | User, service account, admin actor, integration client. |
| Resource | Quote, quote item, order, account, agreement, customer, product catalog. |
| Action | View, edit, price, approve, accept, submit, cancel, retry, repair. |
| Context | Tenant, state, amount, discount, margin, channel, region, environment. |
| Policy | RBAC, ABAC, ReBAC, approval threshold, SoD, feature flag, customer config. |

Example:

```text
Can user U approve quote Q?
```

Expanded:

```text
- Is U authenticated?
- Is U active?
- Is U assigned to tenant T?
- Does U have a role that can approve quotes?
- Does U have authority for account A?
- Is Q in PendingApproval?
- Did U create Q? If yes, maker-checker may deny.
- Is discount within U's limit?
- Is margin above floor?
- Does agreement require finance approval?
- Has quote price snapshot expired?
- Does this customer require two-level approval?
- Is U acting as delegated approver?
- Is this override path allowed?
- What evidence must be recorded?
```

This is why authorization belongs close to domain commands.

## 6. RBAC vs ABAC vs ReBAC vs Workflow Authorization

### RBAC

RBAC uses roles.

```text
SalesRep, SalesManager, PricingAdmin, FulfillmentOperator, SupportAdmin
```

Good for:

- coarse access,
- administration,
- UI entitlement,
- default permission bundles,
- onboarding/offboarding.

Weak for:

- context-heavy decisions,
- dynamic thresholds,
- account-specific authority,
- delegated approval,
- maker-checker,
- object relationship checks.

### ABAC

Attribute-Based Access Control evaluates attributes of subject, object, action, and environment.

Example:

```text
Permit approve_quote if:
  subject.role contains SalesManager
  and subject.tenant == quote.tenant
  and quote.discountPct <= subject.maxDiscountApprovalPct
  and quote.marginPct >= policy.minMarginPct
  and quote.state == PendingApproval
```

Good for:

- commercial rules,
- tenant/account scoping,
- risk-based decisions,
- environment-dependent policy,
- customer-specific policy.

Risk:

- policy becomes hard to reason about,
- attributes become stale,
- debug is difficult without decision trace,
- rule explosion if not governed.

### ReBAC

Relationship-Based Access Control checks relationships.

Example:

```text
User can approve quote if user is manager of quote owner
and quote account belongs to user's sales territory.
```

Good for:

- account teams,
- delegated authority,
- organization hierarchy,
- partner/channel access.

Risk:

- relationship graph freshness,
- recursive evaluation cost,
- difficult audit if graph changes after decision.

### Workflow Authorization

Workflow authorization depends on lifecycle step and prior actors.

Example:

```text
The person who created the quote cannot be the sole final approver.
```

Good for:

- approval flows,
- segregation of duties,
- maker-checker,
- multi-step governance.

Risk:

- hidden coupling between state machine and policy engine,
- bypass through alternate transition path,
- inconsistent UI/API behavior.

Practical enterprise model:

```text
RBAC for coarse permission.
ABAC for contextual policy.
ReBAC for account/organization relationship.
Workflow authorization for lifecycle and approval evidence.
```

## 7. Approval Authority Is Not the Same as Role

A role may grant the ability to participate in approval.
It should not always grant unlimited approval authority.

Weak model:

```text
SalesManager can approve all discounts.
```

Better model:

```text
SalesManager can approve quotes only if:
- quote belongs to same tenant,
- quote belongs to assigned sales region/account scope,
- quote is pending approval,
- discount <= manager threshold,
- margin >= required floor,
- manager did not create the quote,
- no higher-level approval requirement exists,
- approval reason is provided,
- approval evidence is persisted.
```

Approval authority should be modeled explicitly.

Possible authority dimensions:

| Dimension | Example |
|---|---|
| Discount limit | Up to 15%, 25%, 40%. |
| Contract value limit | Up to $100k, $1M, unlimited. |
| Margin floor | Cannot approve below 20% margin. |
| Product family | Can approve connectivity, not managed security. |
| Account scope | Can approve assigned accounts only. |
| Region | EMEA manager cannot approve APAC quote. |
| Customer segment | Enterprise vs SMB. |
| Agreement type | Special pricing agreement requires finance approval. |
| Lifecycle state | Can approve PendingApproval only. |

This belongs in policy, not hardcoded in controller.

## 8. Segregation of Duties and Maker-Checker

Segregation of duties prevents one actor from executing conflicting responsibilities.

In CPQ/order systems, common SoD constraints:

- creator cannot be final approver,
- sales rep cannot approve their own deep discount,
- pricing admin can configure price rules but not approve quote using unpublished rule,
- support admin can repair data only with approved ticket,
- fulfillment operator can retry task but not change commercial terms,
- developer/operator cannot manually update production quote without audit workflow.

Maker-checker pattern:

```text
Maker creates or proposes change.
Checker reviews and approves.
```

Example quote flow:

```text
Draft -> SubmitForApproval -> PendingApproval -> Approved -> Accepted
```

SoD invariant:

```text
A quote requiring approval cannot be finally approved only by the same actor who created or last materially changed the commercial terms.
```

Material changes may include:

- discount changed,
- price overridden,
- contract term changed,
- product bundle changed,
- customer/account changed,
- margin recalculated below threshold,
- agreement override applied.

Implementation consequence:

You need to persist actors and material-change history.

```sql
create table quote_material_change (
    id uuid primary key,
    quote_id uuid not null,
    changed_by varchar(255) not null,
    change_type varchar(100) not null,
    changed_at timestamptz not null,
    correlation_id varchar(100) not null
);
```

Then approval guard can evaluate:

```text
approver != lastMaterialCommercialChanger
```

But this is only a simplified example. Real policy may require two approvers, finance approver, or delegated approver.

## 9. Authorization Must Be State-Aware

An actor's permission may depend on the current lifecycle state.

Example:

| Action | Allowed state | Common guard |
|---|---|---|
| Edit quote | Draft / Rework | Actor can edit quote and quote not locked. |
| Submit for approval | Draft / Priced | Quote is valid and actor can submit. |
| Approve quote | PendingApproval | Actor has approval authority and SoD passes. |
| Accept quote | Approved | Customer/sales authority and quote not expired. |
| Convert to order | Accepted | Conversion not already done. |
| Cancel order | Captured/InProgress | Actor can cancel and downstream supports cancellation. |
| Retry fulfillment | Fallout/FailedTask | Actor can operate fallout and task is retryable. |
| Repair data | Controlled admin state | Approved incident/change ticket exists. |

Do not check authorization without loading current state.

Bad:

```java
@PreAuthorize("hasAuthority('quote.approve')")
@PostMapping("/quotes/{id}/approve")
void approve(@PathVariable UUID id) {
    quoteService.approve(id);
}
```

Better:

```java
@PostMapping("/quotes/{id}/approve")
QuoteResponse approve(@PathVariable UUID id, @RequestBody ApproveQuoteRequest request) {
    ActorContext actor = actorContextResolver.current();
    return quoteApplicationService.approve(new ApproveQuoteCommand(id, request.reason()), actor);
}
```

Inside application service:

```java
@Transactional
public QuoteResponse approve(ApproveQuoteCommand command, ActorContext actor) {
    Quote quote = quoteRepository.getForUpdate(command.quoteId());

    authorizationService.require(
        actor,
        Action.APPROVE_QUOTE,
        quote.toAuthorizationResource(),
        ApprovalContext.fromQuote(quote)
    );

    quote.approve(actor.userId(), command.reason());
    quoteRepository.save(quote);
    auditWriter.quoteApproved(quote, actor, command.reason());
    return mapper.toResponse(quote);
}
```

The annotation may still be useful as a coarse pre-check.
But it cannot replace domain-aware authorization.

## 10. Resource Scoping: Tenant, Account, Customer, Quote, Order

Enterprise authorization usually has several nested scopes.

```text
Tenant
  Customer
    Account hierarchy
      Agreement
        Quote
          Quote item
        Order
          Order item
```

Not every user with tenant access can access every resource in that tenant.

Example scopes:

| Scope | Meaning |
|---|---|
| Tenant scope | User belongs to tenant or customer deployment. |
| Customer scope | User can access specific customer entity. |
| Account scope | User can act on a billing/service/sales account. |
| Territory scope | User is assigned to region/market/segment. |
| Channel scope | Partner/channel user can access only their channel-originated quotes. |
| Resource ownership | User created or owns the quote. |
| Operational scope | User can operate fulfillment tasks for assigned queue. |

Authorization must define which scope applies per action.

Example:

```text
View quote:
  tenant + account visibility may be enough.

Edit quote:
  tenant + quote ownership/team membership + state guard.

Approve quote:
  tenant + account scope + approval authority + SoD.

Cancel order:
  tenant + operational role + lifecycle guard + downstream cancellation policy.

Repair data:
  production admin role + approved incident/change + dual control.
```

The dangerous shortcut is to check only `tenant_id`.
Tenant isolation is necessary but not sufficient.

## 11. Permission Naming and Granularity

Bad permission names are either too broad or too technical.

Bad examples:

```text
ADMIN
WRITE
QUOTE_API_POST
CAN_CLICK_BUTTON_7
```

Better examples:

```text
quote.view
quote.create
quote.edit_commercial_terms
quote.submit_for_approval
quote.approve_discount
quote.accept
quote.convert_to_order
order.view
order.submit
order.cancel
order.retry_fulfillment_task
order.resolve_fallout
catalog.publish
pricing.override_price
support.repair_quote_data
```

Guidelines:

- Name permissions after business actions.
- Avoid endpoint names.
- Avoid UI element names.
- Avoid overly broad wildcard permissions except for carefully governed admin roles.
- Separate view, mutate, approve, operate, and repair actions.
- Separate commercial changes from operational changes.
- Separate normal user actions from support/admin override actions.

Permission granularity trade-off:

| Too coarse | Too fine |
|---|---|
| Easier to administer but risky. | More precise but hard to manage. |
| Encourages overprivileged roles. | Creates policy sprawl. |
| Hidden business risk. | Hard to reason/debug. |

Aim for business-meaningful granularity.

## 12. Policy Engine or Code?

There are three common implementation models.

### 12.1 Hardcoded Authorization

```java
if (actor.hasRole("SALES_MANAGER") && quote.discountPct().compareTo(BigDecimal.valueOf(20)) <= 0) {
    return Permit;
}
```

Good for:

- simple systems,
- stable rules,
- low configuration need,
- easy debugging.

Bad for:

- customer-specific approval rules,
- dynamic authority limits,
- delegated authority,
- audit explanation,
- policy change without deployment.

### 12.2 Database-Driven Policy

Policy stored in tables:

```text
role_permission
approval_threshold
account_assignment
policy_rule
```

Good for:

- customer configuration,
- operational updates,
- admin UI,
- auditability.

Risks:

- schema becomes policy language accidentally,
- rules hard to test,
- partial updates can create inconsistent policy,
- permission cache staleness.

### 12.3 External Policy Engine

Examples in the industry include policy engines using declarative policy language or centralized authorization services.

Good for:

- centralized governance,
- consistent policy across services,
- separation of policy and application logic,
- decision trace.

Risks:

- latency and availability dependency,
- policy/application model mismatch,
- difficult local testing,
- operational complexity,
- policy versioning issues.

Practical rule:

```text
Do not adopt a policy engine to avoid domain modelling.
A policy engine needs a clean domain authorization model even more than hardcoded checks do.
```

## 13. Authorization Service Shape

A useful internal abstraction:

```java
public interface AuthorizationService {
    AuthorizationDecision decide(
        ActorContext actor,
        Action action,
        AuthorizationResource resource,
        AuthorizationContext context
    );

    default void require(
        ActorContext actor,
        Action action,
        AuthorizationResource resource,
        AuthorizationContext context
    ) {
        AuthorizationDecision decision = decide(actor, action, resource, context);
        if (!decision.permitted()) {
            throw new ForbiddenException(decision.safeReasonCode());
        }
    }
}
```

Decision object:

```java
public record AuthorizationDecision(
    boolean permitted,
    String reasonCode,
    Map<String, Object> evaluatedAttributes,
    List<String> obligations
) {}
```

Reason code examples:

```text
TENANT_SCOPE_MISMATCH
MISSING_PERMISSION
QUOTE_NOT_IN_APPROVABLE_STATE
DISCOUNT_EXCEEDS_AUTHORITY
MAKER_CHECKER_VIOLATION
MARGIN_BELOW_APPROVAL_LIMIT
ACCOUNT_OUT_OF_SCOPE
APPROVAL_REASON_REQUIRED
OVERRIDE_NOT_ALLOWED
```

Keep user-facing messages safe.
Do not reveal sensitive details such as another tenant's existence.

Log/internal audit may include more detail, subject to security policy.

## 14. Approval Workflow Design

Approval workflow is not just authorization.

It includes:

- detecting approval requirement,
- creating approval request,
- assigning approvers,
- tracking approval state,
- enforcing SoD,
- collecting reason/evidence,
- invalidating approval on material change,
- resubmitting after change,
- escalating if timeout,
- producing audit evidence.

Example approval requirement detection:

```text
Quote requires approval if:
- discount > allowed self-serve threshold,
- margin < floor,
- contract value > amount threshold,
- enterprise agreement override applied,
- non-standard term selected,
- manual price override exists,
- customer-specific policy says approval required.
```

Approval should be tied to a stable quote version or commercial snapshot.

Bad:

```text
Approve quote ID 123.
```

Better:

```text
Approve quote ID 123, version 7, pricing snapshot S, commercial hash H.
```

Why?

Because otherwise the quote can change after approval.

Approval invalidation rule:

```text
Any material commercial change after approval invalidates approval unless policy explicitly says otherwise.
```

## 15. Commercial Snapshot Hash

A useful pattern is to compute an approval-relevant commercial hash.

Inputs may include:

- quote item structure,
- product offering IDs and versions,
- quantities,
- contract term,
- recurring charges,
- non-recurring charges,
- discounts,
- overrides,
- margin inputs,
- agreement reference/version,
- customer/account reference,
- currency,
- effective dates.

Example:

```text
approval_hash = SHA-256(canonicalized_commercial_snapshot)
```

Approval record:

```sql
create table quote_approval (
    id uuid primary key,
    quote_id uuid not null,
    quote_version int not null,
    approval_hash varchar(128) not null,
    approved_by varchar(255) not null,
    approved_at timestamptz not null,
    approval_level varchar(50) not null,
    reason text not null,
    decision varchar(30) not null,
    correlation_id varchar(100) not null
);
```

Before accepting/converting quote:

```text
current commercial hash must equal approved hash.
```

This makes approval defensible.

Internal verification checklist:

- Is approval tied to quote version?
- Is approval tied to pricing snapshot?
- Are material changes tracked?
- Is approval invalidated automatically?
- Can approved quote be edited?
- Is approval evidence reconstructable?

## 16. Admin Override and Break-Glass Access

Enterprise products often need support/admin paths.

Examples:

- repair corrupted quote state,
- re-drive stuck order,
- cancel failed order task,
- reassign approval,
- fix customer mapping,
- unblock migration.

Danger:

```text
admin role bypasses all policy.
```

Break-glass access must be controlled.

Minimum controls:

- separate permission namespace,
- reason code required,
- ticket/change/incident reference required,
- time-bound access if possible,
- dual approval for destructive action,
- stronger audit logging,
- notification to support/security if required,
- explicit metrics for override usage,
- no silent bypass of tenant scope unless emergency policy allows it.

Example command:

```java
public record RepairQuoteStateCommand(
    UUID quoteId,
    QuoteState targetState,
    String reason,
    String incidentReference,
    boolean dryRun
) {}
```

Authorization guard:

```text
support.repair_quote_state
+ production environment guard
+ incident reference required
+ tenant scope verified
+ action is allowlisted
+ audit obligation enforced
```

## 17. Service-to-Service Authorization

A service token proves service identity, not business authority.

Example:

```text
pricing-service calls quote-service.
```

The quote-service should know:

- is caller service trusted?
- which operations can this service perform?
- is the service acting on behalf of a user?
- should original actor be preserved?
- what tenant context is allowed?
- is this internal command or external customer action?

Do not collapse user and service actor.

Better actor context:

```java
public record ActorContext(
    ActorType actorType,
    String subject,
    String tenantId,
    Optional<String> onBehalfOfUserId,
    Optional<String> clientId,
    Set<String> roles,
    Set<String> permissions,
    String correlationId,
    String causationId
) {}
```

Service-to-service actions may need distinct permissions:

```text
quote.internal.apply_pricing_result
order.internal.mark_decomposition_complete
fulfillment.internal.update_task_status
```

These should not be granted to human users.

## 18. Authorization in Event-Driven Flows

Kafka events complicate authorization.

An event consumer may process an event hours after the original user action.

Questions:

- Does the consumer need to re-authorize?
- Does event represent already-authorized fact?
- Is event a command requiring policy evaluation?
- Was original actor preserved?
- What happens if actor permissions changed since event was produced?

Distinguish event types.

### Domain Event

```text
QuoteApproved
```

This is a fact that should have been authorized before publication.
Consumer usually does not re-authorize the approval.
It validates event authenticity and schema, then reacts.

### Command Message

```text
ApproveQuoteCommand
```

This requests a state change.
Consumer must authorize or ensure producer is a trusted command gateway that already did.

### Integration Callback

```text
FulfillmentTaskCompleted
```

Consumer validates source system authorization and idempotency.

Event envelope should include:

- tenant ID,
- actor ID if relevant,
- service principal,
- correlation ID,
- causation ID,
- policy decision ID if available,
- resource ID,
- event timestamp,
- schema version.

Do not trust actor fields from untrusted external events without verification.

## 19. Authorization Caching and Staleness

Authorization data is tempting to cache:

- roles,
- permissions,
- tenant assignments,
- account assignments,
- approval thresholds,
- feature flags,
- policy documents.

Caching improves latency but introduces stale decisions.

Stale authorization failure modes:

- removed user still approves quote,
- role update not reflected,
- tenant assignment removed but access remains,
- approval threshold changed after quote submission,
- feature disabled but cached flag permits action.

Mitigations:

- short TTL for high-risk permissions,
- event-driven invalidation,
- versioned policy snapshot,
- re-check before terminal actions,
- force re-authentication for sensitive operations,
- deny on policy-load failure for high-risk actions,
- separate low-risk read cache from high-risk mutation cache.

Rule:

```text
Cache may optimize authorization lookup.
Cache must not make policy semantics ambiguous.
```

Internal verification checklist:

- Are permissions cached?
- Where is cache invalidated?
- What is TTL?
- Are high-risk actions revalidated?
- What happens if authorization service is unavailable?
- Are policy versions logged?

## 20. Tenant Scope and Authorization

Tenant isolation has its own full treatment in Part 042.
Here, focus on authorization.

Every authorization decision must include tenant context.

Bad:

```java
quoteRepository.findById(quoteId)
```

Then authorize after loading.

Better:

```java
quoteRepository.findByTenantIdAndId(actor.tenantId(), quoteId)
```

Then authorize action.

Why both?

- Data access scoping prevents accidental leakage.
- Authorization scoping prevents action misuse.
- Defense in depth catches mistakes.

Never rely only on client-provided tenant ID.

Tenant context should be derived from trusted identity/configuration and validated against resource ownership.

## 21. PostgreSQL and Data Model Concerns

Authorization may require efficient lookup.

Common tables:

```text
user_role
role_permission
tenant_membership
account_assignment
approval_authority
approval_policy
quote_approval
resource_acl
admin_override_audit
```

Key design concerns:

- effective date of role/authority,
- policy versioning,
- tenant isolation in tables,
- unique constraints preventing duplicate assignments,
- audit trail for permission changes,
- historical reconstruction of decision,
- performance of permission lookup,
- deletion vs revocation semantics.

Do not physically delete authority records if audit needs historical reconstruction.
Prefer status/effective dates:

```sql
create table approval_authority (
    id uuid primary key,
    tenant_id varchar(100) not null,
    principal_id varchar(255) not null,
    authority_type varchar(100) not null,
    max_discount_pct numeric(7,4),
    max_contract_value numeric(19,4),
    currency char(3),
    effective_from timestamptz not null,
    effective_to timestamptz,
    status varchar(30) not null,
    created_by varchar(255) not null,
    created_at timestamptz not null
);
```

Policy history matters because the question after an incident is often:

```text
Why was this actor allowed at that time?
```

## 22. MyBatis Authorization Query Discipline

Authorization queries are security-sensitive.

Bad dynamic SQL:

```xml
<select id="findQuotes">
  SELECT * FROM quote
  WHERE 1 = 1
  <if test="tenantId != null">
    AND tenant_id = #{tenantId}
  </if>
</select>
```

This can accidentally omit tenant predicate.

Better:

```xml
<select id="getQuoteForActorScope" resultMap="QuoteAuthResourceMap">
  SELECT
    q.id,
    q.tenant_id,
    q.account_id,
    q.state,
    q.owner_user_id,
    q.total_value,
    q.discount_pct,
    q.margin_pct,
    q.version
  FROM quote q
  WHERE q.tenant_id = #{tenantId}
    AND q.id = #{quoteId}
</select>
```

For high-risk commands, fail closed:

```text
If tenant/resource cannot be loaded under actor scope, return not found or forbidden according to security response policy.
```

Do not allow optional tenant filters in security-critical mapper methods.

## 23. Error Semantics: 401, 403, 404

Typical semantics:

| Status | Meaning |
|---|---|
| 401 Unauthorized | Authentication missing/invalid. |
| 403 Forbidden | Authenticated but not allowed. |
| 404 Not Found | Resource does not exist or should not be revealed. |

For cross-tenant resources, many systems return 404 to avoid revealing resource existence.

But internal audit/logging should still record:

```text
DENIED_TENANT_SCOPE_MISMATCH
```

Do not leak:

```text
Quote exists but belongs to another tenant.
```

External error response:

```json
{
  "errorCode": "RESOURCE_NOT_FOUND",
  "message": "The requested resource was not found."
}
```

Internal security log:

```json
{
  "event": "AUTHORIZATION_DENIED",
  "reasonCode": "TENANT_SCOPE_MISMATCH",
  "actor": "user-123",
  "tenant": "tenant-a",
  "resourceType": "QUOTE",
  "resourceId": "quote-999",
  "correlationId": "..."
}
```

## 24. Observability for Authorization

Authorization failures need visibility without leaking sensitive data.

Useful metrics:

```text
authorization_decision_total{action,result,reasonCode}
authorization_denied_total{action,reasonCode}
approval_denied_total{reasonCode}
admin_override_total{action,tenant}
policy_evaluation_latency_ms{action}
policy_cache_hit_ratio
```

Useful log fields:

- actor type,
- actor subject hash or safe ID,
- tenant ID,
- action,
- resource type,
- resource ID if safe,
- decision,
- reason code,
- policy version,
- quote/order state,
- correlation ID,
- causation ID.

Do not log sensitive token contents.
Do not log full JWT.
Do not log PII unnecessarily.

Trace span example:

```text
span: AuthorizationService.decide
attributes:
  auth.action = quote.approve_discount
  auth.result = denied
  auth.reason_code = DISCOUNT_EXCEEDS_AUTHORITY
  auth.policy_version = approval-policy-v17
```

## 25. Testing Authorization

Authorization test quality is often poor.
Teams test only happy path.

For Quote & Order, negative tests matter more.

Test matrix:

| Scenario | Expected result |
|---|---|
| User from tenant A views tenant B quote | Deny / safe 404. |
| Sales rep approves own quote | Deny maker-checker. |
| Manager approves discount above authority | Deny or escalate. |
| Finance approver approves wrong product family | Deny. |
| Expired quote accepted | Deny. |
| Approved quote edited then accepted without reapproval | Deny. |
| Service token calls user-only action | Deny. |
| User token calls internal service action | Deny. |
| Admin repair without incident reference | Deny. |
| Revoked role still used after cache TTL | Deny after invalidation/TTL. |

Unit tests:

- policy predicates,
- decision reason codes,
- SoD rules,
- threshold boundaries,
- state guards.

Integration tests:

- API denies cross-tenant access,
- database query includes tenant scope,
- JWT claims mapped correctly,
- service-to-service permission enforced,
- audit written for denied/approved high-risk actions.

Contract tests:

- error response shape stable,
- 401/403/404 semantics consistent,
- no sensitive detail leaked.

## 26. PR Review Checklist

When reviewing authorization changes, ask:

### Model

- Is the action business-named, not endpoint-named?
- Is permission granularity appropriate?
- Is approval authority separate from role membership?
- Is tenant/account/customer scope explicit?
- Is lifecycle state included?
- Are SoD/maker-checker rules considered?

### Implementation

- Is authorization done server-side?
- Is authoritative resource state loaded before decision?
- Is decision inside the command path, not only UI/controller?
- Are optional tenant predicates avoided?
- Are service tokens separated from user tokens?
- Are admin overrides controlled?

### Data

- Are policy/authority changes auditable?
- Is historical decision reconstructable?
- Is cache staleness acceptable?
- Are unique constraints protecting duplicate assignments?

### Failure

- Does policy service failure fail closed where needed?
- Are denial reason codes safe?
- Are cross-tenant responses non-revealing?
- Are negative tests included?

### Operations

- Are authorization decisions observable?
- Are approval/override metrics present?
- Is there a runbook for policy misconfiguration?
- Is rollout guarded by feature flag or migration plan if policy changes behavior?

## 28. Senior Engineer Mental Model

A senior engineer does not ask only:

```text
Does this endpoint require a role?
```

They ask:

```text
What business authority is being exercised?
What resource is being affected?
What state is it in?
What commercial risk exists?
Who is the actor really?
What tenant/account scope applies?
Could this bypass approval?
Could this leak cross-tenant data?
Could this decision be reconstructed during audit?
What happens if policy changes during a long-running workflow?
What negative tests prove denial paths?
```

Authorization is not middleware decoration.
It is part of the domain model.

For Quote & Order, the most expensive authorization bug is not always a data breach.
It may be a commercially invalid quote that becomes a legally or financially binding order.

Design accordingly.
