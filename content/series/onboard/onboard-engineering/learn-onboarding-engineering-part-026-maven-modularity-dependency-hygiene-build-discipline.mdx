# Part 026 — Maven, Modularity, Dependency Hygiene, and Build Discipline

> **Core idea:** the build is part of the architecture. A weak Maven structure turns every change into hidden coupling, slow CI, dependency drift, security noise, and production uncertainty.

Part ini membahas Maven bukan sebagai tool untuk menjalankan `mvn test`, tetapi sebagai **governance layer** untuk modularity, dependency versions, plugin behavior, artifact reproducibility, security scanning, and CI discipline di sistem Java enterprise.

---

## 1. Source Boundary

Bagian ini memakai:

1. **Apache Maven documentation** sebagai sumber utama untuk POM, dependency management, dependency mechanism, and multi-module behavior.
2. **Enterprise Java build practice umum** untuk reproducible builds, dependency hygiene, vulnerability control, artifact promotion, and CI quality gates.
3. **Quote & Order service architecture dari Part 025** sebagai konteks: domain-heavy Java services, microservices, API/event contracts, PostgreSQL/MyBatis, Kafka, Kubernetes, and enterprise deployment.

Yang tidak diasumsikan:

- struktur Maven internal,
- apakah repository monolith, multi-repo, atau hybrid,
- apakah parent POM internal tersedia,
- apakah build memakai Maven 3 atau Maven 4,
- apakah dependency scanning memakai tool tertentu,
- apakah artifact registry internal berbasis Nexus, Artifactory, GitHub Packages, Azure Artifacts, atau yang lain,
- apakah deployment memakai Helm, Kustomize, Argo CD, Flux, or custom pipeline.

Semua harus diverifikasi di internal repository dan pipeline.

## 2. Why Maven Is an Architecture Concern

Dalam enterprise Java, Maven menentukan:

- module boundary,
- dependency direction,
- library version alignment,
- transitive dependency exposure,
- test execution behavior,
- generated source behavior,
- code quality gates,
- artifact metadata,
- reproducibility,
- vulnerability surface,
- deployable packaging.

Build yang buruk menyebabkan masalah yang terlihat seperti bug runtime:

```text
Works locally, fails in CI.
Works in one service, fails in another.
Same library, different version, different behavior.
Transitive dependency changes behavior after upgrade.
Generated OpenAPI code differs between machines.
Test skipped accidentally.
Migration resource missing from artifact.
Docker image contains wrong jar.
```

Senior engineer harus membaca `pom.xml` seperti membaca design doc.

## 3. Maven Mental Model

Maven bekerja dengan model utama:

```text
Project Object Model (POM)
  groupId
  artifactId
  version
  packaging
  dependencies
  dependencyManagement
  build/plugins
  pluginManagement
  profiles
  modules
```

POM bukan hanya config. POM adalah declaration tentang:

- apa artifact ini,
- apa yang dibutuhkan,
- bagaimana dibangun,
- bagaimana diuji,
- bagaimana dipublikasikan,
- bagaimana ia masuk ke dependency graph enterprise.

Apache Maven documentation menjelaskan dependency management sebagai core feature; Maven membantu mendefinisikan dan menjaga reproducible builds dengan classpath dan library versions yang jelas, terutama untuk multi-module applications.

## 4. Aggregation vs Inheritance

Maven multi-module biasanya memiliki dua konsep yang sering tercampur:

### 4.1 Aggregation

Aggregator POM menentukan module mana yang dibangun bersama.

```xml
<packaging>pom</packaging>

<modules>
  <module>quote-domain</module>
  <module>quote-application</module>
  <module>quote-infrastructure</module>
  <module>quote-api</module>
  <module>quote-service</module>
</modules>
```

Aggregation menjawab:

```text
Which modules are part of this reactor build?
```

### 4.2 Inheritance

Parent POM menentukan shared configuration.

```xml
<parent>
  <groupId>com.company.platform</groupId>
  <artifactId>enterprise-service-parent</artifactId>
  <version>1.12.0</version>
</parent>
```

Inheritance menjawab:

```text
Which dependency versions, plugin versions, and build rules do children inherit?
```

Satu POM bisa menjadi aggregator, parent, atau keduanya. Tetapi konsekuensinya berbeda.

## 5. Enterprise Multi-Module Shape

Contoh untuk satu service besar:

```text
quote-service-parent
  quote-domain
  quote-application
  quote-api-contract
  quote-infrastructure-postgres
  quote-infrastructure-kafka
  quote-infrastructure-clients
  quote-service-runtime
  quote-test-support
```

### 5.1 `quote-domain`

Isi:

- aggregates,
- value objects,
- state machine,
- domain events,
- domain exceptions.

Dependencies:

- hampir tidak ada dependency framework,
- mungkin hanya validation utility kecil,
- no Spring/web/Kafka/MyBatis.

### 5.2 `quote-application`

Isi:

- command handlers,
- query handlers,
- ports/interfaces,
- transaction boundary abstraction if framework-neutral.

Dependencies:

- depends on `quote-domain`,
- may depend on small shared platform abstractions,
- should not depend on concrete DB/Kafka clients.

### 5.3 `quote-api-contract`

Isi:

- API DTOs,
- OpenAPI spec,
- generated server/client model if used,
- API error schema.

Dependencies:

- should not depend on infrastructure,
- be careful if exposing domain types.

### 5.4 `quote-infrastructure-postgres`

Isi:

- MyBatis mappers,
- repository implementations,
- row models,
- SQL resources,
- migration-adjacent test helpers.

Dependencies:

- depends on application ports/domain,
- depends on MyBatis/PostgreSQL driver,
- no controller logic.

### 5.5 `quote-infrastructure-kafka`

Isi:

- event serialization,
- topic producer/consumer,
- outbox relay adapter,
- schema registry integration.

### 5.6 `quote-service-runtime`

Isi:

- main application,
- framework configuration,
- controller wiring,
- dependency injection,
- packaging.

This module assembles the service. It should not become the place where business logic hides.

## 6. Dependency Direction as Architecture Enforcement

Maven module dependencies can enforce architecture.

Healthy direction:

```text
quote-domain
  no internal module dependencies

quote-application
  -> quote-domain

quote-infrastructure-postgres
  -> quote-application
  -> quote-domain

quote-infrastructure-kafka
  -> quote-application
  -> quote-domain

quote-api
  -> quote-application
  -> quote-domain only if intentional

quote-service-runtime
  -> quote-api
  -> quote-infrastructure-postgres
  -> quote-infrastructure-kafka
  -> quote-application
  -> quote-domain
```

Unhealthy direction:

```text
quote-domain -> quote-infrastructure-postgres
quote-domain -> spring-web
quote-application -> quote-service-runtime
quote-infrastructure-postgres -> quote-api DTOs
quote-api -> quote-infrastructure-kafka
```

If Maven allows bad dependency direction, code review must catch it every time. Better: make illegal coupling impossible.

## 7. Parent POM Responsibilities

Parent POM should centralize build governance.

Typical responsibilities:

```text
Java version
encoding
compiler flags
plugin versions
Surefire/Failsafe config
dependency versions or BOM import
quality plugins
artifact metadata
repository policy
source/javadoc behavior
reproducibility settings
```

Example:

```xml
<properties>
  <java.version>17</java.version>
  <maven.compiler.release>${java.version}</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
        <configuration>
          <release>${java.version}</release>
        </configuration>
      </plugin>
    </plugins>
  </pluginManagement>
</build>
```

The exact versions must follow internal policy. Do not copy numbers blindly.

## 8. `dependencyManagement` vs `dependencies`

This distinction matters.

### 8.1 `dependencyManagement`

Defines versions and dependency metadata for children, but does not add the dependency by itself.

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <version>${postgresql.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>
```

### 8.2 `dependencies`

Actually adds dependency to current module.

```xml
<dependencies>
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
  </dependency>
</dependencies>
```

Rule:

```text
Parent manages versions.
Child declares what it actually uses.
```

Bad smell:

```text
Parent POM adds many direct dependencies, so every child receives everything.
```

Consequence:

- domain module accidentally sees web framework,
- test classpath bloated,
- dependency conflicts hidden,
- unused dependencies spread everywhere,
- vulnerability scan noisy.

## 9. BOM Usage

BOM means Bill of Materials.

BOM helps align versions across related dependencies.

Example pattern:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.vendor.platform</groupId>
      <artifactId>vendor-bom</artifactId>
      <version>${vendor.bom.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

Benefits:

- consistent library versions,
- fewer transitive conflicts,
- easier upgrades,
- framework alignment.

Risks:

- BOM hides many version decisions,
- upgrading BOM changes many dependencies at once,
- override may violate tested combinations,
- multiple BOMs can fight.

Senior review question:

```text
Does this dependency version come from a trusted BOM, parent POM, or random child override?
```

## 10. Dependency Scope Discipline

Common scopes:

```text
compile
  Needed to compile and run.

provided
  Needed to compile but provided by runtime/container.

test
  Needed only for tests.

runtime
  Needed at runtime but not compile.

optional
  Not transitively required by consumers.
```

Bad scope creates real problems.

Example:

- test library in compile scope increases runtime artifact and vulnerability surface,
- servlet API in compile instead of provided may conflict with runtime,
- PostgreSQL driver missing at runtime causes production boot failure,
- optional dependency not understood by downstream causes missing class.

Review dependency scope as seriously as code.

## 11. Transitive Dependency Hygiene

Every dependency brings a graph.

Command:

```bash
mvn dependency:tree
```

Use it to answer:

- Why is this library on classpath?
- Which module introduced vulnerable dependency?
- Are two versions competing?
- Did a framework starter pull unnecessary libraries?
- Is logging binding duplicated?
- Is old Jackson/Netty/Guava/etc. dragged transitively?

Example output pattern:

```text
com.company:quote-service-runtime
+- com.company:quote-infrastructure-kafka
|  +- org.apache.kafka:kafka-clients
|  \- io.confluent:kafka-schema-registry-client
+- com.company:quote-infrastructure-postgres
|  +- org.mybatis:mybatis
|  \- org.postgresql:postgresql
```

A senior engineer should not approve dependency addition without understanding its transitive graph.

---

## 12. Exclusions: Use Carefully

Exclusion example:

```xml
<dependency>
  <groupId>com.vendor</groupId>
  <artifactId>vendor-client</artifactId>
  <version>${vendor.client.version}</version>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>
```

Exclusions are sometimes necessary. But they are not harmless.

Ask:

- Why is the transitive dependency excluded?
- Is replacement provided elsewhere?
- Is runtime behavior tested?
- Will next vendor upgrade reintroduce it differently?
- Is exclusion documented?

Bad smell:

```text
Large list of exclusions copied from StackOverflow or another service.
```

Exclusions should have a reason.

## 13. Plugin Management vs Plugin Usage

Like dependencies, Maven plugins have two layers.

### 13.1 `pluginManagement`

Defines plugin versions/config defaults.

```xml
<pluginManagement>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <version>${surefire.version}</version>
    </plugin>
  </plugins>
</pluginManagement>
```

### 13.2 `plugins`

Actually applies plugin to build.

```xml
<plugins>
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
  </plugin>
</plugins>
```

Plugin versions should not float. Floating plugin versions make builds non-reproducible.

## 14. Surefire vs Failsafe

Common convention:

```text
Surefire
  Unit tests.
  Usually runs in test phase.
  Name pattern often *Test.

Failsafe
  Integration tests.
  Usually runs in integration-test/verify phases.
  Name pattern often *IT.
```

Build discipline:

```bash
mvn test
  fast feedback

mvn verify
  full verification including integration tests
```

Risk:

- integration tests named incorrectly and skipped,
- CI runs `mvn test` but not `mvn verify`,
- failsafe not bound to lifecycle,
- flaky tests silently excluded,
- profile required but undocumented.

For Quote & Order systems, skipping integration tests can miss:

- MyBatis SQL bug,
- PostgreSQL locking bug,
- migration failure,
- Kafka serialization issue,
- outbox transaction bug.

## 15. Generated Sources and Contract Code

Enterprise services often generate code from:

- OpenAPI specs,
- Avro/Protobuf schemas,
- JSON schema,
- database migration metadata,
- internal API contracts.

Build must define:

- where source spec lives,
- when generation runs,
- whether generated code is committed,
- how generator version is pinned,
- how generated diff is reviewed,
- whether generated model leaks into domain.

Bad smell:

```text
Generated code differs by developer machine because generator version is local.
```

Better:

```text
Generator runs in Maven with pinned plugin version and deterministic config.
```

Generated code belongs near API/infrastructure boundary, not domain core.

---

## 16. Reproducible Builds

A reproducible build means the artifact can be rebuilt predictably from source, dependencies, and build config.

Important controls:

- pinned dependency versions,
- pinned plugin versions,
- no dynamic version ranges,
- consistent Java version,
- consistent encoding/timezone where relevant,
- deterministic generated sources,
- no local machine paths baked into artifacts,
- no undeclared dependency on local installed artifacts,
- artifact checksum/signature where required.

Bad:

```xml
<version>LATEST</version>
```

Bad:

```xml
<version>[1.0,)</version>
```

Bad:

```bash
mvn install:install-file ... # required manually before build
```

Enterprise builds must not depend on tribal local setup.

---

## 17. Maven Profiles: Useful but Dangerous

Profiles can control environment-specific behavior.

Example:

```xml
<profiles>
  <profile>
    <id>integration-test</id>
    <properties>
      <skipITs>false</skipITs>
    </properties>
  </profile>
</profiles>
```

Risks:

- local and CI build different artifacts,
- tests only run under undocumented profile,
- production build depends on manual profile,
- profile activates based on local file/env variable,
- profile hides dependency difference.

Rule:

```text
Profiles may change verification behavior, but production artifact behavior should be controlled and auditable.
```

Ask:

- Which profiles does CI use?
- Which profiles does release use?
- Are profile differences documented?
- Could a developer accidentally build a different artifact?

## 18. Versioning Internal Modules

For multi-module service in one reactor, modules usually share version:

```xml
<version>1.8.0-SNAPSHOT</version>
```

For shared libraries across services, versioning becomes contract governance.

Questions:

- Is library API stable?
- Who owns it?
- How are breaking changes communicated?
- Are services upgraded independently?
- Is there a BOM for internal platform libraries?
- Are old versions still supported?

Bad smell:

```text
Shared common library contains everything: auth, DTOs, utils, domain enums, API clients, DB helpers, test fixtures.
```

Risk:

- all services coupled,
- upgrades become all-or-nothing,
- transitive dependency leak,
- version conflict,
- accidental breaking change.

Prefer smaller, purpose-specific libraries:

```text
platform-observability
platform-security-context
platform-api-error-model
platform-testcontainers-support
quote-api-client
catalog-api-client
```

## 19. Dependency Upgrade Strategy

Dependency upgrades are production changes.

Classify upgrade:

```text
Patch upgrade
  Usually bug/security fix, but still test.

Minor upgrade
  New behavior possible, check release notes.

Major upgrade
  Breaking behavior likely, needs design/testing.

BOM upgrade
  Many dependencies change, treat as coordinated upgrade.

Security emergency upgrade
  Fast path, but still needs compatibility verification.
```

Upgrade checklist:

- release notes reviewed,
- CVE context understood,
- dependency tree before/after compared,
- contract tests run,
- integration tests run,
- performance-sensitive areas checked,
- deployment/rollback plan known.

For Kafka/PostgreSQL/Jackson/Netty/security libraries, minor version changes can affect runtime behavior. Do not assume patch is harmless without CI evidence.

## 20. Dependency Vulnerability Management

Dependency scanning is not enough. You need triage.

For each finding:

```text
Is the vulnerable class actually on runtime classpath?
Is the vulnerable code path reachable?
Is this direct or transitive?
Which module introduced it?
Is there a patched version compatible with our BOM?
Can we exclude/override safely?
Is mitigation possible without upgrade?
What customer/deployment modes are affected?
```

Bad behavior:

- suppress all findings permanently,
- upgrade random transitive dependency without testing,
- ignore because “it is only a library”,
- treat scanner severity as complete risk model.

Good behavior:

- document triage,
- patch or mitigate,
- add regression tests where behavior changes,
- track exception expiration,
- align with internal security policy.

## 21. Build Speed and CI Feedback

Build speed is engineering productivity and quality risk.

If CI is too slow:

- developers batch changes,
- tests get skipped locally,
- review feedback slows,
- flaky tests tolerated,
- hotfix confidence drops.

Maven build performance levers:

```bash
mvn -T 1C verify
```

But parallel builds require module dependencies and tests to be safe.

Other levers:

- split unit and integration stages,
- avoid starting full application for domain tests,
- avoid full context for every test,
- use testcontainers selectively,
- isolate slow E2E tests,
- cache dependencies in CI,
- avoid unnecessary generated source regeneration,
- track slow test report.

Do not optimize by skipping correctness-critical tests silently.

## 22. Artifact Packaging

For deployable service, build output must answer:

- which jar is runtime artifact?
- are dependencies packaged inside?
- are migration files included?
- are config defaults included?
- are OpenAPI specs included?
- are generated resources included?
- is build metadata included?
- does Docker build use the correct artifact?

Common issue:

```text
Maven builds several jars, Dockerfile copies the wrong one.
```

Build should make artifact identity explicit.

Example:

```text
target/quote-service-runtime-1.8.0.jar
```

Dockerfile should not rely on ambiguous wildcard if multiple jars exist.

## 23. Build Metadata and Traceability

Production artifact should be traceable to:

- git commit,
- branch/tag,
- build number,
- build timestamp,
- dependency versions,
- image digest,
- source repository,
- CI run.

This helps incident response:

```text
Which code is running?
Which dependency version included vulnerable package?
Which migration was packaged?
Which OpenAPI contract was generated?
```

Maven can include build metadata via plugin/resource filtering, but ensure:

- no secrets included,
- no non-reproducible path leaks,
- no local machine identity leaks.

## 24. Enforcing Architecture with Maven

Maven can support architecture enforcement through:

- module boundaries,
- dependency convergence rules,
- banned dependency rules,
- duplicate class detection,
- enforcer plugin,
- forbidden APIs plugin,
- dependency analysis,
- test separation,
- code generation placement.

Examples of policies:

```text
quote-domain must not depend on spring-web.
quote-domain must not depend on mybatis.
quote-api-contract must not depend on quote-infrastructure-postgres.
All modules must use Java 17 release target.
No SNAPSHOT dependencies in release build.
No dynamic versions.
No duplicate logging bindings.
```

Even if exact enforcement plugin differs internally, the principle stands: **architecture should fail the build when violated**.

## 25. MyBatis, PostgreSQL, Kafka Dependency Placement

For Quote & Order services:

### 25.1 MyBatis

Should live in persistence infrastructure module.

```text
quote-infrastructure-postgres
  -> mybatis
  -> postgresql driver
```

Domain/application should not depend on MyBatis classes.

### 25.2 PostgreSQL Driver

Usually runtime/infrastructure dependency.

Check:

- driver version aligned,
- SSL/cert behavior,
- timezone behavior,
- JSONB handling,
- batching behavior,
- connection pool compatibility.

### 25.3 Kafka Client

Should live in Kafka infrastructure module.

Check:

- client version compatible with broker/platform,
- serializer/deserializer versions,
- schema registry client,
- retry configuration source,
- security mechanism.

### 25.4 Testcontainers

Should be test-scoped.

```xml
<scope>test</scope>
```

Do not leak Testcontainers into runtime artifact.

## 26. Common Build Anti-Patterns

### 26.1 Parent POM as Dependency Dumpster

Symptoms:

- parent includes all dependencies,
- every module sees everything,
- domain can import web framework,
- vulnerability scan noisy.

Fix:

- parent manages versions,
- modules declare dependencies they use.

### 26.2 Copy-Paste POMs

Symptoms:

- versions repeated everywhere,
- plugin config inconsistent,
- test behavior differs between modules,
- upgrades require many edits.

Fix:

- centralize in parent/BOM,
- keep child POM small.

### 26.3 Undocumented Profiles

Symptoms:

- CI uses hidden profile,
- local build misses integration tests,
- release artifact differs from developer artifact.

Fix:

- document profile matrix,
- make CI command visible,
- minimize behavior-changing profiles.

### 26.4 Generated Code Drift

Symptoms:

- generated sources committed but stale,
- generator version differs,
- API contract change not reviewed.

Fix:

- pin generator,
- fail build on stale generated code,
- review spec diff.

### 26.5 Dependency Override Without Reason

Symptoms:

- child module overrides BOM version,
- no release note,
- no compatibility test,
- no owner.

Fix:

- document why,
- test behavior,
- feed change back into parent if standard.

## 27. PR Review Checklist for Maven Changes

When reviewing `pom.xml` changes, ask:

### Dependency

- Is the dependency actually needed?
- Which module should own it?
- Is scope correct?
- What transitive dependencies are introduced?
- Does it duplicate existing capability?
- Does it increase runtime attack surface?

### Version

- Is version managed centrally?
- Is override intentional?
- Is BOM alignment preserved?
- Are release notes checked?
- Is upgrade major/minor/patch/security?

### Modularity

- Does this dependency violate layer boundary?
- Does domain remain framework-free?
- Does API depend on infrastructure accidentally?
- Does shared library create unwanted coupling?

### Build Behavior

- Are plugin versions pinned?
- Does CI run the relevant lifecycle phase?
- Are tests skipped accidentally?
- Are generated sources deterministic?
- Does packaging still include required resources?

### Security

- Does dependency introduce CVEs?
- Are exclusions justified?
- Are suppressions temporary and documented?
- Is runtime classpath understood?

### Release

- Is artifact version correct?
- Is release build reproducible?
- Are SNAPSHOT dependencies banned for release?
- Is Docker packaging affected?
- Is rollback compatible?

Run or inspect:

```bash
mvn -q help:evaluate -Dexpression=project.modules
```

Then draw:

```text
parent
  module A
  module B
  module C
```

Answer:

- Which modules are domain/application/infrastructure/runtime?
- Which module should be framework-free?
- Which module is deployable artifact?

Run:

```bash

```

Pick one service and answer:

- Where does Kafka client enter?
- Where does PostgreSQL driver enter?
- Where does web framework enter?
- Are any test libraries in compile scope?
- Are there duplicate logging bindings?

Inspect domain module dependencies.

It should not need:

```text

mybatis

```

- Are tests skipped in release pipeline?

## 30. Senior-Level Build Review Heuristics

A Maven change is suspicious if:

- it adds dependency to parent `dependencies`, not child,
- it adds compile-scoped dependency for test-only usage,
- it overrides BOM version without explanation,
- it excludes transitive dependency without replacement explanation,
- it changes plugin config and test count drops,
- it introduces profile that CI does not use,
- it changes generated code without spec diff,
- it changes packaging without Docker/pipeline update,
- it adds shared library dependency with large transitive graph,
- it makes domain module depend on infrastructure.

A Maven change is strong if:

- module ownership is clear,
- dependency scope is minimal,
- version is centrally managed,
- dependency tree impact is known,
- tests run in correct phase,
- generated code is deterministic,
- release artifact is traceable,
- architecture boundary becomes more enforceable.

---

## 31. Key Takeaways

1. Maven is part of architecture governance.
2. Parent POM should manage versions and plugins; child modules should declare what they actually use.
3. Multi-module boundaries should enforce dependency direction.
4. Dependency scope mistakes become runtime, security, and packaging problems.
5. BOM upgrades and dependency overrides are production changes.
6. Generated code must be deterministic and reviewed as contract change.
7. CI must run the lifecycle phase that actually proves readiness.
8. Senior engineers review `pom.xml` changes with the same seriousness as Java code.
