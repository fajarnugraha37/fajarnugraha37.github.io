# Part 028 — Contract Compatibility and Backward-Compatible API Evolution

> **Core idea:** changing an API is easy; preserving every real consumer’s expectations is hard. Compatibility is not only about schema. It is also about behavior, timing, defaults, errors, authorization, pagination, and operational guarantees.

Dalam enterprise Quote & Order, API consumer bisa berupa UI, CRM adapter, billing adapter, fulfillment orchestrator, customer integration, partner gateway, batch reconciliation, reporting tool, test automation, atau generated SDK. Sebagian consumer mungkin berjalan di cloud yang sama. Sebagian lain mungkin on-prem, behind customer firewall, upgrade lambat, atau dimiliki tim lain.

Karena itu, backward compatibility bukan nice-to-have. Ia adalah bagian dari product engineering.

Yang tidak diasumsikan:

- apakah TMF conformance menjadi requirement contractual,
- apakah on-prem customer bisa upgrade serentak.

Semua harus diverifikasi di internal release process dan customer integration documentation.

## 2. Compatibility Is a Multi-Dimensional Contract

Banyak engineer menganggap API compatibility hanya berarti:

```text
field tidak dihapus = aman
```

Itu terlalu sempit.

Compatibility mencakup:

- URI stability,
- method semantics,
- request schema,
- response schema,
- required/optional fields,
- enum values,
- nullability,
- defaulting behavior,
- status codes,
- error codes,
- pagination semantics,
- sorting semantics,
- authorization behavior,
- idempotency behavior,
- latency/timeout behavior,
- event side effects,
- state transition behavior,
- rate limits,
- callback/notification behavior,
- generated client behavior.

Contoh perubahan yang terlihat kecil tetapi breaking:

```text
Add new enum value: APPROVAL_ESCALATED
```

Bagi client yang menggunakan exhaustive switch tanpa default, ini bisa crash.

Contoh lain:

```text
Previously missing agreementId meant “use default agreement”.
Now missing agreementId means validation error.
```

Schema sama, behavior berubah. Itu tetap breaking.

## 3. Compatibility Classes

Klasifikasikan perubahan sebelum review.

### 3.1 Safe Additive Change

Biasanya aman:

- menambah optional response field,
- menambah optional request field dengan default yang tidak mengubah behavior lama,
- menambah endpoint baru,
- menambah query parameter optional yang tidak mengubah default result,
- menambah error detail field tanpa mengubah `code`,
- menambah link/reference tambahan.

Tetap perlu test, karena beberapa client tidak toleran terhadap unknown fields.

### 3.2 Conditionally Compatible Change

Mungkin aman jika consumer tolerant:

- menambah enum value,
- menambah validation warning,
- mengubah sorting default dengan explicit versioning,
- menambah pagination metadata,
- menambah stricter validation untuk data yang sebelumnya invalid tapi diterima,
- mengubah precision/scale price representation,
- mengubah field from nullable to always-present if clients tolerate it.

### 3.3 Breaking Change

Umumnya breaking:

- rename field,
- remove field,
- remove endpoint,
- change field type,
- make optional request field required,
- make nullable response field non-null if clients distinguish null/missing poorly,
- change status code class,
- change error code semantics,
- change idempotency behavior,
- change default pagination size radically,
- change order creation from sync to async without migration,
- change state machine semantics,
- change authorization requirement without rollout plan.

### 3.4 Semantic Breaking Change

Paling berbahaya karena sulit dideteksi schema diff:

- price calculation changes for same input,
- quote acceptance now reprices automatically,
- order submission now triggers fulfillment immediately,
- cancellation now cascades to service orders,
- inventory lookup now filters inactive product instances,
- agreement resolution priority changes,
- retry endpoint now creates new fulfillment task instead of resuming old one.

Semantic compatibility harus diuji dengan golden scenarios, not only schema tools.

## 4. Contract Evolution Principles

### Principle 1 — Prefer additive evolution

Tambahkan field baru sebagai optional. Jangan ubah makna field lama diam-diam.

Buruk:

```json
{
  "price": 100.0
}
```

lalu mengubah makna dari monthly recurring charge menjadi total contract value.

Lebih baik:

```json
{
  "monthlyRecurringCharge": 100.0,
  "totalContractValue": 3600.0
}
```

### Principle 2 — Keep old behavior until consumers migrate

Jika behavior lama salah tetapi sudah diandalkan, buat migration path.

```text
v1: missing agreementId uses default agreement
v1.1: warning returned when agreementId missing
v1.2: explicit defaultAgreementApplied flag
v2: agreementId required
```

### Principle 3 — Never use internal refactor as API reason

Consumer tidak peduli bahwa internal table berubah.

Breaking API hanya boleh karena product/domain reason yang kuat, bukan karena repository rename.

### Principle 4 — Make compatibility visible in CI

Compatibility yang hanya bergantung pada reviewer memory akan gagal.

CI harus mengecek:

- OpenAPI diff,
- schema compatibility,
- contract tests,
- generated client compilation,
- important golden scenario behavior,
- event schema compatibility.

### Principle 5 — Separate external model from internal model

Internal model boleh berubah. External contract harus stabil.

```text
External API DTO != Domain Aggregate != Persistence Row
```

## 5. Versioning Strategies

Tidak ada satu strategi yang selalu benar.

### 5.1 URI Versioning

```http
/api/v1/quotes
/api/v2/quotes
```

Pros:

- jelas,
- mudah untuk gateway/routing,
- mudah untuk docs.

Cons:

- bisa mendorong big-bang version,
- duplicate implementation,
- v1/v2 coexistence cost tinggi,
- migration customer lambat.

### 5.2 Header Versioning

```http
Accept: application/vnd.company.quote.v2+json
```

Pros:

- URI tetap bersih,
- version per representation.

Cons:

- kurang visible,
- tooling/gateway bisa lebih kompleks,
- customer support/debugging lebih sulit.

### 5.3 Query Parameter Versioning

```http
GET /quotes/Q-1?apiVersion=2
```

Pros:

- mudah dicoba,
- explicit.

Cons:

- sering dianggap kurang ideal untuk cache/routing,
- bisa tercampur dengan business query parameter.

### 5.4 Capability/Feature Negotiation

```http
X-Client-Capabilities: quote-approval-v2,async-pricing
```

Pros:

- berguna untuk gradual rollout,
- consumer bisa opt-in.

Cons:

- combinatorial complexity,
- sulit didokumentasikan,
- mudah menjadi hidden versioning.

### 5.5 TMF Version Alignment

Untuk TMF APIs, versioning juga terkait standard version seperti v4/v5 dan extension behavior.

Pertanyaan yang harus dijawab:

- Apakah external API benar-benar TMF version tertentu?
- Apakah hanya TMF-inspired?
- Apakah customer contract mensyaratkan conformance?
- Apakah extension field mengikuti convention?
- Bagaimana mapping v4/v5 ke internal model?

## 6. Deprecation Strategy

Deprecation bukan sekadar menulis “deprecated” di docs.

Deprecation yang sehat punya:

1. reason,
2. replacement,
3. migration guide,
4. timeline,
5. usage telemetry,
6. customer notification,
7. support readiness,
8. fallback/rollback policy,
9. removal approval.

Example deprecation note:

```yaml
deprecated: true
description: |
  Deprecated since 2026-08. Use agreementRef.id instead.
  This field will be supported until at least 2027-02 for existing integrations.
```

Runtime signal:

```http
Deprecation: true
Sunset: Wed, 03 Feb 2027 00:00:00 GMT
Link: <https://docs.example.com/migration/quote-agreement-ref>; rel="deprecation"
```

Sesuaikan dengan policy internal. Jangan invent header policy tanpa alignment.

## 7. OpenAPI Diff as Quality Gate

OpenAPI diff dapat mendeteksi banyak breaking changes:

- removed path,
- removed operation,
- removed request/response field,
- changed type,
- new required field,
- removed enum value,
- changed response status,
- changed security requirement.

Namun OpenAPI diff tidak cukup untuk:

- pricing behavior,
- state machine behavior,
- defaulting change,
- authorization rule change,
- performance regression,
- idempotency behavior,
- event side effects,
- data consistency expectations.

CI gate ideal:

```text
1. Generate or load OpenAPI spec
2. Compare against previous released spec
3. Classify diff: safe / warning / breaking
4. Require explicit approval for warning/breaking
5. Run consumer contract tests
6. Run golden scenario tests
7. Publish changelog artifact
```

## 8. Consumer-Driven Contracts

Consumer-driven contract testing menjawab:

> Consumer mana yang benar-benar memakai field/behavior ini?

Contract examples:

- CRM adapter expects `quote.id`, `quote.state`, `quote.totalPrice`, `quote.validFor`.
- UI expects validation error path for quote item characteristics.
- Billing adapter expects order completed event has `billingAccountId`.
- Fulfillment adapter expects order item action values `ADD`, `MODIFY`, `DELETE`.

Provider harus membuktikan contract tersebut tetap terpenuhi.

Pattern:

```text
Consumer publishes contract
Provider verifies contract in CI
Breaking change fails provider pipeline
```

Risiko:

- contract terlalu implementation-specific,
- consumer tidak update contract,
- terlalu banyak brittle contracts,
- contract hanya schema, bukan behavior.

Contract test harus fokus pada externally meaningful behavior.

## 9. Generated Clients and Compatibility

Banyak enterprise integration memakai generated client dari OpenAPI.

Breaking for generated client:

- rename operationId,
- change field type,
- change enum name,
- add required field,
- change nullable semantics,
- alter discriminator/polymorphism,
- remove response schema,
- change package/name generation due to schema rename.

Senior review question:

> Apakah perubahan OpenAPI ini membuat generated client lama gagal compile atau gagal runtime?

Untuk critical API, CI bisa compile sample generated clients.

## 10. Enum Evolution

Enum tampak sederhana, tetapi sering breaking.

Example:

```json
{
  "state": "PENDING_APPROVAL"
}
```

Menambah:

```text
APPROVAL_ESCALATED
```

Risiko:

- client exhaustive switch crash,
- UI tidak punya label,
- automation menganggap unknown state sebagai terminal,
- reporting pipeline reject value,
- database constraint di consumer gagal.

Mitigation:

- docs: clients must tolerate unknown enum values,
- include lifecycle category:

```json
{
  "state": "APPROVAL_ESCALATED",
  "stateCategory": "IN_PROGRESS"
}
```

- provide fallback behavior,
- announce enum expansion,
- contract tests for unknown value handling.

## 11. Nullability, Optionality, and Defaults

Tiga konsep ini berbeda:

```text
missing field    => server did not send field
null field       => server sent explicit no-value
empty string     => value present but empty
empty array      => no elements
zero             => numeric value zero
```

Kesalahan umum:

- mengubah missing menjadi null,
- mengubah null menjadi empty string,
- membuat optional field required,
- mengubah default silently,
- memakai null untuk multiple meanings.

Untuk quote/order:

- `approvalStatus: null` bisa berarti not evaluated, not required, unknown, or hidden.
- `discountAmount: 0` berbeda dari no discount.
- `agreementId` missing berbeda dari explicit no agreement.

API harus explicit:

```json
{
  "approval": {
    "required": true,
    "status": "PENDING"
  }
}
```

bukan:

```json
{
  "approvalStatus": null
}
```

## 12. Error Compatibility

Client sering bergantung pada error code.

Breaking changes:

- changing `QUOTE_NOT_FOUND` to `RESOURCE_NOT_FOUND`,
- returning 500 instead of 409,
- changing validation detail path,
- removing correlation ID,
- changing auth failure from 403 to 404 without agreement,
- combining multiple error codes into one generic error.

Error taxonomy harus versioned seperti API.

Example stable error:

```json
{
  "code": "QUOTE_STATE_CONFLICT",
  "message": "Quote cannot be accepted from current state.",
  "details": [
    {
      "code": "EXPECTED_STATE",
      "expected": ["APPROVED"],
      "actual": "PENDING_APPROVAL"
    }
  ],
  "correlationId": "..."
}
```

Message boleh berubah untuk readability. Code semantics tidak boleh berubah diam-diam.

---

## 13. Pagination Compatibility

Pagination sering dianggap detail teknis, padahal bisa breaking.

Breaking examples:

- default sort berubah dari created desc ke updated desc,
- token format berubah dan old token gagal,
- page size default turun drastis,
- filter semantics berubah,
- list endpoint tidak stable saat data berubah,
- hidden tenant filter berubah result count.

Safer design:

```http
GET /orders?customerAccountId=CA-1&pageSize=50&pageToken=abc
```

Response:

```json
{
  "items": [ ... ],
  "nextPageToken": "def",
  "sort": "createdAt desc, id desc"
}
```

Document stable ordering. Jangan menjanjikan total count jika mahal atau inconsistent.

## 14. Behavioral Compatibility in Quote & Order

Schema-compatible, behavior-breaking examples:

### Quote Pricing

Before:

```text
POST /quotes/{id}/pricing-runs recalculates prices but keeps quote editable.
```

After:

```text
POST /quotes/{id}/pricing-runs locks quote until approval.
```

This breaks UI and sales workflow.

### Quote Acceptance

Before:

```text
Accept quote uses existing price snapshot.
```

After:

```text
Accept quote automatically reprices.
```

This can create commercial dispute.

### Order Submission

Before:

```text
POST /orders creates captured order only.
```

After:

```text
POST /orders immediately triggers fulfillment.
```

This changes operational side effects.

### Cancellation

Before:

```text
Cancellation is best-effort request.
```

After:

```text
Cancellation automatically cancels downstream service orders.
```

This changes blast radius.

Behavioral changes require design review, release notes, customer migration, and regression tests.

## 15. Compatibility and Event Side Effects

REST API calls often publish events.

Changing event side effects can break consumers even if REST response unchanged.

Example:

```http
POST /orders
```

Before publishes:

```text
OrderCreated
```

After publishes:

```text
OrderCreated
OrderAccepted
OrderDecompositionRequested
```

Potential impact:

- duplicate downstream processing,
- unexpected fulfillment start,
- reporting count changes,
- alert threshold changes,
- replay behavior changes.

Contract compatibility must include:

- API response,
- DB state change,
- emitted events,
- audit records,
- downstream commands.

## 16. Migration Patterns

### 16.1 Expand-Contract for API

```text
1. Add new field alongside old field
2. Populate both
3. Update consumers
4. Mark old field deprecated
5. Measure usage
6. Remove only after approved sunset
```

Example:

```json
{
  "agreementId": "EA-1",
  "agreementRef": {
    "id": "EA-1",
    "href": "/agreements/EA-1",
    "version": "2026.03"
  }
}
```

### 16.2 Dual Behavior Behind Capability Flag

```text
legacyPricing=true  => old behavior
pricingModel=v2     => new behavior
```

Use sparingly. Too many behavior flags become untestable.

### 16.3 Shadow Mode

Run new logic but do not expose result.

```text
calculate old price => returned
calculate new price => logged/compared
```

Useful for pricing, eligibility, decomposition, and validation changes.

### 16.4 Adapter-Based Migration

Keep external API stable. Change internal model behind mapping layer.

```text
External Contract v1 -> Adapter -> New Domain Model
```

### 16.5 Parallel Version

Maintain `/v1` and `/v2` concurrently.

Use when behavior differs too much for additive migration.

Cost:

- duplicate support,
- extra testing,
- data mapping,
- security patching,
- documentation burden.

## 17. Compatibility Test Matrix

For each API change, build matrix:

| Dimension | Questions |
|---|---|
| Consumer | UI, CRM, billing, fulfillment, customer, partner, batch? |
| Contract | schema, error, event, behavior? |
| Runtime | cloud, on-prem, customer-managed? |
| Version | current, previous, long-term supported? |
| Data | old data, new data, partially migrated data? |
| State | draft, approved, accepted, in fulfillment, fallout? |
| Failure | retry, timeout, duplicate, partial failure? |
| Security | role, tenant, support/admin, service account? |
| Observability | metrics/logs/traces compatible? |

A change is not production-ready until high-risk cells are tested or consciously accepted.

## 18. Java DTO Versioning Patterns

Avoid reusing domain objects as API DTOs.

```java
public record QuoteResponseV1(
        String id,
        String state,
        MoneyResponse totalPrice,
        Integer version
) {}
```

For v2:

```java
public record QuoteResponseV2(
        String id,
        String state,
        QuoteStateCategory stateCategory,
        MoneyResponse totalPrice,
        AgreementRefResponse agreementRef,
        Integer version
) {}
```

Mapping layer:

```java
final class QuoteApiMapper {

    QuoteResponseV1 toV1(QuoteView quote) {
        return new QuoteResponseV1(
                quote.id().value(),
                quote.state().name(),
                MoneyResponse.from(quote.totalPrice()),
                quote.version()
        );
    }

    QuoteResponseV2 toV2(QuoteView quote) {
        return new QuoteResponseV2(
                quote.id().value(),
                quote.state().name(),
                quote.state().category().name(),
                MoneyResponse.from(quote.totalPrice()),
                AgreementRefResponse.from(quote.agreementRef()),
                quote.version()
        );
    }
}
```

Do not let `QuoteAggregate` become your API schema.

## 19. Database and Compatibility

API compatibility often depends on data compatibility.

Example: adding `agreementRef.version` to response.

Questions:

- Do old rows have agreement version?
- If missing, what do we return?
- Is backfill required?
- Does old app version tolerate new column?
- Does new app tolerate old rows during rolling deployment?
- Does migration block startup?
- Is on-prem upgrade path different?

API change may require database expand-contract:

```text
1. Add nullable column
2. Deploy app writing both old/new
3. Backfill old rows
4. Read from new field with fallback
5. Mark old field deprecated
6. Remove old only after all versions upgraded
```

## 20. Rollout and Observability

Compatibility rollout needs telemetry:

- API version usage by consumer,
- deprecated field usage,
- deprecated endpoint calls,
- error rate by version,
- unknown enum errors,
- idempotency conflicts,
- validation failures after change,
- consumer-specific latency,
- adapter retries,
- customer support tickets.

Do not remove old behavior until telemetry proves low/no usage or explicit customer agreement exists.

## 22. Failure Modes

| Failure | Cause | Detection | Prevention |
|---|---|---|---|
| Customer integration breaks after upgrade | removed/renamed field | support ticket, 4xx spike | OpenAPI diff + deprecation |
| Generated client fails compile | operationId/schema rename | SDK build failure | sample SDK CI |
| UI crashes on new enum | non-tolerant switch | frontend error logs | unknown enum strategy |
| Quote pricing dispute | semantic pricing change | customer complaint | golden scenario diff + migration notice |
| Order side effects change | REST response same, events changed | downstream incident | event contract review |
| Deprecated endpoint still used | no telemetry | removal outage | usage dashboard + customer comms |
| Old data fails new response | missing backfill/default | 500 errors | data compatibility test |
| On-prem upgrade stuck | incompatible rolling sequence | upgrade failure | upgrade matrix test |

## 23. Testing Strategy

Minimum testing layers:

### 23.1 OpenAPI Compatibility Test

```text
previous-released-openapi.yaml
current-openapi.yaml
        |
        v
compatibility diff
        |
        v
safe / warning / breaking
```

### 23.2 Consumer Contract Test

```text
CRM Adapter Contract
Billing Adapter Contract
UI Contract
Fulfillment Adapter Contract
        |
        v
Provider verification
```

### 23.3 Golden Scenario Test

Examples:

- create quote with enterprise agreement,
- calculate price with discount,
- submit approval,
- accept quote,
- create order,
- cancel order before decomposition,
- retry fallout task,
- retrieve order list with pagination.

Compare:

- response schema,
- important values,
- state transition,
- events emitted,
- audit records,
- error behavior.

### 23.4 Backward Data Test

Run new app against old database snapshot.

Run old app against expanded schema if rolling deployment requires it.

### 23.5 Client Tolerance Test

Use sample old clients against new API.

Test:

- unknown fields,
- unknown enum,
- missing optional fields,
- new error details,
- pagination token continuity.

## 26. Key Takeaways

- Compatibility bukan hanya field schema; behavior juga contract.
- Additive change biasanya paling aman, tetapi tetap perlu consumer tolerance.
- Enum, nullability, defaulting, error codes, pagination, and side effects sering menjadi hidden breaking changes.
- OpenAPI diff penting tetapi tidak cukup untuk semantic behavior.
- Consumer-driven contracts dan golden scenarios melindungi real integration.
- Deprecation membutuhkan telemetry, migration guide, customer communication, dan removal governance.
- External API DTO harus dipisah dari domain model dan persistence model.
- On-prem dan enterprise customer membuat API evolution lebih lambat tetapi harus lebih disiplin.
