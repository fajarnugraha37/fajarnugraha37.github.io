# Part 049 — Configuration, Secrets, Feature Flags, and Customer Customization

## 1. Why This Part Matters

In an enterprise CPQ and order-management product, configuration is not just a convenience mechanism. It is part of the product's operational contract.

A small configuration mistake can:

- route orders to the wrong downstream fulfillment adapter,
- disable an approval gate,
- expose data across tenants,
- apply the wrong pricing behavior for a customer,
- break an on-prem deployment where external network access is restricted,
- create a production incident that cannot be reproduced in lower environments.

For Quote & Order systems, configuration is dangerous because it is often treated as "not code", while in reality it can change behavior as deeply as code.

The senior-engineer mindset is:

> Configuration is executable business and operational intent. It must be typed, scoped, validated, versioned, observable, auditable, and reversible.

## 2. Source Notes and Boundaries

Public/industry references used in this part:

- Kubernetes ConfigMaps are intended to decouple non-confidential configuration from container image content so the same image can run across environments. Kubernetes documentation explicitly warns that ConfigMaps do not provide secrecy or encryption.
- Kubernetes Secrets are intended for confidential data, but Kubernetes documentation warns that Secrets are stored unencrypted by default unless cluster encryption and access controls are configured properly.
- The Twelve-Factor App methodology recommends storing deploy-varying configuration in the environment rather than baking it into code.
- Feature flag practices are industry patterns, not a single universal standard. Internal usage must be verified.

This part does **not** assume how CSG internally stores configuration, secrets, feature flags, customer overrides, or environment overlays.

Any concrete statement about the internal implementation must be verified in codebase, GitOps repositories, platform docs, deployment manifests, onboarding sessions, and production runbooks.

## 3. Configuration Is Not One Thing

A common mistake is putting every variable under the same mental bucket: `config`.

That creates ambiguity. Different configuration types have different safety properties.

| Category | Example | Owner | Change Frequency | Risk | Should Be Secret? |
|---|---|---:|---:|---:|---:|
| Deployment config | DB host, Kafka bootstrap server, service URL | Platform/team | Per environment | High | Sometimes |
| Runtime behavior config | timeout, retry count, batch size | Engineering/SRE | Occasional | High | No |
| Product behavior config | enable amendment flow, quote expiry days | Product/engineering | Customer/release dependent | High | No |
| Customer-specific config | customer adapter mapping, tenant feature setting | Delivery/product/engineering | Customer dependent | Very high | Sometimes |
| Security config | token issuer, audience, JWKS URL | Security/platform | Rare | Critical | Sometimes |
| Secret | DB password, API client secret, private key | Platform/security | Rotated | Critical | Yes |
| Feature flag | release toggle, kill switch, migration switch | Engineering/product/SRE | Frequent/temporary | Medium to critical | No |
| Catalog/business data | product offering, price, eligibility | Catalog/product owner | Business lifecycle | Critical | No |
| Agreement data | contract-specific pricing/discount/terms | Commercial system | Business lifecycle | Critical | No |

A senior engineer asks first:

> Is this value environment configuration, tenant configuration, product configuration, commercial data, security control, or a secret?

If the answer is unclear, the design is already risky.

## 4. Core Invariants

A production-grade configuration system should preserve these invariants.

### 4.1 Scope invariant

Every configuration value must have an explicit scope.

Possible scopes:

- global,
- environment,
- region,
- cluster,
- namespace,
- service,
- tenant,
- customer,
- account,
- user segment,
- feature rollout cohort.

Dangerous smell:

```text
A value exists, but nobody can explain who it applies to.
```

### 4.2 Ownership invariant

Every configuration value must have an owner.

The owner is accountable for:

- correctness,
- approval of changes,
- rollback decision,
- documentation,
- deprecation/removal.

### 4.3 Validation invariant

Configuration must be validated before it affects runtime behavior.

Validation includes:

- type validation,
- required field validation,
- range validation,
- enum validation,
- cross-field validation,
- environment compatibility,
- tenant compatibility,
- secret reference existence,
- downstream endpoint reachability when safe to test,
- migration/version compatibility.

### 4.4 Determinism invariant

For a given request, the service should be able to explain which configuration version influenced the decision.

For example:

```text
quoteId=Q-1001
pricingConfigVersion=pricing-ruleset-2026.07.01
featureFlagSnapshot=amendment-v2:on,price-cache-v3:off
catalogVersion=consumer-fiber-2026.06
agreementVersion=EA-934-v7
```

Without this, incident reconstruction becomes guesswork.

### 4.5 Secret isolation invariant

Secrets must not appear in:

- Git history,
- container image layers,
- logs,
- metrics labels,
- traces,
- error responses,
- support exports,
- test snapshots,
- PR screenshots,
- documentation examples using real values.

### 4.6 Rollback invariant

A configuration change must have a known rollback path.

The rollback path can be:

- revert GitOps commit,
- flip feature flag,
- restore previous config version,
- redeploy previous artifact,
- rotate secret back only if security policy permits,
- apply emergency override.

If rollback is not safe, the change needs a rollout plan, not a direct production edit.

## 5. Configuration Layering Model

A practical enterprise layering model looks like this:

```text
code defaults
  -> build-time constants
  -> deployment environment config
  -> platform config
  -> service config
  -> tenant/customer config
  -> runtime feature flags
  -> request-specific commercial context
```

But not all layers should override all other layers.

A dangerous anti-pattern is allowing late-bound customer configuration to override security-critical or data-isolation behavior.

### 5.1 Recommended precedence discipline

| Rule | Meaning |
|---|---|
| Security constraints should not be overridden by customer config. | Customer-specific flexibility must not weaken security. |
| Tenant identity must come from trusted context, not request body config. | Request payload is not authority. |
| Catalog/agreement data should not be implemented as feature flags. | Business data needs lifecycle, audit, and effective dating. |
| Operational kill switches should be narrow and observable. | Broad kill switches hide behavior and create unknown states. |
| Defaults must be safe. | Missing config should fail closed where risk is high. |

## 6. ConfigMap, Secret, and Environment Variables

In Kubernetes-based deployment, common mechanisms include:

- ConfigMaps,
- Secrets,
- environment variables,
- mounted files,
- external secret stores,
- sidecar or CSI-based secret injection,
- application-level configuration server,
- GitOps-managed manifests.

### 6.1 ConfigMap usage

Use ConfigMaps for non-sensitive configuration such as:

- log level,
- feature group defaults,
- timeout defaults,
- endpoint names without credentials,
- service discovery metadata,
- static routing tables where safe.

Do not put sensitive values into ConfigMaps.

Bad:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: quote-order-config
data:
  billingPassword: "super-secret"
```

Better:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: quote-order-config
data:
  billingBaseUrl: "https://billing.example.internal"
  billingTimeoutMs: "2000"
---
apiVersion: v1
kind: Secret
metadata:
  name: quote-order-billing-secret
type: Opaque
stringData:
  billingClientSecret: "managed-by-secret-system"
```

### 6.2 Secret usage

Secrets require extra discipline:

- encryption at rest in cluster datastore,
- least-privilege RBAC,
- restricted namespace access,
- mounted as files when rotation behavior matters,
- no logging,
- no metrics labels,
- no accidental exception exposure,
- clear rotation playbook,
- emergency revocation process.

A Kubernetes Secret is not automatically safe merely because the object kind is `Secret`.

### 6.3 Environment variable trade-off

Environment variables are simple and portable, but they have trade-offs:

Good for:

- static per-deployment config,
- container runtime configuration,
- connection settings,
- feature defaults.

Risky for:

- high-frequency dynamic config,
- large structured config,
- secret rotation without restart,
- per-request customer-specific behavior,
- complex nested config.

## 7. Feature Flags Are Not a Substitute for Architecture

Feature flags are useful, but dangerous when they become permanent architecture branches.

### 7.1 Feature flag categories

| Flag Type | Purpose | Expected Lifetime | Example |
|---|---|---:|---|
| Release flag | Hide incomplete code | Short | `newQuoteValidationEnabled` |
| Experiment flag | Compare behavior | Short/medium | `pricingCacheStrategy=B` |
| Ops flag | Kill switch/degradation | Long but narrow | `disableFulfillmentSubmit` |
| Migration flag | Support phased rollout | Short/medium | `readFromNewOrderProjection` |
| Permission-like flag | Customer entitlement | Usually wrong | `allowDiscountOverride` |
| Business-rule flag | Domain behavior | Usually wrong | `skipApprovalForEnterpriseAgreement` |

The last two are often smells.

Permissions should belong to authorization/entitlement models. Business rules should belong to domain/configuration models with audit and lifecycle.

### 7.2 Feature flag invariants

Every flag should have:

- owner,
- creation date,
- expected removal date,
- default value,
- allowed values,
- affected services,
- affected tenants/customers,
- safe rollback behavior,
- dashboard or telemetry,
- test coverage for both states when both states can be live.

### 7.3 Kill switch design

A kill switch must answer:

- What is disabled?
- Is the operation rejected, queued, degraded, or silently ignored?
- What user-facing error is returned?
- Is state left consistent?
- Is downstream protected?
- Is the kill switch visible in dashboards?
- Who can activate it?
- How is it audited?

Bad kill switch:

```java
if (flags.isEnabled("disable_order_processing")) {
    return;
}
```

Better shape:

```java
if (opsFlags.fulfillmentSubmissionDisabled(tenantId)) {
    audit.record(
        AuditEvent.fulfillmentSubmissionBlocked(orderId, tenantId, "OPS_KILL_SWITCH")
    );

    order.markFulfillmentSubmissionBlocked("OPS_KILL_SWITCH");
    orderRepository.save(order);

    throw new ServiceTemporarilyUnavailableException(
        "Fulfillment submission is temporarily disabled for this tenant"
    );
}
```

The important distinction: the better version leaves a business-visible and auditable state.

## 8. Customer-Specific Configuration

Enterprise products often support customer-specific behavior.

That does not mean every customer should become a code branch.

### 8.1 Healthy customization

Healthy customization is:

- declarative,
- schema-validated,
- versioned,
- documented,
- testable,
- observable,
- bounded to allowed extension points,
- removable or upgradable.

Examples:

- customer-specific downstream endpoint,
- adapter credential reference,
- quote expiry policy within allowed range,
- allowed order types,
- catalog visibility rules,
- integration mapping profile,
- notification template selection.

### 8.2 Dangerous customization

Dangerous customization is:

- arbitrary code per customer,
- hidden `if customerId == X` branches,
- undocumented database flags,
- support-only toggles without audit,
- flags that bypass validation,
- customer-specific SQL patches,
- custom behavior not covered by tests,
- behavior that changes API semantics for only one customer.

Example smell:

```java
if (tenantId.equals("big-telco-x")) {
    // Special rule requested during launch weekend
    skipApproval = true;
}
```

This is not customization. It is institutionalized production risk.

### 8.3 Configuration schema example

A safer customer configuration shape:

```yaml
customerProfileId: "telco-x-prod"
version: 7
owner: "quote-order-platform"
effectiveFrom: "2026-07-01T00:00:00Z"
quotePolicy:
  expiryDays: 30
  allowManualDiscount: true
  maxManualDiscountPercent: 15
fulfillment:
  adapterProfile: "telco-x-oss-v2"
  submitTimeoutMs: 3000
  retryPolicy: "standard-order-submit"
security:
  allowedIssuerRefs:
    - "telco-x-idp-prod"
```

This shape is better because the system can validate it.

## 9. Typed Configuration in Java

Avoid stringly typed configuration scattered across services.

Bad:

```java
String timeout = System.getenv("ORDER_TIMEOUT");
int timeoutMs = Integer.parseInt(timeout);
```

Better:

```java
public record FulfillmentClientConfig(
    URI baseUri,
    Duration connectTimeout,
    Duration readTimeout,
    RetryPolicyConfig retryPolicy
) {
    public FulfillmentClientConfig {
        if (connectTimeout.isNegative() || connectTimeout.isZero()) {
            throw new IllegalArgumentException("connectTimeout must be positive");
        }
        if (readTimeout.compareTo(Duration.ofSeconds(30)) > 0) {
            throw new IllegalArgumentException("readTimeout must not exceed 30 seconds");
        }
    }
}
```

A typed config object gives:

- validation,
- testability,
- documentation,
- IDE navigation,
- safer refactor,
- explicit defaults,
- better startup failure.

## 10. Startup Validation vs Runtime Validation

Some config should fail fast at startup.

Examples:

- missing DB URL,
- invalid Kafka bootstrap address,
- invalid JWT issuer configuration,
- invalid enum value,
- invalid duration value,
- impossible thread pool size.

Some config must be validated at runtime.

Examples:

- tenant-specific adapter profile,
- feature flag cohort,
- customer agreement reference,
- catalog version reference,
- external endpoint health,
- secret rotation state.

The key is to distinguish:

```text
Invalid deployment config -> fail startup.
Invalid tenant/customer config -> isolate affected tenant/customer and produce actionable diagnostics.
Invalid request-specific config reference -> reject request with domain-specific error.
```

## 11. Secrets and Rotation

Secret rotation is not complete when the secret store value changes.

A rotation plan must include:

1. Create new credential.
2. Deploy or expose new credential reference.
3. Ensure clients can use both old and new credentials during overlap if needed.
4. Rotate consuming services.
5. Verify traffic uses new credential.
6. Revoke old credential.
7. Confirm no failures after revocation.
8. Audit the rotation.

Failure modes:

| Failure | Cause | Detection | Mitigation |
|---|---|---|---|
| Service still uses old secret | Env var requires restart | Auth failures after revocation | Restart rollout or mount secret as file with reload support |
| New secret malformed | Manual secret update | Startup failure or downstream 401 | Validate secret format before rollout |
| Secret leaked to logs | Debug logging | Log scan/secret scanner | Redact, rotate, incident response |
| Partial tenant failure | Tenant-specific credential issue | Tenant-scoped error spike | Tenant-specific rollback or credential reissue |
| On-prem customer cannot rotate | Manual deployment process | Support ticket/expiry alert | Provide documented rotation playbook |

## 12. Config and Secret Observability

Do not log secret values.

But do expose safe metadata:

- config version,
- feature flag version,
- customer profile version,
- secret reference name/hash prefix if policy allows,
- active adapter profile,
- rollout cohort,
- validation result,
- last reload time,
- config source.

Example structured log:

```json
{
  "event": "customer_config_loaded",
  "tenantId": "tenant-123",
  "customerProfileId": "telco-x-prod",
  "customerProfileVersion": 7,
  "adapterProfile": "telco-x-oss-v2",
  "configSource": "gitops",
  "validationStatus": "valid"
}
```

## 13. GitOps and Config Change Control

For GitOps-managed configuration, a config change is a production change.

A strong change process includes:

- PR review,
- schema validation,
- policy validation,
- secret reference validation,
- tenant-scope validation,
- diff preview,
- rollout plan,
- rollback plan,
- deployment window awareness,
- audit trail.

A config PR should be reviewed with nearly the same seriousness as a code PR if it can change quote/order behavior.

## 14. Environment Promotion

The same artifact should generally move across environments, while configuration changes per environment.

Bad:

```text
Build different image for dev, test, staging, and prod.
```

Better:

```text
Build one image.
Promote image digest.
Inject environment-specific configuration through controlled deployment mechanism.
```

This supports:

- reproducibility,
- rollback,
- artifact traceability,
- supply-chain control,
- easier production debugging.

## 15. Quote & Order Configuration Examples

### 15.1 Quote expiry policy

Potential fields:

```yaml
quotePolicy:
  defaultExpiryDays: 30
  maxExpiryDays: 90
  allowManualExpiryExtension: true
  extensionRequiresApproval: true
```

Review questions:

- Is this global or customer-specific?
- Does changing it affect existing quotes or only new quotes?
- Is expiry snapshot stored on quote?
- Is there an audit record when expiry is extended?
- Is the approval state invalidated when expiry changes?

### 15.2 Fulfillment adapter profile

```yaml
fulfillmentAdapter:
  profileId: "oss-v2-standard"
  submitEndpointRef: "oss-submit-url"
  credentialRef: "oss-client-secret"
  timeoutMs: 3000
  retryPolicyRef: "oss-standard-retry"
  idempotencyHeader: "X-Order-Submission-Id"
```

Review questions:

- Is endpoint tenant-scoped?
- Is credential tenant-scoped?
- Is retry policy safe for non-idempotent downstreams?
- Is failure observable per adapter profile?
- Is the adapter profile version stored on order or fulfillment task?

### 15.3 Pricing behavior flag

```yaml
pricing:
  cacheEnabled: true
  cacheTtlSeconds: 300
  requireAgreementSnapshot: true
```

Review questions:

- Could cache return stale price after agreement update?
- Is cache key tenant/customer/agreement/catalog aware?
- Is price snapshot persisted on quote?
- Is there a reprice command?

## 16. Failure Modes

| Failure Mode | Typical Cause | Impact | Detection | Prevention |
|---|---|---|---|---|
| Wrong tenant gets wrong adapter | Missing tenant scoping | Order sent to wrong downstream | Tenant-specific integration errors | Tenant-scoped config validation |
| Secret leaked into logs | Logging exception/env dump | Security incident | Secret scanner/log alert | Redaction and logging policy |
| Feature flag left permanently | No lifecycle owner | Complexity and inconsistent behavior | Flag inventory report | Expiry/removal policy |
| Config works in cloud but not on-prem | Assumes managed service/network | Customer deployment failure | On-prem deployment test | Deployment-mode matrix |
| Kill switch hides business state | Silent return | Lost orders/unexplained behavior | Missing order status update | Business-visible blocked state |
| Config changed without artifact trace | Manual edit | Hard-to-debug incident | Config drift detection | GitOps and audit |
| Customer override bypasses approval | Over-broad flag | Revenue leakage/compliance issue | Approval audit mismatch | Domain-owned approval config |
| Secret rotation breaks service | No overlap/restart plan | Production outage | Auth error spike | Rotation runbook and validation |

Test:

- config parsing,
- config validation,
- default behavior,
- invalid values,
- feature flag branching,
- customer profile validation,

### 17.2 Integration tests

Test:

- ConfigMap/Secret injection in local Kubernetes or deployment template rendering,
- missing secret reference,

### 17.3 Contract tests

Test:

- adapter profile shape,

### 17.4 Production-like tests

Test:

- staging deployment with production-like config size,
- on-prem packaging config,

- kill switch exercise,
- config rollback exercise,
- tenant override regression.

## 18. PR Review Checklist

When reviewing config-related code or manifest changes, ask:

- What exact behavior changes?
- What scope does this affect?
- Is it tenant/customer/environment-specific?
- Who owns this value?
- Is it validated?
- Is it documented?
- Is it observable?
- Does it contain a secret?
- Could it weaken auth, tenant isolation, approval, audit, or pricing correctness?
- Does it require restart?
- Is there a rollback path?
- Does it work in cloud and on-prem deployment modes?
- Is there a test for invalid config?
- Is there a test for both feature flag states?
- Is the flag temporary or permanent?
- Is business data being incorrectly modeled as config?

## 19. Internal Verification Checklist

Check internally:

- Where service configuration lives: GitOps repo, Helm values, Kustomize overlays, config service, DB table, or another system.
- Which values are managed by platform vs product team vs delivery team vs customer.
- Whether configuration has schema validation.
- Whether production config changes require PR approval.
- Whether there is drift detection between Git and cluster.
- Whether secrets are stored in Kubernetes Secret, cloud secret manager, external vault, sealed secrets, CSI driver, or another mechanism.
- Whether Kubernetes Secrets are encrypted at rest in each supported deployment mode.
- Whether secret access is namespace-scoped and least-privilege.
- Whether secret rotation is documented and tested.
- Whether feature flags have owner, expiry, and cleanup process.
- Whether customer-specific config is declarative and versioned.
- Whether support engineers can change config manually.
- Whether manual changes are audited.
- Whether config version appears in logs/traces/diagnostic endpoints.
- Whether tenant/customer config is included in backup/restore strategy.
- Whether on-prem customers have different config packaging constraints.
- Whether feature flags are used to bypass domain validation or approval.
- Whether pricing/catalog/agreement business data is incorrectly stored as operational config.

## 20. Practical Exercises

### Exercise 1 — Build a configuration inventory

Create a table for one service:

```text
name | type | scope | owner | default | source | restart required | risk | validation | rollback
```

Classify each config as:

- deployment config,
- runtime behavior config,
- customer config,
- secret,
- feature flag,
- business data masquerading as config.

### Exercise 2 — Review a feature flag

Pick one active feature flag and answer:

- Why does it exist?
- Who owns it?
- What is the default?
- Which tenants/customers are affected?
- What is the removal date?
- Is both-branch behavior tested?
- What happens if the flag provider is unavailable?

### Exercise 3 — Trace one secret

Pick one non-production secret and trace:

```text
secret source -> deployment manifest -> pod -> application config -> downstream call -> rotation path
```

Do not expose the secret value.

### Exercise 4 — Model a customer config schema

For one customer-specific behavior, write a declarative schema and validation rules.

Avoid `if customerId == X` logic.

## 21. Senior Engineer Heuristics

- A config value without owner is future production debt.
- A config value without validation is a delayed incident.
- A feature flag without removal plan becomes accidental architecture.
- A customer override without schema becomes hidden product fork.
- A secret without rotation plan is not operationally mature.
- A kill switch without business-visible state creates silent data loss.
- A config change without observability is hard to debug.
- A deployment system that allows manual production drift will eventually drift.
- A system that cannot explain which config version affected a quote cannot defend pricing behavior.

## 22. Summary

Configuration, secrets, feature flags, and customer customization are all control surfaces.

They change system behavior, security posture, business correctness, and operational risk.

A production-grade Quote & Order platform needs configuration that is:

- typed,
- scoped,
- owned,
- validated,
- auditable,
- observable,
- reversible,
- compatible with cloud and on-prem constraints,
- separated clearly from catalog, agreement, and authorization data.

The senior engineer does not ask only whether config works.

The senior engineer asks:

> Can this configuration be safely changed, explained, audited, rolled back, and supported across every customer deployment mode?
