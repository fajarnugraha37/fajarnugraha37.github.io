# Part 027 — REST API Design for Quote, Order, Catalog, and Integration Boundaries

> **Core idea:** an enterprise REST API is not just a controller method. It is a long-lived contract that defines what customers, UI clients, adapters, automation, monitoring, and support teams can safely depend on.

Dalam sistem Quote & Order, API sering berada di jalur paling berisiko: quote creation, pricing, approval, order submission, cancellation, amendment, catalog lookup, customer lookup, and integration handoff. API yang buruk tidak hanya menyebabkan bug teknis. Ia bisa menyebabkan quote salah harga, order double-submit, fulfillment tidak sinkron, billing handoff salah, atau customer integration rusak setelah upgrade.

Part ini membahas REST API design dari sudut pandang engineer yang harus menjaga **domain correctness**, **contract compatibility**, **operability**, dan **enterprise integration stability**.

---

## 1. Source Boundary

Bagian ini memakai:

1. **HTTP Semantics RFC 9110** untuk mental model method, status code, request/response semantics, caching, and representation.
2. **OpenAPI Specification** sebagai format standard untuk mendeskripsikan HTTP APIs.
3. **TM Forum Open API / TMF630 REST API Design Guidelines** sebagai reference style untuk API telco/BSS/OSS.
4. **Quote & Order domain model dari Part 018–024** sebagai konteks internal reasoning.

Yang tidak diasumsikan:

- apakah internal API mengikuti TMF v4, v5, atau custom model,
- apakah API gateway tertentu dipakai,
- apakah error model sudah distandardisasi,
- apakah idempotency header sudah tersedia,
- apakah public API dan internal API dipisah,
- apakah OpenAPI spec generated dari code atau design-first,
- apakah endpoint ini exposed ke customer, UI internal, adapter, atau service-to-service only.

Semua detail tersebut harus diverifikasi di internal repository, API docs, gateway configuration, and integration contracts.

## 2. API as Contract, Not Controller

Controller adalah implementation detail. API contract adalah janji sistem.

Sebuah endpoint seperti:

```http
POST /quotes
```

bukan hanya berarti “buat row quote”. Ia membawa janji:

- siapa yang boleh membuat quote,
- field apa yang wajib,
- customer/account/agreement mana yang valid,
- catalog version mana yang dipakai,
- apakah pricing langsung dihitung,
- apakah request bisa di-retry,
- apakah duplicate request menghasilkan quote kedua,
- error apa yang returned untuk invalid configuration,
- apakah response sudah snapshot atau live reference,
- event apa yang dipublish,
- audit apa yang dicatat,
- apakah consumer lama tetap aman setelah field baru ditambah.

Dalam enterprise system, API design harus dimulai dari **business command**, bukan dari table.

Buruk:

```http
POST /quote-table
PUT /quote-table/123
POST /order-table
```

Lebih baik:

```http
POST /quotes
POST /quotes/{quoteId}/price
POST /quotes/{quoteId}/submit-for-approval
POST /quotes/{quoteId}/accept
POST /orders
POST /orders/{orderId}/cancel
```

Bukan karena command-style endpoint selalu lebih RESTful, tetapi karena beberapa domain action memang memiliki semantics yang lebih spesifik daripada field update.

## 3. Resource vs Command Mental Model

REST mendorong resource-oriented design. Namun Quote & Order domain memiliki banyak **business commands**:

- calculate price,
- submit quote for approval,
- approve quote,
- reject quote,
- accept quote,
- convert quote to order,
- validate order,
- cancel order,
- retry failed fulfillment task,
- resume fallout order.

Kesalahan umum adalah memaksakan semua command menjadi generic `PATCH`.

Contoh berisiko:

```http
PATCH /quotes/{quoteId}
{
  "state": "APPROVED"
}
```

Masalah:

- actor intent tidak jelas,
- approval authority tidak jelas,
- transition guard mudah dilewati,
- audit sulit menjawab “why”,
- validation logic tersebar,
- client terlihat bisa menulis state langsung.

Lebih defensible:

```http
POST /quotes/{quoteId}/approval-decisions
{
  "decision": "APPROVE",
  "reason": "Discount approved under enterprise agreement EA-2026-001"
}
```

atau:

```http
POST /quotes/{quoteId}:approve
```

Gaya endpoint bisa berbeda per organization, tetapi prinsipnya sama: **API harus mengekspresikan business intent, bukan memberi client akses langsung ke internal state.**

## 4. API Boundary Types

Tidak semua API memiliki risiko yang sama.

| Boundary | Consumer | Stability expectation | Design priority |
|---|---|---:|---|
| Public/customer API | customer integration, partner | sangat tinggi | compatibility, documentation, auth, idempotency |
| UI backend API | internal frontend | medium-high | UX flow, performance, safe evolution |
| Service-to-service API | internal services | high | clear ownership, observability, failure semantics |
| Adapter API | CRM/billing/fulfillment integration | very high | transformation, retry, reconciliation |
| Admin/support API | operators/support | high risk | authorization, audit, guardrails |
| Internal diagnostic API | engineering/SRE | restricted | safety, redaction, rate limiting |

Senior engineer harus bertanya:

> Endpoint ini kontrak untuk siapa?

Satu endpoint yang dipakai UI internal bisa berubah lebih cepat. Endpoint yang dipakai customer integration on-prem mungkin harus didukung selama bertahun-tahun.

## 5. Resource Naming for Quote & Order

Resource naming harus stabil dan domain-aware.

Contoh resource utama:

```text
/catalogs
/product-offerings
/product-specifications
/product-offering-prices
/customers
/customer-accounts
/agreements
/quotes
/quote-items
/orders
/order-items
/product-inventory
/service-orders
/fallout-tasks
/approval-decisions
/audit-events
```

Namun tidak semua entity internal perlu menjadi top-level resource. Misalnya `priceComponent`, `validationFinding`, atau `decompositionTask` mungkin lebih aman sebagai sub-resource atau response component tergantung lifecycle ownership.

Rule praktis:

- Jadikan top-level resource jika ia memiliki lifecycle, identity, authorization, query, dan audit sendiri.
- Jadikan embedded object jika ia hanya bagian dari aggregate snapshot.
- Jadikan command resource jika ia merepresentasikan action yang perlu audit dan retry.

Contoh:

```http
GET /quotes/{quoteId}
GET /quotes/{quoteId}/items
GET /quotes/{quoteId}/validation-findings
POST /quotes/{quoteId}/pricing-runs
POST /quotes/{quoteId}/approval-requests
POST /quotes/{quoteId}/approval-decisions
```

## 6. HTTP Method Semantics

Method semantics harus konsisten.

### GET

Gunakan untuk read-only retrieval.

```http
GET /quotes/{quoteId}
GET /orders/{orderId}
GET /product-offerings?customerAccountId=...
```

GET harus aman dari side effect bisnis. Jangan gunakan GET untuk memicu recalculation, retry, approval, atau event publish.

### POST

Gunakan untuk create resource atau execute business command.

```http
POST /quotes
POST /quotes/{quoteId}/pricing-runs
POST /orders
POST /orders/{orderId}/cancellation-requests
```

POST boleh tidak idempotent secara default, tetapi untuk order/quote critical commands sebaiknya didukung idempotency key.

### PUT

Gunakan untuk replace resource representation jika client mengirim complete representation dan semantics-nya jelas.

Dalam domain Quote & Order, PUT sering lebih jarang aman karena banyak object punya server-controlled state, version, audit, dan derived fields.

### PATCH

Gunakan untuk partial update yang benar-benar field-level dan tidak merepresentasikan business transition.

Contoh yang mungkin aman:

```http
PATCH /quotes/{quoteId}
{
  "description": "Updated customer-facing quote description"
}
```

Contoh yang tidak aman:

```http
PATCH /orders/{orderId}
{
  "state": "COMPLETED"
}
```

### DELETE

Hati-hati. Untuk quote/order enterprise, delete fisik sering salah. Biasanya domain membutuhkan cancel, withdraw, expire, archive, atau soft-delete dengan audit.

```http
POST /quotes/{quoteId}/withdrawals
POST /orders/{orderId}/cancellation-requests
```

## 7. Status Code Discipline

HTTP status code harus menjelaskan outcome teknis request, bukan seluruh business state.

Contoh umum:

| Scenario | Status | Reason |
|---|---:|---|
| Quote created | `201 Created` | resource baru dibuat |
| Quote retrieved | `200 OK` | representation returned |
| Async order accepted | `202 Accepted` | command diterima tapi belum selesai |
| Invalid JSON/schema | `400 Bad Request` | request tidak valid secara syntax/shape |
| Missing/invalid token | `401 Unauthorized` | authentication gagal |
| Authenticated but forbidden | `403 Forbidden` | permission tidak cukup |
| Quote not found | `404 Not Found` | resource tidak ada atau tidak visible |
| Version conflict | `409 Conflict` | optimistic lock/state conflict |
| Validation failed | `422 Unprocessable Content` atau org-specific | request valid secara syntax tapi gagal business validation |
| Rate limited | `429 Too Many Requests` | throttling |
| Downstream unavailable | `503 Service Unavailable` | temporary dependency failure |

Catatan: organisasi bisa memilih `400` untuk semua validation failure, atau menggunakan `422`. Yang penting adalah konsisten, terdokumentasi, dan machine-readable.

Anti-pattern:

```json
{
  "success": false,
  "errorCode": "QUOTE_NOT_FOUND"
}
```

returned dengan `200 OK`.

Itu menyulitkan client, gateway, monitoring, retry, dan incident triage.

## 8. Error Model That Engineers and Integrators Can Use

Enterprise API error harus machine-readable dan human-actionable.

Minimal fields:

```json
{
  "type": "https://docs.example.com/errors/quote-state-conflict",
  "code": "QUOTE_STATE_CONFLICT",
  "message": "Quote cannot be accepted because it is pending approval.",
  "details": [
    {
      "field": "quoteId",
      "issue": "Current state is PENDING_APPROVAL; expected APPROVED."
    }
  ],
  "correlationId": "7df2b2d8-0f23-4b3d-a90f-1d3f4d22d841"
}
```

Error taxonomy sebaiknya memisahkan:

- authentication error,
- authorization error,
- validation error,
- state conflict,
- concurrency conflict,
- idempotency conflict,
- downstream dependency error,
- rate limit,
- internal server error.

Untuk Quote & Order, business validation error harus detail tetapi tidak membocorkan data tenant lain atau PII.

Contoh validation details:

```json
{
  "code": "QUOTE_VALIDATION_FAILED",
  "message": "Quote is not order-ready.",
  "details": [
    {
      "path": "/items/2/productOfferingId",
      "code": "OFFERING_NOT_ELIGIBLE",
      "message": "Product offering is not eligible for the selected customer account."
    },
    {
      "path": "/items/3/discounts/0",
      "code": "DISCOUNT_REQUIRES_APPROVAL",
      "message": "Discount exceeds the user's approval authority."
    }
  ],
  "correlationId": "..."
}
```

## 9. Idempotency for Unsafe Commands

Idempotency wajib dipikirkan untuk:

- create quote from external system,
- submit quote for approval,
- accept quote,
- create order,
- cancel order,
- retry fulfillment task,
- post payment/billing handoff command,
- publish downstream command.

Pattern umum:

```http
POST /orders
Idempotency-Key: CRM-OPP-12345-ORDER-SUBMISSION-1
```

Server menyimpan:

```text
idempotency_key
request_hash
business_operation
response_reference
status
created_at
expires_at
```

Important invariant:

```text
same idempotency key + same request semantics => same logical result
same idempotency key + different request body => conflict
```

Response untuk duplicate safe retry:

```http
200 OK
```

atau:

```http
201 Created
```

tergantung apakah response original disimpan. Yang penting behavior documented.

Jangan memakai random UUID client sebagai satu-satunya dedupe jika external system memiliki natural business key seperti CRM opportunity ID, quote number, order submission ID, atau customer request ID.

## 10. Optimistic Locking and Versioned Updates

Quote/order lifecycle rentan race:

- dua user edit quote yang sama,
- approval masuk saat quote direprice,
- quote accepted saat catalog changed,
- cancel requested saat fulfillment completed,
- retry clicked dua kali oleh operator.

Gunakan versioning eksplisit:

```http
PATCH /quotes/{quoteId}
If-Match: "quote-version-17"
```

atau body-level version:

```json
{
  "expectedVersion": 17,
  "description": "Updated description"
}
```

Conflict response:

```http
409 Conflict
```

```json
{
  "code": "VERSION_CONFLICT",
  "message": "Quote has changed since it was last read.",
  "currentVersion": 18,
  "correlationId": "..."
}
```

Senior review question:

> Apa yang terjadi jika dua actors mengirim command valid secara bersamaan?

## 11. Pagination, Filtering, Sorting, and Search

List endpoint harus didesain untuk data besar.

Buruk:

```http
GET /orders
```

mengembalikan semua order.

Lebih aman:

```http
GET /orders?customerAccountId=CA-1001&state=IN_PROGRESS&pageSize=50&pageToken=...
```

Principles:

- default page size kecil,
- maximum page size enforced,
- stable sort,
- cursor/page token untuk dataset besar,
- filter fields indexed,
- response menyertakan next token,
- query by tenant/customer scoped,
- jangan expose arbitrary SQL-like filtering tanpa governance.

Untuk audit/support query, jangan memaksa endpoint customer-facing menjadi reporting API. Reporting/search workload bisa membutuhkan read model berbeda.

## 12. Field Selection and Expand Strategy

Quote/order responses bisa besar.

Risiko response besar:

- latency tinggi,
- payload timeout,
- client memory pressure,
- accidental PII exposure,
- compatibility sulit,
- cache tidak efektif.

Pattern:

```http
GET /quotes/{quoteId}?fields=id,state,totalPrice,version
GET /quotes/{quoteId}?expand=items,prices,approvalStatus
```

Namun `expand=*` harus dihindari untuk resource kompleks.

Rule:

- default response harus berguna tapi bounded,
- expansion harus explicit,
- setiap expansion harus punya performance budget,
- sensitive expansion harus authorized,
- API docs harus menyebut cost/usage.

## 13. Snapshot vs Reference in API Responses

Quote/order API harus jelas apakah field adalah snapshot atau live reference.

Contoh:

```json
{
  "productOffering": {
    "id": "PO-123",
    "href": "/product-offerings/PO-123",
    "name": "Business Fiber 1Gbps",
    "version": "2026.03"
  }
}
```

Pertanyaan kritis:

- `name` ini snapshot saat quote dibuat atau live value dari catalog?
- `version` wajib untuk reproducibility?
- Jika catalog offering berubah, quote lama berubah tampilannya atau tetap stabil?
- Apakah order menggunakan snapshot quote atau lookup ulang?

Untuk quote/order, banyak data harus snapshot:

- catalog version,
- product offering name saat quote,
- price components,
- discount basis,
- agreement terms used,
- customer/account reference and possibly display snapshot,
- approval basis.

Resource reference tetap berguna, tetapi snapshot menjaga auditability.

## 14. API Security and Tenant Boundary

Setiap endpoint harus menjawab:

```text
Who is calling?
Which tenant/customer scope?
Which account/agreement scope?
Which action permission?
Which data fields may be returned?
Which audit event must be recorded?
```

Risiko umum:

- `GET /quotes/{id}` tidak mengecek tenant,
- list endpoint leak cross-tenant melalui filter,
- error message membocorkan existence resource tenant lain,
- admin endpoint tidak audit,
- support endpoint dapat bypass approval,
- downstream adapter memakai service account terlalu luas.

Untuk resource not visible karena tenant/authz, organisasi harus memilih apakah response `404` atau `403`. Yang penting konsisten dan documented.

## 15. Observability by API Design

API contract harus mendukung tracing.

Headers yang perlu diverifikasi:

```text
X-Correlation-Id
X-Causation-Id
X-Request-Id
Idempotency-Key
```

Minimal observability per API:

- request count by endpoint/method/status,
- latency histogram,
- error code distribution,
- validation failure count,
- idempotency conflict count,
- state conflict count,
- downstream dependency failures,
- business event emitted,
- audit event written.

Jangan log full request body untuk quote/order jika mengandung PII, commercial pricing, agreement details, atau sensitive contract terms.

## 16. OpenAPI as Executable Contract

OpenAPI spec harus menjadi artifact engineering, bukan dokumentasi sampingan.

OpenAPI harus digunakan untuk:

- API review,
- generated client/stub,
- request/response validation,
- compatibility diff,
- contract testing,
- documentation,
- security scheme review,
- sample payload review.

Checklist OpenAPI:

- setiap operation punya `operationId`,
- error response documented,
- auth scheme documented,
- pagination documented,
- idempotency header documented,
- enums documented,
- nullable fields intentional,
- examples realistic,
- breaking change detected in CI,
- TMF extension fields clearly marked if applicable.

Anti-pattern:

```text
Code changes first, OpenAPI updated later by best effort.
```

Better:

```text
API contract is reviewed in the same PR as implementation and tests.
```

## 17. TMF-Aligned API Design Without Blind Copying

TM Forum Open APIs are valuable because they provide shared telco vocabulary and integration expectations. Namun internal implementation tidak harus satu-satu sama dengan external TMF representation.

Healthy pattern:

```text
External TMF API Model
        |
        v
Anti-Corruption / Mapping Layer
        |
        v
Internal Domain Model
        |
        v
Persistence Model
```

Unhealthy pattern:

```text
TMF JSON copied directly into database and business logic everywhere
```

Masalah direct-copy:

- domain logic mengikuti shape API, bukan invariant,
- extension fields menyebar,
- persistence jadi sulit evolve,
- internal model ikut pecah saat TMF version berubah,
- behavior compatibility sulit diuji.

Gunakan TMF untuk:

- resource vocabulary,
- common integration shape,
- customer expectation,
- conformance discussion,
- adapter boundary,
- event naming alignment.

Jangan gunakan TMF sebagai alasan untuk mengabaikan internal aggregate invariant.

## 19. Implementation Skeleton in Java

Controller should be thin:

```java
@RestController
@RequestMapping("/quotes")
final class QuoteController {

    private final CreateQuoteHandler createQuoteHandler;
    private final PriceQuoteHandler priceQuoteHandler;

    @PostMapping
    ResponseEntity<CreateQuoteResponse> createQuote(
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @RequestHeader("X-Correlation-Id") String correlationId,
            @Valid @RequestBody CreateQuoteRequest request,
            Principal principal
    ) {
        var command = request.toCommand(idempotencyKey, correlationId, principal);
        var result = createQuoteHandler.handle(command);

        return ResponseEntity
                .created(URI.create("/quotes/" + result.quoteId()))
                .body(CreateQuoteResponse.from(result));
    }

    @PostMapping("/{quoteId}/pricing-runs")
    ResponseEntity<PriceQuoteResponse> priceQuote(
            @PathVariable String quoteId,
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @RequestHeader("X-Correlation-Id") String correlationId,
            @Valid @RequestBody PriceQuoteRequest request,
            Principal principal
    ) {
        var command = request.toCommand(quoteId, idempotencyKey, correlationId, principal);
        var result = priceQuoteHandler.handle(command);

        return ResponseEntity.accepted().body(PriceQuoteResponse.from(result));
    }
}
```

Controller responsibilities:

- HTTP parsing,
- request validation shape,
- auth context extraction,
- command mapping,
- response mapping.

Controller should not own:

- pricing logic,
- approval rules,
- state transition rules,
- transaction orchestration,
- event publishing details,
- repository SQL.

## 21. Failure Modes

| Failure | Cause | Detection | Prevention |
|---|---|---|---|
| Double order submission | missing idempotency | duplicate orders, duplicate events | idempotency key + unique constraint |
| Approval bypass | state writable through PATCH | audit gap, invalid approved quote | command endpoint + state transition guard |
| Cross-tenant data leak | missing tenant predicate | security incident, support report | tenant enforcement layer + tests |
| Breaking customer integration | removed/renamed field | customer upgrade failure | OpenAPI diff + compatibility review |
| Retry storm | 5xx without retry guidance | dependency saturation | retry-after, rate limit, circuit breaker |
| Untraceable order | missing correlation ID | incident triage delay | mandatory correlation propagation |
| Stale quote accepted | no version check | wrong pricing/order | quoteVersion/If-Match guard |
| Huge response outage | unbounded expand/list | high latency, OOM | pagination + bounded expansions |

## 22. Testing Strategy

Minimum tests:

1. **Controller contract tests**
   - request validation,
   - status code,
   - error shape,
   - auth failure,
   - correlation ID response.

2. **API compatibility tests**
   - OpenAPI diff,
   - required fields not removed,
   - enum expansion checked,
   - response schema backward compatible.

3. **Idempotency tests**
   - same request + same key returns same logical result,
   - different request + same key returns conflict,
   - retry after timeout safe.

4. **Authorization tests**
   - same tenant allowed,
   - different tenant denied,
   - insufficient role denied,
   - admin/support action audited.

5. **State transition tests**
   - illegal command returns 409/422,
   - stale version returns 409,
   - terminal state immutable.

6. **Observability tests**
   - correlation ID propagated,
   - audit event written,
   - business event includes causation ID.

Tujuannya bukan rewrite semua API, tetapi membangun habit membaca API sebagai **production contract**.

---

## 25. Key Takeaways

- API enterprise adalah long-lived contract, bukan controller shortcut.
- Business command harus diekspresikan eksplisit jika generic update membuka bypass.
- Idempotency wajib untuk unsafe command seperti create order, accept quote, cancel order, dan retry fulfillment.
- Status code dan error model harus mendukung client automation, monitoring, and incident triage.
- Snapshot/reference harus eksplisit untuk quote/order auditability.
- OpenAPI harus menjadi executable contract dan quality gate.
- TMF alignment berguna, tetapi internal domain invariant tetap harus menjadi pusat desain.
