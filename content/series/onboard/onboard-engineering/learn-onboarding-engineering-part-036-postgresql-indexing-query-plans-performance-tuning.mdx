# Part 036 — PostgreSQL Indexing, Query Plans, and Performance Tuning

> Core idea: indexes are not magic speed buttons.  
> They are workload-specific data structures with read benefits, write costs, storage costs, migration costs, and operational consequences.

In Quote & Order systems, query performance is not just an optimization concern.

Poor query design can cause:

- quote search latency spikes,
- catalog browse slowness,
- pricing calculation bottlenecks,
- order list timeouts,
- fulfillment worker lag,
- Kafka consumer lag due to slow persistence,
- lock duration increase,
- connection pool exhaustion,
- failed customer demos,
- production incidents during large customer migration.

This part teaches how to reason from first principles:

```text
business access pattern -> SQL predicate/order -> planner estimate -> query plan -> index design -> measurement -> production guardrail
```

## 1. Source Boundary and Fact Discipline

This part uses public PostgreSQL documentation for query planning, `EXPLAIN`, indexes, planner statistics, multicolumn indexes, partial indexes, and index-only scans. It does not assume CSG's internal schema, workload, indexes, query plans, table sizes, or production settings.

PostgreSQL documentation explains that the planner creates a query plan for each query and that choosing the right plan is critical for performance. `EXPLAIN` shows the plan generated by the planner. PostgreSQL also documents planner statistics used for row estimates, multicolumn indexes, partial indexes, `CREATE INDEX`, and index-only scans.

Official references used for this part:

- PostgreSQL `EXPLAIN`: https://www.postgresql.org/docs/current/using-explain.html

- PostgreSQL planner statistics: https://www.postgresql.org/docs/current/planner-stats.html
- PostgreSQL `ANALYZE`: https://www.postgresql.org/docs/current/sql-analyze.html

## 2. Mental Model: Query Performance Is a Contract with the Workload

A database does not optimize for your intention. It optimizes for the SQL it receives, the statistics it has, and the indexes available.

Bad mental model:

> "This query has an index somewhere, so it should be fast."

Better mental model:

> "This query has these predicates, this sort order, this cardinality, this table size, this tenant distribution, and this expected result count. Does the planner have an index path that matches that shape?"

Indexes should be designed from access patterns, not from column names.

Example access pattern:

```text
Sales user opens active quotes for customer account in one tenant,
sorted by updated_at descending,
first 50 rows only.
```

Possible SQL shape:

```sql
SELECT quote_id, quote_number, state, updated_at, total_amount
FROM quote
WHERE tenant_id = :tenantId
  AND customer_account_id = :accountId
  AND state IN ('DRAFT', 'PENDING_APPROVAL', 'APPROVED')
ORDER BY updated_at DESC
LIMIT 50;
```

Potential index:

```sql
CREATE INDEX idx_quote_account_active_updated
ON quote (tenant_id, customer_account_id, state, updated_at DESC)
WHERE state IN ('DRAFT', 'PENDING_APPROVAL', 'APPROVED');
```

But this is not automatically correct. You need to measure:

- row count per tenant,
- cardinality of account,
- distribution of state,
- sort cost,
- update frequency,
- index maintenance cost,
- whether partial predicate matches actual SQL exactly enough,
- whether this index duplicates an existing index.

## 3. The Performance Review Loop

Do not tune randomly.

Use this loop:

```text
1. Identify business operation
2. Capture exact SQL
3. Capture representative bind values
4. Run EXPLAIN (ANALYZE, BUFFERS) in safe environment
5. Compare estimated rows vs actual rows
6. Identify scan/join/sort/aggregate bottleneck
7. Design one index or query change
8. Re-measure
9. Evaluate write/storage/migration cost
10. Add regression test or monitoring signal
```

The key discipline:

> Every index should have a named access pattern.

If no one can name the access pattern, the index is suspicious.

## 4. Reading Query Plans: What to Look For First

A PostgreSQL plan is a tree of operations.

Start with these questions.

### 4.1 Is the estimated row count close to actual?

Example symptom:

```text
estimated rows: 10
actual rows: 300000
```

This usually means planner statistics do not reflect the data distribution, or predicates are correlated in ways the planner does not understand.

Consequences:

- wrong join order,
- wrong join algorithm,
- sequential scan when index would help,
- nested loop explosion,
- sort/hash memory pressure.

### 4.2 Is the query scanning far more rows than it returns?

Example:

```text
Rows Removed by Filter: 5,000,000
Returned rows: 50
```

This means the index does not match the selective predicates or the query shape.

### 4.3 Is there an expensive sort?

If a query filters then sorts a large result set, an index matching both filter and order may help.

Example:

```sql
WHERE tenant_id = ? AND state = ?
ORDER BY created_at DESC
LIMIT 100
```

Potential index:

```sql
ON product_order (tenant_id, state, created_at DESC)
```

### 4.4 Is a nested loop multiplying work?

Nested loops are not bad. They are excellent when the outer side is small and inner lookup is indexed.

They are dangerous when planner underestimates outer rows.

### 4.5 Are buffers high?

`EXPLAIN (ANALYZE, BUFFERS)` helps show whether the query is reading many pages from shared buffers or disk.

A query can be CPU-bound, IO-bound, sort-bound, lock-bound, or network-bound. Do not assume.

## 5. Index Types You Will Actually Need Often

PostgreSQL supports many index types. For Quote & Order service work, B-tree is usually the default first tool.

### 5.1 B-tree indexes

Good for:

- equality,
- range,
- sorting,
- prefix of multicolumn indexes,
- unique constraints,
- common foreign key lookups.

Examples:

```sql
CREATE INDEX idx_quote_tenant_state_updated
ON quote (tenant_id, state, updated_at DESC);
```

```sql
CREATE UNIQUE INDEX uq_quote_number_per_tenant
ON quote (tenant_id, quote_number);
```

### 5.2 Partial indexes

A partial index indexes only rows matching a predicate.

Good for hot subsets:

- active quotes,
- open orders,
- unprocessed outbox rows,
- ready tasks,
- failed integration attempts pending retry,
- non-terminal workflow states.

Example:

```sql
CREATE INDEX idx_outbox_unpublished
ON outbox_event (created_at ASC)
WHERE published_at IS NULL;
```

This can be much smaller and cheaper than indexing all historical outbox rows.

Caution: the query predicate must imply the index predicate. If the SQL differs too much, the planner may not use it.

### 5.3 Multicolumn indexes

Use when queries filter/sort by a combination of columns.

Column order matters.

General guideline:

```text
equality predicates first,
then range/sort columns,
then optional covering columns via INCLUDE if useful.
```

Example:

```sql
CREATE INDEX idx_order_list
ON product_order (tenant_id, customer_account_id, state, submitted_at DESC);
```

This suits:

```sql
WHERE tenant_id = ?
  AND customer_account_id = ?
  AND state = ?
ORDER BY submitted_at DESC
LIMIT 50
```

It may not suit:

```sql
WHERE submitted_at > ?
ORDER BY state
```

### 5.4 Covering indexes / index-only scans

PostgreSQL supports index-only scans when the query can be answered from the index and visibility requirements are satisfied.

Example:

```sql
CREATE INDEX idx_quote_list_covering
ON quote (tenant_id, customer_account_id, updated_at DESC)
INCLUDE (quote_number, state, total_amount);
```

Use with care:

- included columns increase index size,
- every update touching indexed/included columns has cost,
- index-only scan depends on visibility map conditions,
- wide included columns can be harmful.

### 5.5 GIN indexes for JSONB or array-like search

GIN can help when searching inside JSONB or arrays.

But for core quote/order fields, prefer relational columns when fields are:

- filtered often,
- joined often,
- sorted often,
- constrained,
- used in state transitions,
- needed for audit/reporting.

Do not hide hot predicates inside JSONB just because it is flexible.

### 5.6 BRIN indexes for large append-heavy tables

BRIN can be useful for very large append-heavy tables where physical order correlates with time.

Possible candidates:

- audit event table,
- state history table,
- outbox archive,
- integration attempt history.

Verify with real data. BRIN is not a replacement for precise B-tree access on hot operational paths.

## 6. Access Patterns in Quote & Order

### 6.1 Quote search/list

Common filters:

- tenant,
- customer account,
- quote state,
- owner/sales rep,
- updated date,
- quote number,
- expiry date.

Potential indexes:

```sql
CREATE INDEX idx_quote_account_state_updated
ON quote (tenant_id, customer_account_id, state, updated_at DESC);
```

```sql
CREATE INDEX idx_quote_owner_updated
ON quote (tenant_id, owner_user_id, updated_at DESC)
WHERE state IN ('DRAFT', 'PENDING_APPROVAL', 'APPROVED');
```

Review risk:

- Too many list-screen-specific indexes can slow writes.
- Search filters may be dynamic; one composite index cannot serve all combinations.
- Full-text-like search requires a different strategy.

### 6.2 Quote by quote number

This should usually be a unique lookup per tenant.

```sql
CREATE UNIQUE INDEX uq_quote_number_tenant
ON quote (tenant_id, quote_number);
```

If quote number is customer-visible, treat duplicate prevention as a business invariant.

### 6.3 Order list by customer/status/date

```sql
CREATE INDEX idx_product_order_account_state_submitted
ON product_order (tenant_id, customer_account_id, state, submitted_at DESC);
```

If most orders are terminal and UI mostly shows active orders, partial index may help:

```sql
CREATE INDEX idx_product_order_active_account
ON product_order (tenant_id, customer_account_id, submitted_at DESC)
WHERE state NOT IN ('COMPLETED', 'CANCELLED', 'FAILED_TERMINAL');
```

### 6.4 Worker picking ready tasks

```sql
CREATE INDEX idx_order_task_ready
ON order_item_task (tenant_id, priority DESC, available_at ASC, created_at ASC)
WHERE state = 'READY';
```

This supports:

```sql
WHERE tenant_id = ?
  AND state = 'READY'
  AND available_at <= now()
ORDER BY priority DESC, created_at ASC
LIMIT ?
FOR UPDATE SKIP LOCKED
```

Measure with concurrency. A perfect-looking index may still contend under heavy worker load.

### 6.5 Outbox relay

```sql
CREATE INDEX idx_outbox_unpublished_created
ON outbox_event (created_at ASC)
WHERE published_at IS NULL;
```

If multi-tenant relay partitions work:

```sql
CREATE INDEX idx_outbox_unpublished_tenant_created
ON outbox_event (tenant_id, created_at ASC)
WHERE published_at IS NULL;
```

Be careful if a global relay processes all tenants. Tenant-first index may not be optimal for global oldest-first scanning.

### 6.6 Integration attempts and retry

```sql
CREATE INDEX idx_integration_attempt_due
ON integration_attempt (tenant_id, next_attempt_at ASC)
WHERE state IN ('PENDING_RETRY', 'UNKNOWN_OUTCOME');
```

This supports scheduled retry workers.

### 6.7 State history/audit lookup

For debugging one aggregate:

```sql
CREATE INDEX idx_order_state_history_order_time
ON order_state_history (tenant_id, order_id, changed_at ASC);
```

For global time-window audit search, a different index or partitioning strategy may be needed.

## 7. Composite Index Design from First Principles

A multicolumn B-tree index is ordered lexicographically.

For:

```sql
CREATE INDEX idx ON quote (tenant_id, customer_account_id, state, updated_at DESC);
```

The index is useful for queries starting with:

```text
tenant_id
tenant_id + customer_account_id
tenant_id + customer_account_id + state
tenant_id + customer_account_id + state + updated_at order/range
```

It is not equally useful for a query that only filters `state`.

### 7.1 Equality before range

Good:

```sql
WHERE tenant_id = ?
  AND customer_account_id = ?
  AND state = ?
  AND updated_at >= ?
ORDER BY updated_at DESC
```

Index:

```sql
(tenant_id, customer_account_id, state, updated_at DESC)
```

### 7.2 Sort order matters with LIMIT

For list screens:

```sql
ORDER BY updated_at DESC LIMIT 50
```

An index that can provide rows in the correct order may avoid sorting many rows.

### 7.3 Low-cardinality columns are not useless when combined

`state` alone may be low-cardinality. But `(tenant_id, state, updated_at)` can be excellent for active-work queues or dashboards.

### 7.4 Tenant ID first is common, but not always automatically best

If every query is tenant-scoped, tenant-first often helps.

But consider:

- dedicated tenant databases,
- global background jobs,
- cross-tenant operational dashboards,
- very skewed tenant sizes,
- partitioning by tenant or time.

Index design must match deployment reality.

## 8. Pagination: Offset Is Often a Hidden Time Bomb

Offset pagination looks simple:

```sql
ORDER BY updated_at DESC
LIMIT 50 OFFSET 500000;
```

The database still has to walk past many rows.

For large operational tables, prefer keyset pagination when possible.

Example:

```sql
SELECT quote_id, quote_number, updated_at
FROM quote
WHERE tenant_id = :tenantId
  AND customer_account_id = :accountId
  AND (updated_at, quote_id) < (:lastUpdatedAt, :lastQuoteId)
ORDER BY updated_at DESC, quote_id DESC
LIMIT 50;
```

Supporting index:

```sql
CREATE INDEX idx_quote_keyset
ON quote (tenant_id, customer_account_id, updated_at DESC, quote_id DESC);
```

Keyset pagination is better for stable scrolling and large result sets.

Trade-offs:

- harder UI semantics for arbitrary page number,
- requires deterministic ordering,
- cursor must encode sort keys,
- filters must remain stable across page requests.

## 9. Statistics and Misestimation

The planner depends on statistics.

PostgreSQL `ANALYZE` collects statistics about table contents and stores them for the planner to choose efficient plans.

Misestimation can happen because:

- stale statistics,
- skewed tenant data,
- correlated columns,
- dynamic predicates,
- low statistics target,
- JSONB expressions without useful stats,
- temporary data distribution changes after migration/backfill.

Example correlation:

```text
tenant_id = 'large-enterprise-a'
state = 'IN_PROGRESS'
```

Maybe this tenant has 90% of active orders, while others have 1%. Generic estimates can be wrong.

Senior engineer move:

- compare estimated vs actual rows,
- run `ANALYZE` in non-production reproduction,
- inspect `pg_stats`,
- consider extended statistics for correlated columns where appropriate,
- avoid assuming local dev data represents production.

## 10. Index Cost: Writes, Storage, Vacuum, and Migration

Every index has a cost.

### 10.1 Write amplification

When a row is inserted, updated, or deleted, indexes may also be updated.

More indexes means:

- slower writes,
- more WAL,
- more storage,
- more replication lag risk,
- more vacuum work,
- more migration time.

Hot tables such as order task, outbox, integration attempt, and quote/order current state need careful index budgets.

### 10.2 Update-heavy columns

Indexing a frequently updated column can be expensive.

Example:

```text
order_item_task.state changes READY -> CLAIMED -> IN_PROGRESS -> COMPLETED
```

Indexes involving `state` are useful for picking work, but every state transition updates them.

This is still often worth it for partial indexes on hot states. Measure.

### 10.3 Large covering indexes

`INCLUDE` columns can avoid heap fetches, but they make indexes larger.

Avoid including:

- large JSONB payloads,
- large text descriptions,
- rarely needed columns,
- frequently updated columns.

### 10.4 Index build in production

Creating indexes on large tables can affect production.

PostgreSQL supports `CREATE INDEX CONCURRENTLY`, which reduces write blocking compared with regular index creation, but it has trade-offs and cannot run inside a normal transaction block.

For enterprise/on-prem deployments, index migration must consider:

- table size,
- lock behavior,
- migration framework support,
- rollback path,
- customer maintenance windows,
- replication lag,
- disk headroom,
- failed concurrent index cleanup.

## 11. Query Shape Anti-Patterns

### 11.1 Function on indexed column

Bad:

```sql
WHERE lower(quote_number) = lower(:quoteNumber)
```

A normal index on `quote_number` may not help.

Options:

- store normalized value,
- use expression index,
- use case-insensitive type/strategy if appropriate.

### 11.2 Leading wildcard search

```sql
WHERE quote_number LIKE '%1234'
```

A normal B-tree index is not useful for arbitrary leading wildcard search.

Use a search-specific strategy if the requirement is real.

### 11.3 Optional filters with OR explosion

```sql
WHERE (:state IS NULL OR state = :state)
  AND (:accountId IS NULL OR customer_account_id = :accountId)
```

This can produce poor plans.

Better:

- generate query shape based on actual filters,
- maintain a limited set of supported search patterns,
- avoid infinite dynamic filter combinations on huge tables.

### 11.4 Unbounded queries

```sql
SELECT * FROM product_order WHERE tenant_id = :tenantId;
```

Dangerous for large tenants.

Require:

- pagination,
- date range,
- state filter,
- result limit,
- async export path for large extracts.

### 11.5 Selecting too many columns

`SELECT *` harms:

- network cost,
- memory use,
- index-only scan possibility,
- API response time,
- future compatibility.

List screens should fetch list fields, not full aggregate payload.

## 12. JSONB Performance Trade-offs

JSONB is useful for flexible attributes, raw payload storage, extension fields, and customer-specific metadata.

But do not use JSONB as an excuse to avoid modelling hot fields.

Promote a JSONB field to a relational column when it becomes:

- a frequent filter,
- a sort key,
- a join key,
- a lifecycle guard,
- a tenant/security predicate,
- an approval condition,
- an audit query requirement.

Example:

```text
quote.attributes -> 'commercialSegment'
```

If many workflows filter by commercial segment, store it as a proper column or a controlled projection.

JSONB indexes can help, but they should be deliberately designed and measured.

## 13. Partitioning and Large Tables

Partitioning is not a first-line index replacement. It is a table-management and pruning strategy.

Potential candidates:

- audit event by time,
- order state history by time,
- integration attempt archive by time,
- outbox archive by time,
- very large tenant-isolated operational tables.

Questions before partitioning:

- What is the pruning key?
- Do queries include the pruning key?
- How many partitions will exist?
- How does migration work?
- How does retention/drop partition work?
- How do unique constraints behave?
- Does on-prem deployment support this operationally?
- Does ORM/MyBatis SQL include partition key predicates?

Bad partitioning makes operations harder without improving queries.

## 14. Performance Tuning by Workload Area

### 14.1 Catalog read path

Catalog queries often need:

- effective date,
- lifecycle state,
- offering/specification relationship,
- characteristic lookup,
- eligibility filter,
- tenant/customer segment filter.

Optimization options:

- publish-time materialized read model,
- cache of active catalog version,
- denormalized offering search projection,
- index on active/effective offerings,
- avoid deep joins at quote configuration time.

Risk:

- stale catalog cache,
- incorrect effective date,
- missing version snapshot,
- slow invalidation.

### 14.2 Pricing path

Pricing is often latency-sensitive.

Potential bottlenecks:

- repeated catalog joins,
- discount rule lookup,
- agreement lookup,
- margin threshold lookup,
- per-item N+1 queries,
- missing index on price list effective date.

Senior review question:

> Does pricing execute predictable bounded queries, or does quote size multiply DB calls?

### 14.3 Order ingestion path

Order submission writes multiple records and may emit events.

Performance risks:

- too many indexes on write-heavy tables,
- synchronous validation queries too broad,
- large transaction duration,
- outbox insert bottleneck,
- unique constraint contention,
- state history write amplification.

### 14.4 Fulfillment worker path

Worker performance depends on:

- efficient ready-task lookup,
- short claim transaction,
- idempotent completion,
- retry scheduling index,
- avoiding hot tenant starvation,
- bounded batch size.

### 14.5 Audit and history path

Audit writes must be reliable. Audit reads may be less latency-sensitive but must be queryable during incidents.

Options:

- aggregate-specific index,
- time-window index,
- partition by time,
- separate operational read model,
- export to observability/search system.

## 15. Slow Query Triage

When investigating a slow query, collect:

- exact SQL,
- bind parameters,
- query plan with actuals,
- table sizes,
- index definitions,
- row estimates vs actual rows,
- buffer usage,
- execution time vs planning time,
- lock wait time,
- frequency,
- endpoint/consumer causing it,
- tenant/customer involved,
- recent migrations/data changes.

Then classify:

| Symptom | Likely direction |
|---|---|
| Sequential scan on huge table | Missing/mismatched index, low selectivity, stale stats |
| Rows removed by filter very high | Index does not match predicate |
| Expensive sort | Index order may help, or reduce result set |
| Nested loop huge actual rows | Misestimate, missing join index |
| Hash join memory pressure | Query shape/data volume issue |
| Slow only for one tenant | data skew, tenant-specific hot spot |
| Slow after migration | stale stats, changed distribution, missing new index |
| Slow under load only | lock contention, IO saturation, connection pool |

Do not jump straight to "add index".

## 16. MyBatis Query Performance Discipline

MyBatis makes SQL visible. Use that advantage.

### 16.1 Mapper method should reveal access pattern

Bad:

```java
List<QuoteRecord> search(QuoteSearchRequest request);
```

Better for hot paths:

```java
List<QuoteSummaryRecord> findActiveQuotesByAccount(
    TenantId tenantId,
    AccountId accountId,
    Instant beforeUpdatedAt,
    UUID beforeQuoteId,
    int limit
);
```

The method tells reviewers:

- tenant-scoped,
- active quotes,
- account-based,
- keyset pagination,
- summary projection,
- bounded limit.

### 16.2 Avoid accidental N+1

Example anti-pattern:

```text
fetch 50 quote rows
for each quote:
  fetch quote items
  fetch prices
  fetch approvals
```

This becomes 151 queries.

Options:

- fetch summary projection,
- batch fetch by IDs,
- precomputed read model,
- explicit detail endpoint,
- cache stable catalog metadata.

### 16.3 Dynamic SQL must be bounded

Dynamic search is useful, but enterprise tables can be huge.

Set rules:

- required tenant predicate,
- maximum limit,
- allowed sort fields,
- indexed filter combinations,
- reject or route unsupported broad search to async export.

## 17. Index Review Checklist

Before adding an index, answer:

- Which exact query/access pattern needs it?
- What is the current plan?
- What are estimated vs actual rows?
- What table size and tenant distribution were tested?
- What index already exists that overlaps?
- Is the query read-heavy enough to justify write cost?
- Does the index help sorting or only filtering?
- Should it be partial?
- Should it be unique because it enforces an invariant?
- Does it include tenant ID correctly?
- Does it support keyset pagination?
- Is it safe to build in production/on-prem?
- Does migration use `CONCURRENTLY` where needed?
- How will we detect regression?

An index PR without a plan before/after is weak.

---

## 18. Query Review Checklist

For every query touching large tables:

- Is tenant predicate mandatory?
- Is result size bounded?
- Does it avoid `SELECT *`?
- Does it avoid accidental cross-tenant scan?
- Does it match an indexable predicate shape?
- Does sorting match an index where needed?
- Does pagination avoid large offset for big datasets?
- Are joins using indexed keys?
- Does dynamic SQL generate stable query shapes?
- Are JSONB filters justified and indexed if hot?
- Is the query inside a transaction that holds locks?
- Is the query run per item in a loop?
- Is there a performance test or captured plan?

## 19. Operational Guardrails

Production performance needs feedback loops.

Verify existence of:

- slow query logging,
- `pg_stat_statements`,
- top query dashboard,
- query latency by endpoint/consumer,
- lock wait dashboard,
- table/index size dashboard,
- index usage dashboard,
- dead tuple/vacuum dashboard,
- outbox lag metric,
- worker claim latency,
- customer/tenant-specific performance view.

Important metrics:

- p50/p95/p99 query latency,
- calls per query fingerprint,
- rows scanned vs returned,
- shared/local/temp blocks,
- temp file usage,
- index hit ratio,
- sequential scans on large tables,
- replication lag,
- connection pool wait time.

A query that is fine at p50 can still break customer experience at p99.

## 20. Performance Testing Strategy

### 20.1 Test with realistic cardinality

A query that is fast with 100 rows tells you almost nothing.

Test with:

- realistic tenant sizes,
- skewed large tenant,
- terminal vs active state distribution,
- historical rows,
- large quote item counts,
- large catalog versions,
- outbox backlog,
- retry backlog.

### 20.2 Test before and after plan

Store before/after plans in PR or design doc.

At minimum:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Use representative bind values. Generic values can hide skew.

### 20.3 Test write impact

Adding indexes can slow writes.

Measure:

- order submission latency,
- quote update latency,
- worker task transition latency,
- outbox insert throughput,
- migration duration.

### 20.4 Test under concurrency

A query can be fast alone but harmful under contention.

Test:

- worker claim concurrency,
- bulk quote search,
- catalog publish while reads happen,
- migration/backfill while normal traffic runs,
- retry storm scenario.

- Use of JSONB indexes.
- Use of partitioning.
- Index migration pattern.
- Whether `CREATE INDEX CONCURRENTLY` is supported by migration tooling.
- On-prem maintenance window constraints.
- Known performance incidents.

## 23. Key Takeaways

- Query performance starts from access patterns, not from columns.
- `EXPLAIN (ANALYZE, BUFFERS)` is a core senior-engineer tool.
- Estimated vs actual rows often reveal why the planner chose a bad plan.
- Multicolumn indexes must match predicate and sort shape.
- Partial indexes are powerful for hot workflow states.
- Covering indexes can help list views but increase write/storage cost.
- Offset pagination can become a latency time bomb on large tables.
- JSONB is useful, but hot business predicates deserve explicit modelling.
- Every index should have a named owner/access pattern and migration plan.
- Performance tuning is incomplete without production observability and regression guards.
