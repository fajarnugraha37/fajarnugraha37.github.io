# Part 070 — Final Part: Production Game Day, Failure Scenarios, and Principal-Level Review

## 1. Source notes and scope boundary

This is the final part of the series.

It uses public reliability references as inspiration:

- Google SRE material describes Disaster Recovery Testing, DiRT, and Wheel of Misfortune-style exercises as ways to learn and test incident response preparedness.
- AWS Well-Architected defines game days as simulations of failures or events to test systems, processes, and team responses, and recommends conducting them regularly to build operational muscle memory.
- AWS operational excellence guidance recommends anticipating failure, performing pre-mortem exercises, and validating response procedures.
- Previous parts of this series provide the Quote & Order domain, architecture, data, Kafka, Kubernetes, testing, security, observability, and operational foundations.

This part does **not** assume CSG's real incident process, on-call model, game day practice, deployment topology, or internal runbooks.

Use the exercises as a design framework.

Before running anything against real environments, verify internal policy, authorization, customer impact boundaries, change windows, compliance constraints, and incident-management expectations.

---

## 2. Core thesis

A system is not production-ready because its happy path works.

A system is production-ready when the team has practiced what happens when the happy path breaks.

For Quote & Order, a game day should test not just infrastructure reliability, but business correctness under stress:

- Can we detect stale catalog usage?
- Can we stop duplicate order creation?
- Can we recover from Kafka replay safely?
- Can we diagnose pricing drift?
- Can we handle fulfillment fallout?
- Can we repair data defensibly?
- Can we prove who approved what and why?
- Can we contain tenant isolation issues?
- Can we roll forward after a failed migration?
- Can support and engineering explain customer impact?

A principal-level engineer does not wait for production to teach the team these lessons.

They design controlled exercises that reveal weaknesses before customers do.

---

## 3. Game day principles

### 3.1 Safety first

Never run a disruptive scenario casually.

A responsible game day has:

- explicit scope,
- approved environment,
- clear stop condition,
- rollback/restore plan,
- owner for every injected failure,
- communication channel,
- observer roles,
- data protection boundary,
- customer impact boundary,
- post-exercise write-up.

### 3.2 Practice real actions

A weak game day is a meeting where people discuss what they would do.

A strong game day makes people perform the action:

- open dashboard,
- read logs,
- follow runbook,
- identify correlation ID,
- inspect Kafka lag,
- query database safely,
- disable feature flag,
- pause consumer,
- roll back deployment,
- run reconciliation report,
- prepare customer/support update,
- write postmortem notes.

### 3.3 Test business failure, not just infrastructure failure

A pod crash is useful.

But Quote & Order systems also fail through:

- wrong price,
- wrong approval,
- wrong catalog version,
- wrong order item action,
- duplicate event,
- missing audit,
- stuck fallout,
- stale inventory,
- broken billing handoff,
- customer-specific config drift.

These failures can be more damaging than a clean outage because they may remain hidden.

### 3.4 Separate drill, incident, and chaos

Use distinct exercise types.

| Exercise type | Purpose | Risk level |
|---|---|---|
| Tabletop | Validate reasoning and roles | Low |
| Wheel of Misfortune | Practice diagnosis and incident coordination | Low to medium |
| Staging game day | Exercise tools/runbooks in realistic environment | Medium |
| Production-safe drill | Validate real observability/procedure with tightly controlled blast radius | High |
| Chaos experiment | Continuously validate assumptions using controlled fault injection | High and requires maturity |

For a new engineer, start with tabletop and staging drills.

## 4. Game day setup template

Before each scenario, define:

```md
## Scenario name

### Hypothesis
What do we believe the system/team can handle?

### Injected failure
What controlled fault will be introduced?

### Environment
Local / dev / test / staging / production-safe subset.

### Scope
Services, tenants, test accounts, topics, tables, APIs.

### Expected detection
Which alert, dashboard, log, trace, metric, or reconciliation report should reveal it?

### Expected response
Which runbook or operator actions should be executed?

### Expected recovery
How do we return system/data to safe state?

### Stop condition
What condition aborts the exercise?

### Evidence to collect
Timeline, screenshots, logs, traces, queries, decisions, gaps.

### Learning output
Postmortem, ADR, runbook update, dashboard change, backlog item, test improvement.
```

A game day without a learning artifact is just theater.

## 5. Scenario 1 — Pricing bug causes undercharged quote

### Failure injection

Introduce a controlled pricing rule defect in a non-production/staging environment:

- a discount stacks when it should not,
- an agreement price overrides base price incorrectly,
- a recurring charge is omitted,
- a currency/rounding rule is misapplied,
- an approval threshold is not triggered.

### Why this matters

Pricing bugs are commercial correctness failures.

They may not crash the system.

They may quietly create revenue leakage or unauthorized customer commitments.

### Expected system behavior

The system should provide:

- price calculation trace,
- price component breakdown,
- quote version snapshot,
- approval basis,
- audit event,
- anomaly detection if margin/discount crosses threshold,
- ability to invalidate/reprice drafts,
- safe handling of already accepted quotes.

### Diagnosis questions

- Which quote versions are affected?
- Which catalog/product offerings are affected?
- Which customers/accounts/agreements are affected?
- Was any quote accepted?
- Was any order created?
- Was billing handoff triggered?
- Is audit evidence sufficient to explain the wrong price?

### Recovery strategy

| Quote state | Likely recovery |
|---|---|
| Draft | Reprice and notify user/session |
| Pending approval | Cancel/restart approval with corrected basis |
| Approved but not accepted | Invalidate approval and require re-approval |
| Accepted but not ordered | Business decision: honor, amend, or reissue |
| Ordered | Coordinate order/billing/legal/customer handling |

### Internal verification checklist

- Is pricing explainability available?
- Can price components be queried by quote/version?
- Are approvals tied to pricing snapshot hash/version?
- Can stale approvals be invalidated?
- Are pricing anomalies monitored?
- Is there a support procedure for pricing correction?

## 6. Scenario 2 — Catalog publish creates stale or incompatible quotes

### Failure injection

Publish a catalog change that affects an active quote journey:

- product offering becomes inactive,
- characteristic changes required/optional status,
- bundle component changes,
- price reference changes,
- eligibility rule changes.

### Why this matters

Catalog is the control plane for product and commercial behavior.

A catalog change can invalidate configuration, pricing, approval, order decomposition, and fulfillment.

### Expected system behavior

The system should define whether quote uses:

- live catalog lookup,
- catalog version reference,
- immutable catalog snapshot,
- hybrid lookup + compatibility guard.

It should prevent silent mutation of accepted commercial commitments.

### Diagnosis questions

- Which quotes referenced the old catalog version?
- Are draft quotes auto-revalidated?
- Are accepted quotes immutable?
- Can quote-to-order conversion still use old catalog snapshot?
- Does decomposition use quote snapshot or current catalog?
- Are customer-specific catalog overrides affected?

### Recovery strategy

- Identify affected catalog version and offering IDs.
- Identify active quote versions referencing changed offerings.
- Revalidate draft/pending quotes.
- Preserve accepted quote commitments unless explicit business rule says otherwise.
- Gate order conversion if decomposition cannot support old catalog shape.
- Document migration strategy for long-running quotes.

### Internal verification checklist

- Is catalog versioning explicit?
- Are effective dates handled consistently?
- Does quote store catalog snapshot/reference?
- Is catalog publish atomic?
- Are publish events consumed idempotently?
- Is there a catalog rollback/revert policy?

## 7. Scenario 3 — Duplicate quote acceptance creates duplicate product orders

### Failure injection

Submit the quote acceptance/convert-to-order command twice:

- user double-click,
- API retry after timeout,
- gateway retry,
- client retries with same idempotency key,
- client retries without idempotency key,
- concurrent requests from two sessions.

### Why this matters

Duplicate order creation is one of the most dangerous lifecycle bugs.

It can trigger duplicate fulfillment, duplicate billing, and duplicate customer impact.

### Expected system behavior

- Stable idempotency key for quote conversion.
- Unique constraint on quote-to-order conversion where applicable.
- Optimistic or pessimistic locking around transition.
- Command handler returns existing order for duplicate accepted command.
- Audit shows duplicate attempt without creating duplicate commitment.
- Events are emitted once or deduped by consumers.

### Diagnosis questions

- Did two orders get created?
- Did two outbox events get created?
- Did two fulfillment requests get sent?
- Did the second request return idempotent result?
- Was one request rejected due to state transition guard?
- Did the audit trail record both attempts?

### Recovery strategy

If duplicate order was created:

1. contain downstream side effects;
2. identify canonical order;
3. cancel or mark duplicate order using explicit workflow;
4. prevent fulfillment/billing duplication;
5. repair audit/reference tables;
6. add regression test and constraint;
7. write postmortem with missing guard.

### Internal verification checklist

- Is idempotency implemented at API and domain level?
- Is there a DB unique constraint for quote conversion?
- Are events deduped?
- Are external fulfillment calls idempotent?
- Are client retry policies documented?
- Are duplicate commands tested with concurrency?

## 8. Scenario 4 — Kafka replay produces duplicate side effects

### Failure injection

Replay a topic or reset consumer offset in staging.

Target events:

- `QuoteAccepted`,
- `QuoteConvertedToOrder`,
- `ProductOrderValidated`,
- `ServiceOrderSubmitted`,
- `BillingHandoffRequested`.

### Why this matters

Replay is one of Kafka's strengths.

It becomes dangerous when consumers are not replay-safe.

### Expected system behavior

- Consumers dedupe by event ID or aggregate/version.
- External side effects are guarded by idempotency keys.
- Projections can rebuild safely.
- Replay mode can suppress external calls where appropriate.
- DLQ handling is defined.
- Metrics reveal replay progress and duplicate counts.

### Diagnosis questions

- Which consumers are projection-only?
- Which consumers trigger external side effects?
- Which consumers write to DB?
- Are inbox/processed-event tables used?
- Does consumer offset commit happen after durable side effect?
- Are duplicate events visible in metrics?

### Recovery strategy

- Pause affected consumers if side effects are unsafe.
- Identify duplicate side effects.
- Reconcile external systems.
- Mark duplicate attempts as ignored where safe.
- Repair projections if needed.
- Add replay-safe mode or consumer guard.

### Internal verification checklist

- Is there an official replay procedure?
- Are replay-safe and non-replay-safe consumers identified?
- Is event schema compatibility enforced?
- Are consumer offsets managed manually or via platform tooling?
- Is DLQ replay documented?
- Are external side effects idempotent?

## 9. Scenario 5 — PostgreSQL lock storm during order update or migration

### Failure injection

In staging, simulate:

- long-running transaction on order rows,
- concurrent update pressure,
- migration requiring heavy lock,
- missing index causing slow update/select,
- `SELECT FOR UPDATE` contention.

### Why this matters

Database lock incidents often look like application latency incidents.

Symptoms appear as timeouts, connection pool saturation, Kafka consumer lag, and cascading retries.

### Expected system behavior

- Lock waits visible in DB dashboard.
- Slow queries visible with query fingerprints.
- Connection pool saturation alert.
- API timeout budget prevents indefinite wait.
- Retry policy avoids amplification.
- Migration plan avoids high-risk locks.

### Diagnosis questions

- Which query is waiting?
- Which transaction holds the lock?
- Which endpoint/job caused it?
- Are retries increasing pressure?
- Is Kafka consumer lag rising?
- Are Kubernetes pods restarting due to liveness failures?
- Is migration involved?

### Recovery strategy

- Stop traffic/job causing pressure if safe.
- Kill only confirmed problematic transaction if approved.
- Disable unsafe retry path.
- Roll forward/abort migration according to plan.
- Add missing index or query fix after incident.
- Add lock testing to migration pipeline.

### Internal verification checklist

- Is DB lock monitoring available?
- Are migration locks tested before release?
- Are slow queries captured with bind-safe fingerprints?
- Is connection pool telemetry available?
- Are retry policies visible/configurable?
- Are repair procedures approved?

## 10. Scenario 6 — Failed schema migration during rolling deployment

### Failure injection

Use a staging deployment with two app versions and simulate a migration issue:

- old app cannot read new nullable/default field semantics,
- new app expects column before migration completed,
- migration locks large table,
- backfill partially completes,
- constraint validation fails,
- rollback attempts after irreversible data change.

### Why this matters

Enterprise systems often support rolling upgrades, customer-managed deployment windows, and on-prem upgrade variability.

Migration compatibility is not optional.

### Expected system behavior

- Expand-contract rollout plan.
- New schema compatible with old and new app versions during transition.
- Migration is observable.
- Backfill is chunked and resumable.
- Constraint validation is staged.
- Rollback/roll-forward decision is documented.

### Diagnosis questions

- Which app versions are running?
- Which migration version applied?
- Is schema partially migrated?
- Did backfill create inconsistent data?
- Are events generated with old or new schema?
- Can old version run safely after migration?

### Recovery strategy

- Stop rollout.
- Keep compatible version serving if possible.
- Resume/repair migration if safe.
- Roll forward preferred if data has changed irreversibly.
- Run validation queries.
- Document on-prem/customer upgrade guidance.

### Internal verification checklist

- What migration tool is used?
- Does CI test rolling compatibility?
- Is backfill resumable?
- Are large-table migrations reviewed separately?
- Are on-prem upgrade paths documented?
- Is migration rollback policy realistic?

## 11. Scenario 7 — Tenant isolation leak through support/export/reconciliation path

### Failure injection

In a safe test environment, create data for two tenants and test non-standard paths:

- support search,
- admin export,
- reconciliation report,
- Kafka replay tool,
- data repair script,
- background backfill,
- cache lookup,
- read model projection.

### Why this matters

Tenant isolation is often well-tested on normal APIs and poorly tested in operational tooling.

### Expected system behavior

- Tenant ID is required and validated everywhere.
- Repository layer enforces tenant predicate.
- Cache key includes tenant context.
- Events carry tenant metadata.
- Logs do not expose cross-tenant data.
- Admin/support override is explicit and audited.

### Diagnosis questions

- Which path leaked data?
- Was tenant context missing, defaulted, or ignored?
- Was leakage caused by DB query, cache, projection, event, or export?
- Did audit record access?
- Did alerting detect unusual cross-tenant access?

### Recovery strategy

- Disable affected tool/path.
- Identify exposed data scope.
- Preserve audit evidence.
- Notify internal security/compliance path according to policy.
- Repair projection/cache/export artifact.
- Add cross-tenant negative tests.
- Add repository guard or RLS defense-in-depth if appropriate.

### Internal verification checklist

- Are tenant tests present for operational tooling?
- Is tenant context mandatory in background jobs?
- Are support/admin actions audited?
- Are exports access-controlled?
- Does cache include tenant ID?
- Does event replay preserve tenant metadata?

## 12. Scenario 8 — Fulfillment fallout and stuck order recovery

### Failure injection

Simulate downstream fulfillment failure:

- service order API timeout,
- downstream accepts request but callback never arrives,
- downstream returns validation error,
- partial task completion,
- cancellation requested while fulfillment in progress,
- duplicate callback received.

### Why this matters

Order systems do not fail cleanly.

They get stuck between local state and external reality.

### Expected system behavior

- Fulfillment task state machine is explicit.
- Unknown outcome is modelled.
- Retry is classified as safe/unsafe.
- Manual fallout queue exists.
- Resume checkpoint is durable.
- Duplicate callback is idempotent.
- Order aggregate reflects partial progress honestly.

### Diagnosis questions

- Did downstream receive the request?
- Is external reference stored?
- Is callback correlation possible?
- Is task retry-safe?
- Is order in partial/fallout state?
- Has billing been triggered prematurely?
- Can operator resume from checkpoint?

### Recovery strategy

- Query integration attempts and external references.
- Determine external truth.
- Mark task as failed/unknown/fallout according to policy.
- Retry only if side effect is idempotent.
- Use manual intervention where required.
- Reconcile order, service order, inventory, and billing handoff.

### Internal verification checklist

- Is fallout queue implemented?
- Are downstream references durable?
- Is timeout handled as unknown outcome?
- Are duplicate callbacks idempotent?
- Are manual actions audited?
- Does runbook cover partial fulfillment?

## 13. Scenario 9 — Observability gap during quote-to-order journey

### Failure injection

Remove or break a propagation point in staging:

- missing correlation ID from REST to Kafka,
- missing causation ID from event to consumer,
- logs missing quote/order ID,
- trace context lost across async boundary,
- metric cardinality explosion suppresses dashboard usability,
- PII redaction removes useful business key without replacement.

### Why this matters

A system can be functionally correct and operationally opaque.

Operational opacity increases time to detect, time to diagnose, and customer communication risk.

### Expected system behavior

- Correlation ID survives across request/event/job boundaries.
- Causation ID explains command/event chain.
- Business IDs are logged safely.
- Traces link synchronous and asynchronous work where possible.
- Dashboards answer business journey questions.
- PII redaction does not destroy debuggability.

### Diagnosis questions

- Can we trace one quote from creation to order?
- Can we identify the event that caused a downstream call?
- Can support search by safe business ID?
- Can we identify affected tenant/customer without leaking PII?
- Are errors grouped by meaningful business/process dimension?

### Recovery strategy

- Add missing context propagation.
- Standardize event envelope metadata.
- Update logging middleware/interceptors.
- Add dashboard panel for missing journey stage.
- Add automated test for context propagation.

### Internal verification checklist

- What is the standard correlation ID field?
- Is causation ID used?
- Are quote/order IDs safe to log?
- Is trace context propagated across Kafka?
- Are dashboards journey-based?
- Are logs redacted consistently?

## 14. Scenario 10 — Authentication or authorization misconfiguration

### Failure injection

In a safe environment, simulate:

- wrong JWT audience accepted,
- expired token accepted,
- service token used as user token,
- user approves quote above authority,
- maker approves own quote where segregation of duties should apply,
- admin override without audit reason.

### Why this matters

Security bugs in Quote & Order can become commercial governance failures.

The risk is not only unauthorized data access.

It is unauthorized revenue commitment.

### Expected system behavior

- Token validation rejects wrong issuer/audience/expiry.
- Role is not treated as sufficient authority for every business action.
- Approval authority is evaluated against amount, margin, customer/account, and agreement context.
- Maker-checker rules are enforced where required.
- Admin/break-glass actions require reason and audit.
- Negative tests cover privilege escalation.

### Diagnosis questions

- Which layer accepted invalid identity/authority?
- Was auth enforced at endpoint only or domain command level?
- Was approval basis snapshotted?
- Did audit capture actor and reason?
- Are security alerts emitted for denied or suspicious action?

### Recovery strategy

- Disable unsafe action path.
- Rotate/reconfigure token validation if needed.
- Re-evaluate affected approvals/quotes/orders.
- Produce audit report.
- Add negative authorization tests.
- Review permission model and approval authority source.

### Internal verification checklist

- Are JWT validation tests present?
- Is service-to-service auth separated from user auth?
- Are approval permissions domain-aware?
- Is segregation of duties implemented?
- Are override actions audited?
- Are authorization failures monitored?

## 15. Game day scoring rubric

Use a simple scorecard after every scenario.

| Dimension | 1 — Weak | 3 — Usable | 5 — Strong |
|---|---|---|---|
| Detection | No alert/dashboard | Detected with manual effort | Fast, clear, actionable signal |
| Diagnosis | Requires tribal knowledge | Runbook helps partially | Clear journey reconstruction |
| Containment | Ad hoc | Known mitigation but rough | Safe, tested containment |
| Recovery | Manual and risky | Possible with expert help | Documented, repeatable, audited |
| Data safety | Unknown impact | Some validation queries | Full reconciliation/repair plan |
| Customer impact | Hard to explain | Approximate blast radius | Precise affected entity list |
| Audit evidence | Incomplete | Mostly reconstructable | Complete business evidence |
| Test coverage | Missing | Basic regression | Unit/integration/contract/E2E guard |
| Documentation | Outdated | Partial runbook | Updated runbook + ADR/backlog |
| Ownership | Unclear | Named owner during drill | Stable owner and follow-up plan |

A score below 3 does not mean failure.

It means the drill found valuable work.

## 16. Principal-level review after the game day

After each exercise, produce a review with this structure:

```md
# Game Day Review: <Scenario>

## Summary
What happened and what was tested?

## Hypothesis
What did we expect the system/team to handle?

## Result
Was the hypothesis confirmed, partially confirmed, or disproven?

## Timeline
Key detection, diagnosis, mitigation, recovery, and communication events.

## What worked
Concrete strengths.

## What failed or was unclear
Concrete gaps.

## Business impact model
Which quotes/orders/customers/tenants/workflows would be affected in production?

## Technical findings
Code, data, event, DB, deployment, security, observability findings.

## Operational findings
Runbook, dashboard, alert, ownership, communication findings.

## Follow-up actions
Owner, priority, due date, validation plan.

## Artifacts to update
Tests, runbooks, dashboards, ADRs, design docs, onboarding docs.
```

A good review does not merely say "we need better monitoring".

It says exactly which signal is missing, which dashboard should show it, which code path should emit it, and which runbook step depends on it.

## 17. Final internal verification checklist

Use this final checklist as a comprehensive onboarding maturity review.

### Domain and lifecycle

- Are quote and order state machines documented?
- Are illegal transitions tested?
- Are quote versioning and quote acceptance semantics clear?
- Are order cancellation/amendment/retry/resume semantics clear?
- Are fulfillment fallout states explicit?

### Catalog and pricing

- Is catalog versioning effective and auditable?
- Are accepted quotes tied to catalog/pricing snapshots?
- Can pricing decisions be explained after the fact?
- Are approval thresholds and margin guardrails testable?
- Is stale approval invalidation implemented?

### Data and events

- Is source-of-truth map documented?
- Are PostgreSQL constraints used for critical invariants?
- Is outbox/inbox implemented where needed?
- Are Kafka consumers idempotent?
- Is replay procedure documented?
- Are schema compatibility rules enforced?

### Security and audit

- Is JWT validation complete?
- Are service and user identities separated?
- Is authorization transition-aware?
- Is tenant isolation tested in background/support paths?
- Is audit evidence complete for approval, override, data repair, and lifecycle transition?

### Operations and reliability

- Are SLOs defined for business journeys?
- Are dashboards journey-oriented?
- Are alerts actionable?
- Are runbooks current?
- Are data repair procedures approved and auditable?
- Are ORR gates used before risky releases?
- Are game days or incident drills practiced?

### Engineering leadership

- Are PR review standards explicit?
- Are design docs and ADRs used for risky decisions?
- Are architecture reviews focused on trade-offs and failure modes?
- Are legacy refactors done incrementally with characterization tests?
- Are onboarding learnings turned into durable docs?

## 19. The final mental model

The whole series can be compressed into one sentence:

> Quote & Order engineering is the discipline of preserving commercial, operational, data, integration, and evidence truth across long-running, distributed, customer-specific enterprise workflows under continuous change.

That is why this role requires more than Java, Kafka, PostgreSQL, Kubernetes, or TMF knowledge.

It requires the ability to reason about:

- domain commitments,
- lifecycle invariants,
- distributed consistency,
- failure modes,
- customer impact,
- audit evidence,
- operational recovery,
- team decision quality.

The final standard is simple:

You should be able to review a change and say:

- why the design exists,
- when it fails,
- how failure is detected,
- how failure is contained,
- how data is repaired,
- how the customer is protected,
- how the decision is defended later.

That is the level of engineering this series was designed to build.
