# Part 025 — Java 17+ Service Architecture in Enterprise Backend Systems

> **Core idea:** a production Java service is not a pile of controllers, services, mappers, and DTOs. It is an executable boundary around business decisions, lifecycle invariants, data transactions, external contracts, and operational evidence.

Part ini membahas bagaimana membangun dan membaca service Java 17+ untuk sistem enterprise seperti CPQ, Quote Management, Order Management, and Quote-to-Cash. Fokusnya bukan syntax Java. Fokusnya adalah **architecture sense**: bagaimana service tetap modular, testable, observable, transaction-safe, and defensible ketika domain dan integrasi menjadi kompleks.

---

## 1. Source Boundary

Bagian ini memakai:

1. **Java 17 public documentation** sebagai baseline bahasa/platform. Oracle JDK 17 documentation mencakup language guide, API docs, release notes, migration guide, and tool specifications. Record classes, sealed classes, and pattern matching for `instanceof` adalah bagian penting untuk membuat model data/closed hierarchy lebih eksplisit di Java modern.
2. **Enterprise backend engineering practice umum** untuk layering, transaction boundary, API contracts, testing, observability, and deployment readiness.
3. **Quote & Order domain model dari part sebelumnya**: quote/order aggregate, state machine, consistency model, TMF vocabulary, and catalog-driven architecture.

Yang **tidak diasumsikan**:

- framework internal yang dipakai,
- package convention internal,
- apakah service memakai Spring Boot, Quarkus, Micronaut, Jakarta EE, atau framework lain,
- apakah arsitektur internal memakai strict DDD, hexagonal architecture, layered architecture, atau campuran,
- apakah model internal sama dengan TM Forum resource model,
- cara service discovery, authentication, tracing, and deployment internal.

Semua hal tersebut harus diverifikasi di repository dan dokumentasi internal.

## 2. Why Java Service Architecture Matters in Quote & Order

Dalam sistem biasa, service architecture sering diperlakukan sebagai urusan style:

```text
Controller -> Service -> Repository
```

Dalam Quote & Order enterprise, itu tidak cukup.

Service harus menjaga:

- quote lifecycle correctness,
- order lifecycle correctness,
- pricing and approval validity,
- catalog version consistency,
- customer/agreement authority,
- transaction boundary,
- idempotency,
- audit trail,
- Kafka event publication,
- API compatibility,
- tenant isolation,
- observability,
- safe rollback and migration.

Jika architecture boundary lemah, bug tidak muncul sebagai compile error. Bug muncul sebagai:

- quote accepted dengan stale price,
- order dibuat dua kali karena retry,
- approval bypass karena transition guard tersebar,
- audit tidak lengkap,
- event published tapi database transaction rollback,
- customer tenant leakage,
- migration tidak backward compatible,
- API response berubah dan mematahkan customer integration.

Service architecture yang baik membuat bug semacam ini **sulit terjadi** dan **mudah dideteksi**.

## 3. Senior-Level Mental Model

Jangan mulai dari package. Mulai dari pertanyaan ini:

```text
What decision does this service own?
What facts does it persist?
What commands can change those facts?
What invariants must never be violated?
What external contracts does it expose or consume?
What evidence does it emit when a decision is made?
```

Untuk service Quote Management, contohnya:

```text
Owned decision:
  Whether a quote can move from Draft/Priced/PendingApproval/Approved/Accepted.

Owned facts:
  Quote header, quote item, pricing snapshot, approval state, lifecycle history.

Commands:
  CreateQuote, ConfigureQuote, PriceQuote, SubmitForApproval, ApproveQuote,
  AcceptQuote, ExpireQuote, ConvertToOrder.

Invariants:
  Accepted quote must have valid price snapshot.
  Quote cannot be accepted if approval is required but not approved.
  Quote cannot be converted twice.

External contracts:
  REST API, Kafka events, maybe TMF648-compatible mapping.

Evidence:
  Audit event, domain event, structured logs, metrics, trace spans.
```

Service architecture adalah cara membuat ownership ini eksplisit di code.

## 4. A Production-Oriented Layer Model

Model layer yang berguna untuk enterprise Java service:

```text
api / inbound adapter
  REST controllers, request DTOs, response DTOs, auth extraction,
  idempotency header parsing, HTTP error mapping.

application
  command handlers, use cases, transaction boundary, orchestration inside service,
  authorization call, domain invocation, repository coordination, outbox write.

domain
  aggregate, value object, state machine, invariant, domain service,
  domain error, domain event.

infrastructure
  database mapper/repository implementation, Kafka producer/consumer,
  external client, cache, clock, ID generator, telemetry integration.

configuration
  dependency wiring, framework configuration, feature flags, properties,
  security configuration, observability configuration.
```

Yang penting bukan nama foldernya. Yang penting adalah arah dependency.

```text
api -> application -> domain
infrastructure -> application/domain interfaces
configuration -> everything for wiring only
```

Domain tidak boleh bergantung pada controller, framework HTTP, Kafka library, SQL mapper, or generated OpenAPI class.

Jika domain layer tahu tentang `HttpServletRequest`, Kafka `ConsumerRecord`, MyBatis `SqlSession`, or framework annotation yang tidak perlu, itu tanda coupling mulai bocor.

## 6. Layer Responsibilities

### 6.1 API Layer

API layer bertugas menerjemahkan dunia HTTP menjadi command/query internal.

Ia boleh melakukan:

- parse request,
- validate shape dasar,
- extract auth context,
- extract tenant context,
- extract idempotency key,
- map HTTP error,
- call application handler,
- map response DTO.

Ia tidak boleh menjadi tempat:

- pricing calculation,
- approval rule,
- lifecycle transition decision,
- database transaction orchestration,
- Kafka publishing decision,
- fallback business behavior.

Bad smell:

```java
@PostMapping("/{quoteId}/accept")
public QuoteResponse accept(@PathVariable String quoteId) {
    Quote quote = quoteMapper.findById(quoteId);
    if (quote.getStatus().equals("APPROVED") && quote.getTotal().compareTo(BigDecimal.ZERO) > 0) {
        quote.setStatus("ACCEPTED");
        quoteMapper.update(quote);
        kafkaTemplate.send("quote-events", quote);
    }
    return mapper.toResponse(quote);
}
```

Masalah:

- state transition tersebar di controller,
- status string rapuh,
- tidak jelas transaction boundary,
- event mungkin terkirim sebelum/di luar commit,
- no authorization guard,
- no audit,
- no idempotency,
- no invariant name.

Lebih sehat:

```java
@PostMapping("/{quoteId}/accept")
public QuoteResponse accept(
    @PathVariable String quoteId,
    @RequestHeader("Idempotency-Key") String idempotencyKey,
    AuthenticatedUser user
) {
    var command = new AcceptQuoteCommand(
        new QuoteId(quoteId),
        new IdempotencyKey(idempotencyKey),
        UserContext.from(user)
    );

    var result = acceptQuoteHandler.handle(command);
    return quoteApiMapper.toResponse(result.quote());
}
```

Controller menjadi adapter, bukan decision center.

### 6.2 Application Layer

Application layer adalah use-case boundary.

Ia bertugas:

- membuka transaction,
- load aggregate,
- call authorization port,
- call domain method,
- persist aggregate,
- write audit/outbox in same transaction,
- return result.

Contoh:

```java
public final class AcceptQuoteHandler {
    private final QuoteRepository quotes;
    private final AuthorizationPort authorization;
    private final AuditPort audit;
    private final OutboxPort outbox;
    private final Clock clock;

    @Transactional
    public AcceptQuoteResult handle(AcceptQuoteCommand command) {
        authorization.require(command.user(), Permission.ACCEPT_QUOTE, command.quoteId());

        Quote quote = quotes.getForUpdate(command.quoteId());

        QuoteAccepted event = quote.accept(
            command.user().userId(),
            Instant.now(clock),
            command.idempotencyKey()
        );

        quotes.save(quote);
        audit.record(AuditEntry.from(event, command.user()));
        outbox.enqueue(event);

        return new AcceptQuoteResult(quote);
    }
}
```

Catatan:

- `Quote.accept(...)` memegang invariant.
- Handler memegang orchestration.
- Repository memegang persistence.
- Outbox ditulis dalam transaction yang sama.

### 6.3 Domain Layer

Domain layer harus menjawab:

```text
Can this business action happen now?
If yes, what state changes and domain events result?
If no, what named business error explains why?
```

Contoh:

```java
public final class Quote {
    private final QuoteId id;
    private QuoteState state;
    private PriceSnapshot priceSnapshot;
    private ApprovalState approvalState;
    private QuoteVersion version;
    private boolean convertedToOrder;

    public QuoteAccepted accept(UserId actor, Instant acceptedAt, IdempotencyKey key) {
        ensureNotConverted();
        ensureStateAllowsAcceptance();
        ensurePriceStillValidAt(acceptedAt);
        ensureApprovalSatisfied();

        this.state = QuoteState.ACCEPTED;

        return new QuoteAccepted(
            id,
            version,
            actor,
            acceptedAt,
            key,
            priceSnapshot.total()
        );
    }

    private void ensureStateAllowsAcceptance() {
        if (state != QuoteState.APPROVED) {
            throw new IllegalQuoteTransition(state, QuoteState.ACCEPTED);
        }
    }
}
```

Domain method harus punya nama bisnis. Jangan sembunyikan state mutation di generic setter.

Bad smell:

```java
quote.setStatus("ACCEPTED");
quote.setUpdatedAt(now);
```

Lebih baik:

```java
quote.accept(actor, now, idempotencyKey);
```

Method name menjadi business command.

### 6.4 Infrastructure Layer

Infrastructure layer boleh tahu detail:

- SQL,
- MyBatis mapper,
- Kafka topic,
- HTTP client,
- cache,
- framework config,
- telemetry client,
- secret/config mechanism.

Tetapi ia tidak boleh mengambil business decision.

Contoh mapper event:

```java
public final class QuoteEventMapper {
    public OutboxRecord toOutboxRecord(QuoteAccepted event) {
        return new OutboxRecord(
            event.eventId(),
            "quote.accepted.v1",
            event.quoteId().value(),
            serialize(event),
            event.acceptedAt()
        );
    }
}
```

Mapper boleh mentransformasi. Ia tidak boleh memutuskan apakah quote boleh accepted.

## 7. DTO, Domain Model, Persistence Model, and Event Model

Satu kesalahan umum di enterprise Java service adalah memakai satu class untuk semuanya.

```text
QuoteDto = API request/response
QuoteEntity = database row
Quote = domain aggregate
QuoteEvent = Kafka event
```

Keempatnya berbeda.

### 7.1 API DTO

API DTO adalah contract ke consumer.

Ia harus stabil, backward compatible, and documented.

```java
public record QuoteResponse(
    String id,
    String state,
    String version,
    MoneyResponse totalPrice,
    List<QuoteItemResponse> items,
    OffsetDateTime validUntil
) {}
```

API DTO bisa membawa field yang nyaman untuk consumer, tetapi tidak selalu cocok sebagai domain model.

### 7.2 Domain Model

Domain model menjaga invariant.

```java
public final class Quote {
    private QuoteId id;
    private QuoteState state;
    private QuoteVersion version;
    private List<QuoteItem> items;
    private PriceSnapshot priceSnapshot;
}
```

Domain model tidak perlu mengikuti JSON contract.

### 7.3 Persistence Model

Persistence model mengikuti kebutuhan SQL.

```java
public record QuoteRow(
    UUID id,
    String tenantId,
    String state,
    long version,
    BigDecimal totalAmount,
    String currency,
    Instant validUntil,
    Instant createdAt,
    Instant updatedAt
) {}
```

Persistence model bisa memiliki field teknis: row version, deleted flag, tenant column, partition key, audit metadata.

### 7.4 Event Model

Event model adalah published fact.

```java
public record QuoteAcceptedEventV1(
    String eventId,
    String correlationId,
    String causationId,
    String tenantId,
    String quoteId,
    long quoteVersion,
    String acceptedBy,
    Instant acceptedAt,
    MoneyPayload totalPrice
) {}
```

Event model harus replay-safe dan versioned.

### 7.5 Why Separation Matters

Jika satu class dipakai untuk semua layer:

- API change menjadi DB change,
- DB optimization menjadi API breaking change,
- domain invariant bocor ke serialization annotation,
- internal field tidak sengaja expose ke consumer,
- event replay bergantung pada class domain terbaru,
- migration menjadi sulit.

Separation bukan ceremony. Separation adalah risk control.

## 8. Java 17+ Features That Help Architecture

### 8.1 Records for Value Carriers

Oracle documentation describes record classes as a special kind of class for modelling plain data aggregates with less ceremony.

Gunakan records untuk:

- command objects,
- query objects,
- immutable DTO,
- event payload,
- simple value carrier,
- test fixture input.

Contoh:

```java
public record AcceptQuoteCommand(
    QuoteId quoteId,
    UserContext user,
    IdempotencyKey idempotencyKey,
    CorrelationId correlationId
) {}
```

Jangan pakai record untuk aggregate yang perlu lifecycle mutation internal kompleks.

Bad use:

```java
public record Quote(
    QuoteId id,
    QuoteState state,
    List<QuoteItem> items
) {}
```

Jika `Quote` perlu transition method dan consistency rule, class biasa sering lebih cocok.

### 8.2 Sealed Classes for Closed Domain Outcomes

Oracle documentation explains sealed classes/interfaces as a way to specify which classes are permitted to extend or implement a type.

Gunakan sealed types untuk closed hierarchy:

```java
public sealed interface QuoteCommandResult
    permits QuoteCommandResult.Accepted,
            QuoteCommandResult.Rejected,
            QuoteCommandResult.NoOp {

    record Accepted(Quote quote, QuoteAccepted event) implements QuoteCommandResult {}
    record Rejected(QuoteRejectionReason reason) implements QuoteCommandResult {}
    record NoOp(String reason) implements QuoteCommandResult {}
}
```

Manfaat:

- result type eksplisit,
- compiler membantu exhaustiveness di pattern matching/switch jika versi Java mendukung,
- menghindari stringly-typed outcome,
- bagus untuk domain decision yang finite.

### 8.3 Pattern Matching for `instanceof`

Pattern matching for `instanceof` membuat type check dan extraction lebih singkat dan robust.

Contoh:

```java
if (error instanceof QuoteDomainException quoteError) {
    return errorMapper.toApiError(quoteError);
}
```

Gunakan untuk clarity, bukan untuk membuat giant type-dispatch procedural code.

### 8.4 Avoid Preview Features Unless Explicitly Allowed

Java 17 memiliki beberapa feature yang pada saat itu masih preview, misalnya pattern matching for switch. Jangan memakai preview feature di production enterprise kecuali:

- build tool mengaktifkan preview secara resmi,
- runtime environment konsisten,
- policy internal mengizinkan,
- compatibility impact dipahami,
- team sepakat.

Enterprise codebase biasanya lebih menghargai stability daripada syntax novelty.

## 9. Command Handling Pattern

Untuk domain-heavy system, command handling sering lebih jelas daripada generic service method.

```text
HTTP request -> API DTO -> Command -> Handler -> Aggregate -> Repository -> Outbox/Audit
```

Contoh command:

```java
public record CreateOrderFromQuoteCommand(
    QuoteId quoteId,
    CustomerId customerId,
    TenantId tenantId,
    UserContext actor,
    IdempotencyKey idempotencyKey,
    CorrelationId correlationId
) {}
```

Handler:

```java
public final class CreateOrderFromQuoteHandler {
    private final QuoteRepository quotes;
    private final OrderRepository orders;
    private final IdempotencyRepository idempotency;
    private final OutboxPort outbox;

    @Transactional
    public CreateOrderFromQuoteResult handle(CreateOrderFromQuoteCommand command) {
        return idempotency.execute(command.idempotencyKey(), () -> {
            Quote quote = quotes.getForUpdate(command.quoteId());
            Order order = Order.createFromAcceptedQuote(quote, command.actor(), command.correlationId());

            orders.save(order);
            quotes.markConvertedToOrder(quote.id(), order.id());
            outbox.enqueueAll(order.domainEvents());

            return new CreateOrderFromQuoteResult(order.id(), order.state());
        });
    }
}
```

Kenapa command handler membantu:

- satu use case punya satu entry point,
- authorization/idempotency/transaction mudah ditemukan,
- test bisa fokus ke command behavior,
- PR review lebih jelas,
- failure mode lebih mudah dimodelkan.

## 10. Query Handling Pattern

Tidak semua endpoint perlu domain aggregate.

Query endpoint sering butuh optimized read model:

```java
public record SearchQuotesQuery(
    TenantId tenantId,
    Optional<CustomerId> customerId,
    Optional<QuoteState> state,
    PageRequest pageRequest
) {}
```

Query handler:

```java
public final class SearchQuotesHandler {
    private final QuoteReadRepository readRepository;
    private final AuthorizationPort authorization;

    public Page<QuoteSummary> handle(SearchQuotesQuery query, UserContext user) {
        authorization.requireTenantAccess(user, query.tenantId());
        return readRepository.search(query);
    }
}
```

Command side dan query side boleh berbeda model.

```text
Command model:
  invariant-rich aggregate.

Query model:
  optimized projection, pagination, filtering, search.
```

Jangan memaksa aggregate besar hanya untuk list page.

## 11. Transaction Boundary

Application handler biasanya tempat paling tepat untuk transaction boundary.

Rule of thumb:

```text
One business command = one local DB transaction, unless intentionally designed otherwise.
```

Dalam transaction:

- check idempotency,
- load aggregate with locking if needed,
- enforce invariant,
- persist state,
- write audit,
- write outbox.

Di luar transaction:

- publish Kafka event via outbox relay,
- call slow external system jika tidak harus atomic,
- send email/notification,
- run asynchronous decomposition.

Bad smell:

```text
DB update -> external HTTP call -> DB update -> Kafka publish
```

Masalah:

- jika HTTP call sukses tapi DB update kedua gagal,
- jika Kafka publish gagal setelah DB commit,
- jika transaction panjang menahan lock,
- jika external timeout membuat DB lock storm.

Lebih sehat:

```text
transaction:
  validate command
  update local state
  write outbox event

async:
  outbox relay publishes event
  downstream consumer performs external work
  result event updates process state
```

## 12. Error Taxonomy

Enterprise services butuh error taxonomy yang jelas.

Minimal:

```text
Domain error
  Business rule violation: illegal transition, price expired, approval required.

Authorization error
  User/role/tenant/action not allowed.

Validation error
  Request shape invalid, missing required field, invalid enum.

Conflict error
  Optimistic lock conflict, duplicate idempotency key with different payload.

Not found error
  Resource not found within authorized scope.

Integration error
  Downstream timeout, unavailable, invalid response.

Infrastructure error
  DB unavailable, Kafka unavailable, config missing.
```

Jangan semua dilempar sebagai `RuntimeException` lalu map ke HTTP 500.

Contoh domain error:

```java
public abstract class QuoteDomainException extends RuntimeException {
    private final String code;
    private final QuoteId quoteId;

    protected QuoteDomainException(String code, QuoteId quoteId, String message) {
        super(message);
        this.code = code;
        this.quoteId = quoteId;
    }

    public String code() { return code; }
    public QuoteId quoteId() { return quoteId; }
}

public final class PriceExpired extends QuoteDomainException {
    public PriceExpired(QuoteId quoteId) {
        super("QUOTE_PRICE_EXPIRED", quoteId, "Quote price snapshot is no longer valid.");
    }
}
```

API error mapping:

```json
{
  "code": "QUOTE_PRICE_EXPIRED",
  "message": "Quote price snapshot is no longer valid.",
  "correlationId": "...",
  "details": {
    "quoteId": "..."
  }
}
```

Good error design helps:

- customer integration,
- support diagnosis,
- alert triage,
- test assertions,
- audit explanation,
- operational dashboards.

## 13. Validation: Shape, Reference, Business, and Authorization

Pisahkan validation menjadi beberapa level.

### 13.1 Shape Validation

Dikerjakan di API boundary.

Contoh:

- required field,
- string length,
- enum parse,
- date format,
- list size limit,
- money scale.

### 13.2 Reference Validation

Dikerjakan di application/domain boundary.

Contoh:

- product offering exists,
- customer exists,
- agreement exists,
- catalog version valid,
- quote belongs to tenant.

### 13.3 Business Validation

Dikerjakan di domain.

Contoh:

- quote cannot be accepted before approval,
- discount requires approval,
- order cannot be cancelled after terminal completion,
- amendment must reference active installed product.

### 13.4 Authorization Validation

Dikerjakan sebelum action berubah state.

Contoh:

- user can approve discount threshold,
- user can accept quote for account,
- user can retry fallout task,
- operator can perform manual override.

Bad smell:

```text
Validation duplicated in controller, service, repository, and UI with inconsistent rules.
```

Better:

```text
API validates shape.
Application validates reference/authorization.
Domain validates business invariant.
Database validates persistence integrity.
```

## 14. Value Objects

Primitive obsession adalah sumber banyak bug enterprise.

Bad:

```java
void approve(String quoteId, String userId, String amount, String currency, String tenantId)
```

Better:

```java
void approve(QuoteId quoteId, UserId userId, Money threshold, TenantId tenantId)
```

Value object membantu:

- validation centralized,
- type safety,
- API/domain conversion explicit,
- test readability,
- SQL mapping clarity.

Contoh:

```java
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        if (amount.scale() > currency.getDefaultFractionDigits()) {
            throw new IllegalArgumentException("Invalid money scale");
        }
    }

    public Money plus(Money other) {
        requireSameCurrency(other);
        return new Money(amount.add(other.amount), currency);
    }

    private void requireSameCurrency(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch");
        }
    }
}
```

Untuk CPQ/pricing, `Money` bukan detail kecil. Itu correctness boundary.

## 15. State as Type, Not String

Bad:

```java
if ("APPROVED".equals(quote.getStatus())) { ... }
```

Better:

```java
public enum QuoteState {
    DRAFT,
    PRICED,
    PENDING_APPROVAL,
    APPROVED,
    ACCEPTED,
    EXPIRED,
    REJECTED,
    CANCELLED,
    CONVERTED_TO_ORDER
}
```

Even better untuk transition:

```java
public final class QuoteStateMachine {
    private static final Map<QuoteState, Set<QuoteState>> ALLOWED = Map.of(
        DRAFT, Set.of(PRICED, CANCELLED),
        PRICED, Set.of(PENDING_APPROVAL, APPROVED, EXPIRED, CANCELLED),
        PENDING_APPROVAL, Set.of(APPROVED, REJECTED, EXPIRED, CANCELLED),
        APPROVED, Set.of(ACCEPTED, EXPIRED, CANCELLED),
        ACCEPTED, Set.of(CONVERTED_TO_ORDER),
        CONVERTED_TO_ORDER, Set.of(),
        EXPIRED, Set.of(),
        REJECTED, Set.of(),
        CANCELLED, Set.of()
    );

    public void requireTransition(QuoteState from, QuoteState to) {
        if (!ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
            throw new IllegalQuoteTransition(from, to);
        }
    }
}
```

Transition rule harus mudah dibaca dan mudah diuji.

## 16. Handling Idempotency at Service Level

Idempotency bukan hanya API concern. Ia harus masuk application command boundary.

```text
Idempotency key + command fingerprint + tenant + actor + operation type
```

Rules:

- same key + same fingerprint returns same result,
- same key + different fingerprint returns conflict,
- idempotency record created/checked in transaction,
- side effects derive from persisted state/outbox,
- retry must not duplicate order/quote/event.

Pseudo-flow:

```java
@Transactional
public Result handle(Command command) {
    var previous = idempotency.find(command.scope(), command.key());
    if (previous.isSameFingerprint(command.fingerprint())) {
        return previous.result();
    }
    if (previous.existsWithDifferentFingerprint()) {
        throw new IdempotencyConflict(command.key());
    }

    Result result = executeBusinessChange(command);
    idempotency.record(command.scope(), command.key(), command.fingerprint(), result);
    return result;
}
```

Idempotency belongs close to state mutation.

## 17. Event Publication Boundary

Do not publish Kafka events directly from domain object or controller.

Bad:

```java
quote.accept();
kafkaTemplate.send("quote.accepted", quote);
repository.save(quote);
```

Better:

```text
transaction:
  quote.accept()
  repository.save(quote)
  outbox.enqueue(QuoteAccepted)

after commit:
  outbox relay publishes Kafka event
```

Domain event should represent business fact:

```java
public record QuoteAccepted(
    EventId eventId,
    TenantId tenantId,
    QuoteId quoteId,
    QuoteVersion quoteVersion,
    UserId acceptedBy,
    Instant acceptedAt,
    CorrelationId correlationId,
    CausationId causationId
) {}
```

Event publication is infrastructure. Event meaning is domain.

## 18. Framework Annotations: Useful but Dangerous

Framework annotations are not architecture.

Bad smell:

```java
@Service
public class QuoteService {
    @Autowired QuoteMapper mapper;
    @Autowired KafkaTemplate kafka;
    @Autowired RestTemplate rest;

    public void doEverything(...) { ... }
}
```

Annotation-driven wiring is fine, but it can hide boundary problems.

Check:

- Are transactions placed at correct command boundary?
- Are repositories interfaces or direct mapper calls everywhere?
- Does domain depend on framework annotations?
- Are validation annotations being mistaken for business rules?
- Are async annotations used without failure model?
- Are retries applied without idempotency?

Framework power should reinforce architecture, not replace it.

## 19. Observability Built Into the Service

Every command handler should make operational evidence easy.

Minimum signal:

- command name,
- tenant ID,
- aggregate ID,
- actor ID where appropriate,
- correlation ID,
- causation ID,
- idempotency key hash,
- transition from/to,
- result code,
- latency,
- downstream dependency latency,
- retry count,
- outbox event count.

Structured log example:

```json
{
  "event": "quote_command_completed",
  "command": "AcceptQuote",
  "tenantId": "t-123",
  "quoteId": "q-456",
  "fromState": "APPROVED",
  "toState": "ACCEPTED",
  "correlationId": "c-789",
  "causationId": "api-request-001",
  "result": "success",
```

Metric examples:

```text
quote_command_total{command="AcceptQuote", result="success"}

```

Observability is part of service design, not post-release cleanup.

## 20. Security and Tenant Boundary in Code Structure

Tenant isolation must not rely on developer memory.

Bad:

```java
quoteMapper.findById(quoteId);
```

Better:

```java
quoteRepository.getByIdWithinTenant(tenantId, quoteId);
```

Repository method names should encode scope.

```java
Optional<Quote> findByTenantAndId(TenantId tenantId, QuoteId quoteId);
Page<QuoteSummary> searchWithinTenant(TenantId tenantId, QuoteSearchCriteria criteria);
```

Application handler should pass `TenantId` explicitly.

Never infer tenant from request body alone. Prefer authenticated/security context or trusted gateway context, then validate consistency with resource ownership.

## 21. Testing Strategy for Service Architecture

### 21.1 Domain Tests

Fast, no framework, no DB.

```java
@Test
void acceptedQuoteCannotBeAcceptedAgain() {
    Quote quote = QuoteFixtures.acceptedQuote();

    assertThatThrownBy(() -> quote.accept(actor, now, key))
        .isInstanceOf(IllegalQuoteTransition.class);
}
```

### 21.2 Application Handler Tests

Use mocks/fakes for ports. Verify orchestration:

- authorization called,
- aggregate loaded with correct tenant scope,
- transaction semantics if integration test,
- outbox event written,
- audit written,
- idempotency behavior.

### 21.3 Persistence Tests

Use real PostgreSQL/Testcontainers if possible.

- mapper correctness,
- optimistic locking,
- row-level tenant scoping,
- query plan for heavy queries,
- migration compatibility.

### 21.4 API Tests

- request validation,
- response compatibility,
- error mapping,
- idempotency header behavior,
- authorization negative cases.

### 21.5 Event Tests

- event schema,
- version compatibility,
- outbox record content,
- replay-safe consumer behavior.

## 22. Common Anti-Patterns

### 22.1 Anemic Domain with Giant Service

Symptoms:

- domain objects have only getters/setters,
- all business rules in `QuoteService`,
- service method has 300 lines,
- tests mock everything and prove little,
- lifecycle rules duplicated.

Risk:

- invariant drift,
- approval bypass,
- impossible PR review,
- fragile refactor.

### 22.2 DTO Leakage Everywhere

Symptoms:

- controller DTO passed directly to repository,
- API field names appear in SQL mapper,
- OpenAPI generated class used as domain aggregate,
- event schema uses internal persistence class.

Risk:

- API change breaks persistence,
- persistence change breaks API,
- accidental field exposure,
- versioning impossible.

### 22.3 Stringly-Typed Domain

Symptoms:

- state as string,
- action as string,
- permission as string,
- amount as string,
- tenant as string everywhere.

Risk:

- typo bugs,
- invalid states,
- no compiler help,
- weak tests.

### 22.4 Hidden Transaction Boundary

Symptoms:

- nested service calls with unclear `@Transactional`,
- external calls inside transaction,
- event publishing inside transaction but outside outbox,
- no lock/optimistic version policy.

Risk:

- duplicate events,
- lock contention,
- partial side effects,
- race conditions.

### 22.5 Framework-Centric Architecture

Symptoms:

- packages named only by framework roles,
- domain class full of framework annotations,
- tests require full application context for everything,
- business logic hard to run in isolation.

Risk:

- slow feedback,
- poor domain clarity,
- hard migration,
- poor modularity.

## 23. PR Review Checklist

When reviewing Java service changes, ask:

### Domain and Lifecycle

- What business command is being implemented?
- Which aggregate owns the invariant?
- Are illegal states impossible or merely undocumented?
- Is state transition explicit and tested?
- Are business errors named and mapped correctly?

### API Contract

- Is API DTO separate from domain/persistence/event model?
- Is the change backward compatible?
- Are new enum values safe for consumers?
- Is error response stable?
- Is idempotency required?

### Transaction and Data

- Where is transaction boundary?
- Are external calls inside transaction?
- Is locking/optimistic versioning correct?
- Is outbox written atomically with state change?
- Are tenant filters enforced at repository boundary?

### Events

- Is event a business fact, not a command?
- Is event schema versioned?
- Is event replay-safe?
- Is correlation/causation included?
- Are duplicate events safe?

### Observability

- Can support trace this command in logs?
- Are metrics emitted for success/failure?
- Are domain errors counted?
- Is correlation ID propagated?
- Is audit written for business decision?

### Security

- Is authorization checked before mutation?
- Is tenant boundary explicit?
- Are sensitive fields redacted?
- Are operator/manual paths audited?

### Testing

- Are invariant tests present?
- Are negative tests present?
- Are mapper/SQL tests present if query changed?
- Are API compatibility tests updated?
- Are event contract tests updated?

## 26. Key Takeaways

1. Java service architecture is a correctness mechanism, not folder decoration.
2. API DTO, domain model, persistence model, and event model should usually be separate.
3. Application handlers are good places for transaction, authorization, idempotency, audit, and outbox coordination.
4. Domain objects should expose business commands, not generic setters.
5. Java 17 records and sealed classes help express immutable carriers and closed outcome hierarchies, but they do not replace modelling discipline.
6. Transaction and event boundaries are where many production bugs are born.
7. Senior PR review should focus on invariant, compatibility, data safety, observability, and operational recoverability.
