# Part 031 — Java Service Productivity Patterns

## 1. Source notes and scope boundary

This part uses public Java ecosystem practices and general enterprise backend engineering experience.

Public references to verify independently:

- Spring Boot documentation describes development-time services such as Docker Compose and Testcontainers support for dependencies used during local development.
- Apache Maven documentation describes multi-module project behavior and reactor build concepts.
- Testcontainers documentation provides Java modules for running disposable infrastructure dependencies such as PostgreSQL during tests.
- OpenTelemetry documentation provides vendor-neutral APIs, SDKs, and instrumentation patterns for telemetry.

This part does **not** assume that CSG Quote & Order uses Spring Boot, Maven, Gradle, Testcontainers, Docker Compose, OpenTelemetry Java Agent, or a specific internal service template.

Use the `Internal verification checklist` sections to verify actual team conventions.

## 2. Core thesis

Java service productivity is not mostly about typing code faster.

It is about reducing the time and cognitive load between:

1. understanding the change,
2. finding the right code,
3. running the service,
4. writing the test,
5. debugging the behavior,
6. validating integration impact,
7. reviewing safely,
8. deploying confidently,
9. diagnosing production behavior later.

In enterprise Quote & Order systems, productivity loss often comes from:

- unclear module boundaries,
- slow builds,
- hard-to-run services,
- hidden configuration,
- brittle tests,
- inconsistent fixtures,
- hard-to-read mapper SQL,
- poor diagnostics,
- unclear ownership,
- dependency drift,
- missing golden paths.

A senior engineer improves productivity by making the safe path the easiest path.

## 3. Productivity pattern map

A productive Java service has strong defaults in these areas:

| Area | Productivity question |
|---|---|
| Project structure | Can an engineer find the right place to change behavior? |
| Build system | Can an engineer build only what they need quickly? |
| Local run | Can an engineer run service dependencies predictably? |
| Configuration | Can an engineer understand active profiles and defaults? |
| Testing | Can an engineer write confidence-building tests cheaply? |
| Fixtures | Can an engineer create realistic quote/order data without pain? |
| Diagnostics | Can an engineer explain failures from logs/traces/errors? |
| Dependencies | Can an engineer upgrade safely and avoid drift? |
| API/event contracts | Can an engineer detect compatibility issues early? |
| Documentation | Can a new engineer make first useful PR without tribal knowledge? |

Productivity is a property of the system around the engineer.

## 4. Service structure patterns

A Java service becomes easier to work with when its structure exposes intent.

A useful service structure usually separates:

- API/controller layer,
- application/use-case layer,
- domain model/rules,
- persistence/repository/mappers,
- external adapters,
- event publishing/consuming,
- configuration,
- test fixtures,
- operational support.

Example conceptual layout:

```txt
quote-service/
  src/main/java/com/example/quote/
    api/
      QuoteController.java
      dto/
    application/
      CreateQuoteCommandHandler.java
      AcceptQuoteCommandHandler.java
    domain/
      Quote.java
      QuoteState.java
      QuotePricingSnapshot.java
      QuoteLifecyclePolicy.java
    persistence/
      QuoteMapper.java
      QuoteRepository.java
    events/
      QuoteAcceptedEventPublisher.java
      QuoteEventEnvelope.java
    integration/
      CatalogClient.java
      PricingClient.java
    config/
      QuoteServiceConfiguration.java
  src/test/java/com/example/quote/
    fixtures/
    unit/
    integration/
    contract/
```

The exact package names do not matter as much as the ability to answer:

- where is business behavior expressed?
- where are transactions started?
- where are external calls made?
- where are events emitted?
- where are tests for each behavior?
- where are fixtures shared?

## 5. Avoiding architecture-by-folder-only

Layered packages do not guarantee good architecture.

A service can have packages named `api`, `service`, `repository`, and `domain` while still being hard to change.

Symptoms:

- controllers contain business rules,
- domain objects are passive DTOs,
- repository methods mutate lifecycle state directly,
- event publishing is scattered,
- transaction boundary is implicit,
- authorization checks are duplicated,
- fixtures depend on database rows directly,
- tests assert implementation details rather than behavior.

Senior review question:

> Does this structure make the important business invariants easier to find, test, and protect?

For Quote & Order, important invariants include:

- quote cannot be accepted with expired price,
- accepted quote should preserve pricing snapshot,
- approval evidence should match approved commercial terms,
- order state should be derivable from item/task state,
- outbox event should represent committed state,
- tenant boundary should be present in all data access paths.

## 6. Build productivity

Java enterprise builds can become slow because of:

- too many modules built by default,
- slow integration tests mixed with fast unit tests,
- annotation processing overhead,
- unnecessary dependency graph breadth,
- generated code every build,
- Docker image build inside local loop,
- no test categorization,
- no cache strategy,
- no module ownership.

### 6.1 Build feedback loops

Measure build loops separately:

| Loop | Target question |
|---|---|
| Compile changed module | Can I check syntax/type errors quickly? |
| Unit tests | Can I validate local behavior in seconds/minutes? |
| Mapper/integration tests | Can I validate DB behavior without full suite? |
| Contract tests | Can I validate API/event compatibility? |
| Full CI | Can release confidence be built automatically? |

Do not optimize only full CI.

Developer productivity depends heavily on the inner loops.

### 6.2 Maven multi-module ergonomics

If Maven is used, learn:

- parent POM conventions,
- module graph,
- dependency management,
- profiles,
- plugin management,
- reactor build behavior,
- how to build one module and required dependencies,
- how tests are split between Surefire/Failsafe if applicable.

Example commands to verify internally:

```bash
mvn -pl quote-service -am test
mvn -pl quote-service -DskipITs test
mvn -pl quote-service -Dtest=QuoteLifecycleTest test
mvn -pl quote-service -DskipTests package
```

Do not assume these exact profiles exist.

Document the real commands in the service README.

## 7. Local profile design

A productive Java service should have a predictable local mode.

A good local mode answers:

- where does PostgreSQL come from?
- where does Kafka come from?
- how are migrations applied?
- how are secrets replaced locally?
- how is tenant context seeded?
- how is auth mocked or simulated?
- how are downstream services simulated?
- how do I see logs/traces locally?
- how do I reset local state?

### 7.1 Local profile maturity

| Maturity | Experience |
|---|---|
| Ad hoc | Ask teammate for commands and configs |
| Scripted | One script starts most dependencies |
| Containerized | Docker Compose/Testcontainers handles dependencies |
| Golden path | README + scripts + fixtures + diagnostics work reliably |
| Self-service | New engineer gets first useful PR with minimal human help |

A senior engineer should improve local profile maturity over time.

### 7.2 Local config anti-patterns

Avoid:

- committing personal config,
- requiring real production credentials,
- undocumented environment variables,
- magic profile names,
- local behavior diverging too far from CI,
- tests requiring services started manually,
- local DB state that cannot be reset.

## 8. Test fixture productivity

In Quote & Order systems, test fixtures can make or break productivity.

Bad fixture pattern:

```java
Quote quote = new Quote();
quote.setState("APPROVED");
quote.setPrice(new BigDecimal("100"));
quote.setCustomerId("123");
// 50 more setters...
```

Problems:

- unclear business meaning,
- fragile when fields change,
- invalid states easy to create,
- tests hide intent,
- data builders duplicate everywhere.

Better fixture pattern:

```java
Quote quote = QuoteFixtures.approvedEnterpriseQuote()
    .withDiscountPercent(20)
    .withPriceValidUntil(clock.instant().plus(Duration.ofDays(5)))
    .build();
```

Even better, fixtures should encode domain language:

- `draftQuoteForEnterpriseCustomer()`
- `approvedQuoteWithExpiredPrice()`
- `acceptedQuoteAlreadyConvertedToOrder()`
- `orderInFalloutWithOneFailedItem()`
- `tenantAQuoteVisibleOnlyToTenantA()`

### 8.1 Fixture quality checklist

A good fixture is:

- deterministic,
- named by business state,
- valid by default,
- explicit when invalid,
- easy to override safely,
- usable in unit and integration tests,
- tenant-aware,
- compatible with migration tests,
- documented enough for new engineers.

## 9. Diagnostics inside Java services

Debuggability is productivity.

A Java service should expose enough diagnostic context to answer:

- what request/command happened?
- who/what actor initiated it?
- which tenant/customer/quote/order was involved?
- which version of quote/order was used?
- which downstream dependency failed?
- was failure validation, authorization, timeout, conflict, or unknown outcome?
- did we publish event/outbox row?
- what is the correlation ID?

### 9.1 Logging pattern

Prefer structured logs with stable fields:

```json
{
  "message": "Quote acceptance failed",
  "tenantId": "tenant-a",
  "quoteId": "Q-1001",
  "quoteVersion": 7,
  "reasonCode": "QUOTE_PRICE_EXPIRED",
  "correlationId": "corr-123",
  "actorType": "USER",
  "service": "quote-service"
}
```

Avoid:

- raw stack traces without domain context,
- PII in logs,
- high-cardinality values in metrics labels,
- inconsistent field names,
- logs that say `failed` but not why,
- logs without correlation ID.

### 9.2 Error taxonomy

A productive service has a clear error taxonomy:

| Category | Example | Developer benefit |
|---|---|---|
| Validation | invalid quote configuration | reproducible input issue |
| Authorization | approver lacks authority | security/path issue |
| Conflict | stale quote version | concurrency/lifecycle issue |
| Dependency | pricing service timeout | integration issue |
| Data | missing catalog snapshot | data/migration issue |
| Unknown outcome | downstream accepted but response lost | idempotency/reconciliation issue |

When errors are categorized, debugging gets faster.

## 10. Dependency hygiene

Enterprise Java services often suffer from dependency drift.

Symptoms:

- multiple versions of same library,
- transitive dependency surprises,
- security scan noise,
- shared library upgrades blocked by hidden coupling,
- old API versions kept forever,
- custom framework abstractions nobody owns.

### 10.1 Dependency review questions

Ask:

- Is this dependency needed at runtime or test-only?
- Is the version centrally managed?
- Does it introduce transitive vulnerabilities?
- Does it duplicate another library already used?
- Is it maintained?
- Does it create classpath conflicts?
- Does it increase startup time or memory materially?
- Can the same capability be provided by platform/golden path?

### 10.2 Shared library caution

Shared internal libraries can increase productivity when they standardize:

- authentication context,
- tenant propagation,
- event envelope,
- observability fields,
- error model,
- test fixtures,
- client resilience defaults.

They reduce productivity when they become:

- dumping ground,
- release coupling point,
- hidden framework,
- dependency upgrade bottleneck,
- source of magic behavior.

Treat shared libraries as products with owners, changelogs, and compatibility guarantees.

## 11. Java service golden path

A Java service golden path should provide:

- standard module template,
- build/test commands,
- local run profile,
- Dockerfile/container standard,
- health/readiness endpoints,
- structured logging defaults,
- OpenTelemetry defaults,
- auth/tenant context pattern,
- error model pattern,
- API documentation generation,
- Kafka producer/consumer template,
- PostgreSQL migration template,
- Testcontainers examples,
- CI/CD pipeline defaults,
- Kubernetes manifest defaults,
- runbook template.

The golden path is not meant to remove engineering judgment.

It removes accidental setup friction so engineers can spend judgment on domain risk.

## 12. Quote & Order Java productivity scenarios

### 12.1 Add new quote validation rule

A productive path should make it easy to:

1. find validation policy,
2. add unit test for valid/invalid cases,
3. add API integration test if response contract changes,
4. verify error code,
5. confirm audit/log behavior if relevant,
6. run only affected test suite,
7. update acceptance criteria evidence.

If this requires running the whole platform manually, productivity is poor.

### 12.2 Add new Kafka event field

A productive path should make it easy to:

1. find event schema/envelope,
2. update producer,
3. verify backward compatibility,
4. update fixture/sample event,
5. run producer/consumer tests,
6. verify trace/correlation propagation,
7. update documentation.

### 12.3 Add new database query

A productive path should make it easy to:

1. write mapper method,
2. run against real PostgreSQL locally/test,
3. seed realistic tenant data,
4. inspect `EXPLAIN`,
5. add index if needed,
6. verify tenant predicate,
7. add regression test.

## 14. PR review checklist for Java service productivity

When reviewing Java service changes, ask:

- Is the changed behavior located in the right layer?
- Is the business invariant easy to find?
- Are tests named by business behavior?
- Does the fixture express domain intent?
- Can a developer run the relevant tests quickly?
- Are logs/traces/errors diagnostic enough?
- Are tenant/security/audit fields preserved?
- Does the change follow service conventions?
- Does the dependency change have a reason?
- Does the PR improve or degrade local/CI feedback loop?
- Does documentation need an update?

Productivity is a review concern.

## 16. Summary

Java service productivity is created by systems:

- clear structure,
- fast builds,
- reliable local profiles,
- good fixtures,
- useful diagnostics,
- dependency hygiene,
- golden paths,
- documentation,
- ownership.
