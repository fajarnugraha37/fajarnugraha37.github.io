# Part 049 — Anti-Patterns and Failure Modes

> Engineering effectiveness work fails not because teams lack metrics, tools, dashboards, or process language.
> It fails because improvement systems become disconnected from delivery reality.

This part is a field guide for detecting when engineering effectiveness and developer experience work has started to drift.

The goal is not cynicism.

The goal is operational honesty.

A senior engineer should be able to look at a team, a platform, a CI pipeline, an incident process, a metric dashboard, or a quarterly roadmap and ask:

- Are we reducing real friction?
- Are we moving risk earlier?
- Are we improving flow without hiding quality problems?
- Are we making engineers more capable, or just more compliant?
- Are we solving systemic problems, or producing artifacts about them?

## 2. Core thesis

Every engineering effectiveness practice has a shadow version.

| Good practice | Shadow version |
|---|---|
| Flow metrics | Metric theater |
| DORA metrics | Ranking teams by proxy numbers |
| DevEx surveys | Satisfaction theater without action |
| Platform engineering | Centralized bureaucracy with nicer branding |
| Golden paths | Mandatory path that blocks legitimate variation |
| Observability | Dashboard sprawl without diagnosis power |
| Alerting | Interrupt factory |
| Incident review | Blame laundering |
| Automation | Brittle script pile |
| Governance | Approval tax |
| Architecture standards | Document-only enforcement |
| Agile/Scrum | Ceremony without learning |

The senior engineer's job is not just to implement good practices.

The senior engineer must detect when good practices have degraded into their shadow forms.

---

## 3. Why anti-patterns are especially dangerous in enterprise systems

In simple systems, a bad practice is visible quickly.

In enterprise Quote & Order systems, bad practices can hide for months because:

- the system has many services;
- customer journeys cross team boundaries;
- deployments may span cloud, on-prem, tenant-specific, and integration-specific environments;
- business state is long-lived;
- failures may appear as data inconsistency, stuck orders, missing events, or manual correction effort;
- governance can hide under compliance language;
- delivery latency can be normalized as "enterprise reality";
- platform gaps can be compensated by heroic senior engineers.

The result is dangerous:

> The system can look mature while engineers are silently paying a huge friction tax.

## 5. Anti-pattern 1 — Metric theater

Metric theater happens when measurement becomes performative.

Symptoms:

- dashboards are presented in reviews but do not change backlog priority;
- metrics are reported without narrative;
- teams debate whether numbers are "good" instead of what friction they reveal;
- metrics are used to compare teams without context;
- the measurement pipeline is not trusted;
- the same metric appears every quarter with no action.

Bad example:

```text
Our lead time is 5.3 days.
This is below the target of 6 days.
No action required.
```

Better example:

```text
Median lead time is acceptable, but p90 lead time is driven by review delay on cross-service API changes.
The improvement bet is to add earlier design review for high-risk API changes and define primary reviewer routing.
```

Metric theater is not caused by having metrics.

It is caused by measuring without inquiry.

---

## 6. Metric interpretation checklist

Before using any engineering metric, answer:

- What decision can this metric influence?
- What behavior could this metric unintentionally incentivize?
- What qualitative evidence explains the number?
- Is the metric actionable at team level?
- Is the metric lagging, leading, or diagnostic?
- Can the metric be gamed?
- Does the metric represent customer impact, engineer experience, or internal process state?
- What will we stop, start, or change because of it?

If no decision changes, the metric is probably decoration.

## 7. Anti-pattern 2 — DORA cargo cult

DORA metrics are powerful.

But they become cargo cult when organizations copy metric names without understanding system context.

Failure modes:

- treating deployment frequency as a universal speed contest;
- measuring change lead time inconsistently across teams;
- counting all production incidents as change failures even when unrelated to deployment;
- ignoring batch size and deployment topology;
- using MTTR as a single number instead of decomposing recovery;
- setting elite-performance targets without platform investment;
- comparing cloud-native teams and on-prem enterprise release teams without normalization.

In Quote & Order, this matters because one "change" can involve:

- Java service code;
- OpenAPI contract;
- database migration;
- Kafka event schema;
- pricing rule;
- product catalog model;
- tenant configuration;
- Kubernetes deployment;
- GitOps sync;
- external BSS/OSS integration;
- customer-specific rollout.

A single DORA number may hide several value streams.

---

## 8. Better DORA usage

Use DORA metrics as questions, not targets.

| Metric | Bad question | Better question |
|---|---|---|
| Deployment frequency | Are we elite? | What constrains safe small-batch release? |
| Lead time | Are developers slow? | Which wait states dominate change flow? |
| Change fail rate | Who broke production? | What failure classes escaped earlier detection? |
| Failed deployment recovery time | Why did ops take so long? | Which recovery stage lacked tooling, ownership, or evidence? |

DORA should drive improvement hypotheses:

```text
Hypothesis:
Lead time p90 is high because integration-impacting changes wait for late review.

Experiment:
Introduce risk-based early review for API/event/db changes.

Expected signal:
Reduced p90 review wait and fewer late rework loops.
```

## 9. Anti-pattern 3 — Activity equals productivity

Activity is easy to count:

- commits;
- PRs;
- story points;
- comments;
- tickets closed;
- meetings attended;
- deployments executed.

But activity is not productivity.

A team can produce many PRs while making the system worse.

A senior engineer can close few tickets while removing a systemic bottleneck for twenty engineers.

A platform team can produce many features nobody adopts.

An engineer can look inactive while preventing a major architectural mistake.

SPACE exists partly because developer productivity is multidimensional.

Do not collapse it into activity volume.

---

## 10. Signals of activity bias

You may have activity bias if:

- people optimize for visible ticket closure over hard systemic work;
- large refactors are avoided because they do not map cleanly to sprint metrics;
- incident prevention work is considered less valuable than feature output;
- PR count is used as performance proxy;
- architectural thinking is seen as "not delivery";
- enablement work is invisible unless it creates many tickets;
- developers fragment work to look busy.

Better evaluation question:

```text
What capability, risk reduction, flow improvement, or customer outcome did this work create?
```

---

## 11. Anti-pattern 4 — Local optimization

Local optimization improves one part of the system while harming the whole.

Examples:

- Developers merge faster by reducing review depth, increasing production failures.
- CI becomes faster by skipping meaningful tests, increasing release risk.
- Platform team standardizes everything, slowing product teams.
- Architects centralize decisions, reducing inconsistency but increasing wait time.
- Operations handles all incidents, reducing product-team interruption but weakening service ownership.
- QA catches more issues late, hiding poor developer feedback loops.

The question is not:

```text
Did this stage improve?
```

The question is:

```text
Did total value flow improve without increasing hidden risk?
```

---

## 12. Local optimization diagnostic

For any improvement proposal, inspect:

| Dimension | Question |
|---|---|
| Upstream | Does this push work earlier in a useful way or just shift burden? |
| Downstream | Does this create more manual work for release, ops, QA, support, or platform? |
| Risk | Does this hide risk or reduce it? |
| Flow | Does total lead time improve or only one queue? |
| Quality | Does defect escape risk increase? |
| Cognitive load | Does this simplify or complicate the developer mental model? |
| Ownership | Does accountability become clearer or blurrier? |

## 13. Anti-pattern 5 — Golden path as golden cage

A golden path is supposed to reduce cognitive load.

It becomes a golden cage when:

- teams cannot deviate even for legitimate reasons;
- the path is optimized for the platform team's convenience, not product-team flow;
- the path lacks escape hatches;
- the path is documented but not automated;
- the path cannot handle enterprise edge cases;
- the path ignores on-prem/customer-specific constraints;
- contributions back to the path are difficult.

For Quote & Order, a good Java service golden path should help with:

- service scaffolding;
- local run;
- Testcontainers defaults;
- PostgreSQL migration safety;
- Kafka event publishing/consuming;
- OpenTelemetry;
- Kubernetes deployment;
- config/secrets;
- CI/CD;
- runbooks;
- service catalog metadata.

But it must not block legitimate variation such as:

- special latency requirements;
- customer-specific integration adapters;
- migration-only services;
- batch/reconciliation jobs;
- on-prem deployment constraints;
- security-sensitive components.

---

## 14. Golden path health test

A golden path is healthy when:

- a new service can be created quickly;
- common concerns are built in;
- developers understand what is default versus optional;
- exceptions are explicit and reviewed by risk;
- teams can contribute improvements;
- the platform team measures adoption and friction;
- path documentation matches actual tools;
- the path is versioned;
- migration from older patterns is supported;
- feedback loops are short.

A golden path is unhealthy when:

- people work around it;
- exceptions are hidden;
- the path has no owner;
- the path breaks silently;
- docs are stale;
- adoption is mandated but unsupported;
- product teams feel slower after adopting it.

---

## 15. Anti-pattern 6 — Platform team as ticket queue

Platform engineering is not simply "a team that handles everyone else's tickets."

Failure symptoms:

- platform work is dominated by ad hoc requests;
- no product roadmap exists for platform capabilities;
- platform team measures ticket closure instead of adoption/outcome;
- product teams cannot self-serve common needs;
- every exception requires manual approval;
- platform engineers become human APIs;
- platform users do not know what capabilities exist;
- the platform team becomes a bottleneck while believing it is being helpful.

A platform team should move repeated demand into reusable capability.

Bad pattern:

```text
Every team asks platform to create a new Kafka topic manually.
```

Better pattern:

```text
Topic creation is self-service through a governed workflow with naming conventions, ownership metadata, schema requirements, and audit trail.
```

---

## 16. Ticket-to-capability conversion

When platform receives repeated tickets, classify:

| Ticket pattern | Capability opportunity |
|---|---|
| Create service | Service template |
| Create database | Database provisioning workflow |
| Add topic | Kafka topic self-service |
| Debug deploy | Deployment diagnostics panel |
| Add dashboard | Observability template |
| Fix CI | CI golden pipeline |
| Add secret | Secret management workflow |
| Explain ownership | Service catalog metadata |
| Diagnose incident | Runtime debugging playbook |

The platform backlog should contain fewer one-off tasks over time.

---

## 17. Anti-pattern 7 — Observability wallpaper

Observability wallpaper is a large amount of telemetry that does not help diagnosis.

Symptoms:

- dashboards are visually impressive but rarely used;
- service dashboards do not map to business journeys;
- logs lack correlation IDs;
- traces stop at service boundaries;
- Kafka events cannot be followed across services;
- alerts link to dashboards that do not answer the next question;
- high-cardinality fields are missing where needed and excessive where harmful;
- dashboards show infrastructure health but not quote/order lifecycle health;
- engineers still ask, "Where do I look?" during incidents.

Observability should reduce diagnosis time.

If it does not, it is telemetry decoration.

---

## 18. Observability usefulness test

For each dashboard, ask:

- Which incident question does it answer?
- Which business journey does it represent?
- Which service owner uses it?
- Which alert links to it?
- Which runbook refers to it?
- Which correlation ID can connect it to traces/logs/events?
- Can it distinguish dependency failure from internal failure?
- Can it distinguish customer-specific issue from platform-wide issue?
- Can it reveal stuck state, not just hard failure?
- Is it still accurate after recent architecture changes?

If the dashboard does not answer an operational question, retire or redesign it.

---

## 19. Anti-pattern 8 — Alerting as notification broadcast

Alerts are not news.

Alerts are action contracts.

Bad alert:

```text
CPU high on pod qao-pricing-abc123.
```

Better alert:

```text
Pricing latency p95 exceeds SLO for 15 minutes; quote submission failure rate increased for tenant group A.
Likely impact: quote creation delays.
First action: check pricing dependency dashboard and recent deployment diff.
Runbook: <link>
Owner: Pricing service team.
```

Alerting fails when:

- alerts have no owner;
- alerts have no action;
- alerts fire too often;
- alerts are routed to too many people;
- alerts detect causes without user impact;
- alerts detect symptoms too late;
- alerts do not distinguish severity;
- alerts have no runbook;
- alerts are not reviewed after incidents.

---

## 20. Alert fatigue failure cascade

Alert fatigue causes a cascade:

```text
Noisy alert
  -> ignored alert
  -> delayed detection
  -> longer diagnosis
  -> larger customer impact
  -> more manual recovery
  -> more stress
  -> less trust in monitoring
  -> even more ignored alerts
```

To break the cascade, every alert should have:

- user/business impact;
- threshold rationale;
- owner;
- first diagnostic step;
- escalation path;
- runbook;
- lifecycle review date;
- link to incident/change history.

---

## 21. Anti-pattern 9 — Blameless wording, blameful reality

Many organizations use blameless language while still practicing blame.

Signs:

- incident review asks "who approved this?" before "what allowed this to happen?";
- action items are assigned only to the person closest to the mistake;
- timelines omit ambiguous signals and confusing context;
- postmortems avoid discussing organizational pressure;
- repeated incidents produce training reminders instead of system changes;
- human error is treated as root cause;
- leadership privately asks for a culprit.

Blamelessness is not politeness.

Blamelessness is a method for discovering system causes.

---

## 22. Incident review quality test

A good incident review identifies:

- how the issue was introduced;
- why it was not caught earlier;
- how it was detected;
- why detection did or did not work;
- how diagnosis happened;
- what evidence was missing;
- how mitigation happened;
- what manual recovery was required;
- which customers/tenants/workflows were impacted;
- what would make recurrence less likely;
- what would make recovery faster next time.

A weak incident review contains:

- vague root causes;
- ownerless actions;
- "add more tests" without specificity;
- "improve monitoring" without alert design;
- "be more careful";
- no timeline;
- no customer impact analysis;
- no recurrence analysis.

---

## 23. Anti-pattern 10 — Automation theater

Automation theater happens when scripts exist but the system is not actually safer or easier.

Symptoms:

- automation is undocumented;
- only one person knows how to run it;
- scripts require manual preconditions hidden in tribal knowledge;
- automation fails silently;
- automation lacks audit trail;
- automation has no rollback strategy;
- automation is not idempotent;
- automation bypasses governance;
- automation handles happy path only;
- automation is harder to debug than manual work.

In enterprise systems, bad automation can amplify damage.

Automation should reduce toil and risk, not just keystrokes.

---

## 24. Automation readiness checklist

Before automating an operational task, ask:

- Is the task repeatable and predictable?
- Can inputs be validated?
- Can execution be audited?
- Is the operation idempotent?
- Is rollback or compensation defined?
- Are permissions scoped?
- Are dry-run and preview modes possible?
- Are failure modes visible?
- Is there a safe manual fallback?
- Is ownership clear?
- Will automation reduce future toil, or create hidden maintenance toil?

---

## 25. Anti-pattern 11 — Documentation graveyard

Documentation graveyard happens when docs exist but are not connected to work.

Symptoms:

- docs are not referenced in PR templates;
- runbooks are not linked from alerts;
- architecture decisions are not linked from code or service catalog;
- onboarding docs do not match current setup;
- docs explain ideal workflow, not actual workflow;
- docs are written after the fact for compliance;
- docs have no owner or freshness signal;
- developers ask the same questions repeatedly despite docs existing.

Documentation is infrastructure only when it is used in workflow.

---

## 26. Make docs executable in the process

Connect docs to:

- service templates;
- PR checklist;
- CI failure messages;
- alerts;
- runbooks;
- onboarding tasks;
- architecture decision records;
- service catalog metadata;
- incident reviews;
- migration playbooks;
- release checklists.

A document hidden in a wiki is not a system.

A document connected to decision points is a capability.

---

## 27. Anti-pattern 12 — Governance by approval queue

Governance should reduce risk.

Approval queues often only delay risk.

Symptoms:

- architecture approval happens late;
- reviewers lack context;
- decisions are made in meetings without artifacts;
- standards are enforced manually;
- exceptions are not tracked;
- teams wait days for low-risk changes;
- high-risk changes pass because nobody has time to inspect deeply;
- governance optimizes for consistency over learning;
- approvals replace engineering ownership.

Good governance moves risk discovery earlier and automates low-risk compliance.

---

## 28. Governance redesign principles

Better governance uses:

- risk tiers;
- lightweight ADRs;
- self-service standards;
- automated checks;
- exception records;
- reusable patterns;
- early consultation for high-risk work;
- ownership metadata;
- periodic review of standards;
- path to improve standards based on real friction.

Example:

```text
Low-risk endpoint addition:
- OpenAPI lint passes
- contract tests pass
- no breaking changes
- service owner approval only

High-risk cross-domain API change:
- ADR required
- consumer impact review
- migration plan
- observability plan
- rollback/compatibility strategy
```

---

## 29. Anti-pattern 13 — Ownership ambiguity

Ownership ambiguity is one of the most expensive failure modes.

Symptoms:

- incidents bounce across teams;
- PRs wait because nobody knows reviewer ownership;
- data quality issues are "integration problems";
- Kafka event ownership is unclear;
- platform and product teams disagree on responsibility;
- runbooks list channels, not owners;
- service catalog ownership is stale;
- teams own code but not production behavior.

In Quote & Order, ownership must cover:

- service code;
- APIs;
- events;
- database tables;
- business lifecycle states;
- operational dashboards;
- alerts;
- runbooks;
- data repair workflows;
- customer/tenant configuration;
- dependency contracts.

---

## 30. Ownership boundary test

For each capability, ask:

- Who owns the customer/business outcome?
- Who owns the runtime service?
- Who owns the data model?
- Who owns event contract compatibility?
- Who owns operational recovery?
- Who owns customer-specific configuration?
- Who reviews changes?
- Who is paged?
- Who accepts exceptions?
- Who funds improvement?

If the answer is "several teams," define the coordination protocol.

---

## 31. Anti-pattern 14 — Hero culture

Hero culture feels good in the short term.

It is damaging in the long term.

Symptoms:

- the same senior engineers fix incidents repeatedly;
- manual recovery is praised instead of automated;
- obscure knowledge increases status;
- people hesitate to document because expertise gives leverage;
- escalation depends on personal availability;
- teams normalize after-hours intervention;
- retros celebrate effort but not system improvement;
- fragile systems survive because heroes compensate.

A top engineer does not become indispensable by hoarding knowledge.

A top engineer becomes valuable by making the team more capable.

---

## 32. Hero-to-system conversion

When you notice hero work, convert it:

| Hero action | System improvement |
|---|---|
| Manually fixes stuck order | Recovery playbook + repair tool |
| Knows which logs to inspect | Dashboard + runbook links |
| Remembers deployment steps | Automated release workflow |
| Understands hidden config | Service catalog metadata |
| Reviews all risky PRs | Risk-based reviewer routing |
| Debugs Kafka by intuition | Event traceability pattern |
| Knows DB migration danger | Migration checklist + CI gate |

---

## 33. Anti-pattern 15 — Retrospective without system change

Retrospectives fail when they produce feelings but not system change.

Symptoms:

- same retro themes repeat;
- action items are vague;
- action items are not prioritized;
- systemic issues are considered "too big";
- retro actions are not linked to backlog;
- no metric or evidence is used;
- improvements depend on individual behavior only;
- nobody reviews previous action outcomes.

A good retro creates at least one of:

- explicit decision;
- backlog item;
- experiment;
- policy change;
- platform improvement;
- documentation/runbook update;
- automation;
- measurement change;
- ownership clarification.

---

## 34. Anti-pattern 16 — Improvement work with no budget

Engineering effectiveness requires capacity.

It does not happen for free.

Failure symptoms:

- improvement work is always squeezed between feature tasks;
- technical debt is acknowledged but never scheduled;
- platform work is expected to happen through heroics;
- incident actions compete with feature commitments and lose;
- Scrum planning ignores operational and DevEx work;
- the team has many improvement ideas but no delivery mechanism.

Make improvement visible:

```text
Sprint capacity allocation:
- Product feature delivery
- Operational reliability actions
- Developer experience improvements
- Platform/golden path work
- Incident follow-up
- Technical debt retirement
```

Even a small fixed capacity can change behavior.

---

## 35. Anti-pattern 17 — Big-bang transformation

Large transformation programs often fail because they attempt to change too much before trust exists.

Symptoms:

- broad roadmap without pilot;
- central team defines process for everyone;
- tooling rollout before workflow fit;
- success measured by adoption count rather than outcome;
- no local champions;
- teams feel change is done to them;
- feedback is collected late;
- exceptions are treated as resistance.

Better pattern:

```text
Narrow pilot
  -> measurable friction reduction
  -> internal case study
  -> reusable pattern
  -> voluntary adoption
  -> governance support
  -> scale with feedback
```

---

## 36. Anti-pattern 18 — Tool-first DevEx

Developer experience is not equal to tools.

Tool-first DevEx starts with:

```text
Let's buy/build a portal, dashboard, bot, or platform tool.
```

Outcome-first DevEx starts with:

```text
Where do engineers lose time, confidence, focus, or safety?
```

Tool-first symptoms:

- tool adoption is high but friction remains;
- portal has many pages but weak golden paths;
- automation exists but does not cover real edge cases;
- dashboards exist but diagnosis remains slow;
- surveys improve because tooling looks modern, but delivery does not improve;
- teams work around the tool.

Tools should implement a workflow improvement, not substitute for one.

---

## 37. Anti-pattern 19 — Treating enterprise constraints as excuses

Enterprise constraints are real:

- compliance;
- customer-specific deployments;
- on-prem environments;
- integration contracts;
- long-lived data;
- security controls;
- regulated change management;
- legacy systems.

But "enterprise reality" can become an excuse for avoidable friction.

Bad framing:

```text
Deployments are slow because enterprise systems are complex.
```

Better framing:

```text
Which part of deployment slowness is inherent risk, and which part is avoidable wait, manual work, unclear ownership, poor tooling, or late validation?
```

Respect constraints.

Do not worship them.

---

## 38. Anti-pattern 20 — Ignoring socio-technical coupling

Software delivery is socio-technical.

Technical architecture and team architecture interact.

Failure symptoms:

- architecture requires frequent cross-team coordination but planning assumes independent teams;
- service boundaries do not match ownership boundaries;
- platform capabilities do not match team cognitive load;
- observability is service-centric while incidents are journey-centric;
- database ownership is shared informally;
- API/event contracts cross teams without interaction model;
- governance assumes control but lacks feedback.

A system can be technically elegant and organizationally impossible.

---

## 39. Socio-technical review questions

For major design decisions, ask:

- Which team owns this runtime behavior?
- Which team owns customer impact?
- Which teams must coordinate to change it?
- Can one team test it locally?
- Can one team deploy it safely?
- Can one team observe it in production?
- Can one team recover it during incident?
- Does this increase or reduce cognitive load?
- Does this require a new platform capability?
- Does this create hidden governance dependency?

---

## 40. Failure mode — The invisible improvement backlog

Many teams have improvement work, but it is invisible.

Examples:

- improving CI speed;
- fixing flaky tests;
- improving local setup;
- adding missing dashboards;
- documenting runbooks;
- reducing manual release steps;
- improving migrations;
- creating event fixtures;
- building data repair tooling;
- cleaning ownership metadata.

If not visible, this work loses to feature urgency.

Make it explicit.

Use categories:

```text
Engineering Effectiveness Backlog
- Flow bottlenecks
- DevEx friction
- Reliability/incident learning
- Platform/golden path gaps
- Observability gaps
- Operational toil
- Governance simplification
- Ownership clarity
```

---

## 41. Failure mode — Improvement without adoption design

A technically good improvement can fail if adoption is not designed.

Example:

```text
A new service template is created.
No migration path exists.
No team is piloted.
No docs connect it to onboarding.
No examples exist.
No old path is deprecated.
No feedback channel exists.
```

Adoption design includes:

- pilot team;
- migration path;
- example repository;
- docs;
- office hours;
- champions;
- deprecation plan;
- feedback mechanism;
- support model;
- adoption metric;
- outcome metric.

---

## 42. Failure mode — Improvement without deletion

Engineering systems accumulate.

Every tool, dashboard, alert, checklist, template, and process has carrying cost.

Improvement without deletion increases cognitive load.

Ask quarterly:

- Which dashboard is unused?
- Which alert is noisy?
- Which checklist duplicates automation?
- Which CI job no longer adds value?
- Which wiki page is stale?
- Which template is obsolete?
- Which approval step is redundant?
- Which platform path should be deprecated?

A mature engineering effectiveness program removes as well as adds.

---

## 43. Failure mode — Confusing standardization with consistency

Standardization means everyone does the same thing.

Consistency means people can understand and operate the system predictably.

They are related but not identical.

Bad standardization:

```text
Every service must use the same deployment pattern even when workload type differs.
```

Better consistency:

```text
Every service must expose ownership, health, metrics, tracing, runbook, deployment metadata, and rollback strategy.
Implementation can vary by workload type within approved patterns.
```

Standardize interfaces and expectations.

Allow controlled variation in implementation.

---

## 44. Failure mode — Treating learning as optional

In complex systems, learning is not extra.

Learning is how the system stays safe.

Learning mechanisms include:

- incident reviews;
- game days;

## 50. Summary

Engineering effectiveness anti-patterns usually do not look like obvious failure.

They look like:

- dashboards;
- ceremonies;
- portals;
- templates;
- reviews;
- automation;
- standards;
- metrics;
- documentation.

The question is whether those artifacts improve the real system.

A top senior engineer can detect when an artifact has become detached from value.

The operating principle:

> If it does not improve flow, safety, learning, ownership, reliability, or developer capability, it is not engineering effectiveness. It is system decoration.
