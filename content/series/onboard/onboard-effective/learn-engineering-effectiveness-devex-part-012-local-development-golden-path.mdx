# Part 012 — Local Development Golden Path

## 1. Source notes and scope boundary

This part uses public platform engineering and developer-experience concepts:

- Backstage describes a developer portal model with a software catalog and templates to help teams ship high-quality code while preserving autonomy.
- Team Topologies describes platform-as-a-product and cognitive load reduction as ways to support fast flow.
- Testcontainers provides disposable real dependencies for testing, including databases and message brokers.
- Docker Compose, dev containers, local Kubernetes, and remote development environments are common options, but this part does not assume any specific CSG tooling.

This part does **not** assume CSG uses Backstage, Docker Compose, Tilt, Skaffold, dev containers, local Kubernetes, Telepresence, Testcontainers, or any particular internal developer portal.

The goal is to define the properties of a good golden path and the questions to verify internally.

---

## 2. Core thesis

A local development golden path is not a script.

It is a supported, documented, repeatable route from zero context to safe contribution.

For a Senior Java Engineer working on Quote & Order, the golden path should answer:

> How do I clone, build, run, test, debug, inspect, and change this service without guessing, asking five people, or bypassing production-like safety?

A good golden path is:

- fast enough for daily use;
- realistic enough to catch meaningful issues;
- safe enough to avoid leaked secrets/customer data;
- documented enough for onboarding;
- flexible enough for advanced workflows;
- owned enough to stay current.

A bad golden path is:

- a stale README;
- a script only one person understands;
- a local setup that works only on one laptop;
- a remote shared environment everyone breaks;
- a shortcut that skips tests, auth, tenant, Kafka, or database behavior.

---

## 3. Golden path vs paved road vs cage

Terminology matters.

| Concept | Meaning | Healthy form | Failure mode |
|---|---|---|---|
| Golden path | Recommended path for common work | Fast, documented, supported | Stale or unrealistic |
| Paved road | Platform-supported default | Reduces repeated decisions | Becomes bureaucracy |
| Escape hatch | Approved deviation path | Enables special cases | Becomes ungoverned sprawl |
| Cage | Mandatory path that blocks valid work | None | Teams route around platform |

The best golden path makes good behavior easy.

It does not remove engineer judgment.

## 4. The local development lifecycle

A complete local golden path covers the full loop.

```mermaid
flowchart LR
  A[Prepare machine] --> B[Clone repository]
  B --> C[Install/pin tools]
  C --> D[Build]
  D --> E[Run unit tests]
  E --> F[Start dependencies]
  F --> G[Run service]
  G --> H[Seed test data]
  H --> I[Call API / trigger event]
  I --> J[Debug]
  J --> K[Observe logs/traces/metrics]
  K --> L[Run relevant tests]
  L --> M[Open PR]
```

Each step should have:

- one official command if possible;
- expected output;
- common failure modes;
- troubleshooting link;
- owner;
- update cadence.

## 5. Golden path levels

Not every workflow needs full local production simulation.

Use levels.

### 5.1 Level 0 — Read and navigate

Goal:

- understand repository structure and domain concepts.

Supports:

- architecture map;
- package guide;
- domain glossary;
- ownership map;
- API/event/database map.

Useful for:

- first-day onboarding;
- PR review;
- support investigation.

### 5.2 Level 1 — Build and unit test

Goal:

- validate local toolchain and fast feedback.

Supports:

- pinned Java version;
- Maven/Gradle command;
- fast unit test command;
- no external services required.

Useful for:

- domain logic changes;
- mapper-independent validation;
- first PR.

### 5.3 Level 2 — Service with local dependencies

Goal:

- run one service with local PostgreSQL/Kafka/test dependencies.

Supports:

- Docker Compose or Testcontainers/dev script;
- local configuration profile;
- seed fixtures;
- sample API calls;
- structured logs.

Useful for:

- API work;
- DB work;
- Kafka work;
- debugging service behavior.

### 5.4 Level 3 — Multi-service workflow

Goal:

- run a minimal quote-to-order workflow.

Supports:

- service set selection;
- mock/simulator for external systems;
- identity/test user setup;
- sample catalog/customer data;
- local event flow.

Useful for:

- integration workflows;
- quote acceptance;
- order creation;
- fulfillment callback simulation.

### 5.5 Level 4 — Production-like remote development

Goal:

- use controlled shared/ephemeral environment for realistic integration.

Supports:

- ephemeral namespace/tenant;
- safe test data;
- observability access;
- deployment preview;
- cleanup policy.

Useful for:

- high-risk integration;
- customer-specific config;
- performance-sensitive paths;
- end-to-end verification.

A good platform offers multiple levels.

Forcing every change through Level 4 is too slow.

Pretending Level 1 proves everything is unsafe.

## 6. Local setup principles

### 6.1 Pin versions

Pin or document:

- Java/JDK version;
- Maven/Gradle version;
- Docker version;
- PostgreSQL version;
- Kafka version if local;
- Node/PNPM/Yarn version if UI tools involved;
- CLI tool versions;
- IDE plugins if required;
- OS caveats.

Ambiguous versions create onboarding friction.

### 6.2 Make commands copy-pasteable

A developer should not reverse-engineer setup from paragraphs.

Good:

```bash
./dev/bootstrap.sh
./dev/test-unit.sh
./dev/start-deps.sh
./dev/run-quote-service.sh
./dev/seed-fixtures.sh
./dev/smoke-quote-acceptance.sh
```

The exact command names do not matter.

The consistency does.

### 6.3 Fail with useful messages

A script that fails with a cryptic stack trace is not a golden path.

Better failure output:

```text
PostgreSQL container failed to start.
Likely causes:
1. Docker is not running.
2. Port 5432 is already in use.
3. Your Docker memory limit is too low.

Try:
- docker ps
- lsof -i :5432
- ./dev/doctor.sh

Owner: platform-devex-channel
```

### 6.4 Include `doctor` checks

A `doctor` command can verify:

- JDK version;
- Docker running;
- required ports free;
- CLI installed;
- repository hooks installed;
- credentials present or missing;
- network access;
- disk space;
- common environment variables.

Example:

```bash
./dev/doctor.sh
```

### 6.5 Separate safe local secrets from real secrets

Local development should not require production secrets.

Use:

- local fake credentials;
- dev identity provider or token generator;
- simulator keys;
- secrets manager integration for approved dev environments;
- clear policy for customer data.

Never normalize copying real secrets into local `.env` files.

## 7. Java service golden path

For enterprise Java services, the golden path should include these workflows.

### 7.1 Build

Questions:

- What command builds the service?
- Does it require external access?
- Are dependency repositories configured?
- How are generated sources handled?
- Can a single module build independently?

Example shape:

```bash
./mvnw -pl quote-service -am clean verify
```

or:

```bash
./gradlew :quote-service:build
```

Verify actual internal build tool.

### 7.2 Run

Questions:

- What profile runs locally?
- Which dependencies are local?
- Which dependencies are mocked?
- Which dependencies are remote shared dev?
- How is tenant context simulated?
- How is auth simulated?

Example shape:

```bash
SPRING_PROFILES_ACTIVE=local ./mvnw -pl quote-service spring-boot:run
```

### 7.3 Test

Commands should separate feedback levels:

```bash
./dev/test-unit.sh
./dev/test-integration.sh
./dev/test-contract.sh
./dev/test-migration.sh
./dev/test-e2e-smoke.sh
```

Not every engineer runs every test locally all the time.

But every test category should be discoverable.

### 7.4 Debug

Document:

- IDE remote debug port;
- how to attach debugger;
- how to set local profile;
- how to invoke one sample request;
- how to inspect DB rows;
- how to inspect emitted events.

Example:

```bash
JAVA_TOOL_OPTIONS="-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005" \
  ./dev/run-quote-service.sh
```

### 7.5 Observe locally

Local observability should include:

- structured logs;
- correlation ID in logs;
- health endpoint;
- metrics endpoint if safe;
- trace export to local collector if available;
- sample dashboard or logs query.

Local debugging without observability creates bad production habits.

## 8. PostgreSQL golden path

Quote & Order systems rely heavily on PostgreSQL-like system-of-record behavior.

Local DB workflow should be first-class.

### 8.1 Database lifecycle

Support commands:

```bash
./dev/db/start.sh
./dev/db/migrate.sh
./dev/db/seed.sh
./dev/db/reset.sh
./dev/db/psql.sh
```

### 8.2 Fixtures

Provide named fixtures:

- tenant;
- customer;
- account;
- catalog offering;
- active quote;
- priced quote;
- approved quote;
- expired quote;
- product order;
- order in fallout;
- outbox event;
- audit event.

Named fixtures are more useful than random generated data.

### 8.3 Migration testing

Golden path should show:

- how to create migration;
- how to run migration from empty DB;
- how to run migration from previous release fixture;
- how to run migration rollback/roll-forward test if applicable;
- how to inspect lock/query plan risk;
- how to seed large-ish data for local performance smoke.

### 8.4 Query debugging

Document:

- how to run `EXPLAIN`;
- how to see slow queries in local/test;
- how to inspect indexes;
- how to verify tenant predicate;
- how to inspect connection pool behavior.

## 9. Kafka/event golden path

Event-driven development needs local/event ergonomics.

### 9.1 Local event tools

Golden path should answer:

- How do I start Kafka locally?
- How do I view topics?
- How do I publish a sample event?
- How do I consume events by key?
- How do I inspect schema?
- How do I trigger a DLQ scenario?
- How do I replay an event safely in local/dev?

### 9.2 Event fixtures

Provide fixture events:

- `QuoteCreated`;
- `QuotePriced`;
- `QuoteApproved`;
- `QuoteAccepted`;
- `ProductOrderCreated`;
- `OrderItemStateChanged`;
- `ProductOrderCompleted`;
- duplicate event;
- old schema event;
- malformed event;
- wrong tenant event.

### 9.3 Event debugging ergonomics

Every local event should include:

- event ID;
- event type;
- event version;
- aggregate ID;
- aggregate version;
- tenant ID;
- correlation ID;
- causation ID;
- producer;
- timestamp.

The golden path should teach engineers to inspect causality, not just payload shape.

---

## 10. API golden path

API work requires sample requests and clear contracts.

Golden path should include:

- OpenAPI location;
- local Swagger/UI if used;
- sample curl/httpie/Postman requests;
- auth/token setup;
- tenant header/context setup;
- error response examples;
- idempotency example;
- pagination/filter example;
- contract test command;
- generated client process if applicable.

Example request shape:

```bash
curl -X POST http://localhost:8080/quotes \
  -H "Authorization: Bearer $LOCAL_TOKEN" \
  -H "X-Correlation-Id: dev-corr-001" \
  -H "Idempotency-Key: dev-quote-create-001" \
  -H "Content-Type: application/json" \
  -d @fixtures/quote-create-enterprise-bundle.json
```

The actual headers and endpoints must be verified internally.

## 11. Observability golden path

A golden path must teach engineers how to see what happened.

### 11.1 Local log expectations

Logs should include:

- timestamp;
- level;
- service;
- environment/profile;
- correlation ID;
- tenant ID when safe;
- quote/order ID when safe;
- event ID if event processing;
- error code;
- exception class;
- no sensitive data.

### 11.2 Trace expectations

Trace examples should show:

- API request span;
- DB query span if available;
- Kafka publish/consume span if available;
- downstream adapter span;
- error span;
- correlation with logs.

### 11.3 Metrics expectations

Local metrics can show:

- HTTP request count/latency;
- DB pool metrics;
- Kafka producer/consumer metrics;
- outbox backlog;
- business counters for quote/order journey.

Engineers should learn the same observability language locally that they use in production.

## 12. First productive PR golden path

A good onboarding path should guide a new engineer to a safe first PR.

### 12.1 Good first PR categories

- documentation correction;
- test fixture improvement;
- missing negative unit test;
- small log/correlation improvement;
- mapper test improvement;
- runbook link fix;
- sample request update;
- local setup script improvement;
- harmless code cleanup with test.

### 12.2 Avoid first PR categories

- large refactor;
- public API change;
- pricing behavior change;
- order lifecycle state change;
- security boundary change;
- DB migration on hot table;
- Kafka event schema change;
- production config change.

### 12.3 First PR checklist

```md
# First PR Checklist

- [ ] I can build locally.
- [ ] I can run relevant tests locally.
- [ ] I understand the touched code path.
- [ ] I included a small clear PR description.
- [ ] I linked the relevant issue/story.
- [ ] I noted risk level.
- [ ] I included before/after behavior.
- [ ] I asked the correct owner/reviewer.
- [ ] I updated docs/tests if needed.
```

## 13. Golden path ownership model

A golden path must have ownership.

For each golden path, define:

- owner;
- consumers;
- supported workflows;
- unsupported workflows;
- update process;
- feedback channel;
- telemetry/adoption signal;
- deprecation policy.

Example ownership matrix:

| Area | Owner | Consumer | Feedback signal |
|---|---|---|---|
| Java service template | platform/team enablement | backend teams | service creation friction |
| Quote local fixture | quote team | quote/order engineers | onboarding questions |
| Kafka local tools | platform/data infra | event producers/consumers | event debugging time |
| Observability starter | SRE/platform | service teams | missing correlation incidents |
| DB migration guide | DB/platform + product teams | backend teams | migration review issues |

Without ownership, golden paths rot.

## 14. Internal verification checklist

### 14.1 Tooling

- Is there an internal developer portal?
- Are there service templates?
- Is there a standard Java service scaffold?
- Is there standard Docker/Kubernetes manifest generation?
- Is there standard CI template?
- Is there standard OTel/logging setup?
- Are golden paths documented in one place?

### 14.2 Local environment

- Can services run locally?
- Are dependencies local, simulated, or remote shared?
- Is local Kafka supported?
- Is local PostgreSQL supported?
- Is local identity/auth supported?
- Is local tenant setup supported?
- Is local test data supported?

### 14.3 Security/access

- How are dev secrets managed?
- Are production secrets forbidden locally?
- Are customer data snapshots allowed?
- Are sanitized fixtures available?
- How is PII handled in local/dev?

### 14.4 Onboarding

- What is the official first-day path?
- What is the official first-week path?
- Is first productive PR defined?
- Are common setup failures documented?
- Is there a buddy system?

### 14.5 Observability

- Can local traces be emitted?
- Is there a local collector?
- Are logs structured locally?
- Are sample dashboards available?
- Are correlation IDs consistent locally and remotely?

## 15. Golden path maturity model

| Level | Description | Signs |
|---|---|---|
| 0 | Tribal setup | New engineers need many private messages |
| 1 | README setup | Works if docs are current and environment matches |
| 2 | Scripted setup | Bootstrap/build/test commands exist |
| 3 | Supported local stack | DB/Kafka/fixtures/auth workflow available |
| 4 | Self-service golden path | Templates, docs, diagnostics, ownership, support |
| 5 | Measured platform path | Adoption, friction, reliability, and outcomes measured |

Do not pretend maturity is higher than reality.

A truthful Level 2 with active improvement is better than a claimed Level 5 that nobody trusts.

## 16. Golden path anti-patterns

### 16.1 README graveyard

Docs exist but no one knows whether they work.

Fix:

- docs tested during onboarding;
- docs owner;
- last verified date;
- automated checks where possible.

### 16.2 Shared dev environment as local substitute

Everyone depends on one fragile environment.

Fix:

- local minimal stack;
- ephemeral environments;
- clear ownership;
- isolation by tenant/namespace.

### 16.3 One-click setup that hides everything

Automation helps, but total opacity hurts debugging.

Fix:

- expose logs;
- expose commands;
- document components;
- provide `doctor` diagnostics.

### 16.4 Golden path that skips hard parts

A local path that ignores Kafka, DB migrations, auth, or tenant context may create false confidence.

Fix:

- define levels;
- state what each level proves and does not prove.

### 16.5 No escape hatch

Some enterprise work needs special paths.

Fix:

- document exception process;
- learn from exceptions;
- fold repeated exceptions back into platform.

## 19. Part summary

A local development golden path is the recommended, supported route for safe and productive engineering work.

For enterprise Java/Quote & Order systems, it should cover:

- clone/build/test;
- local service run;
- PostgreSQL fixtures and migrations;
- Kafka event workflows;
- API samples;
- auth/tenant simulation;
- debugging;
- observability;
- first productive PR;
- ownership and maintenance.

The goal is not to recreate production perfectly on every laptop.

The goal is to provide the right feedback at the right level with low friction and high trust.
