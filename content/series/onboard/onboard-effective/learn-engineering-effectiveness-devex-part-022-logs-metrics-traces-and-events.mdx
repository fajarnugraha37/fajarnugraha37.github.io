# Part 022 — Logs, Metrics, Traces, and Events

## 1. Source notes and scope boundary

This part uses public observability references:

- OpenTelemetry documentation describes telemetry data such as traces, metrics, and logs, and provides APIs/SDKs/tools for generating, collecting, and exporting that data.
- Google SRE material emphasizes monitoring distributed systems and designing alerts around meaningful symptoms.
- CNCF observability discussions commonly treat logs as useful for debugging, audit, and reconstructing sequences of actions.

This part does not assume the observability backend, logging library, metric library, tracing backend, or event schema implementation used by CSG.

Verify internally:

- logging framework,
- structured logging standard,
- metric backend,
- trace backend,
- OpenTelemetry adoption,
- Kafka event envelope,
- audit model,
- naming conventions,
- PII/commercial-data restrictions.

---

## 2. Core thesis

Logs, metrics, traces, and events are not interchangeable.

Each answers a different type of question.

A strong engineer chooses telemetry by diagnostic need, not by habit.

Bad question:

> Should we add a log?

Better question:

> What question will the next engineer or on-call person need to answer, and which signal is the cheapest reliable way to answer it?

---

## 3. Signal selection matrix

| Need | Best primary signal | Why |
|---|---|---|
| Alert on broad symptom | Metric | Cheap aggregation and thresholding |
| Debug one failed request | Trace + logs | Path plus detail |
| Understand async workflow stop point | Trace + event metadata + metrics | Need causality and backlog/lag |
| Prove business transition happened | Business event/audit event | Domain evidence |
| Reconstruct detailed failure context | Structured logs | Rich context |
| Detect trend/regression | Metric | Time series comparison |
| Diagnose cross-service latency | Distributed trace | Service/span breakdown |
| Investigate security-sensitive action | Audit event + access logs | Evidence and accountability |
| Verify customer journey health | Business metric | Product-impact visibility |

Most real incidents need multiple signals.

## 4. Logs

Logs are detailed records of things that happened.

Good logs are:

- structured,
- searchable,
- contextual,
- safe,
- meaningful,
- consistent,
- not excessive.

### 4.1 Good log line properties

A useful log line includes:

- timestamp,
- severity,
- service name,
- deployment version,
- trace ID,
- correlation ID,
- tenant ID where allowed,
- business object ID where allowed,
- operation name,
- stable error code/category,
- safe contextual attributes.

Example shape:

```json
{
  "level": "WARN",
  "service": "quote-service",
  "operation": "accept_quote",
  "tenant_id": "tenant-123",
  "quote_id": "Q-1001",
  "quote_version": 7,
  "correlation_id": "corr-abc",
  "trace_id": "trace-xyz",
  "error_code": "QUOTE_PRICE_EXPIRED",
  "message": "Quote acceptance rejected because pricing snapshot expired"
}
```

### 4.2 What to log

Log important lifecycle moments:

- command accepted,
- command rejected,
- domain transition performed,
- idempotency duplicate detected,
- downstream call failed,
- Kafka event publication failed,
- consumer retry/DLQ decision,
- migration/backfill chunk completed,
- privileged action attempted,
- repair action executed.

### 4.3 What not to log

Avoid logging:

- raw JWTs,
- secrets,
- passwords,
- API keys,
- full customer PII,
- raw request/response bodies by default,
- detailed pricing/margin data unless policy allows,
- internal stack traces to user-facing logs,
- high-volume noisy success logs without value.

### 4.4 Log levels

Use levels consistently.

| Level | Meaning |
|---|---|
| DEBUG | Developer diagnostic, usually disabled in production |
| INFO | Significant normal lifecycle event |
| WARN | Unexpected but handled condition |
| ERROR | Failure requiring attention or causing request/workflow failure |
| FATAL | Process cannot continue, rarely used in app-level logging |

Do not log handled validation failures as `ERROR` if they are expected business outcomes.

Do not hide real system failures as `INFO`.

## 5. Metrics

Metrics are numeric measurements over time.

They are excellent for:

- alerting,
- trend detection,
- capacity planning,
- regression detection,
- dashboard summaries,
- SLO measurement.

### 5.1 Metric types

Common metric types:

- counter,
- gauge,
- histogram,
- summary,
- up/down counter.

Examples:

- `quote_accept_attempt_total`,
- `quote_accept_failure_total`,
- `quote_accept_duration_seconds`,
- `order_fallout_active_count`,
- `outbox_pending_event_count`,
- `kafka_consumer_lag_age_seconds`,
- `postgres_lock_wait_seconds`,
- `http_server_request_duration_seconds`.

### 5.2 Metric labels

Labels/dimensions make metrics useful.

But high-cardinality labels can make systems expensive or unstable.

Good labels:

- operation,
- result,
- error category,
- service,
- environment,
- region,
- dependency,
- event type,
- workflow type.

Dangerous labels:

- customer name,
- quote ID,
- order ID,
- user ID,
- raw account ID,
- idempotency key,
- unbounded exception message.

Use exemplars/traces/logs for high-cardinality drilldown where supported.

### 5.3 Business metrics

Business metrics are not vanity dashboards.

They tell whether customer journeys are healthy.

Examples:

- quote pricing success rate,
- quote acceptance failure by reason,
- order conversion latency,
- order fallout count,
- fulfillment callback failure rate,
- billing handoff retry count,
- stuck order age.

Business metrics should be owned.

If nobody uses a dashboard, it is decorative.

## 6. Traces

Traces show the path of work across services and components.

A trace consists of spans.

Each span represents a unit of work:

- HTTP request,
- database call,
- Kafka produce,
- Kafka consume,
- pricing calculation,
- catalog lookup,
- order conversion,
- fulfillment adapter call.

### 6.1 What traces answer

Traces answer:

- Which services were called?
- Where was time spent?
- Which dependency failed?
- Did the request cross service boundary correctly?
- Did context propagation survive async boundaries?
- Which deployment version handled the request?
- Which span returned error?

### 6.2 Span attributes

Useful span attributes:

- operation name,
- service name,
- environment,
- deployment version,
- tenant category where safe,
- business operation type,
- event type,
- Kafka topic,
- database operation category,
- error code.

Be careful with high-cardinality attributes depending on backend cost/query model.

### 6.3 Async tracing challenge

Distributed tracing is harder with Kafka and outbox patterns.

Questions:

- Does producer inject trace context into message headers?
- Does consumer extract context?
- Does outbox preserve correlation/causation metadata?
- Is trace sampling consistent enough to debug critical workflows?
- Can a business journey be followed even if trace sampling drops spans?

For business-critical flows, correlation IDs and event metadata are often more durable than traces alone.

## 7. Business events

Business events are domain facts.

Examples:

- `QuoteCreated`,
- `QuotePriced`,
- `QuoteSubmittedForApproval`,
- `QuoteApproved`,
- `QuoteAccepted`,
- `ProductOrderCreated`,
- `OrderItemFalloutRaised`,
- `ProductOrderCompleted`.

These are not merely telemetry.

They may drive downstream systems.

They require compatibility, idempotency, and governance.

### 7.1 Business event metadata

A robust event contains:

- event ID,
- event type,
- event version,
- occurred time,
- tenant ID,
- aggregate type,
- aggregate ID,
- aggregate version,
- correlation ID,
- causation ID,
- producer service,
- schema version.

### 7.2 Event vs log

A log says something happened inside a service.

A business event declares a fact that other systems may rely on.

Do not use business events as casual debug logs.

Do not use logs as source of truth for domain state.

---

## 8. Audit events

Audit events are evidence.

They answer:

- who did what,
- when,
- to which object,
- under which authority,
- with what reason,
- before and after what state,
- from which channel,
- in which tenant.

Examples requiring audit:

- quote approval,
- price override,
- quote acceptance,
- order cancellation,
- fulfillment fallout manual resume,
- support/admin data repair,
- tenant configuration change,
- security denial if policy requires.

Audit events usually have stronger retention, access control, and immutability expectations than normal logs.

---

## 9. Events taxonomy for Quote & Order

Do not mix event types.

| Event type | Purpose | Example |
|---|---|---|
| Domain/business event | Downstream business reaction | `QuoteAccepted` |
| Integration event | External system coordination | `FulfillmentTaskSubmitted` |
| Audit event | Compliance/evidence | `QuoteApprovedByUser` |
| Telemetry event | Diagnostics | structured log event |
| Security event | Security monitoring | `CrossTenantAccessDenied` |
| Platform event | Runtime/deployment | `DeploymentCompleted` |

Confusing these creates bad architecture.

Example anti-pattern:

- downstream billing consumes audit logs,
- support relies on Kafka integration event as audit evidence,
- metrics are derived from unstructured logs with unstable message text,
- debug logs are treated as replayable facts.

## 10. Choosing the right signal: examples

### 10.1 Quote acceptance fails

Need:

- metric: failure count by reason,
- log: quote ID/version and error category,
- trace: API → DB → pricing/catalog check path,
- event: no `QuoteAccepted` emitted if rejected,
- audit: maybe record failed privileged attempt if policy requires.

### 10.2 Order stuck in fulfillment

Need:

- metric: order age in state,
- log: callback processing failure details,
- trace: fulfillment adapter call/callback,
- business event: `OrderItemFalloutRaised`,
- dashboard: active fallout by age,
- runbook: resume/retry steps.

### 10.3 Duplicate Kafka message processed

Need:

- metric: inbox dedupe hit count,
- log: duplicate event ID and aggregate ID,
- trace: consumer processing if available,
- event: no duplicate side-effect event,
- audit: not usually unless business state changed.

### 10.4 Data repair executed

Need:

- audit event: repair ID, approver, before/after summary,
- log: execution progress and validation,
- metric: repair job duration/failure,
- event: correction event if downstream systems must reconcile,
- runbook/evidence bundle.

## 11. Naming conventions

Signal names should be stable and boring.

### 11.1 Metric naming

Prefer names like:

- `quote_accept_attempt_total`,
- `quote_accept_duration_seconds`,
- `product_order_state_transition_total`,
- `outbox_event_pending_count`,
- `fulfillment_callback_failure_total`.

Avoid:

- `stuff_failed`,
- `quote_error_new`,
- `temp_metric_2`,
- names that encode customer-specific details.

### 11.2 Operation naming

Use stable operation names:

- `quote.create`,
- `quote.price`,
- `quote.submit_for_approval`,
- `quote.accept`,
- `order.create_from_quote`,
- `order.decompose`,
- `fulfillment.callback.process`.

Stable naming makes dashboards and alerts survivable across refactors.

---

## 12. Cardinality and cost

Observability has cost.

High-cardinality fields are not automatically bad, but they must be intentional.

Ask:

- Is this field needed for grouping or drilldown?
- Is it bounded?
- Is it sensitive?
- Does the backend support it cost-effectively?
- Should it be a metric label, log field, span attribute, or event payload?

General guidance:

- Use low-cardinality labels for metrics.
- Use logs/traces/events for high-cardinality object IDs.
- Use sampling carefully.
- Never add sensitive IDs without policy check.

---

## 13. Sampling strategy

Sampling reduces volume but can hide rare failures.

Important questions:

- Are error traces always retained?
- Are slow traces sampled differently?
- Are critical business operations sampled more aggressively?
- Are on-prem/customer environments sampled differently?
- Can support request higher sampling during incident?
- Does sampling break journey reconstruction?

For Quote & Order, rare high-impact failures may matter more than high-volume normal paths.

Do not sample away the only evidence of a pricing/approval failure.

## 14. Telemetry quality checklist

For every new signal, ask:

- What question does it answer?
- Who uses it?
- Is it actionable?
- Is it stable?
- Is it safe?
- Is it documented?
- Is it owned?
- Does it duplicate another signal?
- What is the retention requirement?
- How will we know if it breaks?

A signal with no user and no action is noise.

## 16. PR review checklist

When reviewing telemetry:

- Are logs structured?
- Are messages stable and useful?
- Are error categories machine-readable?
- Are metrics named consistently?
- Are metric labels safe and bounded?
- Are traces created around meaningful spans?
- Is context propagated across service/event boundary?
- Are business events distinct from audit events?
- Are sensitive fields excluded?
- Are dashboards/runbooks updated if needed?
- Is the signal tested where critical?

## 17. Practical exercise

Pick one recent bug.

Write down:

1. What signal first showed the issue?
2. What signal should have shown it earlier?
3. What logs were missing?
4. What metric was missing?
5. What trace/span was missing?
6. What event/audit evidence was missing?
7. What field caused search/drilldown friction?
8. What signal would reduce future diagnosis time?

Then create one small improvement PR.

Examples:

- add stable error code,
- add metric by failure reason,
- propagate correlation ID,
- add trace span around adapter call,
- redact unsafe log field,
- add dashboard panel,
- link runbook from alert.

---

## 18. Summary

Logs, metrics, traces, and events are different tools.

Strong observability comes from choosing the right signal for the question:

- metrics for trends and alerts,
- logs for contextual details,
- traces for cross-service path and latency,
- business events for domain facts,
- audit events for evidence and accountability.

In enterprise Quote & Order systems, signal design is not optional.

It is part of correctness, supportability, and developer productivity.
