# Part 010 — Metrics Without Gaming

## 1. Source notes and scope boundary

This part uses public engineering metrics, DevOps, Scrum/Kanban, and productivity research.

Public references to verify independently:

- DORA metrics are widely used to understand software delivery performance and drive continuous improvement.
- SPACE frames developer productivity as multidimensional: satisfaction/well-being, performance, activity, communication/collaboration, and efficiency/flow.
- Scrum with Kanban guidance emphasizes flow metrics such as WIP, Cycle Time, Work Item Age, and Throughput.
- Goodhart's Law is commonly summarized as: when a measure becomes a target, it ceases to be a good measure.

This part does **not** assume CSG uses a specific engineering analytics platform, DORA dashboard, DevEx survey, productivity measurement program, internal KPI structure, or performance-review process.

Use the internal verification checklist to map these ideas to actual team practices.

---

## 2. Core thesis

Metrics should help teams learn.

Metrics should not become a substitute for thinking.

A metric is useful when it helps the team ask better questions:

- Why is work aging?
- Why are PRs waiting?
- Why is CI unreliable?
- Why are deployments scary?
- Why are defects escaping?
- Why is local setup hard?
- Why are incidents hard to diagnose?
- Why do engineers context switch so much?
- Why is production readiness late?

A metric becomes harmful when it becomes a simplistic target:

- increase velocity,
- close more tickets,
- reduce cycle time at all costs,
- deploy more often regardless of readiness,
- reduce PR review time by lowering review quality,
- reduce incident count by under-reporting incidents,
- reduce flaky tests by deleting tests,
- reduce WIP by hiding work outside the board.

The goal is not to avoid metrics.

The goal is to design metrics that encourage honest inspection, better system behavior, and product outcomes.

---

## 3. The danger: Goodhart-style behavior

Goodhart's Law is often summarized as:

> When a measure becomes a target, it ceases to be a good measure.

In engineering organizations, this happens when people optimize the number instead of the system.

Examples:

| Metric target | Gaming behavior | Damage |
|---|---|---|
| Increase velocity | Inflate estimates | Forecast loses meaning |
| Close more tickets | Split work into meaningless tiny tickets | Activity replaces value |
| Reduce cycle time | Avoid complex important work | Risk moves to backlog |
| Increase deployment frequency | Deploy low-risk/no-op changes | Metric improves, customer value unchanged |
| Reduce change failure rate | Hide failures or redefine failure | Learning decreases |
| Reduce MTTR | Mark incident resolved before customer recovery | Recovery signal becomes false |
| Reduce flaky tests | Delete or quarantine tests permanently | Confidence decreases |
| Reduce PR review time | Rubber-stamp reviews | Quality decreases |
| Reduce WIP | Move work to private notes or untracked tasks | Visibility decreases |

Metrics create incentives.

Senior engineers must understand those incentives.

## 4. Metrics as instruments, not goals

A speedometer is useful because it informs driving.

It does not decide destination.

Engineering metrics are the same.

They should help answer:

- Are we improving flow?
- Are we improving quality?
- Are we reducing cognitive load?
- Are we reducing production risk?
- Are we making customer-impacting changes safer?
- Are we learning from incidents?
- Are we improving developer experience?

They should not become the purpose of work.

A healthy metric conversation sounds like:

> Our PR review wait time increased after adding more security-sensitive work. Is this because the security review path is under-capacity, or because we are discovering security requirements too late in refinement?

An unhealthy metric conversation sounds like:

> Review faster. The dashboard is red.

## 5. Metric design principles

### 5.1 Use metrics to improve systems, not judge individuals

Most engineering effectiveness metrics are system-level.

Cycle time is influenced by:

- story size,
- refinement quality,
- PR review availability,
- CI reliability,
- test data,
- environment stability,
- deployment gates,
- dependency availability,
- product ambiguity.

Using it to rank individuals is misleading and damaging.

### 5.2 Pair speed metrics with quality metrics

Speed without quality is dangerous.

Pair:

- cycle time with escaped defects,
- deployment frequency with change failure rate,
- PR review time with defect escape and review rework,
- test duration with confidence and flakiness,
- release frequency with rollback/repair burden.

### 5.3 Pair output metrics with outcome metrics

Output:

- tickets closed,
- PRs merged,
- deployments,
- story points.

Outcome:

- quote acceptance errors reduced,
- order fallout diagnosis time reduced,
- customer escalation reduced,
- CI feedback time reduced,
- onboarding time reduced,
- deployment recovery improved.

Output is easier to measure.

Outcome is usually more important.

### 5.4 Use metric suites, not single metrics

Single metrics are easy to game.

Balanced suites are harder to fake and more informative.

Example:

- WIP,
- cycle time,
- work item age,
- throughput,
- escaped defects,
- PR review latency,
- CI failure rate,
- deployment recovery time,
- developer friction survey.

### 5.5 Keep metrics close to decisions

A metric is useful if someone can act on it.

Bad:

> Organization-wide average productivity score.

Better:

> PRs in Quote Service wait median 2.5 days for first review; 60% of those PRs need a domain owner review; ownership routing is unclear.

Actionable metrics point to a system change.

## 6. Metrics levels

Use different metrics for different levels.

| Level | Useful question | Example metrics |
|---|---|---|
| Individual self-reflection | Where am I blocked or overloaded? | personal WIP, focus time, review load |
| Team improvement | Where does work get stuck? | WIP, cycle time, work item age, blocked time |
| Product delivery | Are we delivering valuable changes safely? | lead time, deployment frequency, reliability, defects |
| Platform/DevEx | Are teams enabled or slowed down? | setup time, build time, CI reliability, support tickets |
| Organization | Are capabilities improving? | DORA trends, reliability, customer impact, satisfaction |

Do not use team metrics to judge individuals.

Do not use organization metrics to manage daily work.

## 8. What not to measure as performance targets

Avoid using these as individual performance targets:

- lines of code,
- commits count,
- PR count,
- story points completed,
- tickets closed,
- review comments count,
- hours online,
- meetings attended,
- incidents handled count.

These are easy to distort.

They may be useful as local diagnostic context, but dangerous as evaluation targets.

Example:

- PR count can increase by splitting trivial work artificially.
- Review comment count can increase by nitpicking.
- Incident count handled can reward firefighting over prevention.
- Lines of code can reward complexity.

A senior engineer should optimize for system capability, not metric theater.

## 9. Metric interpretation examples

### 9.1 Cycle time improved, defects increased

Possible interpretation:

- review quality dropped,
- testing reduced,
- story slicing hides integration risk,
- QA rushed,
- DoD weakened.

Action:

- inspect recent escaped defects,
- review DoD adherence,
- review PR review depth,
- review test coverage by work type.

Do not celebrate speed alone.

### 9.2 Deployment frequency improved, release confidence decreased

Possible interpretation:

- deployments are smaller but observability is weak,
- deployment and release are being confused,
- feature flags hide unvalidated complexity,
- on-prem/customer enablement remains slow.

Action:

- distinguish deploy vs release vs customer enablement,
- add production readiness metrics,
- inspect rollback/roll-forward data.

### 9.3 PR review time improved dramatically

Possible interpretation:

- reviewers are more available,
- PRs got smaller,
- ownership routing improved,
- or reviews became superficial.

Action:

- pair with escaped defects,
- inspect review quality sample,
- inspect PR size.

### 9.4 Velocity increased

Possible interpretation:

- team got better,
- estimates inflated,
- work got easier,
- quality declined,
- unfinished work moved outside sprint,
- technical debt increased.

Action:

- do not use velocity alone,
- pair with cycle time, defects, Sprint Goal completion, and production readiness.

## 10. Metric conversations by Scrum event

### 10.1 Sprint Planning

Use metrics to ask:

- How much WIP can we realistically handle?
- What work aged last sprint?
- Which blockers repeated?
- What was interrupt load?
- What CI/review bottleneck should affect capacity?
- Which risk needs spike before commitment?

Do not use metrics to force more work into Sprint.

### 10.2 Daily Scrum

Use metrics to ask:

- Which item is oldest?
- Which item is blocked?
- Which PR is waiting?
- Which work threatens Sprint Goal?
- What should we stop starting?

### 10.3 Sprint Review

Use metrics to show evidence:

- behavior delivered,
- production readiness,
- quality signals,
- business journey metrics,
- known limitations.

### 10.4 Retrospective

Use metrics to learn:

- where flow broke,
- where quality escaped,
- where friction repeated,
- what improvement to run next.

## 12. Designing a metric safely

Before introducing a metric, answer:

1. What decision will this metric inform?
2. Who will use it?
3. What behavior could it incentivize?
4. How could it be gamed?
5. What balancing metric is needed?
6. What context must accompany it?
7. How often should it be reviewed?
8. What action can be taken from it?
9. What should this metric **not** be used for?

### 12.1 Example: PR review time

Metric:

> Median time to first review.

Decision:

> Are PRs waiting too long before feedback?

Possible gaming:

> Reviewer leaves superficial comment quickly.

Balancing metrics:

- review rounds,
- escaped defects,
- PR size,
- review quality sample,
- author satisfaction.

Context:

- work type,
- risk level,
- owning team,
- reviewer availability.

Not for:

> ranking individual reviewers.

## 13. Metric anti-gaming design patterns

### 13.1 Use ranges, not exact targets

Better:

> We expect most medium-risk PRs to get first meaningful review within one working day.

Worse:

> Every PR must be reviewed in 2 hours.

### 13.2 Use trend, not snapshot

Snapshots overreact to noise.

Trends show direction.

### 13.3 Use segmentation

Segment by:

- work type,
- service,
- risk label,
- team,
- deployment mode,
- customer-facing vs internal,
- planned vs unplanned work.

A migration PR should not be compared to a typo fix.

### 13.4 Use narrative with metric

A metric without narrative becomes a weapon.

Require explanation:

- what changed,
- why it changed,
- what we learned,
- what action we will try.

### 13.5 Use metrics in retrospectives, not performance reviews

The safest use of metrics is team learning.

The most dangerous use is individual ranking.

## 14. Developer productivity and SPACE

The SPACE framework is useful because it resists one-dimensional productivity thinking.

Dimensions:

- Satisfaction and well-being.
- Performance.
- Activity.
- Communication and collaboration.
- Efficiency and flow.

For senior engineers, the lesson is:

> Productivity is not one number.

A team can have high activity and poor flow.

A team can have high flow and poor well-being.

A team can deploy often but produce little customer value.

A team can have strong individual output but weak collaboration.

Use multiple lenses.

## 15. Metrics and psychological safety

Metrics require trust.

If people fear punishment, they will distort data.

Examples:

- hide blocked work,
- avoid incident reporting,
- avoid risky but valuable refactoring,
- avoid adding tests that might fail,
- overestimate stories,
- split work artificially,
- avoid asking for help,
- move work outside the board.

Healthy metrics need psychological safety:

- it is safe to expose blockers,
- it is safe to report failures,
- it is safe to admit uncertainty,
- it is safe to challenge metric interpretation,
- it is safe to improve the system rather than defend the number.

## 16. Metrics review meeting design

A monthly engineering effectiveness review can be useful.

### 16.1 Agenda

1. What improved?
2. What worsened?
3. Which metric is surprising?
4. Which metric may be misleading?
5. Which friction appears repeatedly?
6. Which improvement experiment should we run?
7. Which metric should we stop tracking?
8. Which metric needs better definition?

### 16.2 Output

The meeting should produce:

- one or two improvement experiments,
- one owner per experiment,
- expected signal,
- review date,
- no blame assignment.

Example experiment:

> For two sprints, all PRs over 500 lines need a pre-review note explaining split alternatives. Expected signal: fewer review rounds and lower PR age for high-risk changes.

## 17. Metrics data quality

Metrics are only as good as their data definitions.

Common problems:

- work starts before ticket moves state,
- blocked state not used consistently,
- PR linked to wrong ticket,
- deployment metric counts non-production deploys,
- release metric ignores feature flag enablement,
- incident start/end times inconsistent,
- flaky test count not classified,
- manual work not tracked,
- support/on-call work hidden,
- on-prem releases not represented.

### 17.1 Data definition template

For every metric, document:

```md
Metric name:
Purpose:
Definition:
Start event:
End event:
Scope:
Exclusions:
Segments:
Known limitations:
Owner:
Review cadence:
Not intended for:
```

This prevents metric drift.

## 18. Metrics for platform engineering

Platform metrics are especially easy to game.

Bad platform metric:

> Number of platform features delivered.

Better platform metrics:

- time to create a new service using golden path,
- percentage of services using standard CI template,
- percentage of services with default observability,
- developer satisfaction with platform workflows,
- support tickets per service onboarding,
- mean time to resolve platform support requests,
- reduction in duplicated service scaffolding code,
- deployment setup time,
- secrets/config setup friction,
- upgrade adoption rate.

Platform success is not how much platform builds.

Platform success is how much product teams are enabled.

Telemetry examples:

## 21. Anti-patterns

### 21.1 Metric theater

Dashboards look mature, but no decisions change.

### 21.2 Target fixation

Teams optimize the number and harm the system.

### 21.3 Individual ranking

System metrics are used to judge individuals.

### 21.4 Context-free comparisons

Teams with different work types are compared directly.

### 21.5 Too many metrics

Nobody knows what matters.

### 21.6 Metrics without ownership

Dashboard exists, but no one reviews or acts.

### 21.7 Hidden work

Metrics look good because real work moved outside tracking.

### 21.8 Punishing transparency

Teams report fewer problems because reporting problems has negative consequences.

## 23. Practical exercise: metric safety review

Choose one metric your team uses.

Answer:

1. What behavior does this metric encourage?
2. What behavior might it accidentally discourage?
3. How could it be gamed?
4. What balancing metric is missing?
5. Is it being used for learning or judgment?
6. Does the team trust it?
7. Is the data definition clear?
8. What decision does it inform?
9. Should it be changed, paired, segmented, or retired?

Example:

Metric:

> Sprint velocity.

Possible gaming:

- inflate estimates,
- split work artificially,
- avoid difficult work,
- hide unplanned work.

Balancing metrics:

- Sprint Goal completion,
- production readiness,
- escaped defects,
- work item age,
- unplanned work rate.

## 25. Senior engineer operating habit

When someone presents a metric, ask:

1. What decision will we make differently because of this?
2. What system behavior does this metric incentivize?
3. What balancing metric should we inspect?
4. What context is missing?
5. How could this be gamed?
6. What is the smallest improvement experiment suggested by this signal?

This turns metrics from theater into learning.

## 26. Summary

Metrics are powerful because they shape attention.

They are dangerous because they shape incentives.

Healthy engineering metrics are:

- system-oriented,
- context-aware,
- paired with balancing metrics,
- used for learning,
- connected to decisions,
- reviewed with psychological safety,
- grounded in product and production outcomes.

Unhealthy metrics are:

- individual ranking tools,
- context-free targets,
- easy to game,
- disconnected from decisions,
- optimized at the expense of quality,
- used to create pressure instead of insight.

For enterprise Quote & Order teams, metrics should help improve the system that delivers customer value:

- backlog clarity,
- PR flow,
- CI reliability,
- deployment confidence,
- observability,
- incident recovery,
- domain correctness,
- developer experience.

The best metric is not the one that looks impressive.

The best metric is the one that helps the team make a better next decision.
