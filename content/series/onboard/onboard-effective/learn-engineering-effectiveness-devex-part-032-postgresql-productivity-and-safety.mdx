# Part 032 — PostgreSQL Productivity and Safety

## 1. Source notes and scope boundary

This part uses public PostgreSQL documentation and general production database engineering practice.

Public references to verify independently:

- PostgreSQL documentation describes `EXPLAIN`, `EXPLAIN ANALYZE`, indexes, transactions, constraints, and statistics collection.
- Testcontainers for Java provides a PostgreSQL module for running PostgreSQL containers in tests.
- Spring Boot documentation describes development-time services with Docker Compose and Testcontainers.

This part does **not** assume CSG Quote & Order uses a specific migration tool, database topology, schema design, DB ownership model, Testcontainers pattern, or production access process.

Use the `Internal verification checklist` sections to verify actual standards.

---

## 2. Core thesis

PostgreSQL productivity and PostgreSQL safety must be designed together.

A team that optimizes only for speed can create:

- unsafe migrations,
- missing tenant predicates,
- slow queries,
- lock storms,
- data inconsistency,
- untestable SQL,
- unreliable backfills,
- production repair toil.

A team that optimizes only for safety can create:

- slow feedback loops,
- painful local setup,
- fear of database changes,
- manual DBA bottlenecks,
- delayed refactoring,
- excessive process around low-risk changes.

The goal is a database workflow where engineers can make small, well-tested, observable, reversible-or-repairable changes quickly.

---

## 3. PostgreSQL as a developer feedback loop

Database work has multiple feedback loops:

| Loop | Question |
|---|---|
| Local SQL | Does the query return correct rows? |
| Mapper/repository test | Does application code bind parameters and map results correctly? |
| Migration test | Does schema evolve safely from previous version? |
| Query plan review | Is the query likely to perform on realistic data? |
| Tenant/security test | Does every path enforce tenant and authorization constraints? |
| CI integration test | Does this work in an isolated environment? |
| Production dashboard | Does real workload behave as expected after deploy? |

A productive team shortens these loops without removing them.

## 4. Local PostgreSQL golden path

A local database workflow should answer:

- how do I start PostgreSQL?
- how do I apply migrations?
- how do I seed test data?
- how do I reset data?
- how do I run one mapper test?
- how do I inspect query plans?
- how do I simulate tenant data?
- how do I reproduce production-like data shape safely?

### 4.1 Local database maturity

| Level | Experience |
|---|---|
| Manual | Install PostgreSQL, create DB manually, ask for seed SQL |
| Scripted | One script creates database and applies migrations |
| Containerized | Docker Compose or Testcontainers starts DB consistently |
| Fixture-driven | Named fixtures create domain-realistic states |
| Diagnostic | EXPLAIN, slow query logs, and reset tools are easy |
| Golden path | New engineer can run DB tests and inspect plans without tribal knowledge |

### 4.2 Reset matters

A local database that cannot be reset cheaply slows learning.

Provide one of:

- drop/create database script,
- truncate/reset script,
- schema-per-test strategy,
- container-per-test/suite strategy,
- fixture cleanup strategy.

Make reset safe and obvious.

## 5. Testcontainers and real database behavior

Mocking the database is not enough for serious PostgreSQL work.

Real PostgreSQL behavior matters for:

- SQL syntax,
- JSONB operators,
- indexes,
- constraints,
- transaction isolation,
- locks,
- generated columns,
- time zones,
- decimal precision,
- execution plans,
- migration behavior.

A useful test strategy:

| Test type | Purpose |
|---|---|
| Unit test | Domain rules without DB |
| Mapper integration test | SQL + mapping correctness |
| Migration test | Schema version upgrade correctness |
| Query plan check | Performance risk detection |
| Concurrency test | Race/locking/idempotency behavior |
| Backfill test | Chunking, resume, validation |

Testcontainers can improve repeatability by providing disposable PostgreSQL instances for tests.

## 6. Migration productivity and safety

Migrations should be easy to create and hard to make dangerously.

A good migration workflow includes:

- naming convention,
- review checklist,
- local apply command,
- rollback/roll-forward expectation,
- previous-release upgrade test,
- production-like fixture test for high-risk migrations,
- lock/risk notes,
- validation query,
- on-prem/customer upgrade notes where relevant.

### 6.1 Migration categories

| Category | Example | Review depth |
|---|---|---|
| Low risk additive | nullable column on small table | normal review |
| Medium risk index | add index to active table | query/lock review |
| High risk constraint | new unique/not-null constraint | data validation + rollout plan |
| High risk semantic | change meaning of state | domain/design review |
| Critical | tenant key/data ownership migration | security/data/architecture review |

### 6.2 Expand-contract discipline

For non-trivial changes:

1. expand schema safely,
2. deploy code compatible with old and new,
3. backfill in controlled way,
4. validate data,
5. switch reads/writes,
6. contract old schema only when safe.

This is especially important for rolling deployment and on-prem/customer upgrade paths.

## 7. Query diagnostics

A query is not production-ready just because it returns the right rows.

For important queries, inspect:

- expected row count,
- selectivity,
- index usage,
- join order,
- sort/hash operations,
- actual vs estimated rows,
- buffer usage,
- execution time,
- tenant predicate,
- pagination behavior.

### 7.1 EXPLAIN habit

Use `EXPLAIN` to inspect query plans and `EXPLAIN ANALYZE` carefully when you need actual execution stats.

For write queries or production data, be careful: `EXPLAIN ANALYZE` executes the statement.

### 7.2 Query review checklist

Ask:

- Is this query scoped by tenant where required?
- Does it use stable pagination?
- Can it use an index?
- What happens with large tenants?
- What happens with old/historical data?
- Are nulls handled intentionally?
- Is sorting supported by index or acceptable cost?
- Is this a hot path?
- Is query plan tested with realistic data shape?

## 8. Index productivity and safety

Indexes improve reads but cost writes and storage.

Index review should consider:

- workload frequency,
- selectivity,
- write amplification,
- table size,
- query pattern,
- column order,
- partial index opportunity,
- composite index usefulness,
- uniqueness/invariant enforcement,
- migration lock behavior.

### 8.1 Index smell examples

Smells:

- index added without query plan evidence,
- multiple overlapping indexes,
- index missing tenant leading column where query always scopes tenant,
- index for one-off admin query on hot write table,
- unique index missing tenant key in multi-tenant table,
- `LIKE '%term%'` expected to use normal btree index,
- index created in a blocking way on large active table.

### 8.2 Quote & Order examples

Potentially important query paths:

- quote search by tenant/customer/status,
- quote lookup by tenant/id/version,
- accepted quote to order conversion lookup,
- order search by tenant/customer/state,
- order item lookup by order ID,
- outbox relay pending events,
- inbox dedupe lookup,
- audit reconstruction by aggregate,
- fallout queue by state/created time.

Each query should have an owner and performance expectation.

## 9. Tenant isolation as database productivity

Tenant bugs are expensive.

Make tenant correctness easy:

- repository methods require tenant ID,
- query builders include tenant by default,
- fixtures create multi-tenant data,
- tests assert tenant A cannot see tenant B,
- unique constraints include tenant where required,
- indexes match tenant-scoped queries,
- cache keys include tenant,
- repair scripts require tenant scope.

### 9.1 Bad pattern

```sql
SELECT * FROM quote WHERE id = :quote_id;
```

### 9.2 Better pattern

```sql
SELECT *
FROM quote
WHERE tenant_id = :tenant_id
  AND id = :quote_id;
```

Better still, make unsafe methods hard to call.

## 10. Transaction and locking productivity

Database concurrency issues are hard to debug if transaction boundaries are unclear.

Document:

- where transactions start,
- isolation level assumptions,
- optimistic locking/version columns,
- pessimistic locks if used,
- idempotency record writes,
- outbox write transaction,
- retry strategy,
- deadlock handling,
- lock timeout and statement timeout standards.

### 10.1 Quote/order concurrency scenarios

Test and document:

- two users accept same quote,
- quote expires while being accepted,
- order callback arrives while cancellation happens,
- duplicate fulfillment callback,
- outbox relay retries,
- migration/backfill updates rows while app writes continue.

### 10.2 Version guard pattern

For lifecycle transitions, prefer expected-state/version guards:

```sql
UPDATE quote
SET state = 'ACCEPTED',
    version = version + 1
WHERE tenant_id = :tenant_id
  AND quote_id = :quote_id
  AND version = :expected_version
  AND state = 'APPROVED';
```

Then application can detect conflict from affected row count.

## 11. Data fixture productivity

Database fixtures should model real business states.

Examples:

- `tenant_a_draft_quote_with_two_items`,
- `tenant_a_approved_quote_price_valid`,
- `tenant_a_approved_quote_price_expired`,
- `tenant_a_accepted_quote_already_converted`,
- `tenant_b_quote_same_external_id`,
- `order_in_fallout_one_item_failed`,
- `outbox_pending_order_created_event`,
- `audit_history_for_approval_override`.

Fixtures should support:

- unit tests,
- mapper integration tests,
- migration tests,
- E2E tests,
- query plan tests.

Avoid fixture drift by giving fixtures owners and names based on business states.

## 12. Safe backfill productivity

Backfills are common in enterprise systems.

A productive backfill framework should provide:

- dry-run mode,
- candidate row count,
- chunking,
- resume/checkpoint,
- lock/statement timeout,
- tenant scoping,
- progress metrics,
- validation query,
- error reporting,
- idempotency,
- audit if required.

Bad backfill:

```sql
UPDATE quote SET new_field = compute_value(old_field);
```

Better approach:

- identify candidate rows,
- process chunks,
- update only expected old state,
- validate after each chunk,
- publish progress,
- stop safely on anomaly.

## 13. Database observability for developers

Developers need database signals, not just DBAs/platform teams.

Useful signals:

- slow query examples,
- lock waits,
- deadlocks,
- connection pool saturation,
- transaction duration,
- migration duration,
- table/index bloat if exposed,
- outbox backlog,
- query latency by repository method,
- error rates by SQL state category.

For Quote & Order, add business context:

- quote search latency,
- quote accept transaction latency,
- order creation transaction latency,
- order fallout query latency,
- outbox relay lag,
- audit reconstruction latency.

## 14. Database PR review checklist

When reviewing PostgreSQL-related changes, ask:

### 14.1 Correctness

- Does the query return correct rows for tenant/customer/state/version?
- Are nulls/defaults intentional?
- Are lifecycle invariants preserved?
- Are parent/child states consistent?
- Are audit/outbox side effects considered?

### 14.2 Safety

- Is tenant scope present?
- Is the migration backward compatible?
- Does it work during rolling deploy?
- Is lock behavior reviewed?
- Is backfill chunked if needed?
- Is rollback or roll-forward plan understood?

### 14.3 Performance

- Is this query on a hot path?
- Is there index evidence?
- Is pagination stable?
- Is `EXPLAIN` included for risky query?
- Are realistic row counts considered?

### 14.4 Developer experience

- Can relevant tests be run locally?
- Are fixtures clear?
- Is migration command documented?
- Is validation query included?
- Does failure produce useful diagnostic context?

## 17. Summary

PostgreSQL productivity is not separate from database safety.

A good workflow makes it easy to:

- run real PostgreSQL locally,
- write mapper tests,
- apply migrations,
- seed realistic data,
- inspect query plans,
- enforce tenant scope,
- test concurrency,
- backfill safely,
- observe production behavior.

For Quote & Order systems, database changes are business changes.

The best developer experience is the one that makes safe database work fast and unsafe database work visibly hard.
