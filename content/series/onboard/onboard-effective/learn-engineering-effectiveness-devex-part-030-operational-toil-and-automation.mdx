# Part 030 — Operational Toil and Automation

## 1. Source notes and scope boundary

This part uses public SRE and platform engineering references, especially:

- Google SRE material defining toil as repetitive, automatable, tactical, interrupt-driven operational work with limited enduring value.
- Google SRE workbook guidance on identifying and eliminating toil.
- DORA continuous delivery capabilities such as deployment automation and reliable automated tests.
- Platform engineering principles from earlier parts: platform-as-product, golden paths, self-service, and cognitive load reduction.

This part does **not** assume CSG uses a specific automation platform, runbook runner, ChatOps system, internal developer platform, break-glass model, data repair tool, or operations team structure.

Use internal verification checklists to map toil and automation to actual CSG/team processes.

---

## 2. Core thesis

Operational toil is work that keeps the system running but does not compound unless you turn it into learning, automation, or design improvement.

Toil is not the same as operations.

Some operations work is high-value:

- diagnosing a novel incident,
- designing a safer release process,
- improving observability,
- creating a self-service workflow,
- reviewing production risk,
- learning from postmortems.

Toil is the repeated, manual, reactive work that should either be automated, eliminated, simplified, delegated to a self-service path, or made unnecessary by better design.

For Quote & Order systems, common toil includes:

- manually checking stuck orders,
- manually replaying Kafka events,
- manually extracting support data,
- manually validating migrations,
- manually changing tenant config,
- manually deploying or verifying releases,
- manually triaging flaky tests,
- manually collecting logs for customer incidents,
- manually running data repair scripts,
- manually answering the same onboarding/debugging questions.

A senior engineer asks:

> Which repeated operational task is consuming engineering attention, increasing risk, and failing to create durable improvement?

## 3. Toil taxonomy

### 3.1 Release toil

Examples:

- manual deployment checklist,
- manual version bump,
- manual release note generation,
- manual smoke test execution,
- manual dashboard verification,
- manual feature flag coordination,
- manual customer enablement steps.

Risk:

- human error,
- slow releases,
- after-hours burden,
- inconsistent verification.

### 3.2 Incident toil

Examples:

- repeatedly collecting the same logs,
- manually correlating quote/order IDs across services,
- manually checking Kafka lag/DLQ,
- manually determining tenant/customer impact,
- manually checking whether issue already resolved.

Risk:

- slow MTTR,
- inconsistent diagnosis,
- dependence on experts.

### 3.3 Data repair toil

Examples:

- manually writing SQL for common stuck order states,
- manually validating affected row counts,
- manually inserting missing outbox events,
- manually rebuilding projections,
- manually preparing customer-safe evidence.

Risk:

- data corruption,
- tenant leakage,
- audit gaps,
- repeated emergency work.

### 3.4 Environment toil

Examples:

- manually resetting test environments,
- manually seeding fixtures,
- manually creating tenants/users/config,
- manually fixing broken local setup,
- manually debugging Kubernetes namespace drift.

Risk:

- slow feedback,
- flaky testing,
- onboarding delay.

### 3.5 Support toil

Examples:

- same support query answered repeatedly by engineers,
- manual quote/order status extraction,
- manual explanation of error codes,
- manual customer-specific configuration checks,
- manual runbook execution for known issue.

Risk:

- senior engineers become support bottleneck,
- product knowledge not encoded,
- customer response inconsistent.

### 3.6 Governance toil

Examples:

- repetitive manual compliance evidence gathering,
- repeated architecture exception approvals without standard path,
- manually checking PR checklist items that CI could check,
- manual dependency/security report collection.

Risk:

- bureaucracy,
- slow delivery,
- hidden inconsistency.

## 4. Toil is not always bad

Some manual work is appropriate early.

Manual is acceptable when:

- the process is new and not yet understood,
- the volume is low,
- human judgment is essential,
- automation would encode the wrong abstraction,
- the risk of automation is greater than the toil,
- the task is exploratory or one-off.

Manual becomes toil when:

- it repeats,
- it is predictable,
- it interrupts planned work,
- it can be done by a machine,
- it requires little judgment,
- it scales linearly with system growth,
- it creates no enduring learning,
- errors are likely and costly.

The goal is not to automate everything.

The goal is to automate, eliminate, or productize the right things.

## 5. Toil cost model

Toil costs more than the minutes spent.

### 5.1 Direct cost

- engineer time,
- on-call time,
- support time,
- release time,
- review time.

### 5.2 Context-switch cost

- lost focus,
- delayed sprint work,
- stale PRs,
- increased cycle time,
- higher error probability after interruption.

### 5.3 Risk cost

- manual mistake,
- wrong tenant,
- wrong environment,
- wrong script version,
- missed validation,
- inconsistent support answer,
- untracked production change.

### 5.4 Opportunity cost

- fewer improvements,
- less mentoring,
- delayed architecture cleanup,
- slower product delivery,
- expert bottleneck persists.

### 5.5 Burnout cost

- after-hours work,
- alert fatigue,
- learned helplessness,
- poor morale,
- attrition risk.

A toil backlog item should express these costs.

## 6. Toil discovery methods

### 6.1 Toil diary

For two weeks, record repeated work.

| Date | Task | Trigger | Duration | Frequency | Automatable? | Risk | Owner |
|---|---|---:|---:|---:|---|---|---|
| 2026-xx-xx | Check stuck orders manually | Support ticket | 25m | 3/week | yes | medium | order team |
| 2026-xx-xx | Re-run flaky test pipeline | CI fail | 15m | daily | partly | high | team |

### 6.2 Incident review mining

Look for repeated actions in incidents:

- same query run repeatedly,
- same dashboard missing,
- same log correlation issue,
- same manual mitigation,
- same data repair script pattern.

### 6.3 Support ticket mining

Look for repeated support questions:

- “Why is this order stuck?”
- “Which quote version was accepted?”
- “Did billing receive the order?”
- “Can we reprocess this event?”
- “Which tenant config is active?”

Repeated support questions are often missing self-service observability.

### 6.4 Developer onboarding mining

Look for repeated onboarding friction:

- local setup failure,
- missing environment variable,
- unknown test fixture,
- unclear run command,
- confusing service ownership,
- undocumented debugging flow.

Onboarding toil is DevEx debt.

## 7. Automation is not always the answer

Before automating, ask:

- Can we eliminate the task entirely?
- Can we simplify the system so the task is unnecessary?
- Can we make the task self-service?
- Can we make the task safer with guardrails?
- Can we document it better first?
- Can we improve observability so the task is no longer manual?
- Is full automation worth the maintenance cost?

### 7.1 Eliminate before automate

Bad:

> Automate weekly manual restart of service.

Better:

> Fix memory leak or readiness issue causing the restart need.

### 7.2 Productize before script sprawl

Bad:

> Ten local scripts for data repair, each known by one person.

Better:

> Versioned repair runner with dry-run, tenant scope, approval, audit, validation, and evidence output.

### 7.3 Guardrail before self-service

Bad:

> Anyone can replay any Kafka topic from any offset.

Better:

> Authorized replay tool with tenant/topic scope, dry-run, side-effect warning, rate limit, audit, and rollback/verification guidance.

## 8. Automation opportunity matrix

Prioritize toil with impact and automation suitability.

| Frequency | Risk | Automatable | Priority |
|---|---|---|---|
| High | High | High | automate/productize now |
| High | Low | High | automate if cheap |
| Low | High | Medium | add guardrail/runbook first |
| Low | Low | Low | document or ignore |
| High | High | Low | redesign system/process |

High-value automation candidates usually meet these criteria:

- repeated often,
- interrupts engineers,
- easy to make mistake,
- has clear input/output,
- can be verified automatically,
- has stable domain rules,
- creates measurable improvement.

## 9. Automation levels

### 9.1 Level 0 — Tribal manual

Task exists only in someone's head.

Risk:

- single point of failure,
- inconsistent execution,
- no audit.

### 9.2 Level 1 — Documented manual

Runbook exists.

Improvement:

- repeatable,
- reviewable,
- teachable.

Remaining risk:

- human error,
- still interrupt-driven.

### 9.3 Level 2 — Scripted manual

Script automates steps but engineer triggers it.

Improvement:

- less typing,
- lower error rate.

Remaining risk:

- weak guardrails,
- poor audit if not designed.

### 9.4 Level 3 — Guardrailed self-service

Tool enforces scope, validation, approval, audit.

Improvement:

- safe delegation,
- fewer expert interrupts,
- better evidence.

### 9.5 Level 4 — Automated remediation

System detects and acts automatically.

Improvement:

- fastest recovery,
- low human toil.

Risk:

- wrong automation can amplify incident,
- needs strong confidence, observability, and kill switch.

### 9.6 Level 5 — Designed away

The task no longer exists due to better architecture.

Example:

- idempotent consumers eliminate manual duplicate cleanup,
- self-healing projection rebuild removes manual index repair,
- safe migration framework removes manual checklist steps.

## 10. Quote & Order toil examples

### 10.1 Stuck order investigation

Manual toil:

- support asks engineer,
- engineer queries order table,
- checks item states,
- checks fulfillment task table,
- checks Kafka events,
- checks DLQ,
- gives support answer.

Improvement path:

1. Document diagnostic runbook.
2. Add dashboard for stuck order categories.
3. Add one-click support-safe status view.
4. Add reconciliation job.
5. Add safe resume action where domain permits.
6. Add alert for aging stuck states.

### 10.2 Kafka DLQ reprocessing

Manual toil:

- identify failed messages,
- inspect payload,
- decide retry/suppress/repair,
- reprocess manually,
- verify downstream state.

Improvement path:

1. Standard DLQ metadata.
2. DLQ dashboard by event type/tenant/error.
3. Classification rules.
4. Safe replay tool with dry-run.
5. Idempotency verification.
6. Audit of replay action.

### 10.3 Database migration validation

Manual toil:

- DBA/engineer manually checks table/row counts,
- manual query plan review,
- manual post-deploy validation.

Improvement path:

1. Migration checklist.
2. Standard validation query template.
3. CI migration test with production-like fixture.
4. Automated post-migration validation job.
5. Dashboard for migration duration/backfill progress.

### 10.4 Release verification

Manual toil:

- open dashboard,
- run smoke API calls,
- check pods,
- check Kafka lag,
- check logs,
- update release channel.

Improvement path:

1. Release dashboard.
2. Automated smoke suite.
3. Deployment marker.
4. Health summary command.
5. Automated release verification report.

### 10.5 Onboarding support

Manual toil:

- senior engineer repeatedly helps local setup,
- same Maven/Docker/PostgreSQL/Kafka issue repeats,
- first PR takes long.

Improvement path:

1. Golden path docs.
2. Setup script.
3. Troubleshooting guide.
4. Sample fixture.
5. Local smoke check.
6. First PR path.

## 11. Automation design principles

### 11.1 Make it safe by default

Automation should default to safe mode:

- dry-run first,
- read-only first,
- smallest scope,
- explicit tenant/environment,
- confirmation for dangerous actions,
- guardrails for production,
- audit every privileged action.

### 11.2 Make scope visible

Every automation should show:

- environment,
- tenant,
- service,
- aggregate IDs,
- row count,
- event count,
- expected impact,
- operator,
- approval reference.

### 11.3 Make failure diagnosable

Automation must produce useful output:

- what it tried,
- what succeeded,
- what failed,
- partial state,
- next safe action,
- correlation ID,
- logs link,
- validation result.

### 11.4 Make it observable

Automation should emit:

- metrics,
- audit events,
- structured logs,
- trace spans if relevant,
- run history,
- success/failure counts.

### 11.5 Make it owned

Every automation needs:

- owner,
- repository,
- tests,
- documentation,
- support model,
- deprecation policy.

Unowned automation becomes hidden risk.

---

## 12. Automation anti-patterns

### 12.1 Script graveyard

Many scripts, no owner, no tests, no audit.

### 12.2 Button without guardrails

Self-service UI triggers dangerous production action with little context.

### 12.3 Automation of unclear process

Automates a process nobody understands, encoding wrong behavior.

### 12.4 Automation that hides failure

Automatically retries forever and hides real customer impact.

### 12.5 Automation that creates toil elsewhere

Saves engineering time but increases support, QA, platform, or security burden.

### 12.6 Over-automation

Builds a complex system for rare low-risk task.

### 12.7 Human approval theater

Automation requires approval but approvers have no useful evidence.

Approval should be informed by dry-run and risk output.

## 14. Automation PR review checklist

When reviewing automation, ask:

### Correctness

- Does it encode the right domain invariant?
- Does it handle edge cases?
- Is it idempotent?
- Can it resume after partial failure?

### Safety

- Is environment explicit?
- Is tenant scope explicit?
- Is dry-run supported?
- Are dangerous actions gated?
- Is least privilege used?

### Observability

- Does it log structured output?
- Does it emit metrics?
- Does it create audit evidence?
- Can operators diagnose failure?

### Security

- Does it expose PII?
- Does it respect tenant isolation?
- Are credentials handled safely?
- Are permissions appropriate?

### Operations

- Is there a runbook?
- Is ownership clear?
- Is it tested?
- Is failure behavior documented?
- Is deprecation/removal considered?

## 15. Platform engineering and toil

A platform team should reduce toil for stream-aligned teams by providing paved roads.

Examples:

- service template with logging/tracing/health checks,
- CI pipeline defaults,
- Kubernetes deployment template,
- standardized migration test harness,
- Kafka schema compatibility gate,
- release dashboard template,
- runbook template,
- self-service environment creation,
- support bundle generator.

But platform can also create toil if it becomes:

- ticket queue,
- approval bottleneck,
- undocumented black box,
- rigid cage,
- tool-first solution without user research.

Platform-as-product means asking:

> What toil are product teams experiencing, and what self-service platform capability would reduce it safely?

## 16. Automation and Scrum

Toil reduction belongs in the Product Backlog when it affects delivery, reliability, support, or customer outcomes.

### 16.1 Refinement questions

- What toil is this reducing?
- Who benefits?
- How often does it happen?
- What risk does it remove?
- What is the smallest improvement?
- What evidence proves success?

### 16.2 Sprint Planning questions

- Is this automation more valuable than feature work this sprint?
- Is it needed to protect upcoming release?
- Does it reduce incident/support load?
- Can it be sliced safely?

### 16.3 Sprint Review evidence

Demo:

- before process,
- after process,
- time saved,
- error risk reduced,
- audit/guardrail output,
- dashboard/metric.

### 16.4 Retrospective input

Ask:

- What repeated manual work slowed us this Sprint?
- Which interruptions were avoidable?
- Which runbook step should become a tool?
- Which tool created more toil than it removed?

## 17. Automation maturity for a task

Use this scoring model.

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Documentation | tribal | runbook exists | tested, current, discoverable |
| Safety | manual judgment | basic guardrails | dry-run, scope, approval, audit |
| Execution | manual | scripted | self-service or automatic |
| Observability | ad hoc output | logs/results | metrics, audit, dashboard |
| Ownership | unknown | named owner | lifecycle owner and roadmap |
| Testing | none | manual test | automated tests and fixtures |
| Adoption | expert-only | team usable | support/product/platform usable |

Prioritize improvements that move a high-frequency/high-risk task from 1 to 3 before aiming for 5.

## 20. Final mental model

Toil is operational drag.

Automation is one possible treatment.

The deeper goal is a delivery and operations system where repeated work becomes:

- documented,
- safer,
- observable,
- self-service,
- automated where appropriate,
- or designed away entirely.

For senior engineers, reducing toil is not just convenience.

It improves flow, reliability, onboarding, incident recovery, support quality, and product delivery.

The best automation does not merely save clicks.

It makes the safe path the easy path.
