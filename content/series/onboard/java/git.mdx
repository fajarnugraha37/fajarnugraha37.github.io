# Git Cheat Sheet

## 1. Mental Model Git

Git menyimpan riwayat sebagai graph commit.

```text
Working Directory
      ↓ git add
Staging Area / Index
      ↓ git commit
Local Repository
      ↓ git push
Remote Repository
```

Tiga area utama:

```text
Working tree  → perubahan lokal
Index         → perubahan yang akan masuk commit
HEAD          → commit aktif saat ini
```

Objek utama:

```text
blob    = isi file
tree    = struktur direktori
commit  = snapshot + metadata + parent
tag     = pointer permanen ke commit
branch  = pointer bergerak ke commit
HEAD    = pointer ke branch/commit aktif
```

Invariant penting:

```text
Commit Git bersifat immutable.
Branch hanyalah pointer ke commit.
Merge dan rebase menghasilkan graph yang berbeda.
Reset memindahkan pointer.
Revert membuat commit pembatalan baru.
```

# 10. Rebase

Rebase memindahkan rangkaian commit ke base baru.

```bash
git switch feature/payment
git rebase main
```

Sebelum:

```text
A---B---C main
     \
      D---E feature
```

Sesudah:

```text
A---B---C main
         \
          D'---E' feature
```

Commit `D'` dan `E'` adalah commit baru dengan hash baru.

## Menangani conflict rebase

```bash
git status
```

Perbaiki conflict, lalu:

```bash
git add conflicted-file
git rebase --continue
```

Lewati commit:

```bash
git rebase --skip
```

Batalkan:

```bash
git rebase --abort
```

## Interactive rebase

```bash
git rebase -i HEAD~5
```

Operasi:

```text
pick    gunakan commit
reword  ubah commit message
edit    ubah isi commit
squash  gabungkan dengan commit sebelumnya
fixup   gabungkan tanpa mempertahankan message
drop    hapus commit
```

## Aturan aman

```text
Rebase commit lokal: aman.
Rebase branch shared: berisiko.
Rebase commit yang sudah dipakai orang lain: hindari.
```

# 11. Merge vs Rebase

## Merge

```text
Mempertahankan struktur history asli.
Tidak mengganti hash commit lama.
Aman untuk branch bersama.
Dapat menghasilkan merge commit.
```

## Rebase

```text
Menghasilkan history linear.
Mengganti hash commit.
Cocok untuk membersihkan branch lokal.
Berbahaya pada shared history.
```

Workflow umum:

```bash
git switch feature/payment
git fetch origin
git rebase origin/main
git push --force-with-lease
```

Gunakan:

```bash
git push --force-with-lease
```

Hindari:

```bash
git push --force
```

`--force-with-lease` menolak push jika remote berubah sejak terakhir Anda lihat.

# 13. Reset

`reset` memindahkan HEAD/branch pointer.

## Soft reset

```bash
git reset --soft HEAD~1
```

Hasil:

```text
Commit dibatalkan.
Perubahan tetap staged.
```

## Mixed reset

```bash
git reset HEAD~1
```

atau:

```bash
git reset --mixed HEAD~1
```

Hasil:

```text
Commit dibatalkan.
Perubahan tidak staged.
File tetap berubah.
```

## Hard reset

```bash
git reset --hard HEAD~1
```

Hasil:

```text
Commit dibatalkan.
Staging dibersihkan.
Working tree dibersihkan.
```

Reset lokal ke remote:

```bash
git fetch origin
git reset --hard origin/main
```

Perintah ini destruktif terhadap perubahan lokal yang belum disimpan.

Perbedaan:


# 16. Conflict Resolution

Conflict marker:

```text
<<<<<<< HEAD
kode dari branch aktif
=======
kode dari branch yang digabung
>>>>>>> feature/payment
```

Proses umum:

```bash
git status
```

Perbaiki file, hapus marker, lalu:

```bash
git add conflicted-file
```

Untuk merge:

```bash
git commit
```

Untuk rebase:

```bash
git rebase --continue
```

Gunakan versi branch aktif:

```bash
git checkout --ours file.txt
```

Gunakan versi branch lain:

```bash
git checkout --theirs file.txt
```

Pada rebase, arti `ours` dan `theirs` dapat terasa terbalik karena Git sedang menerapkan ulang commit ke base baru. Selalu inspeksi hasilnya.

# 23. Bisect

Mencari commit penyebab bug dengan binary search.

```bash
git bisect start
git bisect bad
git bisect good <known-good-commit>
```

Git memilih commit tengah. Jalankan test, lalu tandai:

```bash
git bisect good
git bisect bad
```

Selesai:

```bash
git bisect reset
```

Otomatis dengan script:

```bash
git bisect start
git bisect bad
git bisect good <commit>
git bisect run ./test-script.sh
```

Exit code:

```text
0      = good
1–127  = bad
125    = skip
```

# 29. Commit Message

Format umum:

```text
<type>(<scope>): <subject>

<body>

<footer>
```

Contoh:

```text
feat(payment): add transaction retry mechanism

Retry transient gateway failures using exponential backoff.

Refs: PAY-142
```

Type umum:

```text
feat      fitur baru
fix       perbaikan bug
refactor  perubahan struktur tanpa perubahan perilaku
perf      peningkatan performa
test      penambahan/perbaikan test
docs      dokumentasi
build     build system/dependency
ci        pipeline CI/CD
chore     maintenance
revert    pembatalan commit
```

Prinsip commit:

```text
Satu commit = satu perubahan logis.
Commit harus dapat dibuild atau minimal tidak merusak branch.
Hindari commit message seperti "update", "fix", atau "changes".
Jelaskan alasan, bukan hanya perubahan sintaks.
```

```text
    Cocok ketika satu PR dianggap satu unit perubahan.
```

# GitHub Actions Cheat Sheet

## 1. Mental Model

GitHub Actions adalah automation engine berbasis event. Workflow didefinisikan sebagai file YAML di dalam `.github/workflows/`. Satu workflow terdiri dari satu atau beberapa job, dan setiap job dijalankan oleh runner. ([GitHub Docs](https://docs.github.com/actions/using-workflows/workflow-syntax-for-github-actions?utm_source=chatgpt.com))

```text
GitHub Event
    │
    ▼
Workflow
    │
    ├── Job: build
    │     ├── Step: checkout
    │     ├── Step: setup Java
    │     └── Step: Maven build
    │
    ├── Job: integration-test
    │     └── PostgreSQL service container
    │
    └── Job: deploy
          └── Kubernetes / AWS / Azure / on-premises
```

Konsep utama:

```text
Workflow   = proses automation secara keseluruhan
Event      = pemicu workflow
Job        = sekumpulan step yang berjalan pada satu runner
Step       = command atau action
Action     = unit automation reusable
Runner     = compute yang menjalankan job
Artifact   = output workflow yang disimpan
Cache      = data reusable untuk mempercepat workflow
Environment = target deployment dan protection boundary
```

Invariant penting:

```text
Setiap job memiliki filesystem sendiri.
Step dalam job yang sama berbagi filesystem.
Job berbeda tidak otomatis berbagi file.
Data antar-job dipindahkan melalui artifact atau output.
Job tanpa needs dapat berjalan paralel.
Job dengan needs membentuk dependency graph.
```

# 10. Java dan Maven CI

GitHub menyediakan panduan resmi untuk build dan test Java dengan Maven menggunakan GitHub Actions. ([GitHub Docs](https://docs.github.com/actions/guides/building-and-testing-java-with-maven?utm_source=chatgpt.com))

```yaml
name: Java CI

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

permissions:
  contents: read

concurrency:
  group: java-ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven

      - name: Validate Maven Wrapper
        run: ./mvnw --version

      - name: Run verification
        run: |
          ./mvnw \
            --batch-mode \
            --no-transfer-progress \
            clean verify
```

Flags berguna:

```text
--batch-mode
    Menonaktifkan interactive output.

--no-transfer-progress
    Mengurangi noise download dependency.

-DskipTests
    Compile test tetapi tidak menjalankannya.

-Dmaven.test.skip=true
    Melewati compile dan execution test.

-fae / --fail-at-end
    Melanjutkan module lain dan gagal di akhir.

-ff / --fail-fast
    Berhenti pada kegagalan pertama.
```

Untuk CI, utamakan:

```bash
./mvnw clean verify
```

Daripada hanya:

```bash
./mvnw package
```

`verify` menjalankan lifecycle hingga tahap verification, termasuk integration-test plugin yang dikonfigurasi dengan benar.

# 27. Reusable Workflow

Reusable workflow merupakan file dalam `.github/workflows` yang menggunakan event `workflow_call`. Subdirectory di bawah `.github/workflows` tidak didukung untuk reusable workflow. ([GitHub Docs](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows?utm_source=chatgpt.com))

Called workflow:

```yaml
# .github/workflows/reusable-java-ci.yml

name: Reusable Java CI

on:
  workflow_call:
    inputs:
      java-version:
        required: false
        type: string
        default: "21"

    secrets:
      maven-username:
        required: false

      maven-password:
        required: false

    outputs:
      artifact-name:
        description: Name of generated artifact
        value: ${{ jobs.build.outputs.artifact-name }}

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest

    outputs:
      artifact-name: ${{ steps.metadata.outputs.artifact-name }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ inputs.java-version }}
          cache: maven

      - run: ./mvnw clean verify

      - id: metadata
        run: echo "artifact-name=application-${GITHUB_SHA}" >> "$GITHUB_OUTPUT"
```

Caller:

```yaml
jobs:
  java-ci:
    uses: company/platform-workflows/.github/workflows/java-ci.yml@v1
    with:
      java-version: "21"

    secrets:
      maven-username: ${{ secrets.MAVEN_USERNAME }}
      maven-password: ${{ secrets.MAVEN_PASSWORD }}
```

Meneruskan seluruh secret yang tersedia:

```yaml
secrets: inherit
```

Gunakan `inherit` hanya saat trust boundary caller dan called workflow benar-benar dipahami.

Pada nested reusable workflows, permissions hanya dapat dipertahankan atau dikurangi, tidak dapat dinaikkan oleh workflow yang lebih dalam. ([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations?utm_source=chatgpt.com))

# 28. Composite Action

Composite action menggabungkan beberapa step menjadi satu reusable action. Composite action menggunakan file `action.yml`, sedangkan reusable workflow tetap berupa workflow YAML dalam `.github/workflows`. ([GitHub Docs](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations?utm_source=chatgpt.com))

Struktur:

```text
.github/
└── actions/
    └── setup-java-maven/
        └── action.yml
```

`action.yml`:

```yaml
name: Set up Java and Maven
description: Configure Java and validate Maven Wrapper

inputs:
  java-version:
    description: Java version
    required: false
    default: "21"

runs:
  using: composite

  steps:
    - name: Set up Java
      uses: actions/setup-java@v4
      with:
        distribution: temurin
        java-version: ${{ inputs.java-version }}
        cache: maven

    - name: Validate Maven
      shell: bash
      run: ./mvnw --version
```

Penggunaan:

```yaml
steps:
  - uses: actions/checkout@v4

  - uses: ./.github/actions/setup-java-maven
    with:
      java-version: "21"
```

Pilih:

```text
Composite action
    Untuk reuse kumpulan step dalam sebuah job.

Reusable workflow
    Untuk reuse satu atau beberapa job lengkap,
    termasuk runner, permission, environment, dan dependency.
```

# 31. Docker Build dan Push

GitHub merekomendasikan penggunaan official Docker actions untuk login, metadata, Buildx, serta build dan push image. ([GitHub Docs](https://docs.github.com/actions/guides/publishing-docker-images?utm_source=chatgpt.com))

```yaml
name: Publish Container

on:
  push:
    tags:
      - "v*"

permissions:
  contents: read
  packages: write

jobs:
  publish:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Generate image metadata
        id: metadata
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=ref,event=tag
            type=sha,prefix=sha-

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.metadata.outputs.tags }}
          labels: ${{ steps.metadata.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Gunakan immutable image identity:

```text
semantic version
commit SHA
container digest
```

Jangan hanya mengandalkan:

```text
latest
main
stable
```

Tag mutable cocok sebagai alias, bukan deployment identity utama.

# 32. Build Once, Deploy Many

Anti-pattern:

```text
Deploy development
    → build source

Deploy staging
    → build ulang source

Deploy production
    → build ulang source
```

Risiko:

```text
dependency berubah
base image berubah
build tool berubah
artifact berbeda antar-environment
sulit membuktikan apa yang sebenarnya diuji
```

Target:

```text
Commit
    ↓
Build once
    ↓
Immutable JAR / container image
    ↓
Deploy development
    ↓
Promote staging
    ↓
Promote production
```

```yaml
jobs:

      image-digest: ${{ steps.build.outputs.digest }}

    needs:
      - build

```

Deployment input harus berupa:

```text

```

Bukan:

```text

```

# 33. Kubernetes Deployment

```yaml
name: Deploy Kubernetes

on:
  workflow_dispatch:
    inputs:
      image:
        description: Immutable container image digest
        required: true

        description: Target environment
```

# 35. Pull Request Security

Workflow yang menjalankan code dari pull request harus dianggap menjalankan input tidak tepercaya.

Risiko:

```text
malicious build script
dependency execution
secret exfiltration
runner compromise
internal-network access
cache poisoning
shell injection
```

Jangan menjalankan untrusted PR pada self-hosted runner yang memiliki akses jaringan internal atau credential sensitif.

Perhatikan `pull_request_target`: event ini berjalan dalam context base repository dan dapat memiliki akses yang lebih tinggi. GitHub menyediakan panduan khusus karena checkout dan execution code PR secara tidak aman dapat mengekspos repository. ([GitHub Docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target?utm_source=chatgpt.com))

Anti-pattern:

```yaml
on:
  pull_request_target:

jobs:
  dangerous:
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}

      - run: ./mvnw test
```

Dalam pola tersebut, code tidak tepercaya dapat dieksekusi dalam privileged context.

# 37. Pinning Actions

Readable:

```yaml
uses: actions/checkout@v4
```

Lebih reproducible:

```yaml
uses: actions/checkout@<full-commit-sha>
```

Trade-off:

```text
Major tag
    Mudah dipelihara.
    Mendapat patch dalam major version.
    Reference dapat bergerak.

Full commit SHA
    Immutable.
    Lebih aman terhadap perubahan upstream.
    Membutuhkan automation untuk update.
```

Untuk high-assurance workflow:

```text
pin third-party action ke full commit SHA
aktifkan Dependabot untuk github-actions
review update action seperti dependency code
allowlist action yang boleh digunakan
```

GitHub merekomendasikan hardening workflow dan dapat menggunakan Dependabot untuk memperbarui referensi action maupun reusable workflow. ([GitHub Docs](https://docs.github.com/en/actions/reference/security/secure-use?utm_source=chatgpt.com))

Actions Runner Controller atau ARC adalah Kubernetes operator untuk orchestration dan autoscaling self-hosted GitHub Actions runners. ([GitHub Docs](https://docs.github.com/en/actions/concepts/runners/actions-runner-controller?utm_source=chatgpt.com))

Security boundary:

```text

Batasi egress dan ingress.
Gunakan ephemeral workspace.

```

# 41. Environment Separation

Recommended topology:

```text
Public or untrusted PR runner
    ├── no secret
    ├── no internal network
    └── read-only token

Trusted build runner
    ├── package registry write
    ├── artifact signing
    └── no production deployment access

Non-production deploy runner
    ├── development/staging access
    └── no production identity

Production deploy runner
    ├── protected environment
    ├── required approval
    ├── short-lived identity
    └── restricted network
```

Jangan menggunakan satu runner identity untuk seluruh lifecycle.

# 48. Production Workflow Template

```yaml
name: Deploy Production

on:
  workflow_dispatch:
    inputs:
      image:
        description: Immutable image digest
        required: true
        type: string

permissions:
  contents: read
  id-token: write

concurrency:
  group: production
  cancel-in-progress: false

jobs:
  validate:
    runs-on: ubuntu-latest

    steps:
      - name: Validate image
        env:
          IMAGE: ${{ inputs.image }}
        shell: bash
        run: |
          set -euo pipefail

          if [[ ! "${IMAGE}" =~ @sha256:[a-f0-9]{64}$ ]]; then
            echo "Image must use an immutable sha256 digest"
            exit 1
          fi

  deploy:
    needs:
      - validate

    runs-on:
      - self-hosted
      - linux
      - production

    environment:
      name: production

    timeout-minutes: 30

    steps:
      - uses: actions/checkout@v4

      - name: Authenticate
        run: ./scripts/authenticate-production.sh

      - name: Deploy
        env:
          IMAGE: ${{ inputs.image }}
        run: ./scripts/deploy.sh production "${IMAGE}"

      - name: Verify
        run: ./scripts/verify-deployment.sh production

      - name: Write summary
        if: ${{ !cancelled() }}
        env:
          IMAGE: ${{ inputs.image }}
        run: |
          {
            echo "# Production Deployment"
            echo
            echo "- Image: \`${IMAGE}\`"
            echo "- Commit: \`${GITHUB_SHA}\`"
            echo "- Actor: \`${GITHUB_ACTOR}\`"
            echo "- Run: \`${GITHUB_RUN_ID}\`"
          } >> "$GITHUB_STEP_SUMMARY"
```

# 49. Review Checklist

```text
Trigger
[ ] Event dan activity type tepat.
[ ] Branch/path filters tidak memblokir required checks.
[ ] Deployment tidak berjalan dari event tidak tepercaya.

Permissions
[ ] GITHUB_TOKEN permission eksplisit.
[ ] Write permission hanya diberikan jika diperlukan.
[ ] id-token: write hanya pada OIDC job.

Secrets
[ ] Tidak ada secret dalam repository.
[ ] Secret tidak dicetak ke log.
[ ] Production secret dibatasi oleh environment.
[ ] Long-lived cloud credential dihindari.

Actions
[ ] Action berasal dari publisher tepercaya.
[ ] Sensitive action dipin ke commit SHA.
[ ] Dependabot mengelola action updates.

Runner
[ ] Trust level runner sesuai job.
[ ] Untrusted PR tidak berjalan pada privileged runner.
[ ] Self-hosted runner diisolasi atau ephemeral.

Build

Deployment
[ ] Build dan deploy dipisahkan.

[ ] Production memakai environment protection.
[ ] Deployment diserialisasi.
[ ] Rollout diverifikasi.
[ ] Rollback target diketahui.

Supply chain
[ ] Dependency diperiksa.
[ ] Artifact digest tersedia.
```

# 50. Common Anti-Patterns

```text
Menggunakan satu workflow raksasa untuk semua hal.
Memberikan permissions: write-all.
Menyimpan cloud access key jangka panjang.
Menjalankan PR tidak tepercaya pada runner internal.
Menggunakan pull_request_target lalu menjalankan code PR.
Membangun ulang artifact pada setiap environment.
Deploy menggunakan tag latest.
Tidak menetapkan timeout.
Retry tanpa upper bound.
Mengabaikan failure dengan || true.
Menggunakan always() tanpa memahami cancellation.
Menyimpan secret dalam cache atau artifact.
Menggunakan shared mutable self-hosted runner.
Menaruh seluruh logic deployment di YAML.
Mengubah nama required job tanpa memperbarui ruleset.
```

# 53. Rule of Thumb

```text
Workflow
    Orchestration, bukan tempat seluruh business logic.

Runner
    Harus sesuai trust level dan network boundary.

Permission
    Read by default, write by exception.

Secret
    Jangan masuk repository, log, cache, atau artifact.

Cloud access
    Gunakan short-lived identity melalui OIDC.

Pull request
    Perlakukan sebagai untrusted input.

Artifact
    Build sekali dan identifikasi secara immutable.

Deployment
    Promote artifact yang sama antar-environment.

Production
    Gunakan environment approval dan concurrency control.

Self-hosted runner
    Prefer ephemeral dan isolated.

Third-party action
    Review source dan pin ke immutable commit SHA.

Failure
    Harus terlihat, bounded, dan menghasilkan exit code non-zero.

Traceability
    Commit → workflow run → artifact digest → approval → deployment.
```

Cheat sheet ini paling efektif dipasangkan dengan kebijakan repository yang mewajibkan review `CODEOWNERS` untuk `.github/workflows/**` dan memblokir deployment production di luar protected environment.
