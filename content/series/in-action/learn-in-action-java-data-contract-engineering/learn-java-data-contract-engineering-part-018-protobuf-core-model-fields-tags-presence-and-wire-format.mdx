# Part 018 — Protobuf Core Model: Fields, Tags, Presence, and Wire Format

Protobuf looks simple.

```proto
message CaseOpened {
  string case_id = 1;
  string title = 2;
}
```

But production Protobuf engineering is not simple.

The dangerous parts are hidden behind the friendly syntax:

- field numbers are the real wire contract;
- field names are mostly source-level contract;
- default values can erase intent;
- presence is not the same as nullability;
- unknown fields can preserve forward compatibility;
- `oneof` is powerful but easy to evolve incorrectly;
- enum zero values are not optional decoration;
- JSON mapping is a different contract surface from binary Protobuf;
- deleting a field without reserving its tag is a future incident.

This part builds the core mental model before we move into Java generated code and evolution playbooks.

---

## 1. What Protobuf Optimizes For

Protobuf is a language-neutral, platform-neutral, extensible mechanism for serializing structured data.

In practice, teams choose it for:

- compact binary encoding;
- fast parsing;
- generated code across languages;
- gRPC service contracts;
- strongly typed internal APIs;
- mobile/backend communication;
- long-lived messages where compatibility matters.

Protobuf is not a validation language like JSON Schema.

It is primarily a serialization and interface definition system.

It says:

```text
This is how structured fields are encoded, decoded, generated, and evolved.
```

---

## 2. The Wire Contract Is Field Number + Wire Type

In JSON, field name matters directly:

```json
{"caseId": "C-123"}
```

In Protobuf binary encoding, the field number matters.

```proto
message CaseOpened {
  string case_id = 1;
  string title = 2;
}
```

The binary stream does not encode `case_id` as text field name.

It encodes a tag derived from:

```text
field_number + wire_type
```

Mental model:

```text
.proto field name = source/API readability
field number = binary compatibility identity
wire type = low-level encoding class
```

That is why this is safe-ish:

```proto
// v1
string case_id = 1;

// v2
string enforcement_case_id = 1;
```

But this is breaking:

```proto
// v1
string case_id = 1;

// v2
string case_id = 9;
```

The name stayed the same.

The wire identity changed.

---

## 3. Field Number Discipline

Field numbers are not cosmetic.

They are durable protocol addresses.

Rules:

- never reuse a field number for a different meaning;
- never change a field number after release;
- reserve deleted field numbers;
- reserve deleted field names when relevant;
- keep low field numbers for frequent fields if size matters;
- leave gaps for future expansion only when it helps readability.

Example:

```proto
message EnforcementCase {
  string case_id = 1;
  string title = 2;
  CaseStatus status = 3;

  reserved 4, 5;
  reserved "legacy_owner", "legacy_priority";
}
```

The `reserved` declaration prevents accidental reuse in future `.proto` edits.

This is one of the cheapest production safeguards in Protobuf.

Use it aggressively.

---

## 4. Wire Types

Protobuf binary encoding uses a small set of wire types.

You do not need to hand-encode them daily, but you must understand their compatibility consequences.

| Wire Type | Meaning | Common Fields |
|---|---|---|
| VARINT | variable-length integer | `int32`, `int64`, `uint32`, `uint64`, `bool`, enum |
| I64 | fixed 64-bit | `fixed64`, `sfixed64`, `double` |
| LEN | length-delimited | `string`, `bytes`, embedded message, packed repeated fields |
| I32 | fixed 32-bit | `fixed32`, `sfixed32`, `float` |

A field type change may be unsafe if the wire type changes.

Example:

```proto
// v1
string amount = 1; // LEN

// v2
int64 amount = 1;  // VARINT
```

Same field number.

Different wire type.

Old data may decode incorrectly or be skipped.

---

## 5. Binary Encoding Mental Model

For each field, Protobuf writes:

```text
tag + encoded_value
```

The tag is:

```text
(field_number << 3) | wire_type
```

Simplified example:

```proto
message Example {
  int32 id = 1;
  string name = 2;
}
```

Encoded stream conceptually:

```text
field 1 tag -> varint value
field 2 tag -> length -> bytes
```

Important consequences:

- fields can appear in any order;
- missing fields are common;
- default values may not be serialized;
- unknown fields can be skipped and sometimes preserved;
- repeated fields may appear multiple times;
- parsers merge duplicate message fields.

This is why Protobuf is evolution-friendly.

But it also means validation must be explicit when business rules matter.

---

## 6. Scalar Defaults Are Not Domain Defaults

In proto3, scalar fields have default values:

| Type | Default |
|---|---|
| string | empty string |
| bytes | empty bytes |
| bool | false |
| numeric | zero |
| enum | first enum value, usually zero |
| message | not set / default instance depending API |

This creates a domain trap.

```proto
message CaseOpened {
  string case_id = 1;
  int32 priority = 2;
}
```

If `priority` reads as `0`, what does it mean?

- producer explicitly sent priority 0;
- producer omitted priority;
- old producer did not know the field;
- invalid producer forgot to populate it.

Without presence, you cannot distinguish these cases for many scalar fields.

Do not treat Protobuf default values as business truth.

---

## 7. Presence: The Most Misunderstood Concept

Presence means the API can tell whether a field was explicitly set.

Presence is not the same as null.

Presence answers:

```text
Was this field provided by the sender?
```

Value answers:

```text
What value does this field currently have?
```

For production contracts, this distinction matters for:

- PATCH/update commands;
- optional business fields;
- defaulting rules;
- migration from old producers;
- audit evidence;
- partial projection updates.

Example problem:

```proto
message UpdateCasePriority {
  int32 priority = 1;
}
```

If `priority == 0`, does that mean:

- clear priority?
- set priority to 0?
- not provided?

Better:

```proto
message UpdateCasePriority {
  optional int32 priority = 1;
}
```

Now generated APIs can expose presence checks such as `hasPriority()` in languages that support it.

---

## 8. Explicit Presence vs Implicit Presence

A field with implicit presence does not track whether the default value was sent.

A field with explicit presence tracks set/unset state.

Simplified mental model:

| Field Shape | Can Detect Set? | Use Case |
|---|---:|---|
| `int32 priority = 1;` | Usually no for scalar implicit presence | Simple data with no need to distinguish missing/default |
| `optional int32 priority = 1;` | Yes | Patch commands, optional scalar business fields |
| `Priority priority = 1;` where `Priority` is message | Yes-ish at message field level | Rich optional object |
| `oneof priority_change` | Yes by selected case | Mutually exclusive intent |

When in doubt for command-like APIs, prefer explicit presence.

For event facts, use presence carefully; events should usually be complete facts, not ambiguous partial updates.

---

## 9. Message Fields Have Presence

Embedded message fields naturally carry presence.

```proto
message Money {
  string currency = 1;
  int64 units = 2;
  int32 nanos = 3;
}

message PenaltyAssessed {
  string case_id = 1;
  Money amount = 2;
}
```

You can tell whether `amount` was provided.

But inside `Money`, scalar defaults still need discipline.

If `nanos == 0`, that may be valid.

If `currency == ""`, that is probably invalid.

Protobuf does not enforce domain validity automatically.

---

## 10. Enum Zero Value

In proto3, enum first value must be zero.

This is not a minor syntax rule.

It shapes contract design.

Bad:

```proto
enum CaseStatus {
  OPEN = 0;
  CLOSED = 1;
}
```

Why bad?

A missing status defaults to `OPEN`.

That can create false business facts.

Better:

```proto
enum CaseStatus {
  CASE_STATUS_UNSPECIFIED = 0;
  CASE_STATUS_OPEN = 1;
  CASE_STATUS_UNDER_REVIEW = 2;
  CASE_STATUS_ESCALATED = 3;
  CASE_STATUS_CLOSED = 4;
}
```

Now default means unknown/unspecified, not a real lifecycle state.

Rule:

> The zero enum value should almost always be an explicit unspecified/unknown value.

---

## 11. Enum Naming

Avoid generic enum values.

Bad:

```proto
enum Status {
  UNKNOWN = 0;
  OPEN = 1;
  CLOSED = 2;
}
```

Better:

```proto
enum CaseStatus {
  CASE_STATUS_UNSPECIFIED = 0;
  CASE_STATUS_OPEN = 1;
  CASE_STATUS_CLOSED = 2;
}
```

Why prefix values?

- avoids name collisions in some generated languages;
- improves grepability;
- makes logs clearer;
- supports large proto packages.

---

## 12. Repeated Fields

A repeated field is a list.

```proto
message CaseOpened {
  repeated string allegation_codes = 1;
}
```

Subtleties:

- empty list and missing list often look the same in generated APIs;
- ordering may or may not be semantically meaningful;
- duplicate values may or may not be allowed;
- packed encoding can affect binary representation for numeric repeated fields;
- repeated message fields may become large quickly.

Always document collection semantics.

```proto
message CaseOpened {
  // Unique regulatory allegation codes. Order is not significant.
  repeated string allegation_codes = 1;
}
```

Protobuf will not enforce uniqueness.

Your semantic validator must.

---

## 13. Map Fields

Protobuf map syntax:

```proto
message CaseLabels {
  map<string, string> labels = 1;
}
```

A map is syntactic sugar for repeated key/value entry messages.

Use maps for genuinely dynamic key-value collections.

Do not use maps to avoid modeling.

Bad:

```proto
map<string, string> case_data = 1;
```

This destroys contract meaning.

Better:

```proto
message CaseOpened {
  string case_id = 1;
  string title = 2;
  CaseSource source = 3;
  repeated Allegation allegations = 4;
}
```

Map is acceptable for:

- labels;
- localized text;
- feature flags;
- metadata where keys are externally governed;
- sparse extension attributes with strict rules.

Even then, define allowed keys somewhere.

---

## 14. `oneof`: Tagged Union With Intent

`oneof` means exactly one of several fields may be set.

```proto
message CaseEvent {
  string event_id = 1;
  string case_id = 2;

  oneof payload {
    CaseOpened opened = 10;
    CaseEscalated escalated = 11;
    CaseClosed closed = 12;
  }
}
```

This is useful for:

- command intent;
- event envelopes;
- polymorphic payloads;
- mutually exclusive inputs.

Generated APIs expose which case is active.

But evolution is tricky.

Removing a field from `oneof` can lose information.

Moving fields into/out of `oneof` can be unsafe.

Adding a new `oneof` alternative is usually easier for new readers, but old readers will treat it as unknown.

If old systems must understand all event payloads, adding a new `oneof` case is a rollout decision, not just a schema edit.

---

## 15. Unknown Fields

Unknown fields are fields present in binary data but not recognized by the current schema.

Example:

```proto
// Writer v2
message CaseOpened {
  string case_id = 1;
  string title = 2;
  string intake_channel = 3;
}

// Reader v1
message CaseOpened {
  string case_id = 1;
  string title = 2;
}
```

Reader v1 does not know field 3.

In binary Protobuf, the parser can skip unknown fields and, in many runtimes, preserve them if the message is reserialized.

This supports forward compatibility.

But do not build business logic that depends on unknown fields.

Unknown means the application does not understand it.

---

## 16. Field Type Changes

Some field type changes share wire type but still change semantics.

Example:

```proto
// v1
int32 priority = 1;

// v2
int64 priority = 1;
```

Both are VARINT-compatible at wire level in many cases.

But generated APIs change.

Range semantics change.

JSON mapping may change.

Database mapping may change.

Contract compatibility is not only binary parseability.

It also includes semantic and generated-code compatibility.

Rule:

> Avoid changing field type in public contracts. Add a new field and migrate.

---

## 17. Strings, Bytes, and Encoding Boundaries

`string` must contain valid UTF-8.

`bytes` is arbitrary binary.

Use `string` for textual identifiers only if:

- encoding is text;
- normalization rules are defined;
- max length is enforced elsewhere;
- case sensitivity is clear.

Use `bytes` for:

- hashes;
- encrypted blobs;
- binary signatures;
- opaque tokens;
- serialized nested payloads only with extreme caution.

Do not put JSON into `string` or `bytes` unless you are intentionally creating an escape hatch.

Escape hatches become contract debt.

---

## 18. Time and Money in Protobuf

Do not invent ad hoc timestamp fields casually.

Bad:

```proto
int64 created_at = 1; // millis? seconds? nanos? timezone?
```

Better:

```proto
import "google/protobuf/timestamp.proto";

message CaseOpened {
  google.protobuf.Timestamp occurred_at = 1;
}
```

For money, avoid floating point.

Better model:

```proto
message Money {
  string currency_code = 1; // ISO 4217, validated externally
  int64 units = 2;
  int32 nanos = 3;
}
```

Or use an organization-wide shared money type.

Contract discipline matters more than syntax.

---

## 19. Package, Java Package, and Type Identity

Proto package:

```proto
package acme.regulatory.case.v1;
```

Java options:

```proto
option java_package = "com.acme.regulatory.casecontract.v1";
option java_multiple_files = true;
option java_outer_classname = "CaseEventsProto";
```

Do not confuse proto package with Java package.

Proto package is part of schema type naming.

Java package controls generated Java classes.

Good practice:

- keep proto package stable and meaningful;
- configure Java package explicitly;
- avoid generated classes in core domain package;
- avoid package names that imply implementation ownership incorrectly.

---

## 20. File Organization

Recommended layout:

```text
contracts/
  proto/
    acme/
      regulatory/
        case/
          v1/
            case_events.proto
            case_commands.proto
            case_common.proto
        common/
          v1/
            money.proto
            audit.proto
```

Separate:

- common shared value types;
- commands;
- events;
- service definitions;
- internal/private contracts;
- public/external contracts.

Avoid one giant `all.proto` file.

---

## 21. Service Contracts vs Message Contracts

Protobuf defines messages.

gRPC uses Protobuf service definitions.

```proto
service CaseCommandService {
  rpc OpenCase(OpenCaseRequest) returns (OpenCaseResponse);
}
```

Message compatibility and service compatibility overlap but are not identical.

A service contract includes:

- method names;
- request type;
- response type;
- streaming mode;
- status/error model;
- deadline expectations;
- idempotency semantics;
- authentication/authorization semantics.

This part focuses on message model.

Do not mistake message parseability for API compatibility.

---

## 22. Protobuf as Event Contract

Protobuf can be used for Kafka/event streams too.

But the design pressure differs from request/response.

For events:

- events are immutable facts;
- old events may be replayed years later;
- consumers may lag producer versions;
- presence/default ambiguity is dangerous;
- schema registry or descriptor set management becomes important.

For RPC:

- request/response pair is usually short-lived;
- client/server deploy coordination may be tighter;
- service method compatibility matters;
- deadlines and status codes matter.

Same syntax.

Different lifecycle.

---

## 23. Validation Gap

Protobuf schema can say:

```proto
string case_id = 1;
```

It cannot by itself say:

```text
case_id must match ^CASE-[0-9]{8}$
status transition must be legal
amount currency must be ISO 4217
closed_at must be after opened_at
```

You need semantic validation.

Options:

- application validator;
- generated validation plugin;
- custom annotations/options;
- centralized boundary validator;
- contract tests with invalid fixtures.

Never assume generated Protobuf code makes data valid.

It only makes it structured.

---

## 24. Custom Options and Annotations

Protobuf supports custom options.

They can encode governance metadata.

Example conceptually:

```proto
import "google/protobuf/descriptor.proto";

extend google.protobuf.FieldOptions {
  string classification = 50001;
}

message Complainant {
  string email = 1 [(classification) = "PII"];
}
```

Use carefully.

Custom options are powerful for:

- documentation;
- data classification;
- ownership;
- validation hints;
- code generation hints;
- lint policy.

But if runtime enforcement matters, annotations must be connected to validators or codegen.

Metadata without enforcement is documentation, not control.

## 25. Designing a Case Event in Protobuf

Example:

```proto
syntax = "proto3";

package acme.regulatory.case.events.v1;

option java_package = "com.acme.regulatory.casecontract.events.v1";
option java_multiple_files = true;

import "google/protobuf/timestamp.proto";

message CaseEventMetadata {
  string event_id = 1;
  string tenant_id = 2;
  string case_id = 3;
  string correlation_id = 4;
  string causation_id = 5;
  google.protobuf.Timestamp occurred_at = 6;
  google.protobuf.Timestamp published_at = 7;
  string producer = 8;
}

message CaseOpened {
  CaseEventMetadata metadata = 1;
  string title = 2;
  CaseSource source = 3;
  repeated string allegation_codes = 4;
}

enum CaseSource {
  CASE_SOURCE_UNSPECIFIED = 0;
  CASE_SOURCE_PORTAL = 1;
  CASE_SOURCE_EMAIL = 2;
  CASE_SOURCE_REFERRAL = 3;
  CASE_SOURCE_INTERNAL = 4;
}
```

Production notes:

- metadata is a message field, so presence is visible;
- enum zero is unspecified;
- allegation code uniqueness must be validated elsewhere;
- IDs are strings but need format policy;
- timestamps use standard type;
- Java package is explicit and isolated.

## 26. Designing a Patch Command

Patch/update semantics need explicit presence.

Bad:

```proto
message UpdateCaseRequest {
  string case_id = 1;
  string title = 2;
  int32 priority = 3;
}
```

Cannot distinguish omitted title from empty title intent.

Better:

```proto
message UpdateCaseRequest {
  string case_id = 1;
  optional string title = 2;
  optional int32 priority = 3;
}
```

For clear-vs-set semantics, use `oneof`:

```proto
message UpdateCaseOwnerRequest {
  string case_id = 1;

  oneof owner_change {
    string owner_user_id = 2;
    ClearOwner clear_owner = 3;
  }
}

message ClearOwner {}
```

This makes intent explicit.

## 27. Designing Error Payloads

For gRPC, error model often uses status codes plus structured details.

For message contracts, define machine-readable violations.

```proto
message ContractViolation {
  string field_path = 1;
  string code = 2;
  string message = 3;
  string rejected_value = 4;
}

message ValidationFailure {
  string correlation_id = 1;
  repeated ContractViolation violations = 2;
}
```

Field path examples:

```text
metadata.case_id
allegation_codes[2]
source
```

Do not make clients parse human text to understand validation errors.

## 28. Compatibility Thought Experiments

### 28.1 Add a New Field

```proto
// v2
string intake_channel = 9;
```

Usually safe for old readers.

Old readers skip unknown field.

New readers see default if old writers omit it.

But semantic question remains:

> Is default/absence acceptable for business logic?

### 28.2 Rename a Field

```proto
// v1
string case_id = 1;

// v2
string enforcement_case_id = 1;
```

Binary compatibility may survive because tag remains 1.

But source/generator/JSON compatibility may break.

For public APIs, treat rename as risky.

### 28.3 Delete a Field

```proto
reserved 7;
reserved "legacy_score";
```

Safe deletion requires reservation.

Otherwise someone may reuse tag 7 later and old payload data may be interpreted with a new meaning.

### 28.4 Change Enum Meaning

```proto
CASE_STATUS_ESCALATED = 3;
```

Changing the meaning of value 3 while keeping the number is a silent semantic break.

Binary compatibility will not save you.

## 29. Protobuf JSON Mapping Warning

Protobuf has a defined JSON mapping.

But ProtoJSON is not the same contract as Protobuf binary.

Differences matter:

- field names become visible;
- enum names appear as strings by default;
- default values may be omitted;
- unknown fields are generally not handled like binary;
- numeric precision can become a cross-language issue;
- renaming fields can break JSON clients even when binary tag is stable.

If you expose Protobuf through JSON transcoding, you now have two compatibility surfaces:

```text
binary Protobuf compatibility
ProtoJSON compatibility
```

Design and test both.

## 30. Anti-Patterns

### 30.1 Business Meaning in Field Number Comments Only

```proto
string value = 1; // means case ID for now
```

No.

The schema should reveal meaning.

### 30.2 Zero Enum as Real State

```proto
ACTIVE = 0;
```

This makes missing look active.

### 30.3 Reusing Deleted Field Tags

This is one of the worst Protobuf mistakes.

Always reserve.

### 30.4 Dynamic Map Instead of Contract

```proto
map<string, string> everything = 1;
```

This is schema avoidance.

### 30.5 Treating Generated Code as Domain Model

Generated Protobuf classes are boundary representation.

They are not your core domain model.

---

## 31. Production Checklist

For every public `.proto` message:

- [ ] Field numbers are stable and reviewed.
- [ ] Deleted fields are reserved by number and name.
- [ ] Enum zero value is unspecified/unknown.
- [ ] Scalar optionality/presence is intentional.
- [ ] Field names are stable if JSON mapping is exposed.
- [ ] Timestamps use standard/shared representation.
- [ ] Money/decimal values avoid floating point.
- [ ] Repeated field ordering/uniqueness semantics are documented.
- [ ] Maps are justified and governed.
- [ ] `oneof` evolution risk is reviewed.
- [ ] Java package/options are explicit.
- [ ] Generated code is isolated from core domain model.
- [ ] Semantic validation exists outside serialization.
- [ ] Compatibility tests include old binary fixtures.

---

## 32. Mental Model Recap

Protobuf contract engineering is not about writing `.proto` files that compile.

It is about preserving meaning across generated code, binary encoding, services, events, clients, and time.

Core model:

```text
field number = durable wire identity
field name = source/JSON identity
wire type = binary decoding class
presence = set/unset signal
zero enum = default semantic guard
unknown field = forward compatibility mechanism
reserved tag = future safety rail
oneof = explicit mutually exclusive intent
```

If you remember only one thing:

> In Protobuf, the number is the contract. The name is the explanation. The semantic invariant is still your responsibility.
